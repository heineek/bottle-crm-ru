# Журнал аудита безопасности

`GET /api/org/audit-log/` позволяет администраторам организации читать её журнал аудита безопасности:
входы, переключения организации, отклонённые запросы, слияния записей, приостановленные вебхуки,
изменения API-токенов и календарных лент и тому подобное.
Представление:
`SecurityAuditLogListView` (`backend/common/views/audit_log_views.py`), маршрут задан в
`common/urls.py`; события записывает `AuditLogger` в `common/audit_log.py`. Параметры `limit` и `offset`
описаны в разделе [Соглашения](conventions.md#pagination), формы отказов в разделе [Ошибки](errors.md).

## Кто может его читать {#who-may-read-it}

Только администраторы организации (`IsOrgAdmin`: роль `ADMIN` или профиль суперпользователя Django в
этой организации). Участнику отвечают `403`:

```json
{"detail": "You must be an organization administrator to perform this action."}
```

Журнал читается только из сессии вошедшего пользователя. `/api/org/audit-log/` входит в список
запретов для учётных данных в `common/scopes.py` вместе с `/api/webhooks/` и маршрутами токенов,
поэтому персональный токен доступа или API-ключ организации отклоняется до запуска представления,
какие бы области у него ни были (см.
[Токены и API-ключи](tokens-and-api-keys.md#what-no-token-may-do-whatever-its-scopes)). Утёкший токен
не может прочитать, что организация о нём заметила.

Возвращаются только записи организации вызывающего. У таблицы намеренно нет политики RLS (её `org`
пуст у таких событий, как неудачный вход), поэтому барьером служит фильтр представления
`org=request.profile.org`, и запись без организации никогда ему не соответствует.

## Параметры запроса {#query-parameters}

| Параметр | Значение |
| --- | --- |
| `event_type` | Один тип события по значению (`LOGIN_SUCCESS`, `WEBHOOK_PAUSED`, …). Неизвестное значение даёт `400`. |
| `include_token_refresh` | `true`, чтобы показывать записи `TOKEN_REFRESH` вместе со всеми остальными. Любое другое значение или его отсутствие их исключает. |
| `actor` | id пользователя, к которому относится событие. Значение, не являющееся UUID, даёт `400`. |
| `from`, `to` | Дни в формате `YYYY-MM-DD` включительно, в часовом поясе организации. `from` позже `to` даёт `400`. |
| `limit`, `offset` | Постраничный вывод: по умолчанию 25 записей, не больше 100. |

Записи `TOKEN_REFRESH` (вошедший клиент незаметно продлевает свою сессию) составляют большую часть
таблицы, поэтому они исключены из списка и из `count`, если вызывающий не запросил их явно: через
`include_token_refresh=true` или через `event_type=TOKEN_REFRESH`, который выводит только их. Записываются
они в любом случае.

Записи идут от новых к старым. Например, `GET /api/org/audit-log/?event_type=LOGIN_SUCCESS&from=2026-09-01`
выводит входы в организацию за этот месяц. `LOGIN_FAILURE` принимается как фильтр, но ничего не выводит:
см. [Неудачные входы](#failed-sign-ins).

```json
{"event_type": ["Unknown event type."]}
```

## Ответ {#the-response}

Обычная обёртка `limit`/`offset` плюс типы событий, которые может содержать журнал, чтобы клиент мог
предложить их в фильтре без собственного списка:

```json
{
  "count": 213,
  "next": "https://api.example.com/api/org/audit-log/?limit=25&offset=25",
  "previous": null,
  "results": [
    {
      "id": "7d0e...",
      "event_type": "WEBHOOK_PAUSED",
      "event_label": "Webhook Paused",
      "created_at": "2026-09-26T09:12:44.018+00:00",
      "success": true,
      "actor": {"id": "3b1f...", "name": "Dana Reyes", "email": "dana@example.com"},
      "ip_address": null,
      "user_agent": "",
      "request_method": "",
      "request_path": "",
      "details": {"endpoint_id": "91ac...", "creator_id": "3b1f...", "pause_reason": "..."}
    }
  ],
  "event_types": [{"value": "LOGIN_SUCCESS", "label": "Login Success"}]
}
```

`actor` равен `null` для события без пользователя.

Содержимое каждой записи выбирается поле за полем, а не копируется из таблицы:

- **Нет `description`.** Текст записи `ORG_SWITCH` называет организацию, из которой переключился
  пользователь, то есть имя другого тенанта.
- **`details` содержит только заведомо безопасные ключи** (`SAFE_DETAILS`: `action`, `resource`,
  `deleted_count`, `endpoint_id`, `creator_id`, `pause_reason`, `previous_creator_id`, `changed`). Это
  id, счётчики и фразы, написанные сервером. Всё остальное в сохранённых метаданных может содержать
  данные от вызывающего (email, с которым пытались войти, префикс API-ключа, произвольное описание
  подозрительной активности) и не выводится.
- **Запись о слиянии также содержит обе записи** (`EVENT_DETAILS`): запись `RECORD_MERGED` добавляет
  `entity` (`lead`, `contact` или `account`), `kept_id`, `kept_name`, `merged_id` и `merged_name`.
  Объединённая запись удаляется, так что это единственное место, где сохраняется её имя. Эти ключи
  разрешены только для этого события; тот же ключ в любой другой записи не выводится.
- **Запись об API-токене также называет токен** (`EVENT_DETAILS`): записи `API_TOKEN_CREATED` и
  `API_TOKEN_REVOKED` добавляют `token_id`, `token_prefix`, `token_name`, `scopes`, `owner_id` и
  `owner_name`. См. [Изменения учётных данных](#credential-changes). Разрешено только для этих двух
  событий.
- **Изменение модулей также содержит свои ключи** (`EVENT_DETAILS`): запись `MODULES_CHANGED` добавляет
  `switched_off` и `switched_on` (списки ключей модулей) и `reordered` (булево значение). См.
  [Изменения модулей](#module-changes). Разрешено только для этого
  события.
- **Изменение приложения называет приложение** (`EVENT_DETAILS`): записи `APP_INSTALLED`,
  `APP_UPGRADED` и `APP_REMOVED` добавляют `app_id` и `version`. См.
  [Изменения приложений](#app-changes). Разрешено только для этих трёх событий.
- **Пути под `/api/public/` обрезаются до этого префикса.** Некоторые публичные ссылки содержат токен в
  URL (например, ссылка на опрос удовлетворённости), и журнал не должен его повторять.

## Изменения учётных данных {#credential-changes}

Начиная с django-crm 1.13.0 аудиту подлежат два вида учётных данных, которые участник может выпустить
себе сам, потому что каждый из них работает, пока его кто-нибудь не отзовёт. Каждая запись создаётся
для действующей организации, поэтому её администраторы видят её здесь вместе с IP-адресом клиента,
user agent, методом и путём, как и любую другую запись.

| `event_type` | Метка | Кем создаётся | `actor` |
| --- | --- | --- | --- |
| `CALENDAR_FEED_ENABLED` | Calendar Feed Enabled | `POST /api/profile/calendar-feed/`, если у участника не было ленты | участник |
| `CALENDAR_FEED_REGENERATED` | Calendar Feed Regenerated | `POST /api/profile/calendar-feed/`, если лента была заменена (старый URL перестаёт работать) | участник |
| `CALENDAR_FEED_DISABLED` | Calendar Feed Disabled | `DELETE /api/profile/calendar-feed/`, если лента существовала | участник |
| `API_TOKEN_CREATED` | API Token Created | `POST /api/profile/tokens/` | владелец |
| `API_TOKEN_REVOKED` | API Token Revoked | `DELETE /api/profile/tokens/<id>/` (владелец) или `DELETE /api/org/tokens/<id>/` (администратор) | тот, кто отозвал |

Запись о календарной ленте не содержит `details`. Запись об API-токене содержит:

| Ключ | Значение |
| --- | --- |
| `token_id` | id токена |
| `token_prefix` | Префикс для отображения, который уже показывает список токенов (`bcrm_pat_` и четыре символа) |
| `token_name` | Имя, которое дал токену владелец |
| `scopes` | Его области; пустой список означает токен с полным доступом владельца |
| `owner_id`, `owner_name` | Пользователь, которому принадлежит токен, так что отзыв администратором чужого токена называет обоих |

Ни одна запись не содержит URL ленты, исходный токен или его хеш. Действие без эффекта ничего не
записывает: отключение уже выключенной ленты или отзыв уже отозванного токена (на любом из эндпоинтов)
по-прежнему возвращает `200`, но не добавляет запись, поэтому в журнале по одному отзыву на токен.
Отклонённый вызов (создание с `400`, участник с `403` на `/api/org/tokens/`, `404` для токена, который
не ваш или не из вашей организации) тоже ничего не записывает. Если запись аудита не удаётся создать,
действие всё равно выполняется; ошибка уходит в логгер `security.audit`, как и для любого другого
события.

## Изменения модулей {#module-changes}

`PUT /api/org/modules/` создаёт запись `MODULES_CHANGED` (метка Modules Changed), когда администратор
отключает или включает модуль либо меняет порядок модулей; `actor` при этом администратор. Запрос,
который ничего не меняет или отклонён, ничего не записывает. См. [Модули](modules.md).

| Ключ | Значение |
| --- | --- |
| `switched_off` | Ключи модулей, отключённых этим изменением |
| `switched_on` | Ключи модулей, включённых этим изменением |
| `reordered` | `true`, если порядок изменился |

## Изменения приложений {#app-changes}

Установка, обновление и удаление [отраслевого приложения](../features/industry-apps.md) создают по
записи, где `actor` это администратор. Отклонённый запрос ничего не записывает.

| `event_type` | Метка | Кем создаётся |
| --- | --- | --- |
| `APP_INSTALLED` | App Installed | `POST /api/apps/<id>/install/`, а также `POST /api/packs/<id>/apply/`, когда он устанавливает приложение |
| `APP_UPGRADED` | App Updated | `POST /api/apps/<id>/upgrade/` |
| `APP_REMOVED` | App Removed | `POST /api/apps/<id>/remove/` |

| Ключ | Значение |
| --- | --- |
| `app_id` | Id приложения, например `real-estate` |
| `version` | Версия приложения после изменения |

## Неудачные входы {#failed-sign-ins}

Начиная с django-crm 1.13.0 отклонённый вход сотрудника создаёт запись `LOGIN_FAILURE`
(`AuditLogger.login_failure`, вызывается из `common/views/auth_views.py`). У вызывающего ещё нет
организации, поэтому у записи её тоже нет, и этот эндпоинт её никогда не возвращает: неудачные входы
предназначены для оператора, который читает их из таблицы `security_audit_log` или логгера
`security.audit` (`security_audit.log`), а не для просмотра в организации.

`metadata` содержит указанный `email` (обрезанный до 254 символов, пустой, если попытка его не
указала) и `reason`; `user` заполняется, если этот email принадлежит пользователю. Токен или код,
который пробовали, никогда не сохраняется. Причины:

| `reason` | Когда |
| --- | --- |
| `google_unreachable` | Не удалось обратиться к обмену токенов Google |
| `google_code_rejected` | Google отклонил authorization code |
| `google_invalid_id_token` | Поток с кодом не вернул ID token или вернул такой, который не разбирается |
| `google_invalid_token` | Google ID token с телефона не прошёл проверку |
| `google_no_email` | В токене Google нет email |
| `google_email_unverified` | Google не подтверждает этот email |
| `account_disabled` | Пользователь существует, но деактивирован (вход через Google или по email) |
| `magic_link_invalid` | Ссылка для входа неизвестна, использована или истекла; email берётся из самой ссылки, если она существует |
| `code_not_found` | Для этого email нет неиспользованного и неистёкшего кода входа |
| `code_wrong` | Код не совпал |
| `code_attempts_exhausted` | Код не совпал, и это была последняя попытка, поэтому код израсходован |

Эти записи создают анонимные вызывающие, поэтому с каждого IP-адреса клиента их не больше 20 в час
(`LOGIN_FAILURE_ROWS_PER_IP_PER_HOUR` в `common/audit_log.py`, отсчёт в кэше по умолчанию с первой
неудачи). Попытки сверх лимита отклоняются точно так же, как раньше; они не оставляют ни записи, ни
строки в логе.
