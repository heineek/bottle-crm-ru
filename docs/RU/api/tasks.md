# Задачи

Маршруты находятся в `backend/tasks/urls.py`. CRUD, комментарии и вложения в
`backend/tasks/views/task_views.py`; воронки и этапы Kanban и эндпоинт перемещения в
`backend/tasks/views/kanban_views.py`; Kanban-**доски**, отдельная функция, в
`backend/tasks/views/board_views.py`. Авторизация на уровне объектов собрана в
`backend/tasks/access.py`. Правила пагинации, фильтрации и формы ответа, которые здесь
подразумеваются, а не повторяются, описаны в разделе [Соглашения](conventions.md), а принцип
«404 вместо 403», на который ссылается текст ниже, в разделе [Ошибки](errors.md).

## `Task.save()` вызывает `full_clean()` {#tasksave-calls-full_clean}

Прежде всего один факт, который меняет то, как следует читать каждый эндпоинт записи ниже:
**`Task.save()` явно вызывает `self.full_clean()`** (`tasks/models.py:402-404`). Это не поведение по
умолчанию: в разделе [Архитектура: модель данных](../architecture/data-model.md#conventions)
описано, что большинство моделей здесь (`Lead`, `Opportunity`, `Case`) определяют настоящую
валидацию в `clean()`, которая через API никогда не вызывается, потому что их методы `save()` не
вызывают `full_clean()`. `Task` входит в небольшую группу моделей, которые это делают (вместе с
`Comment.save()` и `Attachments.save()`, которые требуют, чтобы `org` комментария или вложения
совпадала с организацией родительской записи; см. ту же страницу). Следствие обратное: когда
`full_clean()` *действительно* выполняется и находит нарушение, он выбрасывает собственный
`django.core.exceptions.ValidationError` Django, а не DRF, а в разделе [Ошибки](errors.md) прямо, в
первом же абзаце, сказано, что `EXCEPTION_HANDLER` в этом коде стандартный, без изменений, из DRF, и
он не умеет отображать это исключение. Если конкретный путь кода представления его не перехватывает,
нарушение правила на уровне модели `Task` доходит до клиента как необработанный **`500`**, а не как
аккуратный `400`.

Единственное правило, которое сейчас проверяет `Task.clean()`: «не больше одной родительской
сущности». Задача может быть связана не более чем с одним из `account`, `opportunity`, `case`, `lead`
(`tasks/models.py:384-400`). Основные эндпоинты создания и изменения защищены от этого дважды:
`TaskCreateSerializer.validate()` (`tasks/serializer.py:331-365`) повторно реализует то же правило и
возвращает аккуратный `400` с названием поля, *а* `TaskListView.post` / `TaskDetailView.put` /
`TaskDetailView.patch` дополнительно оборачивают `serializer.save()` в
`try/except django.core.exceptions.ValidationError` как страховку (`_model_errors`,
`tasks/views/task_views.py:56-66`, используется в `:277-281,577-581,702-706`), поэтому именно для
`POST /api/tasks/`, `PUT /api/tasks/{id}/` и `PATCH /api/tasks/{id}/` это правило сегодня доходит до
клиента как `{"error": true, "errors": {"account": "..."}}` с `400`, а не `500`.

**Не все пути записи имеют такую страховку.** `PATCH /api/tasks/{id}/move/`
(`TaskMoveView.patch`, `tasks/views/kanban_views.py:253-318`), эндпоинт перетаскивания в Kanban,
напрямую задаёт `task.stage`, `task.status` и `task.kanban_order` и вызывает `task.save()` без
`try/except` вокруг (`:310`) и вообще не проходя через `TaskCreateSerializer`. `full_clean()`
проверяет каждое поле экземпляра, а не только те, которых коснулся конкретный эндпоинт, поэтому любое
найденное здесь нарушение на уровне модели, в уже имеющейся у задачи комбинации
`account`/`opportunity`/`case`/`lead` или в любом другом правиле `clean_fields()`, проявляется как
описанный выше необработанный `500`. Это не только теоретический риск через поля родительской
сущности: `TaskStage.maps_to_status` (`tasks/models.py:257-263`) это обычный `CharField`,
`blank=True, null=True`, без ограничения `choices=`. Это свободный текст, который администратор
задаёт при настройке этапа воронки, и он никак не проверяется по `Task.STATUS_CHOICES`. Когда задача
переходит на этап, где он задан, `if stage.maps_to_status: task.status = stage.maps_to_status`
(`kanban_views.py:297-298`) присваивает его прямо в `task.status`, а у этого поля на уровне модели
`choices=` *есть*. Одна опечатка в `maps_to_status` на одном настроенном администратором этапе
превращает каждое следующее перемещение на этот этап в необработанный `500` для всех пользователей,
пока администратор не заметит и не исправит этап. У этого эндпоинта нет аналога двухуровневой
защиты основных CRUD-эндпоинтов.

## Список задач {#list-tasks}

`GET /api/tasks/` (`TaskListView.get`, `tasks/views/task_views.py:233-235`) возвращает один
список с пагинацией. Видимость определяет `visible_tasks_qs` (`tasks/access.py:43-48`):
администратор видит все задачи организации, остальные видят только задачи, которые они создали или
за которые отвечают. Это то же правило, которое применяет детальное представление (docstring модуля
`tasks/access.py`: "the list has to agree with the detail view or the queue lies").

```json
{
  "tasks_count": 24,
  "offset": 10,
  "tasks": [ { "...": "TaskListSerializer" } ],
  "totals": {"count": 24, "open": 18, "overdue": 3, "due_today": 1, "due_this_week": 5, "no_due_date": 6, "unassigned": 2},
  "status": [["New", "New"], ["In Progress", "In Progress"], ["Completed", "Completed"]],
  "priority": [["Low", "Low"], ["Medium", "Medium"], ["High", "High"]],
  "users": [{"id": "...", "user__email": "..."}],
  "accounts_list": [ { "...": "AccountSerializer" } ],
  "contacts_list": [ { "...": "ContactSerializer" } ]
}
```

(`tasks/views/task_views.py:130-209`.) `totals` это один агрегирующий запрос по всему
отфильтрованному с учётом видимости queryset, а не по странице; `overdue`/`due_today`/`due_this_week`/
`no_due_date`/`unassigned` дополнительно требуют, чтобы задача была ещё открыта
(`status != "Completed"`), так что задача, завершённая с опозданием, не считается просроченной
(`:145-167`). `accounts_list`/`contacts_list` это полные каталоги организации для выбора
родительской сущности; `?slim=true` опускает оба (`:203-209`).

Фильтры, читаемые напрямую из `request.query_params`
(`tasks/views/task_views.py:86-129`): `title` (содержит), `status` (точное совпадение), `priority`
(точное совпадение), `assigned_to` (повторяемый список id), `tags` (список id), `search` (ищет по
`title`, вхождение подстроки, а не комбинированный поиск по другим полям, как в
[Лидах](leads.md#list-leads) или [Контактах](contacts.md#list-contacts)),
`due_date__gte`/`due_date__lte`, `created_at__gte`/`created_at__lte`, `account`, `opportunity`,
`case`, `lead` (каждый точное совпадение id родителя) и `cf_<key>` (дополнительное поле равно).

## Создание задачи {#create-a-task}

`POST /api/tasks/` (`TaskListView.post`, `tasks/views/task_views.py:252-349`) принимает JSON или
`multipart/form-data` и валидируется `TaskCreateSerializer` (`tasks/serializer.py:315-389`; см.
[Поля](#fields)). При успехе (`200`): `{"error": false, "message": "Task Created Successfully"}`.
Ошибка валидации возвращает `400` с `{"error": true, "errors": {...}}`, включая правило «не больше
одного родителя» и страховку через собственный `full_clean()` модели, оба описаны
[выше](#tasksave-calls-full_clean).

`account`, `opportunity`, `case` и `lead` ограничиваются организацией вызывающего в
`TaskCreateSerializer.__init__` (`tasks/serializer.py:328-329`). Комментарий там поясняет, что обычный
`ModelSerializer` иначе построил бы каждое из них как `PrimaryKeyRelatedField` по *всем* строкам
таблицы, и что было доказано: задача в одной организации принимала компанию другой организации, а
эндпоинт списка затем показывал название компании той организации запросившему. `created_by` есть в
`Meta.fields`, но он `read_only` (`:389`); комментарий объясняет, что когда поле было доступно для
записи, клиент мог назвать автором задачи любого пользователя любой организации, а это становится
вектором повышения привилегий, как только условие об авторе в `tasks/access.py` начинает для чего-то
использоваться (а оно используется, см. [Поля](#fields)).

`contacts`, `teams`, `assigned_to` и `tags` **не** входят в `TaskCreateSerializer`: представление
разрешает каждое из них из тела запроса после успешной работы сериализатора, в пределах
организации, и применяет `json.loads`, если значение пришло строкой (та же форма, что в
[Обращениях](cases.md#create-a-case)). *Разбор* одинаков для всех четырёх полей на всех методах. У
Задач нет той несогласованности между полями, которая описана для [Лидов](leads.md#fields). С
*записью* всё иначе, и та же ловушка с потерей данных, что описана для [Обращений](cases.md#fields),
действует здесь дословно: `POST` только добавляет (`task_views.py:282,296,308,322`); `PUT` вызывает
`.clear()` для всех четырёх **безусловно**, ещё до проверки, упоминало ли их тело вообще
(`:582,597,610,625`), поэтому `PUT` без `assigned_to` снимает задачу со всех ответственных и, через
`visible_tasks_qs` (`tasks/access.py:43-48`), полностью убирает её из списков задач этих людей;
`PATCH` очищает конкретное M2M-поле, только если его ключ есть в теле (`:709-758`).

## Получение, изменение, удаление {#retrieve-update-delete}

`GET /api/tasks/{id}/` (`TaskDetailView.get`, `tasks/views/task_views.py:460-463`) ищет запись в
пределах организации (`get_task_or_404`, `tasks/access.py:51-65`: некорректный id и задача другой
организации одинаково отвечают `404`) и применяет `assert_task_access` до построения ответа
(`:365`): исключение выбрасывается, а не возвращается, именно потому, что объект `Response`,
возвращённый через этот метод, раньше оборачивался во второй `Response` и падал с `500` вместо ответа
`403` (комментарий в `:361-364`). Ответ вкладывает запись в `task_obj` рядом с `attachments`,
`comments`, `users_mention`, `assigned_data`, `custom_field_definitions`, `users` (администраторы
видят всех активных участников, остальные только других администраторов; та же форма, которую
[Обращения](cases.md#list-cases) используют для выбора ответственного), `users_excluding_team` и
`teams`.

`PUT /api/tasks/{id}/` (`:545-650`) и `PATCH /api/tasks/{id}/` (`:667-781`) оба применяют
`assert_task_access`: доступ здесь имеет только два уровня, а не три, как у обращения:
**`access` (чтение и запись вместе) имеют администратор, автор и ответственный; `delete` более узкий:
администратор и автор** (`tasks/access.py:1-10`). Docstring модуля прямо объясняет, почему задача
объединяет чтение и запись в одно правило, а обращение нет: у обращения может быть *наблюдатель*,
человек, который следит за обращением, не получив его в работу, и у задачи нет аналога этого
дополнительного уровня только для чтения; "everyone who may open one may also work it."
`contacts`/`teams`/`assigned_to`/`tags` заново привязываются из тела запроса так же, как в `POST`.
Успешный ответ: `{"error": false, "message": "Task updated Successfully"}`.

`DELETE /api/tasks/{id}/` (`:797-805`) вызывает `assert_task_delete_access`: только администратор или
автор, без исключения для ответственного, по той же причине, что и в
[Обращениях](cases.md#retrieve-update-delete): назначение на задачу даёт повод работать над ней, а не
стирать её.

## Комментарии и вложения {#comments-and-attachments}

Та же форма, что в [Обращениях](cases.md#comments-and-attachments): `POST /api/tasks/{id}/`
(`TaskDetailView.post`, `tasks/views/task_views.py:481-528`) добавляет `comment` и/или файл
`task_attachment` к существующей задаче с проверкой `assert_task_access`. Комментарий к этому методу
отмечает реальную ловушку: валидация комментария через `CommentSerializer` здесь проваливается
*молча*, потому что этот сериализатор требует `object_id` и `org`, а клиент не отправляет ни то, ни
другое; `is_valid()` возвращает `False`, и задуманная запись просто пропускается, поэтому
представление создаёт `Comment` напрямую через ORM Django, а не через сериализатор (`:488-500`).

`PUT`/`PATCH`/`DELETE /api/tasks/comment/{id}/` (`TaskCommentView`, `:808-946`) изменяют или удаляют
существующий комментарий: администратор или сам автор комментария
(`request.profile == obj.commented_by`, сравнение `Profile` с `Profile`, корректное). **`PUT` на
практике не может изменить комментарий.** Он строит `CommentSerializer(obj, data=params)` без
`partial=True` (`:851`), а `CommentSerializer.Meta.fields` включает обычные (не `read_only`) поля
модели `object_id` и `org` (`common/serializer.py:239-250`): тело из одного `{"comment": "..."}`, то
есть всё, что требует документированный контракт `TaskCommentEditSwaggerSerializer`, не проходит
валидацию из-за отсутствующих `object_id`/`org` и получает `400`. Изменить текст комментария может
только `.patch()` (`partial=True`, `:896`). Отдельно: поскольку `object_id`/`org` в `PATCH`
действительно доступны для записи, автор комментария может передать оба и перенаправить комментарий
на другую запись, в том числе в другой организации или такую, которую он иначе не может прочитать.
`Comment.clean()` (`common/models.py:299-314`) ловит только несовпадающий случай (`org` не совпадает
с `org` новой цели), и только потому, что `Comment.save()` вызывает `self.full_clean()`
(`:316-318`), что превращает это несовпадение в необработанный `500`, а не `400` (тот же сценарий
отказа, что [выше](#tasksave-calls-full_clean), на другой модели); *совпадающая* межорганизационная
пара сохраняется без ошибки. Ни одно из этих поведений здесь не исправлено, о них сообщается в
рамках задачи этой документации. Тот же шаблон `PUT`/`PATCH` есть и в собственном эндпоинте
изменения комментариев [Обращений](cases.md#comments-and-attachments).

`DELETE /api/tasks/attachment/{id}/` (`TaskAttachmentView.delete`, `:949-1000`) ограничен
организацией (`.filter(pk=pk, org=request.profile.org)`, `:975-977`), а его проверка владения
сравнивает `request.profile.user_id` с `self.object.created_by_id` (`:987`); оба исправлены здесь.
Комментарий к этому методу фиксирует, что оба дефекта (поиск без ограничения по вложениям всех
организаций и сравнение `Profile` с `User`, которое молча делало эндпоинт доступным только
администраторам) были подтверждены на живой системе до исправления. Текущее состояние того же
шаблона дефектов в других модулях описано в разделе
[Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks).

## Доски и колонки {#boards-and-columns}

**Kanban-*доски* это отдельная функция, не связанная с собственными полями задачи
`stage`/`pipeline`, со своим семейством моделей (`Board`, `BoardColumn`, `BoardTask`, `BoardMember`,
`tasks/models.py:16-194`) и своими эндпоинтами под `/api/boards/...`, а не под `/api/tasks/...`.**
Это подтверждается в `backend/common/app_urls/__init__.py:26`:
`path("boards/", include((board_urlpatterns, "api_boards")))`, где `board_urlpatterns`
импортируется из `tasks/urls.py:58-75`. Карточка `BoardTask` это не строка `Task`. У неё свои
заголовок, описание, приоритет и ответственные, а на `account`/`contact`/`opportunity` она ссылается
только по желанию, для контекста (`tasks/models.py:116-195`); эндпоинты `/api/tasks/kanban/`,
`/api/tasks/pipelines/...`, `/api/tasks/pipelines/{pipeline_id}/stages/` и `/api/tasks/stages/{id}/`,
неявно упомянутые выше (через `stage` в разделе [Поля](#fields)), работают с настоящими строками
`Task` и относятся к совсем другой системе Kanban.

Доступ к доске определяется участием в конкретной доске, а не всей организацией: `Board.owner` и
строки `BoardMember` несут `role` со значением `owner`/`admin`/`member` (`tasks/models.py:43-81`).
Каждый эндпоинт, работающий с *существующей* доской, сначала проверяет участие (единственное
исключение: создание доски; `POST /api/boards/` не требует ничего, кроме членства в организации,
потому что доски, участником которой можно быть, ещё нет); некоторые дополнительно проверяют роль:

| Эндпоинт | Кто |
| --- | --- |
| `GET /api/boards/` | Любой аутентифицированный участник организации; в результатах только доски, где он владелец или участник (`board_views.py:82-89`) |
| `POST /api/boards/` | Любой участник организации; создаёт доску и по умолчанию три стартовые колонки (`:126-157`) |
| `GET /api/boards/{id}/` | Владелец или участник доски (иначе `404`, а не `403`, `:165-192`) |
| `PUT/PATCH /api/boards/{id}/` | Роль `owner` или `admin` на доске (`:206-271`) |
| `DELETE /api/boards/{id}/` | Только владелец доски (`:282-299`) |
| `GET /api/boards/{board_id}/columns/` | Владелец или участник доски (`:316-329`) |
| `POST /api/boards/{board_id}/columns/` | Роль `owner` или `admin` на доске (`:355-367`) |
| `GET/POST /api/boards/columns/{column_id}/tasks/` | Любой участник доски (без проверки роли, `:413-455`) |
| `PUT /api/boards/tasks/{id}/` | Любой участник доски (без проверки роли, `:490-503`) |
| `DELETE /api/boards/tasks/{id}/` | Любой участник доски: проверка роли перечисляет `owner`/`admin`/`member`, то есть все возможные роли (`:570-583`) |

**Некорректный id доски, колонки или карточки даёт `500`, а не `404`, на каждом эндпоинте из этой
таблицы.** Каждый поиск в `board_views.py` использует `get_object_or_404` Django по первичному ключу
UUID (`:167,319,358,416,445,493,573`), а `get_object_or_404` перехватывает только `DoesNotExist`
модели, но не `ValidationError`/`ValueError`, которые выбрасывает строка, не являющаяся UUID, при
сравнении с UUID-полем. Именно этот класс ошибок предотвращают `get_task_or_404`/`get_case_or_404`
(`tasks/access.py:51-65`, `cases/access.py:57-71`) в остальной части API; доски эту функцию так и не
переняли. Здесь не исправлено, сообщается в рамках задачи этой документации.

**Эндпоинта для изменения или удаления отдельной колонки после создания нет.** `board_urlpatterns`
(`tasks/urls.py:58-75`) определяет только `GET`/`POST /api/boards/{board_id}/columns/`, маршрут списка
и создания, и детального пути `columns/{id}/` нет вовсе. Название, цвет, порядок или WIP-`limit`
колонки сегодня через этот API изменить нельзя, и удалить колонку тоже нельзя.

**`GET /api/boards/{id}/` не возвращает карточки каждой колонки.** `BoardSerializer.columns`
использует `BoardColumnListSerializer` (`tasks/serializer.py:109-121,123-143`), который сообщает по
каждой колонке только `task_count`, а не сами карточки. Чтобы прочитать карточки, отдельно вызовите
`GET /api/boards/{board_id}/columns/`, который использует полный `BoardColumnSerializer` и вкладывает
карточки `BoardTaskSerializer` в каждую колонку (`board_views.py:334-343`).

`PUT /api/boards/tasks/{id}/` (`BoardTaskDetailView.put`, `board_views.py:490-559`) также служит для
перемещения карточки между колонками: передайте `column` (проверяется, что это колонка той же доски;
id колонки с другой доски, в том числе по построению с доски другой организации, даёт `400`, а не
молчаливое бездействие, `:512-529`) и/или `order`; после перемещения представление перенумеровывает и
исходную, и целевую колонки в плотный порядок `0..n-1`, чтобы позиции перетаскивания сохранялись
после перезагрузки (`_resequence_column`, `:22-48`).

Поверхность записи `BoardTaskSerializer` намеренно узкая (`tasks/serializer.py:36-90`): запись
карточки может задать `title`, `description`, `order`, `priority`, `due_date` и ответственных (через
доступное только для записи `assigned_to_ids`, которое представление применяет после сохранения с
фильтром по организации). Всё остальное закрыто двумя разными механизмами: `id`, `created_at`,
`updated_at`, `completed_at`, `org`, `column`, `created_by`, `updated_by`, `contact` и `opportunity`
находятся в `read_only_fields` (`:67-78`): `column`, потому что перемещение карточки идёт через
отдельный поток `PUT` выше, а внешние ключи на записи CRM потому, что без фильтрации они открывали ту
же межорганизационную брешь `PrimaryKeyRelatedField`, от которой был защищён `TaskCreateSerializer`.
`account` приходит к тому же результату иначе: он переопределён как обычный
`SerializerMethodField()` (`:60`) и вообще не указан в `read_only_fields`; переопределение внешнего
ключа модели полем-методом так же надёжно убирает его из поверхности записи, как сказано в
комментарии к самому полю (`:82-84`).

## Календарная лента {#calendar-feed}

Начиная с django-crm 1.13.0, каждый участник может подписать календарное приложение (Google
Calendar, Outlook, Apple Calendar) на свои открытые задачи. Управление реализует `CalendarFeedView`, а
саму ленту `PublicCalendarFeedView`, оба в `backend/common/views/calendar_feed_views.py`;
генератор iCalendar находится в `backend/common/calendar_feed.py`, а модель токена
`CalendarFeedToken` в `backend/common/models.py`.

### Управление лентой {#managing-your-feed}

`/api/profile/calendar-feed/` управляет только собственной лентой вызывающего и ничьей больше:
каждый запрос фильтрует по `org=request.profile.org` и `profile=request.profile`. Маршрут входит в
список запретов для учётных данных в `common/scopes.py`, поэтому персональному токену доступа или
API-ключу организации отказывают независимо от их областей действия (см.
[Токены и API-ключи](tokens-and-api-keys.md#what-no-token-may-do-whatever-its-scopes)). URL ленты
продолжает работать после отзыва токена, которым его можно было бы создать, поэтому создать его
может только сессия авторизованного пользователя.

| Метод | Что делает | Ответ |
| --- | --- | --- |
| `GET` | Читает состояние | `200` `{"error": false, "enabled": true, "created_at": "...", "last_used_at": "..."}` |
| `POST` | Включает ленту или заменяет её | `201`, те же поля плюс `url` |
| `DELETE` | Выключает её | `200` с `enabled: false` |

URL возвращается из `POST` один раз, и прочитать его повторно нельзя: хранится только SHA-256
токена. `POST` для включённой ленты удаляет старый токен в той же транзакции, поэтому старый URL
перестаёт работать в момент появления нового. `last_used_at` показывает, когда календарное приложение
последний раз забирало ленту, и сдвигается не чаще раза в час; до первого обращения оно равно
`null`.

`url` строится из настройки `DOMAIN_NAME` (`common.links.api_url`), публичного адреса API, и никогда
из запроса. Веб-приложение обращается к API со своего сервера по `PUBLIC_DJANGO_API_URL`
(`http://backend:8000` в Docker), поэтому URL, построенный из запроса, указывал бы на хост,
недоступный ни одному календарному сервису, и начинался бы с `http://` за TLS-терминатором. Вне
режима разработки бэкенд отказывается запускаться, если `DOMAIN_NAME` указывает на loopback или не
является абсолютным URL; см. [Переменные окружения](../reference/environment-variables.md).

### Подписка {#the-feed}

`GET /api/public/calendar/{token}.ics` не принимает никаких учётных данных, кроме токена в пути, и
отвечает `text/calendar`. Именно его опрашивает календарное приложение по своему расписанию (Google
обновляет подписанный календарь раз в несколько часов), поэтому изменение задачи попадает в календарь
с задержкой.

- **Какие задачи.** Статус `New` или `In Progress`, срок от 90 дней назад до 365 дней вперёд в
  часовом поясе организации. Только собственные задачи участника: те, у которых `created_by` это его
  пользователь, или те, где он ответственный, в том числе для администраторов (лента
  администратора не включает остальные задачи организации), и никогда задача вне
  `visible_tasks_qs`. Не больше 1 000, с сохранением ближайших к сегодняшнему дню: задачи со сроком
  сегодня или позже, от ближайших, затем просроченные, от самых недавних, пока не будет достигнут
  лимит. Список перечитывается при каждом обращении, поэтому снятие ответственного или удаление из
  организации действует со следующего опроса.
- **Что показывает событие.** Одно событие на весь день в дату срока, помеченное как «свободен», а не
  «занят», с заголовком задачи в качестве названия, `Priority: <priority>` и ссылкой на
  `/tasks/{id}` в веб-приложении в качестве описания и той же ссылкой в поле `URL`. Больше ничего: ни
  собственного описания задачи, ни названий контактов, компаний или других записей, потому что
  подписанный календарь читает сторонний сервис от имени участника.
- **Промахи.** Некорректный, неизвестный, заменённый или отключённый токен, а также токен, профиль,
  пользователь или организация которого больше не активны, отвечают одним и тем же `404`
  `{"error": "Not found"}`.
- **Ограничения частоты.** `CALENDAR_FEED_THROTTLE_IP` (по умолчанию `1000/hour` на IP клиента;
  щедро, потому что календарные сервисы обращаются с общих адресов) и `CALENDAR_FEED_THROTTLE_TOKEN`
  (по умолчанию `60/hour` на ленту, с группировкой по хешу токена). См.
  [Переменные окружения](../reference/environment-variables.md).
- Ответ несёт `Cache-Control: private, max-age=300` и `X-Robots-Tag: noindex`, а в событиях Sentry
  токен вырезается из любого записанного URL.

`/api/public/calendar/` входит в `RequireOrgContext.EXEMPT_PATHS`. Представление находит строку
токена (таблица `calendar_feed_token` не находится под RLS, как и `personal_access_token`), берёт
организацию из её профиля, устанавливает контекст RLS и только после этого читает задачи.

URL является секретом. Любой, у кого он есть, может без входа прочитать заголовки и приоритеты
открытых задач участника, поэтому передавайте его только календарному приложению и пересоздайте
(новым `POST`), если он утёк. В клиентах лентой управляют по адресу `/profile/calendar-feed` в
вебе и в разделе **Профиль → Календарная лента** на телефоне.

## Поля {#fields}

`TaskCreateSerializer.Meta.fields` (`tasks/serializer.py:367-389`) определяет, что принимают
`POST /api/tasks/`, `PUT /api/tasks/{id}/` и `PATCH /api/tasks/{id}/`.

| Поле | Тип | Обязательность | Примечания |
| --- | --- | --- | --- |
| `title` | строка, не длиннее 200 | **обязательное** | Явно сделано `required=True` в `__init__` (`:321`), в соответствии с моделью |
| `status` | одно из `Task.STATUS_CHOICES` | **обязательное** | `New`, `In Progress`, `Completed`, словарь отличается от `Case.status`, см. [Обращения: поля](cases.md#fields) |
| `priority` | одно из `Task.PRIORITY_CHOICES` | **обязательное** | `Low`, `Medium`, `High`, словарь отличается от `Case.priority` |
| `due_date` | дата | необязательное | |
| `description` | текст | необязательное | |
| `account` | uuid | необязательное | В пределах организации; задать можно не больше одного из `account`/`opportunity`/`case`/`lead`. См. [выше](#tasksave-calls-full_clean) |
| `opportunity` | uuid | необязательное | То же правило одного родителя |
| `case` | uuid | необязательное | То же правило одного родителя |
| `lead` | uuid | необязательное | То же правило одного родителя |
| `created_by` |. | **только чтение** | Указано в `Meta.fields`, но определяется сервером; см. [Создание задачи](#create-a-task) |

Не входят в `TaskCreateSerializer`, но принимаются в том же теле запроса: `contacts`, `teams`,
`assigned_to`, `tags` (каждое список id в пределах организации; о том, как их *запись* различается
между методами, см. [выше](#retrieve-update-delete)); а также `task_attachment` (файл multipart) и
`custom_fields` (объект). Последние два тоже не проходят через сериализатор. Представление читает
`custom_fields` прямо из `request.data`, проверяет по строкам `CustomFieldDefinition` организации и
передаёт очищенный результат в `serializer.save(custom_fields=...)` на всех трёх методах записи
(`task_views.py:256-276,556-574,681-699`); `task_attachment` читается из `request.FILES` так же, как
в [Обращениях](cases.md#create-a-case).

`GET /api/tasks/{id}/` возвращает запись через `TaskSerializer`; `GET /api/tasks/` возвращает каждую
строку через более лёгкий `TaskListSerializer`, который дополнительно опускает `description`,
`custom_fields`, `contacts` и `teams` (сравните `TaskSerializer.Meta.fields`,
`tasks/serializer.py:287-309`, с `TaskListSerializer.Meta.fields`, `:256-271`). **Два поля,
объявленные в `TaskSerializer`, на самом деле никогда не доходят до клиента.** `task_attachment` и
`task_comments` объявлены как вложенные поля сериализатора только для чтения (`:280-281`, указаны в
`Meta.fields` в `:306-307`), но у `Task` нет атрибута ни с одним из этих имён. В этом коде нигде не
определён `GenericRelation` (`grep -rn "GenericRelation"` вне virtualenv ничего не находит), поэтому
попытка DRF прочитать `task_attachment`/`task_comments` у экземпляра выбрасывает `AttributeError`, а
поле только для чтения без явного значения по умолчанию превращает его в `SkipField`: ключи молча
опускаются из каждого ответа, а не выдаются пустыми. Нужные клиенту комментарии и вложения приходят
из отдельных ключей верхнего уровня `attachments`/`comments`, которые `TaskDetailView.get` строит
независимо (`:421-430`, [выше](#retrieve-update-delete)); присутствие поля в `Meta.fields` не
доказывает, что оно вообще выдаётся, проверяйте, что модель действительно может разрешить. **`stage`
и `kanban_order` не возвращаются ни одним `GET` и вообще отсутствуют в `Meta.fields` обоих
сериализаторов**. Они есть только в `TaskKanbanCardSerializer` (`:519-540`), который обслуживает
Kanban-эндпоинты (`/api/tasks/kanban/`, `/api/tasks/{id}/move/`), а не эндпоинты создания и
изменения, описанные на этой странице.
