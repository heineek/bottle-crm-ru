# Токены и API-ключи

Помимо JWT-сессии, описанной в разделе [Аутентификация](authentication.md), есть два типа учётных
данных для вызывающих, которым нужно аутентифицироваться без браузера и интерактивного входа:
персональные токены доступа и API-ключ организации. Эта страница описывает CRUD для обоих. Что
представляет собой каждый из них, как он определяется и насколько велик ущерб при его компрометации в
сравнении с остальными, описано в разделах [Архитектура: аутентификация](../architecture/authentication.md#personal-access-tokens)
и [Усиление безопасности](../self-hosting/security-hardening.md#token-surfaces).

## Персональные токены доступа {#personal-access-tokens}

Персональный токен доступа (`bcrm_pat_…`, `PersonalAccessToken` в `backend/common/models.py`)
аутентифицирует как профиль, который его создал, и наследует организацию и роль этого профиля. Его
`scopes` сужают эти права, и это ограничение действительно применяется.

### Области действия {#scopes}

Область действия (scope) имеет вид `<resource>:<action>`. `resource` это корневой сегмент API (первый
сегмент пути после `/api/`, то есть `leads`, `contacts`, `invoices`, `cases`, …) или `*` для всех
сразу. `action` это `read` или `write`. `read` покрывает `GET`/`HEAD`/`OPTIONS`; `write` покрывает
`POST`/`PUT`/`PATCH`/`DELETE`, с одним исключением. Начиная с django-crm 1.13.0 `POST` на один из
точных путей из `READ_ONLY_POST_PATHS` считается `read`: `/api/leads/duplicates/`,
`/api/contacts/duplicates/` и `/api/accounts/duplicates/`. Это поиск дубликатов, который запускает
форма создания: он ничего не записывает и принимает email, телефон и имя в теле только для того,
чтобы они не попадали в URL и журналы доступа. Совпадение точное: путь с лишним или недостающим
сегментом или без завершающего слэша по-прежнему считается `write`. Действие определяется методом и
путём, но никогда не содержимым тела.

Два эндпоинта макросов действуют на обращение, поэтому начиная с django-crm 1.13.0 им нужна область
`cases` в дополнение к собственной. `POST /api/macros/{id}/apply/` изменяет обращение и требует
`macros:write` **и** `cases:write`; раньше токен с `macros:write` мог создать личный макрос и
применить его к обращению, для которого у него не было `cases:write`. `POST /api/macros/{id}/render/`
ничего не записывает и возвращает тему обращения, а также имя и email его контакта, поэтому считается
`read` и требует `macros:read` **и** `cases:read`. Токену, у которого нет хотя бы одной из областей,
отвечают `403` с указанием недостающей. `*:write` покрывает apply, а `*:read` покрывает render,
поэтому API-ключ организации может выполнять render, но не apply. Оба пути сопоставляются целиком,
где id может быть любым одиночным сегментом, который принимает роутер.

`write` не подразумевает `read`. Токен, который может создавать лиды, но не может получать их список,
вполне осмысленная потребность, а область, имя которой преуменьшает выдаваемые права, перестаёт быть
границей.

**Пустой список областей означает отсутствие ограничений.** Все токены, выпущенные до появления этой
проверки, содержат `[]`, а поведение всегда было «наследует роль профиля-владельца», так что трактовка
`[]` как «ничего» отозвала бы все действующие токены при развёртывании. Не передавайте `scopes`, и вы
получите ровно прежнее поведение.

Области проверяются при создании токена. Неизвестный ресурс или действие дают `400`, потому что
иначе вызывающий с опечаткой в имени ресурса думал бы, что ограничил токен, а получил бы токен, который
вообще ничему не соответствует.

Словарь областей и логика сопоставления находятся в `backend/common/scopes.py`; проверка выполняется в
`GetProfileAndOrg`, middleware, через который и так проходит каждый запрос к `/api/`, поэтому новое
представление не может забыть подключиться. Запрос вне области отклоняется с `403` ещё до запуска
представления:

```json
{"detail": "This token is not scoped for write access to leads. It needs the leads:write scope."}
```

Путь вне `/api/<resource>/` не называет ресурс, поэтому сообщение там такое:
`"This token is not scoped for <action> access to this endpoint."`, без подсказки об области.

### Что не может сделать ни один токен, независимо от областей {#what-no-token-may-do-whatever-its-scopes}

`/api/profile/tokens/`, `/api/org/tokens/`, `/api/org/api-key/`, `/api/webhooks/`,
`/api/org/audit-log/` и, начиная с django-crm 1.13.0, `/api/profile/calendar-feed/` недоступны любому
персональному токену доступа и API-ключу организации, включая токен с пустым (неограниченным) списком
областей. Чтобы управлять учётными данными, войдите в систему. URL календарной ленты сам является
учётными данными, которые переживают выпустивший их токен, поэтому он в списке по той же причине (см.
[Задачи](tasks.md#calendar-feed)).

Причина в том, что обе цепочки делают отзыв бесполезным. Токен, который может выпустить другой
токен, невозможно отозвать: после отзыва всё, что он уже создал, продолжает работать. Токен, который
может прочитать API-ключ организации, превращает себя в постоянные учётные данные на всю организацию,
которые переживают его собственный отзыв.

Установленное Django-приложение, которое обслуживает собственный корень под `/api/`, расширяет оба
списка из своего `AppConfig.ready()` (1.43.0): `common.scopes.register_resource(name)` делает `name`
ресурсом области действия, с которым можно создать токен, а `common.scopes.register_credential_path(prefix)`
добавляет префикс пути под `/api/`, недоступный ни одному токену и ни одному ключу организации. Оба
вызова идемпотентны.

`GET /api/profile/tokens/` (`PersonalAccessTokenListCreateView`,
`backend/common/views/pat_views.py:33-47`) возвращает собственные токены вызывающего с фильтром по
`profile=request.profile` и `org=request.profile.org`, поскольку у этой таблицы нет своей политики
RLS (поиск по `token_hash` происходит до появления контекста организации, так что явный фильтр здесь
единственная граница между тенантами, а не дополнительная страховка поверх RLS):

```json
{
  "error": false,
  "tokens": [
    {
      "id": "<uuid>",
      "name": "reporting script",
      "token_prefix": "bcrm_pat_abc1",
      "scopes": [],
      "expires_at": null,
      "last_used_at": "2026-07-30T12:00:00Z",
      "created_at": "2026-07-01T09:00:00Z",
      "revoked_at": null
    }
  ]
}
```

`token_hash` никогда не сериализуется (`PersonalAccessTokenListSerializer`,
`backend/common/serializer.py:1054-1067`, где `fields` содержит ровно перечисленные выше поля); в
любом списке, на этом эндпоинте или на административном ниже, токен идентифицирует только
`token_prefix`.

## Создание и отзыв {#creating-and-revoking}

`POST /api/profile/tokens/` (то же представление, `:49-69`) создаёт токен для вызывающего:

```json
{"name": "reporting script", "scopes": [], "expires_at": null}
```

`name` обязателен (непустой, не длиннее 255 символов); `scopes`, если передан, должен быть списком не
более чем из 32 строк вида `<resource>:<action>` из словаря выше и возвращается в каноническом виде (в
нижнем регистре, без повторов); `expires_at` необязателен, но если передан, должен быть в будущем;
`validate_expires_at` отклоняет прошедшую метку времени с сообщением `"expires_at must be in the future."`
(`backend/common/serializer.py:1092-1097`). При успехе (`201`):

```json
{
  "error": false,
  "id": "<uuid>",
  "name": "reporting script",
  "token_prefix": "bcrm_pat_abc1",
  "scopes": [],
  "expires_at": null,
  "last_used_at": null,
  "created_at": "2026-08-02T10:00:00Z",
  "revoked_at": null,
  "token": "bcrm_pat_abc1...<the full raw token>"
}
```

Поле `token` единственный раз, когда возвращается исходное значение. Оно генерируется, хешируется, а
открытый текст отбрасывается; получить его позже нельзя, можно только отозвать токен и создать новый.
Ошибка валидации возвращает `400` с `{"error": true, "errors": {...}}`, в той же форме, что описана в
разделе [Ошибки](errors.md#validation-errors).

`DELETE /api/profile/tokens/{id}/` (`PersonalAccessTokenDetailView`, `:72-86`) отзывает токен: он
заполняет `revoked_at`, а не удаляет запись. Поиск ограничен `org=request.profile.org` **и**
`profile=request.profile` одновременно, поэтому id чужого токена возвращает `404`, а не `403`: отозвать
токен может только его владелец, и по ответу нельзя понять, что под этим id вообще существует токен
другого пользователя. Повторный отзыв уже отозванного токена ничего не делает и всё равно
возвращает `200`.

## Контроль токенов организации {#organization-token-oversight}

`GET /api/org/tokens/` (`OrgAccessTokenListView`, `backend/common/views/pat_views.py:89-152`) это
отдельный эндпоинт только для администраторов (`permission_classes = (IsAuthenticated, HasOrgContext,
IsOrgAdmin)`), который возвращает все персональные токены доступа в организации, а не только токены
вызывающего. Он намеренно отделён от `profile/tokens/` выше, а не объединён с ним через расширенный
для администратора фильтр, чтобы ради контроля никогда не пришлось ослаблять защиту
«пользователь управляет только своими токенами» на эндпоинте самообслуживания:

```json
{
  "error": false,
  "tokens": [
    {
      "id": "<uuid>",
      "name": "reporting script",
      "token_prefix": "bcrm_pat_abc1",
      "scopes": [],
      "expires_at": null,
      "last_used_at": "2026-07-30T12:00:00Z",
      "created_at": "2026-07-01T09:00:00Z",
      "revoked_at": null,
      "owner": {"id": "<uuid>", "name": "Jane Doe", "role": "USER", "is_active": false},
      "is_live": true
    }
  ],
  "totals": {"count": 12, "live": 9, "orphaned": 2, "unused_90d": 3}
}
```

`owner.is_active: false` при `is_live: true` это именно тот случай, ради которого существует это
представление: токен, принадлежащий профилю, который с тех пор деактивировали. Деактивация профиля
делает его токены недействительными как побочный эффект, а не отдельным шагом отзыва:
`resolve_valid_pat` (`backend/common/pat_auth.py:29-46`) проверяет `pat.profile.is_active` (и
`pat.org.is_active`) при каждом использовании, так что токен из примера выше не сможет снова
аутентифицироваться, пока профиль владельца не активируют заново. `"orphaned"` в `totals` считает
именно такие токены: ещё не отозванные (`is_live`), но бездействующие, потому что их владельца больше
нет. Именно их администратор при оффбординге явно отзывает эндпоинтом ниже.

`DELETE /api/org/tokens/{id}/` (`OrgAccessTokenDetailView`, `:155-176`) отзывает любой токен в
организации администратора с фильтром только по `org=request.profile.org` (без фильтра `profile=`, в
отличие от удаления на эндпоинте самообслуживания выше). Администратор может отозвать токен коллеги,
деактивированного или нет. pk из другой организации по-прежнему даёт `404`. Повторный отзыв уже
отозванного токена ничего не делает и возвращает `200`, как и на эндпоинте самообслуживания.

Ни один из этих эндпоинтов не охватывает токены [участников-приложений](#app-members) (1.43.0): они
не попадают ни в список, ни в его итоги, а их отзыв здесь даёт `404`. Таким токеном управляет
установленное приложение, которому он принадлежит.

## Участники-приложения {#app-members}

Начиная с 1.43.0 у организации могут быть участники, которые являются приложениями, а не людьми
(`Profile.is_app`). В community-редакции их ничто не создаёт; их создаёт установленное
Django-приложение с помощью `common.app_members.create_app_member(org, name)` и выдаёт такому
участнику собственный персональный токен доступа. Участник-приложение является администратором своей
организации в части чтения и того, что администратор может делать с записями, и действует через этот
токен в рамках его областей действия и списка запретов выше. Он записывает записи, но никогда не
конфигурацию: любое изменение настройки организации, доступное только администратору (воронки и
этапы, источники и приём лидов, почтовые ящики, правила согласования, эскалации и маршрутизации,
настройки повторного открытия и устаревания, цели, товары и шаблоны счетов, общие макросы,
дополнительные поля, теги, команды и люди, настройки организации и модули, домены, рабочие часы,
веб-формы, пакеты и приложения), отвечает ему `403`, хотя читать всё это он по-прежнему может.
Создать организацию он тоже не может. Код, который ограничивает запись конфигурации, проверяет
`common.permissions.may_configure(profile)`; `IsOrgAdmin` применяет эту проверку к каждому
небезопасному методу. Его пользователь не может войти в систему: у него нет пароля, он неактивен, а
его адрес находится на зарезервированном домене `apps.bottlecrm.invalid`, на который никогда не
отправляются письма. Деактивация (`common.app_members.deactivate_app_member`) сразу делает его токен
недействительным.

Участник-приложение никогда не считается человеком. `Profile.objects` исключает участников-приложений,
поэтому их нет ни в одном списке участников, выборе ответственного или команды, ротации
маршрутизации, оповещении или письме-оповещении, упоминании, строке Outcomes или Response time,
счётчике участников, строке сотрудника по обращениям, списке наблюдателей обращения или списке
участников доски, и API-ключ организации никогда не действует от его имени. Он не может подписаться
на обращение (`POST /api/cases/{id}/watch/` отвечает `403`). Записи, которые он создаёт, указываются
под его именем, а доска, которую он создаёт, показывает его как `owner` доски. Код, которому нужно
найти участника-приложение, использует `Profile.all_objects`, а эндпоинт, которым владеет
участник-приложение, описан в разделе [Вебхуки](../integrations/webhooks.md#setting-one-up).

## API-ключи организации {#organization-api-keys}

У каждой организации ровно один API-ключ (`Org.api_key`), которым управляют через
`GET`/`POST /api/org/api-key/` (`OrgApiKeyView`, `backend/common/views/organization_views.py:244-326`).
Оба метода доступны только администраторам; это проверяется вручную в `_admin_org_or_error`
(`:255-275`), а не классом разрешений `IsOrgAdmin`, но правило то же:
`request.profile.role == "ADMIN"` или `request.profile.is_organization_admin`.

В отличие от персонального токена доступа, этот ключ не аутентифицирует как конкретного человека:
запрос с ним в заголовке `Token` сопоставляется с первым активным профилем `ADMIN` организации
(`backend/common/middleware/get_company.py`). Организация всегда берётся из `request.profile.org`, а не
из данных клиента, поэтому вызывающий может прочитать или сменить только ключ своей организации.

Ко всем запросам с этим ключом применяются два ограничения, которые middleware проверяет до запуска
любого представления:

- **Только чтение.** Ключ оценивается как список областей `("*:read",)`, поэтому небезопасный метод
  даёт `403`, за исключением трёх `POST` поиска дубликатов выше, которые считаются `read`.
- **Нет доступа к учётным данным.** Действует список запретов выше, поэтому ключ не может прочитать
  или сменить сам себя либо выпустить персональный токен доступа от имени администратора, чью
  личность он заимствует.

Установите `DJANGO_ORG_API_KEY_AUTH=false`, чтобы полностью запретить этот ключ как способ
аутентификации. По умолчанию он включён, чтобы обновление ничего не сломало. Даже в режиме только для
чтения один бессрочный ключ на тенанта, который читает все записи и который нельзя отозвать для
отдельной интеграции, это грубый инструмент; для всего нового лучше подходит персональный токен
доступа с ограниченными областями.

`GET /api/org/api-key/`:

```json
{"error": false, "api_key": "<the current key>"}
```

`POST /api/org/api-key/` выполняет ротацию: генерирует новый ключ и сразу перезаписывает старый:

```json
{
  "error": false,
  "message": "API key rotated. The previous key is no longer valid.",
  "api_key": "<the new key>"
}
```

Сообщение не просто для красоты: старый ключ перестаёт аутентифицировать в момент возврата этого
вызова, без какого-либо льготного периода. Вызывающий без прав администратора получает `403` с
`{"error": true, "errors": "Only organization admins can access the API key"}` от любого из методов;
вызывающий вообще без контекста организации получает `400` с
`{"error": true, "errors": "Organization context required"}`.
