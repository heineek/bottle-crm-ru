# Клиентский портал

Эндпоинты, которые вызывает **клиент**, подключены под `/api/portal/`. Всё остальное в этом разделе
представляет собой внутренний API, которым пользуются ваши сотрудники и скрипты. Это две отдельные
области учётных данных, и токен одной не работает в другой; почему это разделение обеспечивается в
трёх независимых местах, а не в одном, объясняет раздел
[Архитектура: учётные данные клиентского портала](../architecture/authentication.md#customer-portal-credentials).

Пользователь портала представлен строкой `Contact`, а не `User` и не `Profile`. У него нет пароля,
нет аккаунта Google, нет роли, и его нет в списке участников вашей организации. Ему доступны
обращения, в которых он указан, а также статьи справки, которые его организация согласовала и
опубликовала, и больше ничего.

!!! warning "В этой кодовой базе «порталом» называются две разные вещи"
    **Портал счетов и коммерческих предложений** (`/api/public/…`) представляет собой ссылку с
    токеном, отправленную клиенту по почте: обладание URL и есть вся учётная запись, входа нет.
    **Клиентский портал**, описанный здесь, требует входа: клиент доказывает, что контролирует адрес
    электронной почты, и получает токен сессии. Общее у них только слово. Оба типа токенов описаны в
    разделе [Глоссарий: токен портала](../reference/glossary.md#portal-token).

## Вход {#signing-in}

Вход выполняется отдельно для каждой организации. Id организации указан в пути, потому что клиент
пришёл из письма, которое ему отправила эта организация, и попытка входа всегда ищет контакты только в
ней. Выбора организации намеренно нет: `Contact` существует отдельной строкой в каждой организации,
поэтому один и тот же адрес в двух компаниях означает две не связанные между собой связи, а
показ списка для выбора раскрыл бы список клиентов одного тенанта другому.

### Запрос кода {#request-a-code}

`POST /api/portal/login/{org_id}/request/` (`PortalLoginRequestView`,
`backend/common/views/portal_auth_views.py`). Публичный: `permission_classes = []`,
`authentication_classes = []`.

```json
{"email": "customer@example.com"}
```

Этот эндпоинт **всегда возвращает `200`** с одним и тем же телом, независимо от того, принадлежит ли
адрес контакту в этой организации, контакту в *другой* организации, вообще не является контактом, не
прошёл проверку email или упёрся в ограничение частоты:

```json
{"message": "If this email is valid, you will receive a sign-in code."}
```

Обрабатывать `400` не нужно. Единственный другой ответ: `429`, от ограничений на клиента и на
организацию в `backend/common/throttles.py` (`PORTAL_LOGIN_THROTTLE_IP`, по умолчанию `30/hour`, и
`PORTAL_LOGIN_THROTTLE_ORG`, по умолчанию `100/hour`); они срабатывают до того, как проверяются
организация и email, поэтому не раскрывают ни то, ни другое. Единообразие здесь и есть цель: любое
различие в статусе, теле или наблюдаемой работе позволило бы постороннему проверить, с какими из
клиентов его конкурентов вы работаете. По почте отправляется шестизначный код, который хранится
только в виде хеша PBKDF2 и истекает через 10 минут. Не более пяти кодов на контакт в час, как и у
внутренней magic-link-ссылки. Каждый новый запрос аннулирует предыдущий неиспользованный код этого
контакта, поэтому пересланное старое письмо перестаёт работать в тот момент, когда настоящий клиент
запрашивает код снова.

### Обмен кода на сессию {#exchange-it-for-a-session}

`POST /api/portal/login/{org_id}/verify/` (`PortalLoginVerifyView`):

```json
{"email": "customer@example.com", "code": "123456"}
```

```json
{
  "access_token": "<jwt>",
  "contact": {"id": "<uuid>", "name": "Riley Okonkwo", "email": "customer@example.com"},
  "org": {"id": "<uuid>", "name": "Acme"}
}
```

Строка читается под `select_for_update`, поэтому две одновременные попытки не могут увидеть одно и то
же число попыток, и код сгорает после 5 неудачных попыток, даже если затем приходит правильный.
`is_active` контакта проверяется заново в этот момент, а не берётся на веру с момента выпуска кода.

Неудача во всех случаях (истёк, уже использован, неверный код, неизвестный email, контакт
деактивирован, организация не найдена) даёт один и тот же `400`:

```json
{"error": "That code is not valid any more. Request a new one."}
```

## Использование токена сессии {#using-the-session-token}

Передавайте его как `Authorization: Bearer <access_token>`. Он действителен **24 часа**.

**Refresh-токена нет.** Когда токен истекает, клиент запрашивает новый код. Для раздела, который
посещают несколько раз за обращение, это необременительное действие, и оно полностью избавляет этот
раздел от ротации токенов, отзыва refresh-токенов и аннулирования при изменении прав.

Токен содержит `typ: "portal"`, `org_id` и `contact_id` и намеренно **не содержит `user_id`**,
поэтому собственный `get_user` из SimpleJWT его отклоняет. Предъявление токена где-либо вне
`/api/portal/` отклоняется middleware до запуска любого представления:

```json
{"error": "This credential is not valid for this endpoint."}
```

со статусом `403`. Деактивация контакта делает токен недействительным при следующем запросе, потому
что класс аутентификации каждый раз заново читает `is_active`, а не доверяет claim.

## Отключённые модули {#switched-off-modules}

Организация может отключить обращения или базу знаний (см. [Модули](modules.md)). Тогда портал
отвечает так же, как на запрос несуществующего объекта, и никогда не называет модуль: пока обращения
отключены, каждый эндпоинт обращений портала, включая список и создание, отвечает `404`
`{"error": "Case not found"}`, а пока отключена база знаний, список и детальный просмотр статей
отвечают `404` `{"error": "Article not found"}`. Подсказки статей отвечают `200` `{"articles": []}`,
как на пустой запрос. Вход это не затрагивает, как и остальную часть портала.

## Обращения {#cases}

Все четыре эндпоинта ниже требуют токен портала. Каждый запрос фильтруется и по организации, и по
контакту из токена.

### Список {#list}

`GET /api/portal/cases/`

```json
{
  "cases": [
    {
      "id": "<uuid>",
      "name": "Login broken",
      "status": "New",
      "priority": "High",
      "created_at": "2026-08-15T10:04:11Z",
      "closed_on": null
    }
  ],
  "cases_count": 1
}
```

Сначала самые новые, `LimitOffsetPagination` (параметры запроса `limit` и `offset`). Необязательный
`?status=` принимает один из статусов обращения; нераспознанное значение даёт `400`, а не молча
пустой список.

**Область видимости: собственные обращения контакта, а не компании.** Коллега из той же компании не
может прочитать обращение, в котором он не указан. Расширить это позже можно миграцией; сужение позже
означало бы уведомление об утечке.

### Создание {#create}

`POST /api/portal/cases/`

```json
{"name": "Printer on fire", "description": "It started this morning.", "priority": "High"}
```

Возвращает `201` с `{"case": {…}}` в формате детального просмотра ниже. Три поля, и это весь
сериализатор. `org`, `status` и связь с контактом задаёт сервер, а `created_by` остаётся null, потому
что клиент не является `User`. Если тело также передаёт `org`, `status` или `contacts`, они
игнорируются, а не применяются, потому что эти поля вообще не объявлены в сериализаторе.

Пустое или состоящее только из пробелов `name` даёт `400`.

### Детальный просмотр {#detail}

`GET /api/portal/cases/{id}/`

```json
{
  "case": {
    "id": "<uuid>",
    "name": "Login broken",
    "status": "New",
    "priority": "High",
    "description": "Cannot get past the sign-in screen.",
    "created_at": "2026-08-15T10:04:11Z",
    "closed_on": null
  },
  "comments": [
    {
      "id": "<uuid>",
      "comment": "We are looking into it now.",
      "commented_on": "2026-08-15T11:20:03Z",
      "author": "Support",
      "is_mine": false
    }
  ]
}
```

Три вещи, которых этот ответ намеренно не содержит:

- **Внутренние заметки.** `is_internal=False` применяется в запросе, а не в сериализаторе, поэтому
  личная заметка сотрудника никогда не загружается и не может утечь из-за последующего изменения
  того, как формируется ответ.
- **Какой сотрудник ответил.** Каждый комментарий с вашей стороны подписан как `"Support"`. Кто из
  коллег его написал, является внутренней информацией; клиенту нужно знать, что ответила поддержка.
- **Всё остальное об обращении.** Назначение, команды, наблюдатели, счётчики SLA и теги отсутствуют,
  потому что сериализатор их никогда не объявляет, а не потому, что они вырезаются потом.

Несуществующее обращение и обращение, принадлежащее кому-то другому, возвращают одинаковый `404`
`{"error": "Case not found"}`, поэтому перебором id нельзя выяснить, принадлежит ли обращение коллеге.

### Ответ {#reply}

`POST /api/portal/cases/{id}/comment/`

```json
{"comment": "Still seeing the error on my phone."}
```

Возвращает `201` с комментарием в формате выше, где `is_mine` равен `true`, а `author` содержит имя
самого клиента. Не более 10 000 символов; пустой или состоящий только из пробелов комментарий даёт
`400`.

`is_internal` **не** является полем этого сериализатора. Клиент не может писать в закрытую ветку
вашей команды, и передача `"is_internal": true` в теле ни на что не влияет.

На стороне сотрудника ответ приходит как обычный комментарий с `commented_by`, равным null, и
`commented_by_contact`, указывающим на клиента; ту же форму даёт входящий ответ по электронной почте
(см. [Обращения](cases.md)). Он считается ответом клиента везде, где это различие важно: при отметке
первого ответа для SLA и при автоматическом переоткрытии закрытого обращения. Окно переоткрытия
считается в днях по календарю организации (`Org.timezone`): токен портала указывает организацию, и
middleware активирует её часовой пояс для запроса так же, как для вошедшего пользователя.

## Статьи справки {#help-articles}

Часть базы знаний, доступная клиентам для чтения. Три эндпоинта, все только для чтения, все требуют
токен портала.

**Клиенту видно меньше, чем сотруднику.** Подсказчик для сотрудников
(`GET /api/cases/{id}/solution-suggestions/`, см. [Обращения](cases.md)) показывает всё
опубликованное; эти эндпоинты требуют, чтобы статья была **одновременно `is_published` и
`status="approved"`** и принадлежала организации из токена. `PortalBaseView._published_articles`
является единственным местом, где это решается, так же как `_my_cases` для обращений.

Требование обоих условий не является перестраховкой ради перестраховки. Правило «опубликована
значит одобрена» проверяется при записи в `SolutionSerializer.validate`, но оно появилось позже
модели, поэтому строки, созданные до него, могут оказаться опубликованными черновиками. Они остаются
невидимыми для клиентов, а первая правка такой строки приводит пару в порядок.

### Список {#list_1}

`GET /api/portal/articles/`

```json
{
  "articles": [
    {
      "id": "<uuid>",
      "title": "Resetting your password",
      "updated_at": "2026-08-16T09:12:00Z"
    }
  ],
  "articles_count": 1
}
```

Сортировка по заголовку, `LimitOffsetPagination`. Необязательный `?search=` ищет вхождение подстроки
в заголовке или тексте без учёта регистра. Поиск сужает тот же видимый набор, что и список, и никогда
не применяется к `Solution.objects`, поэтому не может стать второй, более широкой лазейкой.

### Детальный просмотр {#detail_1}

`GET /api/portal/articles/{id}/`

```json
{
  "article": {
    "id": "<uuid>",
    "title": "Resetting your password",
    "description": "Open Settings, choose Security, then Reset password.",
    "updated_at": "2026-08-16T09:12:00Z"
  },
  "related": [
    {"id": "<uuid>", "title": "Changing your billing address"}
  ]
}
```

Четыре поля, и это вся проекция. Намеренно отсутствуют: `status` и `is_published` (queryset уже
решил, что клиент может это читать, поэтому повторение решения в payload только создаёт лишнее,
что может утечь), `created_by` (кто из коллег написал ответ, является внутренней информацией; то же
правило подписывает каждый комментарий сотрудника как `"Support"`) и `linked_cases`, которые выдали
бы этому клиенту id обращений других клиентов.

`related` вычисляется по **тегам сотрудников** и никогда их не содержит. Словарь тегов общий с
лидами и сделками и содержит что-то вроде «At Risk» и «VIP», поэтому теги отбирают строки, но не
появляются в ответе: только id и заголовки, не более 3, без самой статьи. Список строится из
`_published_articles`, поэтому общий тег не может привести к черновику или статье другой
организации. Связанность сужает видимый набор и никогда его не расширяет.

Черновик, неопубликованная статья и статья другой организации возвращают тот же `404`
`{"error": "Article not found"}`, что и id, которого никогда не существовало.

### Подсказки {#suggestions}

`GET /api/portal/articles/suggest/?q=`

```json
{
  "articles": [
    {"id": "<uuid>", "title": "Resetting your password", "snippet": "Open Settings, choose…"}
  ]
}
```

Самообслуживание в форме нового обращения: клиент вводит краткое описание, и этот эндпоинт до
отправки обращения отвечает до трёх подходящими статьями. Он работает от запроса, а не от
обращения, потому что в этот момент обращения ещё нет, и поэтому это отдельный эндпоинт, а не
подсказчик для сотрудников.

Пустой или отсутствующий `q` возвращает пустой список. В отличие от стороны сотрудника, недавние
статьи не подставляются: сотрудник, просматривающий новейшие ответы, делает свою работу, а клиент,
которому показали три не относящиеся к делу статьи, просто научится игнорировать эту панель.

## Уведомления {#notifications}

Когда сотрудник публикует публичный ответ или у обращения меняется статус, уведомление получает
каждый указанный в обращении контакт, у которого есть адрес электронной почты. Контакт, вызвавший
изменение, исключается, поэтому никто не получает письмо о собственном ответе, а внутренняя заметка
ничего не запускает.

Ссылка в письме содержит id обращения и id организации и **никаких учётных данных**. Пересылка
письма не передаёт доступ; получателю всё равно нужно войти. В этом отличие от писем со счетами и
коммерческими предложениями, где токен в URL и есть вся учётная запись.

`FRONTEND_URL` служит базой для этой ссылки. См.
[Переменные окружения](../reference/environment-variables.md).
