# Контакты

Маршруты в `backend/contacts/urls.py`: `backend/contacts/views.py` для CRUD и комментариев/вложений,
`backend/contacts/import_views.py` и `backend/contacts/services/csv_import.py` для импорта CSV.
Правила пагинации, фильтрации и структуры ответа, которые здесь подразумеваются и не повторяются,
описаны в разделе [Соглашения](conventions.md).

## Две связи с компанией, а не одна {#two-links-to-an-account-not-one}

Прежде всего: **контакт может быть связан с компанией двумя разными способами**, и эти способы
независимы. `Contact.account` является внешним ключом, который сама модель описывает как «Primary
account this contact belongs to» (`contacts/models.py:71-78`); `Account.contacts` представляет собой
отдельную связь many-to-many (`accounts/models.py:63-65`). Ничто в базе данных не синхронизирует их.
Установка одной сама по себе не устанавливает другую. Слой представлений связывает их при записи:
`link_primary_account(contact)` (`contacts/views.py:48-65`) добавляет контакт в
`contact.account.contacts` всякий раз, когда `account` задаётся через `POST /api/contacts/`,
`PUT /api/contacts/{id}/` или `PATCH /api/contacts/{id}/`, но последующая очистка внешнего ключа
членство в M2M **не** удаляет, намеренно (человек может перестать быть «основным контактом», не
«уйдя из компании»; `contacts/views.py:59-62`).

Обе связи намеренно отдаются в каждом ответе `ContactSerializer`, потому что чтение только одной из
них в зависимости от данных рассказывает неверную историю:

```json
{
  "account": "<uuid or null>",
  "account_detail": {"id": "<uuid>", "name": "Acme Inc"},
  "linked_accounts": [{"id": "<uuid>", "name": "Acme Inc"}]
}
```

`account_detail` разрешает внешний ключ (`contacts/serializer.py:28-39`); `linked_accounts`
представляет собой членство в M2M (`:41-56`). Список контактов на странице компании строится по
`Account.contacts` (M2M), а не по внешнему ключу, поэтому контакт, у которого внешний ключ `account`
задан, но который так и не был добавлен в `contacts` этой компании (именно этот случай описан ниже в
разделе [Импорт CSV](#csv-import)), там не появится, хотя `account_detail` у самого контакта
выглядит правильно.

## Список контактов {#list-contacts}

`GET /api/contacts/` (`ContactsListView.get`, `contacts/views.py:199-201`) возвращает один
постраничный список. В отличие от лидов и компаний, он не делится на две секции. Однако и он не
вызывает DRF-метод `get_paginated_response()`. В разделе [Соглашения](conventions.md#pagination)
единственным эндпоинтом этого API, который так делает, назван `GET /api/cases/solutions/`.
Представление само вручную собирает `count` и `results` (`contacts/views.py:166-167`), без
`next`/`previous`, рядом с набором устаревших ключей, сохранённых для обратной совместимости
(`:168-171`):

```json
{
  "count": 41,
  "results": [ { "...": "ContactSerializer" } ],
  "per_page": 10,
  "page_number": [1],
  "contacts_count": 41,
  "offset": 10,
  "contact_obj_list": [ { "...": "same rows as results" } ],
  "countries": [["GB", "United Kingdom"]],
  "users": [{"id": "...", "user__email": "..."}]
}
```

`active_count` и `inactive_count` (`contacts/views.py:147-148`) вычисляются по всему
отфильтрованному queryset *до* применения какого-либо фильтра `is_active`, поэтому клиент может
показывать «12 активных, 3 неактивных», одновременно запрашивая только одну из групп через
`?is_active=true`/`?is_active=false` (`:149-150`). Это единственный булев фильтр с точным совпадением
в этом эндпоинте; все остальные фильтры здесь ищут вхождение подстроки: `name` (`first_name` или
`last_name`), `city`, `phone`, `email`, `search` (`first_name`, `last_name`, `email` или `phone`), а
также `assigned_to`/`tags` (повторяемые списки id), `created_at__gte/lte` и `cf_<key>`
(`contacts/views.py:90-139`). Вызывающий без прав администратора видит только контакты, за которые
он отвечает или которые он создал (`:83-87`).

## Создание контакта {#create-a-contact}

`POST /api/contacts/` (`ContactsListView.post`, `contacts/views.py:218-311`) проверяется
сериализатором `CreateContactSerializer` (`contacts/serializer.py:102-174`); см. [Поля](#fields). При
успехе (`200`):

```json
{"error": false, "message": "Contact created Successfuly", "id": "<uuid>"}
```

(Строка сообщения в ответе написана именно так, `Successfuly`, а не `Successfully`; пишите
интеграционные тесты против реальной строки, а не ожидаемой.) Два валидатора, о которых стоит знать:
**`email` должен быть уникальным в пределах организации без учёта регистра**, проверяется только
если передан (`validate_email`, `contacts/serializer.py:129-145`); и **`account`, если указан, должен
принадлежать организации вызывающего**: `validate_account` отклоняет UUID из таблицы `Account`
любой другой организации с сообщением `"No such account."`, а не молча прикрепляет запись чужого
тенанта (`contacts/serializer.py:114-127`). `teams`, `assigned_to` и `tags` тоже не входят в
сериализатор: представление разрешает каждое из них из тела запроса, принимая либо JSON-массив, либо
строку в кодировке JSON со списком id (или объектов `{"id": "..."}`), одинаково для всех трёх полей
и одинаково в `POST` (`contacts/views.py:247-284`), `PUT` (`:478-518`) и `PATCH` (`:832-876`).
У контактов нет той несогласованности по полям и HTTP-методам, которую раздел [Лиды](leads.md#fields)
описывает для аналогичных полей там. `contact_attachment` принимается как multipart-файл.

## Получение, изменение, удаление {#retrieve-update-delete}

`GET /api/contacts/{id}/` (`ContactDetailView.get`, `contacts/views.py:565-654`) ищет запись только
в организации вызывающего и превращает некорректный id в `404` так же, как это делают компании
(`get_object`, `:318-332`). `assert_contact_access` (`:334-361`) задаёт самое широкое правило
доступа среди этих четырёх страниц: читать, изменять и комментировать контакт могут администратор,
создатель контакта, один из ответственных **или любой, кто отвечает за компанию, с которой контакт
связан любым из двух способов** (внешний ключ или M2M; `account_ids`, `:363-369`); все остальные
получают `403`. Ответ вкладывает запись под ключ `contact_obj` и также возвращает `address_obj`
(плоские поля адреса, повторённые отдельным объектом), `countries` (`contacts/views.py:608`),
`comments`, `attachments`, `assigned_data`, `tasks`, `users_mention`, `custom_field_definitions` и
три вычисляемых списка с ограничением длины: `opportunities` (до 10, через `Opportunity.contacts`),
`cases` (до 10, через `Case.contacts`) и `colleagues` (до 8: другие контакты, у которых общая
связь с компанией любого из двух видов; сопоставление идёт по связи с компанией, а не по текстовому
полю `organization`, в котором часто указана другая компания). `tasks`, `opportunities`, `cases` и
`colleagues` содержат только записи, которые вызывающий может открыть по правилу чтения
соответствующего модуля, поэтому пользователь без прав администратора видит у того же контакта меньше
строк, чем администратор.

`open_deals` подытоживает все открытые сделки с этим контактом, которые вызывающий может открыть, без
ограничения числа: `count`, `amount` (общая сумма, если все сделки в одной валюте, и `null`, если
валют несколько) и `by_currency` (`[{currency, count, amount}]`, по порядку кодов). Сделка без
валюты учитывается в валюте организации по умолчанию. Используйте его вместо суммирования
`opportunities`, где не больше 10 записей. `opportunity_count` содержит число сделок с этим
контактом, которые вызывающий может открыть, открытых или закрытых, без ограничения.

`PUT /api/contacts/{id}/` (`:441-544`) и `PATCH /api/contacts/{id}/` (`:793-881`) оба вызывают
`link_primary_account` после сохранения (`:477`, `:830`), поэтому изменение `account` любым из этих
методов поддерживает `Account.contacts` в актуальном состоянии так же, как создание. Успех:
`{"error": false, "message": "Contact Updated Successfully"}`.

Ответ детального просмотра также содержит `can_delete`: будет ли принят `DELETE` от этого
вызывающего, чтобы клиент предлагал это действие только в таком случае.

`DELETE /api/contacts/{id}/` (`:670-691`) намеренно уже, чем доступ на чтение и запись: исключения
для ответственных нет, удалить контакт может только администратор или его создатель
(`self.request.profile.user_id != self.object.created_by_id`, `:676-679`).

## Импорт CSV {#csv-import}

Два эндпоинта, оба доступны только администраторам организации или участникам с `has_sales_access`
(`can_mass_import` в `common/permissions.py`). Обычный участник получает `403`:

`POST /api/contacts/import/preview/` (`ContactImportPreviewView`, `contacts/import_views.py`) читает
загрузку `multipart/form-data` из поля `file` (имя должно оканчиваться на `.csv`, ограничение 5 МБ,
проверяется по реально прочитанным байтам, а не по переданному клиентом `Content-Length`;
`_read_upload`), проверяет каждую строку, ничего не записывая, и возвращает:

```json
{
  "header_error": null,
  "valid": [
    {
      "row": 2, "first_name": "Ada", "last_name": "Lovelace", "email": "ada@example.com",
      "phone": "2025551234", "organization": null, "title": null, "department": null,
      "do_not_call": false, "linkedin_url": null, "address_line": null, "city": null,
      "state": null, "postcode": null, "country": null, "description": null,
      "account_id": "<uuid or null>", "assigned_ids": [], "team_ids": [], "tag_names": []
    }
  ],
  "errors": [{"row": 3, "field": "email", "message": "'not-an-email' is not a valid email"}],
  "summary": {"total": 2, "valid": 1, "invalid": 1}
}
```

`POST /api/contacts/import/commit/` (`ContactImportCommitView`) повторно проверяет тот же файл и
записывает данные в одной транзакции (`commit_rows` / `_commit_validated` в
`contacts/services/csv_import.py`); если хотя бы одна строка не проходит проверку, **ничего не
записывается**; конкурентный конфликт (например, дубликат email, созданный другим запросом между
предпросмотром и фиксацией) откатывает весь пакет и возвращает `400`, а не импортирует данные
частично. При успехе (`200`):

```json
{"error": false, "created": 12, "ids": ["<uuid>", "..."]}
```

В CSV должна быть строка заголовков, содержащая как минимум `first_name` и `last_name`; полный список
распознаваемых необязательных заголовков: `email`, `phone`, `organization`, `title`, `department`,
`do_not_call`, `linkedin_url`, `address_line`, `city`, `state`, `postcode`, `country`,
`description`, `account_name`, `assigned_emails`, `team_names`, `tags`
(`REQUIRED_HEADERS`/`OPTIONAL_HEADERS` в `csv_import.py`); нераспознанный заголовок или отсутствие
обязательного отклоняет весь файл с `header_error` ещё до проверки строк. `assigned_emails` и
`team_names` принимают в одной ячейке несколько значений через `;`. Дубликаты отклоняются в пределах
организации: email и телефон (после нормализации) всегда дают жёсткую ошибку; совпадение имени и
фамилии даёт жёсткую ошибку, только если в строке **нет ни** email, **ни** телефона, по которым её
можно было бы отличить от существующего контакта (`csv_import.py`). Файл ограничен 5 000 строками
данных (`MAX_ROWS`).

**Строка с `account_name` устанавливает обе связи с компанией.** `_commit_validated` создаёт каждый
`Contact` с `account_id=vr.account_id`, а затем вызывает `link_primary_account`, как это делают
`POST /api/contacts/` и эндпоинты изменения `PUT`/`PATCH` (см.
[Две связи с компанией](#two-links-to-an-account-not-one)), поэтому импортированный контакт
появляется и в списке контактов этой компании (`Account.contacts`, M2M), и в `account_detail`.

### Сопоставление столбцов (`mapping`) {#column-matching-mapping}

Оба эндпоинта также принимают необязательное поле формы `mapping`, которое переключает их в режим
сопоставления столбцов. Его значение: `"auto"` (угадать каждый столбец по заголовку; распознаются
выгрузки Google Contacts, Outlook и HubSpot) или JSON-объект `{"<column index>": "<field>" | null}`,
который задаёт или переопределяет догадку, причём `null` означает «игнорировать столбец». В этом
режиме файл может быть `.csv` (UTF-8 или Windows-1252; разделитель запятая, точка с запятой или
табуляция) или `.xlsx` (только первый лист), по-прежнему с ограничениями 5 МБ, 5 000 строк и 1 000
столбцов, а имена заголовков не обязаны совпадать со списком выше. Без `mapping` всё описанное выше
действует без изменений.

Некорректное значение не стоит вам человека: оно отбрасывается и учитывается, а остальная часть
строки импортируется. Пропускается только строка, из которой нельзя создать контакт, или строка,
дублирующая существующий контакт (по email в пределах всей организации или по телефону и имени среди
видимых вам контактов). Строки нумеруются с 1, начиная с первой строки под заголовком. Предпросмотр
отвечает (запись `valid` здесь сокращена):

```json
{
  "columns": [{"index": 0, "header": "First Name", "field": "first_name", "samples": ["Ada", "Grace"]}],
  "fields": [{"name": "first_name", "label": "First name", "required": true}],
  "valid": [{"row": 1, "first_name": "Ada", "last_name": "Lovelace"}],
  "skipped": [
    {
      "row": 2, "field": "email",
      "message": "A contact with this email already exists in your organization",
      "cells": ["Grace", "Hopper", "grace@example.com"], "kind": "duplicate"
    }
  ],
  "dropped": [{"field": "phone", "count": 1}],
  "summary": {"total": 2, "valid": 1, "skipped": 1}
}
```

`kind` равен `"duplicate"`, если контакт уже существует (в организации или выше в том же файле), и
`"row"`, если из строки нельзя создать контакт; клиенты ветвятся по нему, а не по `message`.

а фиксация отвечает `{"error": false, "created": 1, "ids": ["<uuid>"], "skipped": [...],
"dropped": [...]}`. Файл, из которого нечего импортировать, получает `400` `"Nothing in this file can
be imported."`. Все четыре эндпоинта импорта контактов и лидов используют общее ограничение частоты
на пользователя `IMPORT_THROTTLE` (по умолчанию `30/minute`; см.
[Переменные окружения](../reference/environment-variables.md#imports)).

## Дубликаты и объединение {#duplicates-and-merging}

`POST /api/contacts/duplicates/` принимает в теле JSON поля, которые пользователь уже ввёл в форму
создания (`email`, `phone`, `first_name`, `last_name`), и отвечает `{"duplicates": [...]}`: не
более 10 активных контактов, сначала самые новые. `GET /api/contacts/{id}/duplicates/` возвращает
такой же список для сохранённого контакта, исключая сам контакт, плюс `can_delete` для этого
контакта. Каждое совпадение содержит только `id`, `name`, `email`, `phone`, `matched_on` (правила,
по которым оно совпало) и `can_delete` (может ли вызывающий поглотить его объединением), но никогда
не саму запись. Оба ищут только среди контактов, которые вызывающий может открыть, поэтому скрытый
контакт не выводится и не учитывается, а скрытый или отсутствующий `{id}` даёт одинаковый `404`.
Значение длиннее допустимого моделью даёт `400`. Проверка из формы создания сделана как `POST`,
который ничего не записывает, чтобы адрес электронной почты и номер телефона никогда не попадали в
URL и в журналы доступа, которые его записывают. Начиная с django-crm 1.13.0 токену для неё нужна
только область `read` модуля (`contacts:read`), поскольку она ничего не записывает; раньше
требовалась `contacts:write`. Ограничение частоты: 120 запросов в минуту на пользователя, а клиенты
применяют debounce с запасом ниже этого порога.

Сопоставление: email без учёта регистра; имя и фамилия вместе. Номера телефонов сравниваются по
последним десяти цифрам (или по всем цифрам более короткого номера, минимум семи) независимо от
разделителей.

`POST /api/contacts/{id}/merge/` с `{"merge_id": "<uuid>"}` объединяет контакт, указанный в теле, с
контактом из URL. Вызывающий должен иметь возможность открыть оба (если один скрыт или отсутствует,
это одинаковый `404`), должен иметь право редактировать сохраняемый (для контактов это любой, кто
может его открыть) и должен подпадать под правило удаления для поглощаемого (администратор,
суперпользователь или его создатель), иначе `403`. Объединение контакта с самим собой, а также
отсутствующий или некорректный `merge_id` дают `400`. На время объединения обе строки блокируются,
а само объединение выполняется в одной транзакции:

- Каждая связь с поглощаемым контактом переходит к сохраняемому: компании (обе связи), лиды, сделки,
  обращения, задачи, карточки на досках, счета, коммерческие предложения, регулярные счета, заказы,
  письма компаний, опросы CSAT и ответы через портал, комментарии, вложения и активность. Связь,
  которая у сохраняемого контакта уже есть, не дублируется.
- Побеждают значения сохраняемого контакта. Его пустые поля, включая дополнительные поля по каждому
  ключу, получают значения другого; владельцы (`assigned_to`, `teams`) берутся, только если у
  сохраняемого контакта их нет; теги объединяются из обоих. Отметка «Не звонить», установленная у
  любого из контактов, сохраняется. Коды входа на портал, выпущенные для поглощаемого контакта,
  удаляются вместе с ним, а его открытые сессии портала перестают работать; если у сохраняемого
  контакта нет email, он получает email поглощаемого, как это могла бы сделать правка.
- Затем поглощённый контакт удаляется, что отправляет обычный вебхук `contact.deleted`, а в журнал
  аудита записывается строка `RECORD_MERGED` с обоими id и обоими именами. Отмены нет. Начиная с
  django-crm 1.13.0 поле `assigned_to` этого вебхука перечисляет владельцев, которые были у
  поглощённого контакта до объединения, даже если они перешли к сохраняемому; раньше оно
  формировалось после переноса и могло оказаться пустым.

Ответ: `{"error": false, "message": "...", "id": "<kept id>"}`.

## Поля {#fields}

Payload контакта также содержит `source`, `source_detail` и `source_ref`, а ещё доступное только для
чтения поле `phone_e164` (телефон, нормализованный для сопоставления).

`CreateContactSerializer.Meta.fields` (`contacts/serializer.py:147-174`) определяет, что принимают
`POST /api/contacts/`, `PUT /api/contacts/{id}/` и `PATCH /api/contacts/{id}/`. В отличие от
`Lead.first_name`/`last_name`, у `Contact.first_name` и `Contact.last_name` нет ни `blank=True`, ни
переопределения в сериализаторе (`contacts/models.py:19-20`). **Оба поля действительно
обязательны**.

| Поле | Тип | Обязательно | Примечания |

| `phone` | string | необязательно | |
| `source` | ключ из [источников лидов](leads.md#lead-sources) организации | необязательно | То же правило, что для `source` лида. Заполняется из лида при его конвертации |

Не входят в сериализатор, но принимаются в том же запросе и разрешаются представлением (см.
[Создание контакта](#create-a-contact)): `teams`, `assigned_to`, `tags` (каждое список id,

`GET /api/contacts/` и `GET /api/contacts/{id}/` дополнительно возвращают, но никогда не принимают на
вход: `id`, `created_by`, `created_at`, `updated_at`, `org` (вложенный), `account_detail`,
`linked_accounts` (оба описаны выше), `contact_attachment` и `custom_fields` (проверяется отдельно по
строкам `CustomFieldDefinition` организации).
