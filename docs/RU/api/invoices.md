# Счета и коммерческие предложения

Маршруты для авторизованных пользователей находятся в `backend/invoices/api_urls.py` и все смонтированы
под `/api/invoices/...`. **Представления DRF лежат в `backend/invoices/api_views.py`, а не в
`views.py`**, который в этом приложении является устаревшим модулем, не относящимся к API. Анонимные
маршруты клиентского портала находятся в `backend/invoices/public_urls.py`, обслуживаются
`backend/invoices/public_views.py` и смонтированы под `/api/public/...`. Авторизация для всех
эндпоинтов счетов, коммерческих предложений и регулярных счетов для авторизованных пользователей
собрана в `backend/invoices/permissions.py`. Правила пагинации, фильтрации и формы ответа, которые
здесь подразумеваются, а не повторяются, описаны в разделе [Соглашения](conventions.md), а принцип
«404 вместо 403», который docstring модуля этой страницы излагает почти дословно, в разделе
[Ошибки](errors.md).

Эта страница охватывает счета, коммерческие предложения, позиции, выписки по компаниям и публичный
портал, то есть эндпоинты, входящие в рамки задачи этой документации. Платежи, товары, шаблоны,
регулярные счета, дашборды и отчёты, а также создание счёта из сделки и из записей времени тоже
входят в этот модуль (`api_urls.py`), но выходят за рамки этой страницы.

## Одно правило доступа для счетов, коммерческих предложений и регулярных счетов {#one-access-rule-for-invoices-estimates-and-recurring-invoices}

`invoices/permissions.py` формулирует одно правило, которое все три типа записей переиспользуют
через `get_invoice_or_error`/`get_estimate_or_error`/`get_recurring_or_error`
(`invoices/permissions.py:101-122`):

```
1. Does this record exist in the caller's org?  -> 404 if not
2. May this caller act on it?                   -> 403 if not
```

Это ровно те два шага, которые раздел
[Ошибки: «Не найдено» или «запрещено»](errors.md#not-found-versus-forbidden) цитирует как docstring
этого модуля. Шаг 2, `has_object_access` (`:32-58`), даёт доступ администратору организации,
суперпользователю Django, автору записи или любому профилю из её `assigned_to`. Отдельного, более
узкого правила для записи и удаления, как у
[Обращений](cases.md#a-cases-read-write-and-delete-rules-differ-on-purpose), нет; для счетов и
коммерческих предложений одно правило покрывает чтение, запись и удаление.

**Два сравнения внутри этого правила намеренно идут с разными типами.** `created_by` это внешний
ключ на `User` (из `AuditModel`), поэтому он сравнивается с `request.user`; `assigned_to` содержит
строки `Profile`, поэтому сравнивается с `request.profile` (`:42-58`). Docstring модуля подчёркивает,
что перепутать их (сравнить `request.profile` с `created_by`, как раньше делали представления
коммерческих предложений) не просто даёт всегда `False`, как та же ошибка в других местах кода:
поскольку это доходит до ORM как `Q(created_by=<Profile instance>)`, Django выбрасывает `ValueError`
из-за несовпадения типов, и список коммерческих предложений для не-администратора отвечал `500`
вместо пустого или неверного списка. Этот конкретный дефект в текущем коде исправлен
(`_get_or_error`/`has_object_access`, как показано), но это наглядный пример того, почему в этом коде
настаивают, чтобы проверка прав была доказуемо протестирована в обе стороны.

## Счета {#invoices}

`GET /api/invoices/` (`InvoiceListView.get`, `invoices/api_views.py:176-194`) вручную собирает ответ с
теми же ключами `count`/`next`/`previous`/`results`, что выдал бы `get_paginated_response()` DRF,
плюс блок `totals`, посчитанный по всем счетам, видимым вызывающему (а не только по странице или
текущему фильтру). Это самодельная форма, а не сгенерированная DRF: и
[Соглашения](conventions.md#pagination), и [Обращения](cases.md#solutions) называют
`GET /api/cases/solutions/` единственным эндпоинтом этого API, который действительно вызывает
`get_paginated_response()`; это представление получает те же четыре ключа, собирая словарь
самостоятельно:

```json
{
  "count": 41,
  "next": null,
  "previous": null,
  "results": [ { "...": "InvoiceListSerializer" } ],
  "totals": {
    "count": 41, "outstanding": "12500.00", "overdue": "3200.00",
    "due_this_month": "4100.00", "paid_this_quarter": "9800.00",
    "draft": "600.00", "action_needed": 5,
    "by_currency": [
      { "currency": "USD", "count": 41, "action_needed": 5, "outstanding": "12500.00", "...": "..." }
    ]
  }
}
```

`totals` считается по `Invoice.objects.filter(pk__in=queryset.values("pk"))`, а не напрямую по
queryset с учётом видимости (`_totals`, `:196-235`), и комментарий объясняет почему: queryset
не-администратора соединяется с `assigned_to` (многие ко многим), поэтому сумма по такому соединению
умножила бы сумму счёта на число его ответственных; повторный запрос по `pk__in` убирает соединение
перед `Sum`. Деньги группируются по валютам, как в эндпоинтах `/api/invoices/reports/`: каждая сумма
это обычное число, когда видимые счета используют не больше одной валюты, и `null`, когда несколько,
а `by_currency` в любом случае содержит по строке на валюту. `count` и `action_needed` суммируются
по всем валютам. `action_needed` это **количество**, а не сумма: счета, ещё находящиеся в `Draft`,
плюс все неоплаченные с прошедшим `due_date` (`:209`). Вызывающий без прав администратора видит
только счета, которые он создал или за которые отвечает (`:96-103`; то же правило, что
[выше](#one-access-rule-for-invoices-estimates-and-recurring-invoices), на уровне списка).

Фильтры (`filter_queryset`, `:105-174`): `search` (ищет по `invoice_title`, `invoice_number`,
`client_name` или `client_email`, вхождение подстроки, не длиннее 100 символов), `status` (точное
совпадение), `account`/`contact`/`opportunity` (точный id), `assigned_to` (точный id), `created_by`
(точный id), `issue_date_gte`/`issue_date_lte`, `due_date_gte`/`due_date_lte`, `cf_<key>` и `sort`:
допустимы только `created_at`/`due_date`/`issue_date`/`total_amount`/`status`, каждый с необязательным
префиксом `-` (`:163-172`); нераспознанное значение `sort` молча игнорируется, и остаётся порядок по
умолчанию `-created_at`.

`POST /api/invoices/` (`:237-292`) валидируется `InvoiceCreateSerializer`
(`invoices/serializer.py:542-618`; см. [Поля](#fields)). При успехе (`201`):

```json
{"error": false, "message": "Invoice created successfully", "invoice": { "...": "InvoiceSerializer" }}
```

Создание счёта ставит в очередь `create_invoice_history` (задачу Celery для журнала изменений) и,
если у счёта уже есть ответственные, `send_email`, чтобы их уведомить (`:261-278`).

`GET /api/invoices/{id}/` (`InvoiceDetailView.get`, `:295-341`) возвращает
`{"invoice": ..., "attachments": [...], "comments": [...], "history": [...], "custom_field_definitions": [...]}`.
`PUT /api/invoices/{id}/` (`:343-400`) принимает **частичное** тело (передаётся `partial=True`, хотя
это `PUT`, `:376`) через тот же `InvoiceCreateSerializer`. **`InvoiceDetailView` определяет только
`get` и `put`, никакого метода удаления счёта не существует**; счёт выводится из оборота через
`POST /api/invoices/{id}/cancel/` и никогда не удаляется. (Для сравнения:
[Коммерческие предложения](#estimates) поддерживают полное удаление.)

Три действия жизненного цикла, каждое защищено `get_invoice_or_error` и каждое является `POST` без
тела запроса:

- `POST /api/invoices/{id}/send/` (`InvoiceSendView.post`, `:403-440`) отказывается повторно отправлять
  счёт в статусе `Paid` или `Cancelled` (`400`); переводит `Draft` → `Sent`, проставляет
  `sent_at`/`is_email_sent` и ставит в очередь `send_invoice_to_client`.
- `POST /api/invoices/{id}/mark-paid/` (`InvoiceMarkPaidView.post`, `:443-481`) записывает `Payment`.
  Если вызывающий их не передал, по умолчанию `amount` равно текущему `amount_due`, `payment_method`
  равно `OTHER`, а `payment_date` сегодняшней дате, но в любом случае всё проходит через
  `PaymentCreateSerializer` (`invoices/serializer.py:365-396`), поэтому платёж на сумму `0` или
  больше остатка всё равно отклоняется (`400`).
- `POST /api/invoices/{id}/cancel/` (`InvoiceCancelView.post`, `:563-599`) отказывает для уже
  `Cancelled` счёта и для `Paid` (`400` в обоих случаях). Отмена нужна для денег, которые никогда не
  будут получены, а не для отката завершённого платежа.

`POST /api/invoices/{id}/duplicate/` (`InvoiceDuplicateView.post`, `:484-560`) копирует поля клиента,
реквизитов, скидки, налога и шаблона счёта и все его позиции в новый счёт `Draft` со свежим
`invoice_number`, `issue_date`, сброшенным на сегодня, и без платежей; ответ `201` с payload
`InvoiceSerializer` нового счёта.

`GET /api/invoices/{id}/pdf/` (`InvoicePDFView.get`, `:602-631`) отдаёт поток `application/pdf`;
при отсутствии PDF-бэкенда ответ `503`, при любой другой ошибке генерации `500`.

## Коммерческие предложения {#estimates}

Та же форма списка, детального просмотра и жизненного цикла, что у счетов, с одним структурным
отличием: **коммерческое предложение можно удалить полностью, а счёт нельзя** (см. [выше](#invoices)).

`GET /api/invoices/estimates/` (`EstimateListView.get`, `:1027-1064`). Та же собранная вручную форма
`count`/`next`/`previous`/`results`, что у списка счетов выше, но без блока `totals`. Фильтры:
`status`, `account`, `search` (ищет по `estimate_number`, `title` или `client_name`), `cf_<key>`.
Видимость подчиняется тому же правилу, что у счетов: не-администратор видит только коммерческие
предложения, которые он создал или за которые отвечает.

`POST /api/invoices/estimates/` (`:1066-1100`) валидируется `EstimateCreateSerializer`
(`invoices/serializer.py:892-1018`; см. [Поля](#fields)). **В отличие от `InvoiceCreateSerializer`,
`EstimateCreateSerializer` не делает `status` доступным только для чтения**: ничто не мешает
аутентифицированному вызывающему из той же организации с правом записи сделать `POST` или `PUT`
коммерческого предложения сразу со `status: "Accepted"`. При этом **не** выполняется ни одна из
проверок и ни один из побочных эффектов публичного потока принятия (см.
[Эндпоинты публичного портала](#public-portal-endpoints)): нет проверки срока действия, и ни одно из
полей `accepted_by_name`/`accepted_by_email`/`accepted_ip`/`accepted_user_agent` не заполняется, хотя
комментарий модели над этими полями называет принятие «авторизацией», и приложение должно записывать,
кто её дал. Об этом здесь сообщается, но не исправляется, в рамках задачи этой документации.

`GET/PUT/DELETE /api/invoices/estimates/{id}/` (`EstimateDetailView`, `:1103-1187`); `DELETE` это
настоящее полное удаление (`estimate.delete()`, `:1182`), защищённое тем же правилом доступа, что
чтение и запись.

`POST /api/invoices/estimates/{id}/convert/` (`EstimateConvertView.post`, `:1189-1266`) создаёт новый
счёт `Draft` из полей клиента, реквизитов, скидки и налога коммерческого предложения и его позиций, а
затем устанавливает `estimate.status = "Accepted"`, `accepted_at = now()` и
`estimate.converted_to_invoice = invoice` (`:1253-1257`). **Именно это поле не даёт повторной
конвертации продублировать счёт**: самая первая проверка представления
`if estimate.converted_to_invoice: return 400` (`:1200-1204`) выполняется раньше всего остального.
Любой клиент, показывающий список коммерческих предложений, должен читать это поле, а не только
`status`, чтобы решить, предлагать ли «выставить счёт»:
`EstimateListSerializer.converted_to_invoice` (`invoices/serializer.py:832,846,866-870`) включён в
строку списка именно для того, чтобы рабочий список мог отличить «принято, счёт ещё не выставлен» от
«счёт уже выставлен» без второго запроса на каждую строку; docstring класса прямо говорит, что без
него список "would offer to raise a second invoice for an estimate that already has one."

`POST /api/invoices/estimates/{id}/send/` (`EstimateSendView.post`, `:1269-1291`) переводит
`Draft` → `Sent` и ставит в очередь `send_estimate_to_client`. `GET /api/invoices/estimates/{id}/pdf/`
(`EstimatePDFView.get`, `:1294-1334`) отдаёт PDF так же, как эндпоинт счёта.

## Позиции {#line-items}

Позиции попадают в базу данных двумя путями с разным охватом валидации.

**Вложенно при создании или изменении счёта.** `line_items` в `InvoiceCreateSerializer`
(`InvoiceLineItemCreateSerializer`, many, `invoices/serializer.py:288-304`) записываются в том же
запросе, что и сам счёт; `validate()` дополнительно отклоняет любую позицию, `product` которой
принадлежит другой организации (`:689-704`: комментарий отмечает, что собственное поле `product`
вложенного сериализатора это `PrimaryKeyRelatedField` без ограничения по товарам всех организаций,
поэтому межорганизационная проверка должна выполняться в родительском сериализаторе, где есть
контекст организации). При `PUT` переданные `line_items` **заменяют** набор. Существующие строки
удаляются и создаются заново (`InvoiceCreateSerializer.update`, `:731-753`); если ключ вовсе не
передан, существующие позиции не трогаются.

**Отдельно, через `POST /api/invoices/{invoice_id}/line-items/`**
(`InvoiceLineItemListView.post`, `invoices/api_views.py:653-679`) и
**`PUT`/`DELETE /api/invoices/{invoice_id}/line-items/{id}/`**
(`InvoiceLineItemDetailView`, `:682-751`). Оба пути идут через `InvoiceLineItemCreateSerializer`
напрямую, без оборачивающего `validate()` родительского сериализатора, и **ни в одном нет проверки в
коде приложения, что `product` принадлежит организации вызывающего**: `InvoiceLineItemCreateSerializer`
не объявляет собственного поля `product` (`invoices/serializer.py:288-304`), поэтому DRF выводит
обычный `PrimaryKeyRelatedField(queryset=Product.objects.all())` по товарам всех организаций, и оба
представления используют его как есть, в отличие от *вложенного* пути, где проверка есть
(`InvoiceCreateSerializer.validate()`, `:689-704`; grep подтверждает, что это единственная проверка
организации `product` во всём `invoices/serializer.py`). Это реальная брешь относительно
[контракта ORM-фильтров](../architecture/multi-tenancy-and-rls.md#the-two-layer-contract): явного
фильтра на уровне приложения, который та страница называет обязательным, здесь нет, но это не
безусловное межтенантное чтение. Таблица `product` (вместе с `invoice_line_item`) сама защищена RLS:
обе входят в `ORG_SCOPED_TABLES` (`common/rls/__init__.py:97`), а политика включена миграцией
`common/migrations/0008_enable_rls_product_invoice_line_item.py`. При роли базы данных без прав
суперпользователя, которую требует раздел [PostgreSQL и RLS](../self-hosting/postgresql-and-rls.md),
queryset `Product.objects.all()` без ограничения видит ноль строк для id чужой организации благодаря
безопасному поведению RLS по умолчанию, и запрос отвечает `400` ("invalid pk"), а не привязывает
строку. Отсутствующий ORM-фильтр подстраховывает защитная сетка. В конфигурации *по умолчанию*, без
`DBUSER`, когда используется суперпользователь Postgres и RLS, согласно разделу
[Мультитенантность и RLS](../architecture/multi-tenancy-and-rls.md#the-two-layer-contract), полностью
обходится, ничто этому не мешает: строка привязывается, и `InvoiceLineItemSerializer.product_name`
(`source="product.name"`, `:254,263`) раскрывает название товара другой организации при каждом
следующем чтении. Можно ли этим воспользоваться в конкретном развёртывании, определяет ровно вопрос
«является ли `DBUSER` суперпользователем?», и поэтому это стоит исправить независимо от настройки
конкретного развёртывания: ORM-фильтр это контракт, RLS это страховочная сетка, а у этого эндпоинта
нет контракта. Здесь сообщается, но не исправляется, в рамках задачи этой документации.

Каждая запись позиции (любым путём) сразу после этого пересчитывает и сохраняет итоги родительского
счёта (`invoice.recalculate_totals(); invoice.save()`). Клиенту не нужен отдельный вызов, чтобы
обновить `total_amount`/`amount_due` после добавления, изменения или удаления позиции.

`InvoiceLineItemCreateSerializer.Meta.fields` (`invoices/serializer.py:291-303`):
`product`, `name`, `description`, `quantity`, `unit_price`, `discount_type`, `discount_value`,
`tax_rate`, `order`. Все они необязательны; `product` допускает null, `name` имеет `blank=True,
null=True`, `description` имеет `blank=True`, `quantity` по умолчанию `1`, `unit_price`/`discount_value`/
`tax_rate`/`order` по умолчанию `0`, а `discount_type` имеет `blank=True` и выбирается из
`DISCOUNT_TYPES` (`PERCENTAGE`, `FIXED`) (`invoices/models.py:512-565,71-74`). Отправка `{}` корректна
и создаёт позицию с `quantity=1`, `unit_price=0`. **Позиции коммерческих предложений работают так
же**; у `EstimateLineItemCreateSerializer` тот же список полей (`invoices/serializer.py:306-321`), но
отдельного эндпоинта для них нет вовсе: позиции коммерческих предложений записываются только вложенно
в `POST`/`PUT /api/invoices/estimates/{id}/`, а в `EstimateCreateSerializer.validate()` (`:969-980`)
**нет вообще никакой проверки организации товара на уровне приложения**, даже той, что есть на уровне
родительского сериализатора в `InvoiceCreateSerializer`. Здесь действует та же оговорка про RLS, что
выше: `product` защищён RLS, поэтому при правильно настроенной роли базы данных (без прав
суперпользователя) это брешь из-за отсутствующего ORM-фильтра, которую ловит страховочная сетка, а при
роли суперпользователя по умолчанию это реальное межтенантное чтение.

## Выписки по компаниям {#account-statements}

| Метод | Путь | Примечания |
| --- | --- | --- |
| GET | `/api/invoices/statements/{account_id}/` | Выписка в виде JSON |
| GET | `/api/invoices/statements/{account_id}/pdf/` | Та же выписка в виде PDF, `Statement_<start>_<end>.pdf` |

Что одной компании выставили и что она оплатила за период (issue #810). Выписка вычисляется при
каждом запросе из имеющихся счетов и платежей (`backend/invoices/statements.py`) и никогда не
хранится, поэтому не может с ними расходиться.

**Только для администраторов.** Участник получает `403` ещё до поиска компании, так что ответ ничего
не говорит о том, какие компании существуют. Правило то же, что у отчётов по счетам
(`_forbid_non_admin_reports`): выписка суммирует все счета компании, включая те, которые участник
открыть не может, и выписка, собранная только из видимых участнику счетов, показала бы клиенту
неверный баланс. Компания из другой организации даёт `404`.

**Период.** `start_date` и `end_date` (`YYYY-MM-DD`, обе включительно) по умолчанию охватывают
текущий месяц до сегодняшнего дня по дню организации. Период длиннее 366 дней или заканчивающийся
раньше, чем начинается, даёт `400` в формате полей DRF (`{"end_date": ["..."]}`).

**Форма.** По одной записи в `currencies` на валюту, по порядку кодов, поскольку между валютами
ничего не конвертируется: `opening_balance`, итоги за период `invoiced`, `paid` и `cancelled`,
`closing_balance` и `entries` в порядке дат. У каждой записи есть `date`, `kind` (`invoice`,
`payment` или `cancellation`), `invoice_id`, `invoice_number`, `description`, `amount` со знаком
(положительное значение увеличивает долг компании) и нарастающий `balance`. Отрицательный баланс
означает переплату компании. Валюта без начального баланса и без операций за период не выводится.

**Что учитывается.** Счёт попадает в выписку, как только клиента попросили оплатить: Черновик и
Ожидает не учитываются. Отменённый счёт остаётся в выписке, если он был отправлен или по нему
платили: он выставлен в дату выставления и сторнирован в день отмены, поэтому выписка за более ранний
месяц по-прежнему закрывается тем балансом, который показывала тогда, а принятый по нему платёж
оставляет компанию с переплатой. Отменённый счёт, который никому не отправляли и по которому не
платили, никогда не выставлялся и не учитывается.

## Номера документов {#document-numbers}

Организация выбирает, как выглядят номера новых счетов и коммерческих предложений, через пять полей в
`GET/PATCH /api/org/settings/`. Читать их может любой участник, менять только администратор (иначе
403). Номер состоит из префикса, затем даты и дефиса, если организация датирует номера, и затем
счётчика, дополненного нулями.

| Поле | По умолчанию | Правило |
|---|---|---|
| `invoice_number_prefix` | `INV-` | До 20 латинских букв, цифр, `-` и `_`; может быть пустым |
| `estimate_number_prefix` | `EST-` | То же правило |
| `number_date_part` | `DAY` | `NONE`, `YEAR` (`2026`), `MONTH` (`202610`) или `DAY` (`20261015`) |
| `number_padding` | `4` | Ширина счётчика, от 1 до 10 цифр. Счётчик, который её перерос, не обрезается |
| `invoice_number_start` | `1` | Наименьшее значение счётчика для следующего счёта, от 1 до 999 999 999. Должно быть `1`, если `number_date_part` не равно `NONE` |

- **Значения по умолчанию соответствуют формату, который был у всех организаций до появления этих
  полей**, поэтому ничего не меняется, пока администратор это не изменит. Уже выданный номер никогда
  не меняется.
- **Счётчик начинается заново при каждом изменении части перед ним.** С `YEAR` первый счёт 2027 года
  получает `INV-2027-0001`. С `NONE` это одна сквозная последовательность.
- **Коммерческие предложения используют ту же часть даты и ширину**, а префикс у них свой. Начальный
  номер относится только к счетам: он нужен организации, которая продолжает последовательность из
  другой системы. Если номера счетов уже превышают его, нумерация продолжается от наибольшего.
- **Учитываются только номера ровно текущего вида.** После перехода с формата по умолчанию на `NONE`
  с префиксом `INV-` прежний `INV-20260915-0007` не учитывается, поэтому следующий счёт получит
  `INV-0001`.
- `PATCH` с `invoice_number_start`, отличным от `1`, и с датированным `number_date_part` даёт 400 в
  `invoice_number_start`. Это касается и `PATCH`, который добавляет дату к последовательности, у
  которой уже задано начало: передайте вместе с ним `invoice_number_start: 1`.

## Эндпоинты публичного портала {#public-portal-endpoints}

**Смонтированы под `/api/public/...`, а не под `/api/invoices/...`**: `backend/crm/urls.py:23`:
`path("api/public/", include("invoices.public_urls", ...))`. Каждое представление здесь задаёт
`authentication_classes = []` и `permission_classes = []` (`invoices/public_views.py`). Эти эндпоинты
действительно анонимны и доступны любому, у кого есть URL, и это задумано (ссылка на счёт или
коммерческое предложение, отправленная по email).

**Организация определяется до установки контекста RLS, через поиск токена без ограничения по
организации. Только поэтому эндпоинт вообще работает под RLS.**
`_resolve_org_context(token, resource_type)` (`invoices/public_views.py:30-46`) вызывает
`common.portal_tokens.resolve_portal_org`, которая хеширует исходный токен из URL (`sha256`) и ищет его
в `common.models.PortalAccessToken`, небольшой таблице без политики RLS, чтобы получить `org_id`, а
затем вызывает `set_rls_context(org_id)`. Только *после* этого представление выполняет собственный
запрос `Invoice`/`Estimate`. Неизвестный или некорректный токен оставляет контекст RLS пустым;
следующий запрос с ограничением тогда ничего не возвращает благодаря безопасному поведению RLS по
умолчанию, и вызывающий получает тот же `404`, что дала бы отключённая ссылка, так что посторонний,
перебирающий значения токенов, ничего не узнаёт о том, настоящий ли токен.
[Архитектура: мультитенантность и RLS](../architecture/multi-tenancy-and-rls.md#portal-tokens)
описывает этот механизм полностью, включая то, почему таблица поиска вообще должна быть без
ограничения (нельзя установить `app.current_org`, пока не известна организация, и нельзя найти
строку, которая назовёт организацию, пока не установлен контекст). Общий шаблон смотрите на той
странице; эта страница описывает его конкретное применение к счетам и коммерческим предложениям.
Каждый эндпоинт ниже дополнительно требует `public_link_enabled=True` у записи, независимо от того,
разрешается ли токен. Администратор может отозвать ранее отправленную ссылку без смены токена.

**Даты на этих эндпоинтах берутся по организации, а не по серверу.** Никто не вошёл в систему,
поэтому больше ничто не установило бы часовой пояс, и каждое «сегодня» было бы днём сервера по UTC.
Как только токен разрешён, `_resolve_org_context` также активирует часовой пояс организации
(`Org.timezone`) до конца запроса. Поэтому истёк ли срок коммерческого предложения (проверка при
принятии ниже и пометка «(Expired)» в PDF коммерческого предложения) определяется по календарному дню
организации: в 23:30 UTC 31 декабря коммерческое предложение, срок которого истекает в этот день, уже
истекло для организации в `Asia/Kolkata` и ещё может быть принято для организации в `UTC`.

- `GET /api/public/invoice/{token}/` (`PublicInvoiceView.get`, `:61-163`). Возвращает поля счёта,
  предназначенные для клиента, платёжный адрес, позиции и историю платежей. Первый просмотр
  проставляет `viewed_at` и переводит `Sent` → `Viewed`.
- `GET /api/public/invoice/{token}/pdf/` (`PublicInvoicePDFView.get`, `:166-206`), тот же PDF, что
  генерирует эндпоинт для авторизованных пользователей, с `include_payments=True`.
- `GET /api/public/estimate/{token}/` (`PublicEstimateView.get`, `:209-301`), та же форма для
  коммерческих предложений; первый просмотр тоже проставляет `viewed_at`.
- `GET /api/public/estimate/{token}/pdf/` (`PublicEstimatePDFView.get`, `:304-344`).
- `POST /api/public/estimate/{token}/accept/` (`PublicEstimateAcceptView.post`, `:347-430`). У
  анонимного вызывающего нет записи `status`, доступной авторизованным пользователям, поэтому принятие
  это отдельный эндпоинт со своими правилами, и все они проверяются на сервере, потому что "the
  frontend is not a trust boundary" (комментарий в `:359-363`): коммерческое предложение должно быть
  сейчас в статусе `Sent` или `Viewed` (иначе `400`); его срок не должен истечь (`estimate.is_expired`,
  проверка по `expiry_date`, иначе `400` с датой истечения в сообщении; здесь это проверяется впервые,
  комментарий модели отмечает, что `expiry_date` раньше "stored and printed on the estimate but
  enforced nowhere"); и тело запроса должно содержать `name` и синтаксически корректный `email` (иначе
  `400`). При успехе представление записывает, кто принял: `accepted_by_name`, `accepted_by_email`
  (обрезанный до максимальной длины столбца), `accepted_ip` (`common.request_meta.client_ip`:
  `REMOTE_ADDR` или, если задан `NUM_PROXIES`, адрес, который видел наш внешний прокси; считается
  свидетельством, а не доказательством) и `accepted_user_agent`, вместе со `status = "Accepted"` и
  `accepted_at`.
- `POST /api/public/estimate/{token}/decline/` (`PublicEstimateDeclineView.post`, `:433-468`): то же
  предусловие `Sent`/`Viewed`, без записи личности, устанавливает `status = "Declined"` и
  `declined_at`.

### Даты расписания регулярных счетов {#recurring-schedule-dates}

`POST /api/invoices/recurring/` и `PUT /api/invoices/recurring/{id}/` (`RecurringInvoiceCreateSerializer`)
принимают `start_date` и `next_generation_date`. Ежедневный генератор выставляет счёт по расписанию,
когда `next_generation_date` приходится на сегодня или раньше в часовом поясе организации, и никогда
не читает `start_date`, поэтому сервер связывает эти две даты:

- При создании опущенный `start_date` равен сегодняшней дате в часовом поясе организации, а опущенный
  `next_generation_date` равен `start_date` (переданному или по умолчанию). Расписание, созданное со
  стартом в следующем месяце без `next_generation_date`, впервые выставит счёт в следующем месяце.
- `next_generation_date` раньше `start_date` отклоняется с `400` и
  `{"errors": {"next_generation_date": ["The next generation date cannot be before the start date."]}}`
  при создании и при любом изменении, передающем одну из дат (другая берётся из сохранённой строки).
  Изменение без обеих дат не проверяется, поэтому расписание, сохранённое до появления этого правила,
  по-прежнему можно переименовать или приостановить.
- `next_generation_date` позже `start_date` допускается (расписание, которое начинается сейчас, а
  первый счёт выставляет в конце месяца).
