# Лиды

Маршруты находятся в `backend/leads/urls.py`, представления разделены между `leads/views/lead_views.py`
(список и детальная карточка) и `leads/views/lead_interactions.py` (редактирование комментариев и
вложений). Правила пагинации, фильтрации и формы ответа, на которые эта страница опирается, не повторяя
их, описаны в разделе [Соглашения](conventions.md), а принцип 404 против 403, упомянутый ниже, в разделе
[Ошибки](errors.md).

## Список лидов {#list-leads}

`GET /api/leads/` (`LeadListView.get`, `backend/leads/views/lead_views.py:246-248`) возвращает не один
список, а два раздела с отдельной пагинацией: открытые лиды и закрытые лиды. Представление полностью
исключает конвертированные лиды из queryset, а оставшееся делит по `status`:

```python
queryset = (
    self.model.objects.filter(org=self.request.profile.org)
    .exclude(status="converted")
    ...
)
...
queryset_open = queryset.exclude(status="closed")
...
queryset_close = queryset.filter(status="closed")
```

(`lead_views.py:90-98,166,187`.) Вызывающий без прав администратора видит только лиды, назначенные ему
или созданные им (`lead_views.py:99-103`); администратор или суперпользователь видит все лиды
организации. Ответ использует собранную вручную обёртку, которую раздел
[Соглашения](conventions.md#pagination) описывает именно для этого эндпоинта:

```json
{
  "per_page": 10,
  "page_number": [1],
  "open_leads": {"leads_count": 42, "open_leads": [ { "...": "LeadSerializer" } ], "offset": 10},
  "totals": {"count": 42, "unworked_over_a_week": 5},
  "close_leads": {"leads_count": 8, "close_leads": [ { "...": "..." } ], "offset": null},
  "contacts": [{"id": "...", "first_name": "..."}],
  "status": [["assigned", "Assigned"], ["in process", "In Process"], ["converted", "Converted"], ["recycled", "Recycled"], ["closed", "Closed"]],
  "source": [["call", "Call"], ["email", "Email"], ["existing customer", "Existing Customer"], ["partner", "Partner"], ["public relations", "Public Relations"], ["compaign", "Campaign"], ["other", "Other"]],
  "tags": [{"...": "..."}],
  "users": [{"id": "...", "user__email": "..."}],
  "countries": [["GB", "United Kingdom"], ["AF", "Afghanistan"]],
  "industries": [["ADVERTISING", "ADVERTISING"]]
}
```

Отдельно стоит отметить `page_number`: представление строит его как `(int(self.offset / 10) + 1,)`
(`lead_views.py:178`), то есть кортеж Python из одного элемента с запятой в конце, который JSON-рендерер
превращает в массив из одного элемента вроде `[1]`, а не в простое целое число.
`totals.unworked_over_a_week` считает лиды в отфильтрованном queryset `open` в рамках организации, у
которых `last_contacted` (а при его отсутствии дата создания) старше 7 дней (`UNWORKED_AFTER_DAYS`,
`lead_views.py:58,60-86`). Это не хранимый статус, а лишь вычисляемый признак застоя.

**`source` это ключ из источников лидов организации** (см. [Источники лидов](#lead-sources)).
У каждой организации изначально их 15 (`call`, `email`, `existing customer`, `partner`,
`public relations`, `campaign`, `other`, `web form`, `meta ads`, `google ads`, `linkedin ads`,
`directory or marketplace`, `whatsapp`, `referral`, `walk-in`), и администраторы добавляют новые.
Старый ключ с опечаткой `compaign` теперь называется `campaign`. Пары `source` в ответе списка выше
по-прежнему содержат исходные семь; список самой организации читайте через `GET /api/leads/sources/`.
`?source=` проверяет точное совпадение с ключом, поэтому ключ, которого нет ни у одного лида, просто
ничего не находит, а не вызывает ошибку.

Фильтры помимо `source` и `status` (`name`, `salutation`, `assigned_to`, `tags`, `city`, `email`,
`rating`, `search`, `created_at__gte/lte`, `close_date__gte/lte`, `cf_<key>`) полностью описаны, с точной
семантикой точного совпадения или вхождения для каждого, в разделе
[Соглашения: фильтрация и поиск](conventions.md#filtering-and-search), где этот эндпоинт служит примером.
`?unanswered=true` оставляет лиды, ожидающие ответа, начиная с самого долгого ожидания; см.
[Лиды без ответа](#unanswered-leads).

## Создание лида {#create-a-lead}

!!! tip "Сбор лидов с собственного сайта"
    Чтобы собирать лиды с публичной страницы, вам не нужен ни этот эндпоинт, ни какие-либо учётные данные
    в HTML вашего сайта. Создайте форму в настройках и встройте полученный фрагмент кода: см.
    [Веб-формы](../integrations/web-forms.md). Этот путь анонимный, ограничен по источнику (origin), имеет
    ограничение частоты, поддерживает капчу и устраняет повторные заявки по email.
    `POST /api/leads/create-from-site/` является более старым эндпоинтом web-to-lead, он по-прежнему
    поддерживается, но устарел и требует аутентифицированного вызывающего.

`POST /api/leads/` (`LeadListView.post`, `lead_views.py:273-409`) принимает `multipart/form-data` (для
необязательного файла `lead_attachment`, который читается прямо из `request.FILES`, `lead_views.py:331`)
или JSON. Тело проверяется `LeadCreateSerializer` (`leads/serializer.py:88-224`); какие именно ключи он
принимает, см. в разделе [Поля](#fields) ниже. При успехе (`200`, а не `201`, см.
[Ошибки: коды статуса](errors.md#status-codes)):

```json
{"error": false, "message": "Lead Created Successfully", "id": "<uuid>"}
```

`id` это id нового лида. Если при создании отправить `"status": "converted"`, лид сразу проходит через
`leads.services.convert_lead_to_account`, и ответ имеет другую форму:

```json
{
  "error": false,
  "message": "Lead Converted Successfully",
  "id": "<uuid>",
  "account_id": "<uuid>",
  "contact_id": "<uuid or null>",
  "opportunity_id": "<uuid or null>"
}
```

Ошибка валидации возвращает `400` с `{"error": true, "errors": {...}}` (`lead_views.py:406-409`), в форме,
описанной в разделе [Ошибки](errors.md#validation-errors). О двух валидаторах стоит знать до интеграции:

- **Уникальность email проверяется без учёта регистра в пределах организации** и только тогда, когда
  email действительно передан (`validate_email`, `leads/serializer.py:107-134`):
  `{"error": true, "errors": {"email": ["Another lead in this organisation already uses that email address."]}}`.
- **Email становится обязательным, но только когда `status` равен `"converted"`**:
  `LeadCreateSerializer.__init__` выставляет `self.fields["email"].required = True` ровно в этом случае,
  а в остальных делает `first_name`, `last_name` и `salutation` необязательными независимо от того, что
  требует сама модель `Lead` (`leads/serializer.py:100-104`). Все остальные поля этого сериализатора
  необязательны; см. [Поля](#fields).

`tags`, `contacts`, `teams` и `assigned_to` **не** входят в `LeadCreateSerializer`. Представление читает
каждое из них прямо из тела запроса после успешной работы сериализатора и после разбора разрешает их в
рамках `org=request.profile.org`. Обрабатываются они **не** единообразно, и это важно, потому что тот же
эндпоинт принимает `multipart/form-data` (см. выше). Точную таблицу по методам и полям и конкретный сбой,
с которым сталкивается multipart-запрос, см. в разделе [Поля](#fields).

## Получение, изменение, удаление {#retrieve-update-delete}

`GET /api/leads/{id}/` (`LeadDetailView.get`, `lead_views.py:568-571`) ищет лид в рамках организации
вызывающего (`get_object`, `:416-417`; лид из другой организации даёт `404`, как и несуществующий, в
соответствии с правилом для чужих организаций, которое в общем виде формулирует раздел
[Ошибки](errors.md#not-found-versus-forbidden)). Затем вызывается `assert_lead_access` (`:419-443`):
**администратор или суперпользователь видит любой лид; любой другой должен быть создателем лида или
одним из ответственных, иначе запрос отклоняется с `403`**, а не `404`, хотя `LeadListView` полностью
скрыл бы этот же лид от этого же пользователя.
[Ошибки: «Не найдено» или «запрещено»](errors.md#not-found-versus-forbidden) вообще не упоминает лиды:
там сказано, что выбор между `403` и `404` внутри организации «зависит от того, что это за ресурс», и в
качестве двух разобранных примеров названы счета (`403`) и личные макросы (`404`). Поэтому источником
того, как на самом деле ведут себя лиды, считайте этот абзац, а не ту страницу: в `leads/` нет ни
комментария, ни теста, фиксирующего это как осознанное решение о раскрытии, как это сделано для счетов
или макросов; это просто поведение кода в его нынешнем виде. Ответ вкладывает запись в `lead_obj`, в
форме, которую раздел [Соглашения](conventions.md#response-shape) описывает именно для этого эндпоинта,
вместе с `attachments`, `comments`, `users_mention`, `assigned_data`, `users`, `users_excluding_team`,
`source`, `status`, `teams`, `countries` и `custom_field_definitions` (`lead_views.py:513-540`).

`PUT /api/leads/{id}/` (`:674-823`) и `PATCH /api/leads/{id}/` (`:847-1064`) оба применяют то же правило
«создатель, ответственный или администратор» прежде, чем что-либо менять, и оба могут конвертировать
лид, если задан `status` (или, только для `PATCH`, `is_converted`). `leads/workflow.py` прямо указывает,
что эта защита охватывает меньше, чем «любой уже завершённый статус»: модуль намеренно разделяет два
понятия, которые раньше смешивались под одним именем (`leads/workflow.py:11-30`).
**`IRREVERSIBLE_STATUSES` содержит только `{"converted"}`** (`:34`): повторная конвертация уже
`converted` лида отклоняется с `400`, а не создаёт молча вторую `Opportunity` для той же `Account`.
`CLOSING_STATUSES` представляет собой отдельный, намеренно *обратимый* набор `{"closed"}` (`:37`;
«повторное открытие закрытого лида является обычной работой», как сказано в docstring модуля на `:24`),
а `recycled` не входит ни в один из наборов. **Конвертация лида в статусе `closed` или `recycled`
проходит успешно** и выполняется полностью, так же как конвертация лида в статусе `assigned` или
`in process`. Защиты от этого нет. Ветка конвертации в `PATCH` возвращает ответ до того, как запустится
`LeadCreateSerializer` (и его `validate_status`, применяющий то же правило только для
`IRREVERSIBLE_STATUSES`), поэтому повторяет проверку прямо в коде (`lead_views.py:875-894`). Каждая
конвертирующая запись (`POST`, `PUT` или `PATCH`) выполняется в одной транзакции с блокировкой строки
лида (`_atomic_when_converting`): сбой на любом шаге не оставляет ни компании, ни контакта, ни сделки, и
лид остаётся неконвертированным, а вторая конвертация, пришедшая в тот же момент, ждёт первую, затем
видит лид уже конвертированным и получает отказ. Письма ответственным отправляются только после
фиксации транзакции. Оба метода заново привязывают `tags`/`contacts`/`teams`/`assigned_to` из тела
запроса, если они переданы, но, как и `POST`, неодинаково для четырёх полей; точную таблицу по методам
см. в разделе [Поля](#fields). При успехе возвращается
`{"error": false, "message": "Lead updated Successfully"}` (или форма ответа о конвертации, приведённая
выше); при ошибке возвращается `{"error": true, "errors": {...}}`.

Детальный ответ также содержит `can_delete`: будет ли принят `DELETE` от этого вызывающего, чтобы клиент
предлагал это действие только в этом случае.

`DELETE /api/leads/{id}/` (`:1080-1095`) разрешён администратору, суперпользователю или создателю лида
(`request.profile.user == self.object.created_by`), остальные получают `403`; кроме того, требуется
совпадение организации лида с организацией вызывающего, хотя `get_object` уже гарантирует это по
построению.

## Комментарии и вложения {#comments-and-attachments}

Добавление комментария или вложения к лиду не является отдельным эндпоинтом: это тот же маршрут
`POST /api/leads/{id}/`, что использует эндпоинт создания, только с существующим `pk`
(`LeadDetailView.post`, `lead_views.py:589-651`). Вызывающий должен быть администратором или
суперпользователем, создателем лида или одним из его ответственных (`:599-610`). Отправьте `comment`
(текст) и/или `lead_attachment` (файл multipart), одно из них или оба, и ответ вернёт ту же форму
`lead_obj`/`attachments`/`comments`, что и `GET`.

Изменение или удаление *существующего* комментария идёт через отдельный маршрут:
`PUT` / `PATCH` / `DELETE /api/leads/comment/{id}/` (`LeadCommentView`,
`backend/leads/views/lead_interactions.py:60-183`), доступный только администратору, суперпользователю или
автору комментария (`request.profile == obj.commented_by`; `commented_by` является внешним ключом на
`Profile`, поэтому это сравнение корректно, в отличие от некоторых сравнений `created_by` в других местах
кода. См. [Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks)).

`DELETE /api/leads/attachment/{id}/` (`LeadAttachmentView.delete`, `lead_interactions.py:203-221`) имеет
реальный пробел, описанный в разделе
[Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks): поиск
выполняется как `self.model.objects.get(pk=pk)` **вообще без фильтра `org=`** (`lead_interactions.py:204`),
поэтому пространство id для удаления вложений не ограничено организацией вызывающего на уровне запроса
ORM, и между этим эндпоинтом и удалением в чужом тенанте стоит только PostgreSQL RLS, если оно правильно
настроено в вашем развёртывании. Проверка владельца на этом же эндпоинте
(`request.profile.user == self.object.created_by`, `:208`) корректна: она сравнивает `User` с `User`,
поэтому найденное вложение может удалить только загрузивший его пользователь, администратор или
суперпользователь; дефект именно в отсутствии ограничения по организации при поиске, а не в проверке
прав.

## Дубликаты и слияние {#duplicates-and-merging}

`POST /api/leads/duplicates/` принимает в виде JSON-тела поля, уже введённые в форму создания (`email`,
`phone`, `first_name`, `last_name`, `company_name`), и отвечает `{"duplicates": [...]}`: не более 10
активных лидов, сначала самые новые. `GET /api/leads/{id}/duplicates/` возвращает такой же список для
сохранённого лида, не включая сам лид, плюс `can_delete` для этого лида. Каждое совпадение содержит
только `id`, `name`, `email`, `phone`, `matched_on` (правила, по которым оно совпало) и `can_delete`
(может ли вызывающий слить его в другой лид), но никогда не саму запись. Оба эндпоинта ищут только среди
лидов, которые вызывающий может открыть, поэтому скрытый лид не показывается и не учитывается, а скрытый
или отсутствующий `{id}` даёт одинаковый `404`. Значение длиннее, чем допускает модель, даёт `400`.
Проверка в форме создания выполняется через `POST`, который ничего не записывает, чтобы адрес email и
номер телефона никогда не попадали в URL и в журналы доступа, которые его записывают. Начиная с
django-crm 1.13.0 токену для неё нужен только scope `read` модуля (`leads:read`), поскольку она ничего
не записывает; раньше требовался `leads:write`. Ограничение частоты составляет 120 запросов в минуту на
пользователя, а клиенты применяют debounce с большим запасом.

Сопоставление: email без учёта регистра; имя и фамилия вместе; название компании точно, но только если
не указано имя человека, потому что два человека из одной компании означают два лида. Конвертированные
лиды никогда не сопоставляются. Номера телефонов сравниваются по последним десяти цифрам (или по всем
цифрам более короткого номера, но не менее семи), независимо от разделителей.

`POST /api/leads/{id}/merge/` с `{"merge_id": "<uuid>"}` сливает лид, указанный в теле, в лид из URL.
Вызывающий должен иметь возможность открыть оба (скрытый или отсутствующий любой из них даёт одинаковый
`404`), должен иметь право изменять сохраняемый лид (для лидов это любой, кто может его открыть) и должен
удовлетворять правилу удаления для поглощаемого лида (администратор, суперпользователь или его создатель),
иначе `403`. Слияние лида с самим собой, а также отсутствующий или некорректный `merge_id` дают `400`.
Конвертированный лид с любой стороны даёт `400`: он уже стал компанией, контактом и сделкой. Обе строки
блокируются на время слияния, которое выполняется в одной транзакции:

- Все связи поглощаемого лида переносятся на сохраняемый: задачи, заявки веб-форм и связанные контакты,
  комментарии, вложения и активность. Связь, которая у сохраняемого лида уже есть, не дублируется.
- Приоритет у значений сохраняемого лида. Его пустые поля, включая дополнительные поля по каждому ключу,
  получают значения другого лида; владельцы (`assigned_to`, `teams`) переносятся, только если у
  сохраняемого лида их нет; теги и связанные контакты объединяются. Сохраняемый лид сохраняет свой
  статус, этап воронки и позицию на доске.
- Затем поглощаемый лид удаляется, что отправляет обычный вебхук `lead.deleted`, а в журнал аудита
  записывается строка `RECORD_MERGED` с обоими id и обоими именами. Отменить слияние нельзя. Начиная с
  django-crm 1.13.0 поле `assigned_to` этого вебхука перечисляет владельцев, которые были у поглощаемого
  лида до слияния, даже если они перешли к сохраняемому; раньше оно строилось после переноса и могло
  оказаться пустым.

Ответ имеет вид `{"error": false, "message": "...", "id": "<kept id>"}`.

## Лиды без ответа {#unanswered-leads}

`GET /api/leads/?unanswered=true` оставляет только лиды, ожидающие ответа, упорядоченные по
`waiting_since` (сначала самое долгое ожидание, затем по id), и сочетается с любым другим фильтром,
например `assigned_to` или `open`. Экспорт в CSV (`GET /api/leads/export/?unanswered=true`) и
сохранённые представления тоже его принимают, поэтому экспортированный или сохранённый список «Без
ответа» содержит те же лиды в том же порядке. Любое значение, кроме `true`, оставляет список без
фильтра. Правило находится в `backend/leads/response.py`.

Пусть `arrival_at` это `last_enquiry_at` лида или его `created_at`, если первого нет. Лид считается
оставшимся без ответа, когда выполнены все три условия:

- его статус `assigned`, `in process` или `recycled` (никогда не `converted` или `closed`);
- `last_outbound_at` равно null или раньше `arrival_at`;
- `arrival_at` не раньше `lead_response_since` организации, момента, когда организация начала
  измерения (проставляется при обновлении до этого релиза, а у более новой организации при её
  создании), чтобы годы старых открытых лидов не заполонили список.

`waiting_since` равно null, если лид не остался без ответа. Иначе это `created_at` лида, когда по нему
никогда не записывалось ничего исходящего и он создан не раньше `lead_response_since`, а в остальных
случаях `arrival_at`. Новый лид, обратившийся дважды, ждёт с момента создания; лид, которому
ответили, а затем он обратился снова, ждёт с этого обращения; а старый лид, созданный до отметки и
обратившийся снова, ждёт с нового обращения, а не со дня создания. `last_outbound_at`,
`first_response_at` и `first_response_by` ведутся по записанным взаимодействиям лида
([Взаимодействия](interactions.md#a-leads-response-fields)).

`GET /api/dashboard/` и `GET /api/dashboard/today/` оба содержат счётчик:

```json
"unanswered_leads": {"count": 3, "oldest_since": "2026-10-24T09:46:00Z"}
```

по лидам, которые видит вызывающий (у администратора вся организация; у участника его собственные и
назначенные ему лиды), где `oldest_since` это самое раннее `waiting_since` или null, если никто не
ждёт. Пока модуль лидов выключен, значение равно `{"count": 0, "oldest_since": null}`.

## Время ответа {#response-times}

`GET /api/leads/response-times/?days=30` показывает, насколько быстро каждый человек даёт лиду первый
ответ:

```json
{
  "since": "2026-09-25",
  "rows": [
    {
      "profile": "8d6c...",
      "name": "Maria Lopez",
      "answered": 12,
      "median_seconds": 340,
      "within_5_minutes": 50,
      "within_1_hour": 83,
      "unanswered_now": 2
    }
  ]
}
```

- **Кто получает какие строки.** Администратор организации получает строку для каждого активного
  участника, включая себя; любой другой получает ровно одну строку, свою. Сравнение коллег является
  агрегатом по организации.
- **`days`** это целое число от 7 до 90, по умолчанию 30; любое другое значение даёт `400` с
  указанием `days`. Окно охватывает последние `days` дней календаря организации, включая сегодня.
  `since` это первый из них, и окно открывается в полночь организации в эту дату.
- **`answered`** считает лиды, на которые человек ответил первым (`first_response_by`), с
  `first_response_at` внутри окна. Лид, созданный до `lead_response_since` организации, не
  учитывается: его время ответа включало бы годы до того, как что-либо записывалось.
- Время ответа на лид равно `first_response_at` минус `created_at` по часам, поэтому ночи и выходные
  учитываются. **`median_seconds`** это медиана по лидам строки (средний, или среднее двух средних) в
  целых секундах с округлением вниз, и null, если лидов нет.
- **`within_5_minutes`** и **`within_1_hour`** это доля в процентах тех лидов, на которые ответили
  не более чем за пять минут и не более чем за час, с округлением вниз, так что 100 означает все до
  одного; 0, если лидов нет.
- **`unanswered_now`** считает назначенные человеку лиды, которые прямо сейчас остаются без ответа,
  независимо от окна.
- **`name`** это имя участника или его email, если имя пустое. Строки отсортированы по нему.

Как и любой маршрут `/api/leads/`, он отклоняется, пока модуль лидов выключен
([Модули](modules.md)).

## Итоги {#outcomes}

Новое в 1.41.0. `GET /api/leads/outcomes/?days=30` показывает, сколько лидов каждый человек выигрывает
и проигрывает и сколько времени занимает выигрыш:

```json
{
  "since": "2026-09-29",
  "measured_since": "2026-10-28",
  "rows": [
    {
      "profile": "8d6c...",
      "name": "Maria Lopez",
      "won": 9,
      "lost": 3,
      "win_rate": 75,
      "median_seconds_to_win": 432000,
      "new_leads": 20
    }
  ],
  "totals": {
    "won": 21,
    "lost": 8,
    "win_rate": 72,
    "median_seconds_to_win": 388800,
    "new_leads": 64
  }
}
```

- **Выигранные и проигранные.** Лид выигран, когда его статус `converted` или `stage_type` его этапа
  равен `won`, проигран, когда его статус `closed` или `stage_type` его этапа равен `lost` (если
  подходит и то, и другое, побеждает выигрыш), и открыт в остальных случаях, включая `recycled`. Лид
  хранит `won_at` и `lost_at`, которые устанавливаются в `Lead.save()`, когда сохранение меняет его
  статус или этап и это меняет его итог: тот итог, который теперь действует, получает время, а другой
  очищается, а у вновь открытого лида очищаются оба. Сохранение, которое не меняет ни статус, ни этап,
  ничего не проставляет, и лид, созданный уже выигранным или проигранным, не получает отметки, так как
  никто не знает, когда он закрылся. Доска, форма редактирования, конвертация и автоматизация сохраняют
  через этот метод; `update()` по queryset через него не проходит. Изменение `stage_type` этапа или удаление этапа не
  переставляет отметки ни одному лиду в нём: каждый сохраняет свои даты, пока сохранение не изменит его
  собственный статус или этап. Слияние сохраняет даты сохраняемого лида и никогда не копирует даты
  другого. Ни одного из этих полей нет в payload лида, и ни одна запись их не принимает.
- **`measured_since`** это дата `lead_outcomes_since` организации, момента, когда она начала ставить
  отметки (при обновлении до этого релиза, а у более новой организации при её создании). Раньше ничего
  не записывалось, поэтому пустая первая неделя читается как «измеряется с», а не как то, что никто
  ничего не выиграл. Ни одна запись его не принимает.
- **Кто получает какие строки.** Администратор организации получает строку для каждого активного
  участника, включая себя, и `totals`; любой другой получает ровно одну строку, свою, а `totals`
  равно null.
- **`days`** это целое число от 7 до 90, по умолчанию 30; любое другое значение даёт `400` с
  указанием `days`. Окно охватывает последние `days` дней календаря организации, включая сегодня;
  `since` это первый из них, и окно открывается в полночь организации в эту дату.
- **`won`** и **`lost`** считают лиды, назначенные человеку сейчас, у которых `won_at` или `lost_at`
  попадает в окно. Заслуга достаётся тому, кто назначен сейчас, а не тому, кто был назначен тогда, и
  лид с двумя ответственными учитывается у обоих. **`new_leads`** считает лиды, назначенные человеку
  сейчас и созданные внутри окна.
- **`win_rate`** это доля `won` от `won + lost` в целых процентах с округлением до ближайшего
  (половина уходит к чётному соседу, так что 12.5 даёт 12), и null, когда оба равны 0.
- **`median_seconds_to_win`** это медиана `won_at` минус `created_at` по лидам строки, выигранным
  внутри окна (средний, или среднее двух средних), в целых секундах с округлением вниз, и null, если
  таких нет.
- **`totals`** считает каждый лид организации один раз, независимо от того, назначен ли кто-нибудь.
- **`name`** это имя участника или его email, если имя пустое. Строки отсортированы по нему.

Как и любой маршрут `/api/leads/`, он отклоняется, пока модуль лидов выключен
([Модули](modules.md)).

## Оповещения о лидах {#lead-alerts}

Новое в 1.39.0; что и когда отправляется, описано в разделе
[Оповещения о лидах](../features/lead-alerts.md).

**Уведомления.** Четыре оповещения являются строками в `GET /api/notifications/` с `verb`
`lead.assigned`, `lead.created`, `lead.enquired` или `lead.waiting`, `entity_type` `Lead`,
`entity_id` и `link` (`/leads/<id>`), указывающими на лид, `entity_name` с его именем и `data`
`{"source": "<source label, or empty>"}`. `actor` строки `lead.assigned` это участник, который
назначил, если назначал человек. Начиная с 1.42.0 строка `lead.enquired` для конвертированного лида
указывает на контакт, которым он стал: `entity_type` `Contact`, `entity_id` и `link`
(`/contacts/<id>`) указывают на контакт, `entity_name` это имя контакта, а `data.source` по-прежнему
источник лида.

**Ваши переключатели.** `GET /api/profile/` (в `user_obj`) и `GET /api/auth/profile/` содержат
`lead_alerts_email` и `lead_alerts_push`, оба по умолчанию `true`. `PATCH /api/profile/` с любым из
них устанавливает его в собственном профиле вызывающего в организации токена и ни в чьём другом;
любое значение, кроме boolean, даёт `400`.

**Напоминание.** `GET /api/org/settings/` содержит `lead_reminder_minutes`: `null` (выключено), `5`,
`15`, `30` или `60`. Администратор задаёт его через `PATCH /api/org/settings/`; любое другое значение
даёт `400`, а `PATCH` от участника даёт `403`. Смена с `null` на значение записывает этот момент, и
напоминания приходят только о лидах, чьё последнее обращение (или создание) не раньше этого момента.
Сам момент в API не виден.

**Телефоны.** Мобильное приложение регистрирует и удаляет свой push-токен:

| Эндпоинт | Тело | Ответ |
| --- | --- | --- |
| `POST /api/devices/` | `{"token", "platform": "android" or "ios", "app_version"?}` | `204`. Создаёт или обновляет строку этого токена в организации вызывающего, принадлежащую вызывающему (телефон, на котором входил другой участник, переходит к вызывающему), с `last_seen_at`, равным текущему моменту. У вызывающего в организации остаются пять строк с самым поздним `last_seen_at`; более старые удаляются |
| `DELETE /api/devices/` | `{"token"}` | `204`, был ли у вызывающего этот токен в этой организации или нет; строка другого участника не затрагивается |

Токен не длиннее 2 048 символов, каждый из которых латинская буква ASCII или цифра, `_`, `:` или `-`
(алфавит FCM; всё остальное даёт `400`), а `app_version` не длиннее 32. Push-уведомления уходят на
пять самых новых телефонов участника, а строка, чей `last_seen_at` старше срока жизни refresh-токена
(14 дней), удаляется без отправки. Ни один из методов никогда не возвращает токен в ответе. Оба
доступны только для сеанса, в который выполнен вход: `/api/devices/` входит в запретный список для
учётных данных (`backend/common/scopes.py`), поэтому персональный токен доступа или API-ключ
организации получают `403`, ведь зарегистрированный телефон продолжает получать оповещения участника
и после отзыва токена, который его зарегистрировал. Ограничение: 60 запросов в минуту на пользователя.

## Источники лидов {#lead-sources}

Откуда пришёл лид, задаётся ключом из списка организации. Эндпоинты не зависят от переключателя
модуля лидов, потому что контакты и сделки читают тот же список.

| Эндпоинт | Кто | Тело | Ответ |
| --- | --- | --- | --- |
| `GET /api/leads/sources/` | любой участник | | `{"sources": [{"id", "key", "label", "is_active", "order"}]}`, по `order`, включая выведенные из использования. Значения по умолчанию создаются при первом обращении |
| `POST /api/leads/sources/` | администратор | `{"label"}` | `201` с новым источником. Ключ это название в нижнем регистре со схлопнутыми пробелами; название, ключ которого в организации уже есть (выведенный из использования или нет), даёт `400`. Не длиннее 64 символов |
| `PATCH /api/leads/sources/{id}/` | администратор | `{"label"?, "is_active"?}` | Источник. Ключ никогда не меняется, поэтому существующие записи продолжают на него указывать. Id другой организации даёт `404` |
| `POST /api/leads/sources/order/` | администратор | `{"keys": [...]}` | `{"sources": [...]}` в новом порядке. Каждый ключ не более одного раза, и все должны принадлежать организации; невключённые ключи идут после перечисленных |

Удаления нет: вместо этого выведите источник из использования. Выведенный из использования источник
остаётся в записях, где он указан, но его нельзя выбрать для новой. Запись не от администратора
даёт `403`.

**Сборки мобильного приложения до 1.13.0** не отправляют заголовок `X-BottleCRM-App` (они
представляются HTTP-клиентом Dart) и не могут показать источник, которого в них никогда не было.
Только для таких запросов пустое значение или `other`, отправленное поверх сохранённого ключа, который
старая сборка не может прочитать, игнорируется (сохранённый ключ остаётся). Читаемые ключи лида это
`call`, `email`, `existing customer`, `partner`, `public relations` и `other` (`campaign` она читала
как Other); у сделки те же плюс `campaign` (`web form` она читала как None и отправляла `NONE`).
`compaign` читается как `campaign`, а значения сделки в верхнем регистре как их ключи.

## Поля {#fields}

`POST`/`PUT`/`PATCH` (каждое представляет собой список id в рамках организации): `tags`, `contacts`,

который одновременно загружает файл (поля multipart приходят строками, а не JSON-массивами):

| Поле | `POST /api/leads/` | `PUT /api/leads/{id}/` | `PATCH /api/leads/{id}/` |
| --- | --- | --- | --- |
| `tags` | просто `id__in=data.get("tags")`, без обработки строк (`lead_views.py:318-323`) | тот же пробел (`:715-721`) | `json.loads`, если строка, `{"id": …}` разворачивается (`:981-995`) |
| `contacts` | тот же пробел (`:325-329`) | `json.loads`, если строка (`:732-745`) | `json.loads`, если строка (`:997-1011`) |
| `teams` | `json.loads`, если строка (`:340-350`) | так же (`:747-758`) | так же (`:1013-1027`) |
| `assigned_to` | `json.loads`, если строка (`:352-364`) | так же (`:760-773`) | так же (`:1029-1043`) |

Если отправить `tags` или `contacts` строкой с JSON в том же запросе, что и загрузку `lead_attachment` в
`multipart/form-data` (на `POST`, или на `PUT` конкретно для `tags`), поиск `id__in` в Django получит
сырую строку. Django перебирает её посимвольно; ни один символ не проходит разбор `UUIDField`, и запрос
падает необработанной ошибкой `500` вместо аккуратного `400`. Тот же сбой уже описан для другого поля в
`contacts/views.py:105-108`. Отправка этих двух полей в настоящем JSON-теле (без файла) работает
нормально, потому что DRF разбирает JSON-тело запроса в настоящий список ещё до того, как его прочитает
представление.

`GET /api/leads/{id}/` и `GET /api/leads/` дополнительно возвращают, но никогда не принимают на вход:
`id`, `created_by`, `created_at`, `updated_at`, `is_sample` (устанавливается только сервером, см.
`leads/serializer.py:80-85`), `lead_attachment` и `lead_comments` (вложенные сериализации вложений и
комментариев этого лида только для чтения: `leads/serializer.py:64-65`), `stage` и `kanban_order`
(управляются эндпоинтами Kanban, а не этой страницей) и `custom_fields` (проверяются отдельно по строкам
`CustomFieldDefinition` организации).
