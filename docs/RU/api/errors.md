# Ошибки

Как отличить неудачный запрос от успешного и как читать тело неудачного ответа.
`REST_FRAMEWORK["EXCEPTION_HANDLER"]` в `backend/crm/settings.py` указывает на собственный обработчик DRF
`rest_framework.views.exception_handler` (без изменений и без подкласса), поэтому исключение, которое
выбрасывает сам DRF (неудачная проверка прав, отсутствующий объект, необработанный `ValidationError`),
возвращается в стандартной форме DRF. Представление, которое само перехватывает ошибки и собирает
`Response` вручную (а так устроено большинство представлений в этом коде), может вернуть и часто
возвращает что-то другое. Ниже описаны оба варианта с реальными примерами, потому что клиент должен
обрабатывать оба.

## Коды статуса {#status-codes}

`200` означает успешное чтение или успешную запись. Многие эндпоинты изменения данных возвращают `200`,
а не `201`, даже при создании и оборачивают результат в форму `{"error": false, ...}`, описанную в
разделе [Соглашения](conventions.md#response-shape), не полагаясь на один лишь код статуса (см.
`POST /api/leads/`, `backend/leads/views/lead_views.py:402-404`). Некоторые всё же используют `201`:
например, создание персонального токена доступа возвращает `201`
(`backend/common/views/pat_views.py:69`). Ни один из вариантов здесь не «правильнее» другого,
проверяйте конкретный эндпоинт.

Кроме того: `400` означает запрос, который сервер понял, но отклонил (валидация или ошибка в форме
запроса, например отсутствует обязательное поле); `401` возвращается только там, где представление
явно так решает (просроченный или некорректный refresh-токен на эндпоинте обновления токена); `403`
означает запрос без учётных данных или с недействительными, а также запрос, который прошёл
аутентификацию, но не имеет права на это действие; `404` означает ресурс, которого не существует, или
ресурс, который существует, но вызывающий не должен иметь возможности отличить его от
несуществующего. См. [«Не найдено» или «запрещено»](#not-found-versus-forbidden); `502` возвращается там,
где представление зависит от внешнего сервиса и этот сервис недоступен, например при обмене токена
Google в [Google OAuth](authentication.md#google-oauth-web)
(`backend/common/views/auth_views.py:110-114`). `429` приходит только от анонимных эндпоинтов, которые
задают собственные ограничения частоты: отправка веб-формы, публичный справочный центр, календарная
лента, а также запросы на вход по magic link и на вход в портал. `REST_FRAMEWORK` не задаёт
`DEFAULT_THROTTLE_CLASSES`, поэтому ни один эндпоинт с аутентификацией его не возвращает. Запросы на
вход также ограничивают число токенов на адрес (пять в час), и при этом лимите они отвечают обычным
`200`, а не `429`, чтобы по ответу нельзя было отличить «лимит исчерпан» от «отправлено» и от
«неверный адрес». См. [Magic links](authentication.md#magic-links).

## Ошибки валидации {#validation-errors}

Преобладающий в этом коде подход отличается от автоматического подхода DRF. Большинство представлений
вызывают `serializer.is_valid()` без `raise_exception=True`, сами проверяют булев результат и вручную
собирают ответ с ошибкой в виде `{"error": true, "errors": serializer.errors}`. Именно эта форма
встречается в бэкенде более 200 раз. Ошибка `validate_<field>` попадает под ключ этого поля, как обычно
в DRF:

```python
def validate_email(self, value):
    ...
    if duplicates.exists():
        raise serializers.ValidationError(
            "Another lead in this organisation already uses that email address."
        )
    return value
```

(`backend/leads/serializer.py:107-133`, `LeadCreateSerializer.validate_email`. Комментарий над ним
объясняет, что проверка появилась потому, что дублирующийся email раньше доходил до базы данных как
необработанный `IntegrityError` и возвращался непрозрачной ошибкой `500`.) `POST /api/leads/` с
дублирующимся email возвращает:

```json
{"error": true, "errors": {"email": ["Another lead in this organisation already uses that email address."]}}
```

Ошибка `validate()`, не привязанная к одному полю, попадает под стандартный ключ DRF
`non_field_errors` (`NON_FIELD_ERRORS_KEY` нигде в этом коде не переопределён) с той же вложенностью:
`{"error": true, "errors": {"non_field_errors": ["..."]}}`.

Меньшая и более новая группа представлений вызывает `serializer.is_valid(raise_exception=True)`,
например `MacroListCreateView.post` (`backend/macros/views.py:123`), и позволяет обработчику исключений
DRF собрать ответ самостоятельно, вообще без обёртки `error`/`errors`:

```json
{"email": ["Another lead in this organisation already uses that email address."]}
```

Обе формы сегодня есть в API. Сверяйтесь со страницей конкретного эндпоинта (или с представлением, если
эндпоинт ещё не описан), а не предполагайте одну из них; не считайте, что наличие или отсутствие ключа
`error` говорит об успехе запроса. Об этом говорит код статуса.

## Ошибки авторизации {#authorization-errors}

Ошибки аутентификации и авторизации проходят через механизм прав DRF без изменений, поэтому всегда
возвращаются как `{"detail": "<message>"}`, будь то стандартное сообщение DRF или заданное в этом коде:

```json
{"detail": "Authentication credentials were not provided."}
```

```json
{"detail": "Organization context is required. Please login again."}
```

Второе сообщение берётся из `HasOrgContext.message` (`backend/common/permissions.py:11-41`), одного из
двух классов прав, которые указывает почти каждое представление, привязанное к организации:
`permission_classes = (IsAuthenticated, HasOrgContext)`, часто с дополнительной проверкой роли, например
`IsOrgAdmin` (`backend/common/permissions.py:44-59`, `"You must be an organization administrator to
perform this action."`). Вернётся ли ошибка как `401` или как `403`, не зависит от того, какой класс прав
не прошёл. `APIView.permission_denied()` в DRF выбрасывает `NotAuthenticated`, если ни один
аутентификатор запроса фактически не сработал, и `PermissionDenied` (`403` с `message` не прошедшего
класса прав), если аутентификация прошла, но не прошла сама проверка прав. DRF отвечает на
`NotAuthenticated` кодом `401` только тогда, когда первый класс аутентификации представления определяет
`authenticate_header`, а ни один из классов для сотрудников (`PATAuthentication`, `JWTAuthentication`,
`APIKeyAuthentication`) этого не делает, поэтому возвращается `403`. На практике: нет учётных данных или
они недействительны → `403`; действительная аутентифицированная сессия, которой это действие не
разрешено → `403`.

## Отключённые модули {#switched-off-modules}

Администратор организации может отключать части CRM (см. [Модули](modules.md)). Запрос
аутентифицированного пользователя к маршруту отключённого модуля получает `404` для любого метода, а
тело ответа объясняет причину:

```json
{"detail": "Tickets is switched off for this organization.", "code": "module_off", "module": "tickets"}
```

`code` всегда равен `module_off`, а `module` содержит ключ модуля, так что клиент может отличить этот
`404` от отсутствующей записи. Публичные ссылки, клиентский портал и входящая почта не используют это
тело: они отвечают так же, как на неизвестную ссылку.

Удаление, которое уничтожило бы записи отключённого модуля или блокируется ими, отклоняется с кодом
`409` и теми же двумя полями:

```json
{"error": true, "errors": "This account has 3 tickets. Tickets is switched off, so switch it on to review them before deleting.", "code": "module_off", "module": "tickets"}
```

Запись, в которой указана запись отключённого модуля (например, событие вебхука, сохранённое
представление или цель веб-формы), получает `400` по этому полю с фразой
`<Label> is switched off for this organization.`

## «Не найдено» или «запрещено» {#not-found-versus-forbidden}

Правило, которое действует везде, где объект ищется по id: запись вне организации вызывающего
возвращает `404`, так же как запись, которой никогда не было, и никогда не `403`. Каждый такой поиск
сначала фильтрует по `org=request.profile.org` (или по эквивалентному queryset под защитой RLS), а уже
потом сопоставляет id, поэтому запрос записи чужой организации просто ничего не находит;
`get_object_or_404(Macro, pk=pk, org=request.profile.org)` (`backend/macros/views.py:148`, повторяется в
`:168` для обычного `GET`) лишь один из десятков примеров такой формы. `invoices/permissions.py` прямо
формулирует причину в собственном docstring модуля:

```
1. Does this record exist *in the caller's org*?  -> 404 if not, so that a
   caller in another org cannot probe for record IDs.
2. May this caller act on it?                     -> 403 if not.
```

(`backend/invoices/permissions.py:5-9`.) Ответ `403` сам по себе подтверждает, что запись существует.
Нельзя получить запрет на действие над тем, чего нет, поэтому `403` оставлен для случая «существует, но
вам нельзя», а `404` для всего остального: именно это не даёт id превратиться в оракул, который
вызывающий из другой организации мог бы прощупывать.

Внутри одной организации ответ на отказ в правах (`403` или сразу `404`) зависит от того, что это за
ресурс. Счета и коммерческие предложения сохраняют шаг 2 как настоящий `403`: участник организации, не
являющийся ни создателем записи, ни ответственным, ни администратором, получает отказ
`{"error": true, "message": "Permission denied"}` (`backend/invoices/permissions.py:80-84`). Коллега может
узнать, что счёт существует, но не может прочитать или изменить его. Личный макрос (в отличие от макроса
уровня организации) идёт дальше и полностью скрывается от всех, кроме владельца и администраторов
организации: `404` даже для вызывающего из той же организации, именно чтобы избежать раскрытия, как в
случае со счетами:

```python
if macro.scope == Macro.SCOPE_PERSONAL and macro.owner_id != request.profile.id:
    # A personal macro you don't own is invisible to you. The list and
    # GET hide it (404). The write verbs must not confirm it exists via
    # a 403 either, or the id space leaks which rows are somebody else's
    # personal macros. Mirror the GET: 404.
    return Response({"detail": "Not found."}, status=status.HTTP_404_NOT_FOUND)
```

(`backend/macros/views.py:156-164`.) Оба варианта представляют собой осознанные, задокументированные
решения для своего ресурса, а не несогласованность, которую нужно замазать. Добавляя проверку
авторизации в новый эндпоинт, решите, какой из двух вариантов нужен вашему ресурсу (раскрывает ли что-то
сам факт, что коллега по организации знает о существовании записи?), а не выбирайте тот, который проще
написать.
