# Макросы

Макрос (в мобильном приложении «сохранённый ответ») это заготовка ответа для редактора обращения,
которая может также содержать действия, меняющие обращение. Маршруты находятся в `backend/macros/urls.py`,
представления в `backend/macros/views.py`, подстановка плейсхолдеров в `backend/macros/render.py`. Все
маршруты лежат под `/api/macros/` и требуют `(IsAuthenticated, HasOrgContext)`. Форматы, которые здесь
подразумеваются, описаны в разделах [Соглашения](conventions.md) и [Ошибки](errors.md).

## Область и видимость {#scope-and-visibility}

Макрос бывает либо `org` (его видит и использует каждый участник организации, а создавать, изменять
и удалять его может только администратор), либо `personal` (виден только владельцу). `POST` от
не-администратора с `scope: "org"` или попытка изменить макрос организации возвращает `403`:

```json
{"error": "Only admins can manage org-scope macros."}
```

Чужой личный макрос на любой метод отвечает `404`, точно так же как несуществующий id, поэтому по
пространству id нельзя узнать, у кого есть личные макросы. Макрос организации, который пытается
изменить не-администратор, отвечает `403`, потому что этот макрос ему и так виден.

## Список, создание, изменение, удаление {#list-create-update-delete}

`GET /api/macros/` возвращает макросы, видимые вызывающему, начиная с последних изменённых, и
принимает `active` (`true` или `false`) и `search` (по заголовку или тексту, без учёта регистра).
Ответ имеет вид `{"results": [...], "totals": {...}, "placeholders": [...]}`; `totals` считает всё
видимое множество независимо от фильтров (`count`, `org`, `personal`, `inactive`,
`with_unknown_placeholders`), а `placeholders` содержит список плейсхолдеров, которые поддерживает
подстановка.

`POST /api/macros/` создаёт макрос; `GET`, `PUT`, `PATCH` и `DELETE /api/macros/{id}/` читают и
изменяют его. `DELETE` выключает макрос организации (`is_active: false`) и удаляет личный.

| Поле | Тип | Примечания |
| --- | --- | --- |
| `title` | строка, не длиннее 255 | Обязательное |
| `body` | текст | Может быть пустым, если у макроса есть хотя бы одно действие |
| `scope` | `org` или `personal` | По умолчанию `org`, для чего нужны права администратора |
| `is_active` | boolean | По умолчанию `true`. Неактивный макрос нельзя подставить или применить |
| `set_status` | статус обращения или `""` | Любой статус, кроме `Duplicate`, который ставит только слияние. `""` означает «не менять» |
| `set_priority` | приоритет обращения или `""` | `""` означает «не менять» |
| `set_assignees` | список id профилей | При применении заменяет ответственных за обращение |
| `add_tags` | список id тегов | При применении добавляется к собственным тегам обращения |

`owner`, `owner_name`, `usage_count`, `unknown_placeholders`, `created_at` и `updated_at` доступны
только для чтения. `set_assignees_details` и `add_tags_details` раскрывают каждый id (`id`, `email` и
`name` либо `id`, `name` и `color`) вместе с его `is_active`, чтобы клиент мог показать
ответственного, которого с тех пор деактивировали, или тег, отправленный в архив, а не выбросить его.

Ошибки валидации, каждая с кодом `400`:

- **Макрос должен что-то делать.** Макрос без текста и без действий отклоняется с
  `{"body": ["A macro needs a body, an action, or both."]}`.
- **`set_assignees` и `add_tags` разрешаются только в организации вызывающего.** Id из другой
  организации отклоняется так же, как несуществующий.
- **Добавлять можно только активных участников и активные теги.** Деактивированный участник или
  архивный тег, которые уже есть в макросе, при сохранении остаются, потому что оба клиента каждый
  раз отправляют весь список целиком.

## Подстановка {#render}

`POST /api/macros/{id}/render/` с `{"case_id": "<uuid>"}` подставляет значения плейсхолдеров
(`%customer_name%`, `%customer_email%`, `%case_id%`, `%case_subject%`, `%agent_name%`,
`%agent_email%`, `%org_name%`) из обращения и возвращает `{"rendered_body": "..."}`. Вызов
засчитывается как одно использование макроса. Обращение, которое вызывающему нельзя открыть,
обращение из другой организации и некорректный id дают один и тот же `404`, потому что
подставленный текст содержит тему обращения, а также имя и email его контакта. Неизвестный
плейсхолдер остаётся в тексте как есть.

## Применение {#apply}

Начиная с django-crm 1.13.0, `POST /api/macros/{id}/apply/` применяет действия макроса к обращению:

```json
{"case_id": "<uuid>", "only": ["status", "tags"]}
```

`only` необязателен. Его ключи: `status`, `priority`, `assignees` и `tags`; он сужает действия
макроса до перечисленных, и так клиент применяет только те действия, которые сотрудник оставил. Без
него применяются все действия макроса.

Запись идёт через `cases.updates.update_case`, ту же функцию, которую используют `PATCH` обращения и
массовое редактирование, поэтому здесь срабатывают все те же проверки: блокировка объединённого
обращения, проверка закрытия (согласование, которого требует подходящее правило `pre_close`),
`Duplicate` только через слияние, ответственные и теги только из активных записей организации, и
письмо каждому новому ответственному. Ответственные заменяют ответственных обращения; теги
добавляются к собственным тегам обращения. Статус `Closed` берёт уже имеющийся у обращения
`closed_on`, а если его нет, то сегодняшнюю дату в часовом поясе организации. Применение не
засчитывается как использование, а подстановка засчитывается.

Отказы в порядке проверки:

| Статус | Когда |
| --- | --- |
| `404` | Макроса нет, он в другой организации или это чужой личный макрос |
| `400` | Макрос неактивен: `{"error": "Macro is inactive."}` |
| `400` | У макроса нет действий: `{"error": "This macro has no actions to apply."}` |
| `400` | `only` не является списком из четырёх ключей: `{"error": "only must be a list of: status, priority, assignees, tags."}` |
| `400` | Ни одного ключа из `only` нет в этом макросе: `{"error": "None of the chosen actions are on this macro."}` |
| `400` | Не передан `case_id`: `{"error": "case_id is required."}` |
| `404` | Обращение вызывающему нельзя открыть, оно в другой организации или id некорректен |
| `403` | Вызывающий может открыть обращение, но не изменить его (это могут только администратор, его автор или ответственный), как и при `PATCH` обращения |
| `400` | Изменение отклонила одна из проверок: `{"error": true, "errors": {...}}`, те же ошибки, что у `PATCH`, при этом ничего не записывается |

Успешный ответ `200`:

```json
{
  "error": false,
  "message": "Macro applied",
  "applied": ["status", "tags"],
  "skipped": []
}
```

`applied` перечисляет применённые действия. `skipped` перечисляет `{"action", "reason"}` для
действий, которым нечего было применять: `assignees`, когда все, кого назначает макрос, теперь
деактивированы (обращение сохраняет своих ответственных, а не остаётся без них), и `tags`, когда все
добавляемые теги в архиве. Если пропущено всё, ничего не записывается, а `message` равно
`"Nothing was applied"`.

### В клиентах {#in-the-clients}

В редакторе обращения в вебе и на телефоне выбор макроса с текстом, как и раньше, вставляет
подставленный текст и показывает его действия чипами под **Также при отправке**. Каждый чип можно
убрать. Оставшиеся действия применяются сразу после публикации ответа, с `only`, равным им; если
применение отклонено, ответ всё равно уже отправлен, а отказ показывается. Макрос без текста
показывает кнопку **Применить**, которая сразу применяет его действия.
