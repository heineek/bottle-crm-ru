# Обращения

Маршруты находятся в `backend/cases/urls.py`. CRUD, комментарии и вложения находятся в
`backend/cases/views.py`; импорт CSV в `backend/cases/import_views.py` / `backend/cases/services/csv_import.py`;
согласования в `backend/cases/approval_views.py` и `backend/cases/approvals.py`; база знаний в
`backend/cases/solution_views.py`. Авторизация на уровне объекта для самого обращения собрана в
`backend/cases/access.py`, для статей базы знаний в `backend/cases/kb_access.py`. Правила пагинации,
фильтрации и формы ответа, на которые эта страница опирается, не повторяя их, описаны в разделе
[Соглашения](conventions.md), а принцип 404 против 403, упомянутый ниже, в разделе [Ошибки](errors.md).

Обращения также являются самым большим модулем в этом коде: Kanban-воронки, слияние и его отмена,
деревья родительских и дочерних обращений, учёт времени, эскалация, маршрутизация, входящая почта и
аналитика тоже находятся под `/api/cases/...`. Эта страница охватывает только эндпоинты, входящие в
рамки этой документации: список, создание, детальную карточку, комментарии и вложения, согласования,
базу знаний и импорт CSV.

## Правила чтения, записи и удаления обращения намеренно различаются {#a-cases-read-write-and-delete-rules-differ-on-purpose}

Прежде всего: **не сводите правила доступа к обращению в одну проверку.** `cases/access.py` задаёт три
явных и разных правила, а docstring модуля объясняет почему: до появления этого модуля три действия
случайно разошлись в трёх разных ответах, и обращение наблюдателя показывалось в его списке, но при
открытии отвечало `403`:

```
read    admin · creator · assignee · watcher
write   admin · creator · assignee
delete  admin · creator
```

(`cases/access.py:20-22`.) Это тот же принцип «читать широко, писать узко», который в общем виде описан
в разделе [Архитектура: права и роли](../architecture/permissions-and-roles.md#read-wide-write-narrow).
Обоснование читайте там; эта страница лишь применяет его. Каждый эндпоинт из разделов
[Получение, изменение, удаление](#retrieve-update-delete) и
[Комментарии и вложения](#comments-and-attachments) вызывает одну из функций
`assert_case_read_access`/`assert_case_write_access`/`assert_case_delete_access`
(`cases/access.py:90-113`), а сама проверка администратора использует форму с двумя написаниями
администратора: `profile.role == "ADMIN" or bool(getattr(profile, "is_admin", False))`
(`cases/access.py:38-40`). Она встречается по всему коду. Эндпоинты раздела
[Согласования](#approvals) тоже используют `cases.access`, с одним намеренным расширением для входящей
очереди; см. этот раздел.

## Список обращений {#list-cases}

`GET /api/cases/` (`CaseListView.get`, `cases/views.py:310-312`) возвращает один список с пагинацией,
упорядоченный по `-created_at, -id` (`case_list_queryset`, `:188-193`): комментарий к queryset поясняет,
что второй ключ сортировки нужен потому, что `-id` сам по себе является случайным UUID и на практике не
давал никакого порядка. Мягко удалённые обращения (`is_active=False`) по умолчанию исключаются;
администратор организации может передать `?include_deleted=true`, чтобы их увидеть (`:194-198`).
Слитые дубликаты (заполнено `merged_into` или `status="Duplicate"`) по умолчанию тоже исключаются;
`?show_merged=true` включает их (`:199-202`). Вызывающий без прав администратора видит только
обращения, где он создатель, ответственный или наблюдатель, через тот же `visible_cases_qs`, который
использует проверка чтения в детальном представлении (`:203-209`), поэтому список и карточка
согласованы по построению.

```json
{
  "cases_count": 42,
  "offset": 10,
  "cases": [ { "...": "CaseSerializer" } ],
  "status": [["New", "New"], ["Assigned", "Assigned"], ["Pending", "Pending"], ["Closed", "Closed"], ["Rejected", "Rejected"], ["Duplicate", "Duplicate"]],
  "priority": [["Low", "Low"], ["Normal", "Normal"], ["High", "High"], ["Urgent", "Urgent"]],
  "type_of_case": [["Question", "Question"], ["Incident", "Incident"], ["Problem", "Problem"]],
  "open_count": 12,
  "urgent_count": 2,
  "awaiting_first_reply": 5,
  "accounts_list": [ { "...": "AccountSerializer" } ],
  "contacts_list": [ { "...": "ContactSerializer" } ],
  "users": [{"id": "...", "user__email": "..."}]
}
```

(`cases/views.py:217-288`.) `open_count`, `urgent_count` и `awaiting_first_reply` считаются по всему
отфильтрованному queryset, а не по странице. `awaiting_first_reply` считает открытые обращения
(`status` равен `New`/`Assigned`/`Pending`), у которых ещё нет `first_response_at`. Это не то же самое,
что нарушение SLA: оно зависит от рабочего календаря организации и вычисляется для каждой строки, а не
в этом агрегате. `accounts_list`/`contacts_list` наполняют выборщики формы создания: для администратора
по всей организации, а для остальных они сужены правилами чтения компаний и контактов
(`visible_accounts_qs`, `visible_contacts_qs`, `:224-227`), теми же, что принимает путь сохранения. В
любом случае они могут быть тяжёлыми, и `?slim=true` убирает оба (`:279-281`).

Фильтры читаются прямо из `request.query_params` (`apply_case_list_filters`, `cases/views.py:97-177`,
общий с `GET /api/cases/watching/`): `name` (вхождение), `status` (повторяемый: список применяет
`status__in`, одно значение даёт точное совпадение), `priority` (точное совпадение), `account` (точный
id), `case_type` (точное совпадение), `assigned_to` (повторяемый список id), `tags` (список id), `search`
(`name` или `description`, вхождение), `created_at__gte`/`created_at__lte` (диапазон дат),
`sla_breached=true` (приближение значка SLA по реальному времени, сырой SQL только для Postgres),
`cf_<key>` (равенство дополнительного поля) и `ordering`: допускаются только `created_at`,
`-created_at`, `priority`, `-priority`, `id`, `-id`, `name`, `-name` (`:83-94,172-175`); всё остальное
молча игнорируется, а не вызывает ошибку.

## Создание обращения {#create-a-case}

`POST /api/cases/` (`CaseListView.post`, `cases/views.py:331-420`) принимает `multipart/form-data` (для
необязательного файла `case_attachment`) или JSON и проверяет тело через `CaseCreateSerializer`
(`cases/serializer.py:284-458`; см. [Поля](#fields)). При успехе (`200`):

```json
{
  "error": false,
  "message": "Case Created Successfully",
  "id": "<uuid>",
  "cases_obj": { "...": "CaseSerializer" }
}
```

Ошибка валидации возвращает `400` с `{"error": true, "errors": {...}}`. О двух валидаторах стоит знать:

- **`account`, если передан, должен принадлежать организации вызывающего**: `validate_account`
  отклоняет id из другого тенанта с `"No such account."` (`cases/serializer.py:304-330`); комментарий к
  нему отмечает, что это закрывает и *запись* в чужой тенант, и *чтение* из него, поскольку ответ на
  создание вкладывает компанию обратно через `CaseSerializer` → `AccountSerializer`.
- **`name` должен быть уникален в пределах организации без учёта регистра** (`validate_name`,
  `:399-413`).

`contacts`, `teams`, `assigned_to` и `tags` **не** входят в `CaseCreateSerializer`. Представление
читает каждое из них из тела запроса после успешной работы сериализатора и разрешает в рамках
`org=request.profile.org` (`cases/views.py:351-389`). В отличие от [лидов](leads.md#fields), где описана
реальная несогласованность в том, как эти четыре поля *разбираются* на разных полях и методах, обращения
разбирают все четыре одинаково на каждом методе: каждое обрабатывается `json.loads`, если приходит
строкой (что происходит всякий раз, когда тот же запрос загружает `case_attachment` как multipart), и
только затем извлекается список id. Сам `case_attachment` читается прямо из `request.FILES`
(`cases/views.py:391-396`) и только на `POST`; почему `PATCH` вообще не может его задать и чем *запись*
этих четырёх полей (а не только разбор) сильно различается между методами, см. в разделе
[Получение, изменение, удаление](#retrieve-update-delete).

## Получение, изменение, удаление {#retrieve-update-delete}

`GET /api/cases/{id}/` (`CaseDetailView.get`, `cases/views.py:579-747`) сначала ищет обращение через
правило чтения (`get_case_or_404`, `:584`: некорректный UUID, обращение из другой организации и
обращение из той же организации, которое вызывающий не может открыть, отвечают одинаковым `404`, никогда
не `500` или `403`, в соответствии с разделом [Ошибки](errors.md#not-found-versus-forbidden)). Если
обращение было слито с другим, ответ вместо самого обращения содержит подсказку о перенаправлении:
`{"redirect_to": "<uuid>", "merged_into": "<uuid>", "source_case_id": "<uuid>", "source_case_name": "..."}`,
если только вызывающий не передал `?show_merged=true` (`:589-601`). Перенаправление возвращается только
после проверки чтения, поэтому `source_case_name` никогда не попадает к вызывающему, который не мог бы
открыть дубликат; раньше оно возвращалось первым и раскрывало название любому участнику организации,
знающему id. Ответ вкладывает запись в `cases_obj` вместе с `attachments`, `comments` (только
публичные), `internal_notes`, `contacts`, `solutions`, `activities` (последние 20), `email_messages`
(последние 50, ветки входящей почты), `merged_from_cases`, `custom_field_definitions`, `status`,
`priority`, `type_of_case`, `comment_permission`, `can_merge`, `approval_rule` и `users_mention`.
`approval_rule` содержит `{"id", "name"}` правила, которое ограничивает закрытие этого обращения
(`find_matching_rule(case, "pre_close")`, то есть правило, к которому привязывается
`request-approval/` без `rule_id`), или `null`, если такого нет; клиенты предлагают «Запросить
согласование» только когда оно задано. `comment_permission` вычисляется тем же
`has_case_write_access`, который применяет эндпоинт публикации комментария (`:612`), поэтому кнопка,
которую показывает клиент, и ответ сервера согласованы по построению; комментарий в этой строке
отмечает, что раньше это было не так (`comment_permission` разрешал создателю или администратору, а
эндпоинт записи ниже разрешал ещё и ответственным).

`PUT /api/cases/{id}/` (`cases/views.py:452-536`) и `PATCH /api/cases/{id}/` (`:842-860`) оба вызывают
`assert_case_write_access` прежде, чем что-либо менять. **`account` нельзя изменить ни одним из этих
методов.** `CaseCreateSerializer.__init__` выставляет `self.fields["account"].read_only = True` всякий
раз, когда задан `self.instance` (`cases/serializer.py:293-295`) (что верно для обоих вызовов изменения
и никогда для создания), поэтому на `PUT`/`PATCH` поле `account` в теле молча отбрасывается ещё до
валидации; `validate_account` не выполняется, и ошибка не возвращается. `PUT` создаёт сериализатор без
частичного режима, поэтому по-прежнему требует `name`/`status`/`priority`, как и `POST`; `PATCH`
передаёт `partial=True` (в `update_case`), поэтому там ни одно из трёх не обязательно. `PATCH` может
затронуть всего одно поле. Начиная с django-crm 1.13.0 запись `PATCH` выполняет `update_case` из
`cases/updates.py`, который также вызывают действия макроса ([Макросы](macros.md#apply)) и массовое
изменение, поэтому все три применяют одинаковую валидацию, одинаковые фильтры по организации и
активности для ответственных и тегов и отправляют одинаковое письмо каждому вновь назначенному.

Закрытие обращения проверяется как *переход*, а не только как целевое значение.
`CaseCreateSerializer.validate()` (`cases/serializer.py:332-397`) оценивает только переход в `"Closed"`
из любого другого статуса, поэтому уже закрытое обращение по-прежнему можно редактировать. При этом
переходе действуют следующие правила:

- **Дату закрытия ставит сервер.** Закрытие без `closed_on` (поле отсутствует или `null`) датируется
  сегодняшним днём в часовом поясе организации (`Org.timezone`, который middleware активирует для
  запроса) функцией `closing_date` из `cases/approvals.py`. `closed_on`, отправленный клиентом, всегда
  имеет приоритет, а некорректный даёт `400` по `closed_on`, и ничего не записывается. Клиентам не
  следует вычислять «сегодня» самостоятельно: начиная с django-crm 1.13.0 ни веб-приложение, ни телефон
  не отправляют дату при обычном закрытии, а организация, сохранённая под устаревшим именем часового
  пояса вроде `US/Eastern`, датируется так же, как любая другая. Уход из `"Closed"` очищает `closed_on`
  (и `resolved_at`), поэтому повторно открытое и снова закрытое обращение получает новую дату, а не
  сохраняет старую.
- **У закрытого обращения всегда есть дата.** Начиная с django-crm 1.13.0 это выполняется для любой
  записи, в результате которой статус равен `"Closed"`, а не только для перехода в него. Отсутствующий
  или `null` `closed_on` у уже закрытого обращения сохраняет записанную дату (поэтому
  `PATCH {"closed_on": null}` там ничего не меняет, а не оставляет обращение без даты), и только при
  отсутствии сохранённой даты ставится сегодняшний день в часовом поясе организации. То же правило
  действует для `PUT`, `PATCH`, массового изменения, применения макроса, перемещения на доске и закрытия
  вместе с дочерними, а сигнал pre-save модели `Case` применяет его к записывающим путям, минующим
  сериализатор API (строки импорта CSV со `status` `Closed` и без `closed_on`, демо-обращения
  отраслевых пакетов).
- **Срабатывает проверка согласования.** Когда активное `ApprovalRule` типа `pre_close` соответствует
  priority/case_type/team обращения (входящим значениям, чтобы запрос не мог одновременно вывести
  обращение из-под правила и закрыть его), требуется строка `Approval` в состоянии `approved` для этого
  обращения и правила, иначе ответ будет `400` с
  `{"errors": {"status": ["An approval is required before this case can be closed (rule: <name>)."]}}`,
  и ничего не записывается.

То же правило датирования действует на каждом пути, закрывающем обращение: `POST` (обращение, созданное
сразу как `"Closed"`), `PUT`, `PATCH`, перемещение на доске (`PATCH /api/cases/{id}/move/`), массовое
изменение (`POST /api/cases/bulk/update/`), действия макроса и `close-with-children`. Проверка
согласования срабатывает на всех них, кроме `POST`, поскольку согласование можно записать только для уже
существующего обращения; массовое изменение помечает такое обращение как `approval_required` и
продолжает с остальными. Проверка нужна потому, что `Case.clean()` (`cases/models.py:193-253`)
формулирует правила, но на пути сохранения никто не вызывает `full_clean()` (у `Case` нет собственного
`save()`, он наследует `BaseModel.save()`), поэтому без проверки на уровне сериализатора подходящее
правило могло быть включено, а `PATCH {"status": "Closed"}` всё равно вернул бы `200` и не записал ни
одного согласования. `PUT` и `PATCH` при успехе отвечают одной и той же буквальной строкой
`{"error": false, "message": "Case Updated Successfully"}`.

**Родительские связи.** `Case.clean()` (`cases/models.py:193-253`) формулирует четыре правила для
`parent`: обращение не может быть собственным родителем, связь не может создавать цикл, глубина дерева
ограничена `Case.PARENT_MAX_DEPTH = 3` уровнями (`:191`), и ничего нельзя связывать со слитым
(`Duplicate`) обращением или от него. Поскольку на пути API `Case.clean()` не выполняется, все четыре
правила применяет `check_parent_link` из `cases/parent_guards.py`, который вызывают и
`CaseCreateSerializer.validate()` (когда запрос содержит `parent`), и эндпоинт связывания. Проверка
глубины учитывает поддерево, которое обращение приносит с собой. `validate_parent()`
(`cases/serializer.py:415-440`) дополнительно отклоняет родителя из другой организации или такого,
которого вызывающий не может открыть, с тем же сообщением, что и для неизвестного id.

`DELETE /api/cases/{id}/` (`cases/views.py:552-559`) вызывает `assert_case_delete_access`: только
администратор или создатель, без исключения для ответственного (см.
[выше](#a-cases-read-write-and-delete-rules-differ-on-purpose)).

## Комментарии и вложения {#comments-and-attachments}

Добавление комментария или вложения идёт через тот же маршрут `POST /api/cases/{id}/`, что использует
детальный эндпоинт, только с телом (`CaseDetailView.post`, `cases/views.py:765-825`), и ограничено
`assert_case_write_access` (`:771`), то есть тем же правилом, о котором сообщает `comment_permission` в
`GET`. Отправьте `comment` (текст и, при необходимости, `is_internal`, истинная строка или булево
значение) и/или `case_attachment` (файл multipart), одно из них или оба. Комментарий, созданный с
`is_internal=true`, является внутренней заметкой и не виден на клиентских поверхностях; ответ
раскладывает их обратно на `comments` (публичные) и `internal_notes` (`:817-822`), и оба возвращаются
любому вызывающему с правом чтения; на этом эндпоинте `is_internal` разделяет отображение, а не доступ.

Изменение или удаление *существующего* комментария идёт через `PUT`/`PATCH`/`DELETE /api/cases/comment/{id}/`
(`CaseCommentView`, `cases/views.py:862-994`). Доступно только администратору организации
(`is_org_admin`: роль `ADMIN`, суперпользователь тоже считается) или автору комментария
(`request.profile == obj.commented_by`, `:900`, `:946`, `:981`). `Comment.commented_by` является внешним
ключом на `Profile` (`common/models.py:414-416`), поэтому это сравнение корректно, в отличие от
некоторых сравнений `created_by` в других местах кода; см.
[Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks).

`object_id`, `org`, `content_type`, `commented_by` и `commented_by_contact` перечислены в
`read_only_fields` у `CommentSerializer` (`common/serializer.py:298-304`). К какой записи относится
комментарий, какой организации он принадлежит и кто его написал, решает сервер, а то, что первые два
поля раньше были доступны для записи, имело два последствия, которые стоит зафиксировать, поскольку
оба теперь закрыты:

- Автор комментария мог через `PATCH` изменить `object_id` и `org` и перенаправить свой комментарий на
  любую запись организации по id, включая обращение, к которому правила доступа его не пускают, или
  перенести его в другую организацию. `Comment.clean()` сравнивает новый `org` с `org` новой цели,
  поэтому *совпадающая* пара из чужой организации проходила эту проверку и сохранялась. Остановить это
  могла только политика RLS, а RLS является страховкой, а не контрактом.
- `PUT` вообще не мог изменить комментарий. `.put()` создаёт сериализатор без частичного режима,
  который требует каждое поле, не являющееся read-only, поэтому обычное тело `{"comment": "..."}` не
  проходило валидацию из-за отсутствующих `object_id`/`org` и получало `400`. Этот дефект был у четырёх
  обработчиков PUT.

Ответ клиента, написанный через [клиентский портал](customer-portal.md), приходит в `comments`, как
любой другой публичный комментарий, с двумя отличиями: `commented_by` равен `null`, потому что у клиента
нет `Profile`, а вместо него автора указывает `commented_by_contact`. Тот же `null` несёт ответ по
входящей почте, и именно его проверяют `_evaluate_reopen` и отметка SLA первого ответа, чтобы отличить
сообщение клиента от сообщения коллеги.

`DELETE /api/cases/attachment/{id}/` (`CaseAttachmentView.delete`, `cases/views.py:1013-1055`) находит
вложение только в обращении, которое вызывающий может открыть в своей организации
(`get_on_visible_record_or_404`, `:1036-1038`), поэтому вложение в скрытом обращении или в записи
другого модуля даёт тот же `404`, что и отсутствующий id, а проверка владельца сравнивает
`request.profile.user_id` с `self.object.created_by_id`, оба являются id `User`, типы совпадают
(`:1040-1043`). Docstring представления описывает два дефекта, которые были в этом самом эндпоинте до
исправления (поиск без ограничения по организации; сравнение `Profile` с `User`, из-за которого эндпоинт
молча стал доступен только администраторам). Сегодня здесь оба исправлены. Есть ли один из этих
дефектов в аналогичном эндпоинте другого приложения, решает само это приложение; проверяйте по текущему
коду того приложения, а не по этому docstring, который тоже устаревает. Актуальный ответ по всем
приложениям см. в разделе
[Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks).

## Согласования {#approvals}

Есть два вида эндпоинтов: правила, которые настраивает администратор, и запросы и решения по
конкретным обращениям в рамках этих правил (`cases/approval_views.py`). Правило (`ApprovalRule`,
`cases/approvals.py:47-116`) сопоставляется с обращением по `trigger_event` (сегодня существует только
`"pre_close"`) и, при необходимости, по `priority`, `case_type` и `team`. Побеждает наиболее конкретное
активное совпадение, а при равенстве самое новое (`find_matching_rule`, `:119-136`).

- `GET /api/cases/approval-rules/` (`ApprovalRuleListCreateView.get`, `approval_views.py:87-103`).
  Доступно любому участнику организации; каждая строка правила содержит `pending_count`, вычисленный по
  журналу `Approval`.
- `POST /api/cases/approval-rules/` (`:105-133`), только для администратора. Список согласующих и
  команда для сопоставления проверяются на принадлежность организации вызывающего перед сохранением
  (`:117-129`).
- `GET/PUT/DELETE /api/cases/approval-rules/{id}/` (`ApprovalRuleDetailView`, `:136-194`); `GET` доступен
  любому участнику; `PUT`/`DELETE` только администратору. Удаление правила с историей запросов не
  удаляет его физически, а мягко отключает (`is_active=False`) (`:183-192`), поскольку у `Approval.rule`
  задано `on_delete=PROTECT`.
- `POST /api/cases/{id}/request-approval/` (`CaseRequestApprovalView.post`). Обращение, которое
  вызывающий не может прочитать, даёт `404` (`get_case_or_404`, то же тело, что и для отсутствующего
  id), а для подачи запроса нужно правило записи обращения (`assert_case_write_access`, то самое
  правило, о котором сообщает `comment_permission`), поэтому читатель без права ответа получает `403`.
  Запрос привязывается к явно указанному `rule_id` (правило должно быть активным и соответствовать
  обращению) или, если он не указан, к результату `find_matching_rule`, то есть к правилу, которое
  называет `approval_rule` в карточке; отсутствие подходящего правила даёт `400`. Второй запрос по той же
  паре «обращение и правило», пока первый находится в состоянии `pending`, отклоняется с `409`, а не
  создаёт дубликат. Ответ `201` представляет собой `ApprovalSerializer(approval).data`.
- `GET /api/cases/approvals/` (`ApprovalInboxView.get`), входящая очередь. Строка показывается, если
  вызывающий является администратором организации, может прочитать обращение, входит в пул согласующих
  правила или подал запрос (`_visible_approvals`): у согласующего обычно нет другого отношения к
  обращению, а принять решение и есть смысл очереди. `?state=` фильтрует (по умолчанию `pending`; `all`
  снимает фильтр), `?case=<id>` ограничивает одним обращением (панель на странице обращения в обоих
  клиентах), а `?mine=true` оставляет только строки, по которым вызывающий может действовать сейчас, и
  намеренно исключает собственные запросы вызывающего: «мне решать», а не «я подал».

Согласование, отклонение и отмена находят согласование по тому же правилу видимости, что и входящая
очередь. Согласование, которое вызывающий не видит, даёт `404` с тем же телом, что и отсутствующий id,
поэтому эти эндпоинты не могут подтвердить существование скрытого согласования; правила ниже относятся
только к согласованиям, которые вызывающий видит.

**И согласование, и отклонение требуют, чтобы запросивший не был согласующим, без исключения для
администратора.** `ApprovalApproveView.post` (`:354-407`) и `ApprovalRejectView.post` (`:410-475`) оба
проверяют по порядку: согласование всё ещё в состоянии `pending` (иначе `400`); вызывающий входит в пул
согласующих правила через `can_be_acted_on_by` (иначе `403`); и отдельно
`approval.requested_by_id == request.profile.id` (иначе `403`, «You cannot approve/reject your own
request; another approver must decide it.», `:382-390` и `:443-451`). Комментарий в обоих местах прямо
говорит, что это действует даже для «администратора, который по умолчанию входит в пул каждого
правила»: быть согласующим и быть запросившим для одного решения взаимоисключающе, независимо от роли.
Сам `Approval.can_be_acted_on_by` (`cases/approvals.py:188-196`) истинен, если профиль явно указан в
`rule.approvers` **или** `profile.role == rule.approver_role`. Обратите внимание, что второе условие
проверяет только `role`, а не флаг `is_organization_admin`, который `is_org_admin` в других местах кода
тоже считает признаком администратора, поэтому профиль, являющийся администратором только через этот
флаг, не становится согласующим автоматически, пока его явно не добавят в `rule.approvers`.

`ApprovalSerializer.can_act` и `.is_own_request` (`cases/serializer.py:1359-1384`) в точности повторяют
проверки эндпоинта согласования, поэтому клиент, отображающий входящую очередь по ответу списка,
получает тот же ответ, что дали бы эндпоинты действий. Обоим нужен `context={"request": request}`; без
него они по умолчанию равны `False`, и комментарий к сериализатору отмечает, что это безопасное значение
по умолчанию, а не ошибка.

`POST /api/cases/approvals/{id}/cancel/` (`ApprovalCancelView.post`, `:478-518`) подчиняется **другому**
правилу, чем согласование и отклонение: отменить может только исходный запросивший или администратор
(`:498-505`). Ограничения «не запросивший» здесь нет, потому что отмена собственного запроса является
обычным случаем.

## Статьи базы знаний {#solutions}

База знаний (`cases/solution_views.py`, `cases/kb_access.py`). Чтение намеренно открыто всей
организации. Каждый участник может читать каждую статью («база знаний, статьи которой скрыты от
сотрудников, отвечающих на обращения, не является базой знаний», docstring модуля
`cases/kb_access.py`), но запись и выпуск подчиняются двум разным, более узким правилам:

```
write     author · admin      title, body, and moving draft ↔ reviewed
release   admin               status → approved, and publish / unpublish
delete    author · admin
```

`release` намеренно уже, чем `write`: процесс проверки (`draft → reviewed → approved` плюс отдельный
флаг `is_published`) имеет смысл, только если тот, кто одобряет статью, не является её автором.
`assert_solution_release_access` вообще не принимает статью в качестве аргумента. Авторство как раз
единственное, что не должно давать это право (`cases/kb_access.py:76-86`).

`GET /api/cases/solutions/` (`SolutionListView.get`, `cases/solution_views.py:120-180`) единственный
эндпоинт этого API, который вызывает `get_paginated_response()` из DRF и возвращает его стандартную
обёртку `count`/`next`/`previous`/`results`; раздел [Соглашения](conventions.md#pagination) называет
именно этот эндпоинт единственным примером. Он добавляет один дополнительный ключ верхнего уровня,
`totals` (`count`/`published`/`draft`/`reviewed`/`approved_unpublished`), который вычисляется по *всей*
базе знаний, а не по текущему фильтру, чтобы четыре карточки статусов оставались осмысленными при
фильтре `?status=` (`:165-177`). Фильтры: `?status=`, `?is_published=` (принимает
`true`/`1`/`yes`/`on`, а не только буквальную строку `"true"`), `?search=` (заголовок или описание,
вхождение) и `?tags=` (id тегов через запятую, совпадение с любым из них, с `distinct()`, чтобы статья
с двумя такими тегами не возвращалась дважды).

`POST /api/cases/solutions/` (`:186-208`) открыт любому участнику для обычного черновика, но
ограничивается `assert_solution_release_access`, как только запрос создал бы уже `approved` или уже
`is_published` статью за один раз (`_wants_release`, `:32-50`): без этого автор мог бы написать и
опубликовать статью одним `POST`, полностью обойдя процесс проверки.

`GET/PUT/PATCH/DELETE /api/cases/solutions/{id}/` (`SolutionDetailView`, `:210-278`): `GET` открыт
любому участнику; `PUT`/`PATCH` требуют `assert_solution_write_access` (автор или администратор) и
снова `assert_solution_release_access`, если запрос переводит статью в `approved` или меняет
`is_published`; `DELETE` требует того же правила записи (а не отдельного, более узкого: удаление
собственного черновика является обычной уборкой).

**Теги.** Статьи используют те же `Tags` в рамках организации, что и лиды, сделки и обращения. Они
возвращаются в ответах списка и карточки как `tags` и записываются передачей `tags` (списка id тегов) в
`POST` или `PATCH`. Запись обрабатывается в представлении, а не в сериализаторе, поэтому фильтр по
организации неизбежен: id разрешаются через `Tags.objects.filter(org=…, is_active=True)`, и id из другой
организации не находится, а не привязывается.

Отсутствие ключа означает «без изменений», и только явный `"tags": []` очищает теги. Это намеренно
отличается от эндпоинтов обращений, где набор тегов очищается и строится заново всякий раз, когда ключ
обрабатывается, так что `PATCH`, который вообще не упоминает теги, их сбрасывает.

Названия тегов видны **только сотрудникам**. Они определяют `related` в эндпоинте статей портала, но
никогда не попадают в ответы портала, потому что словарь общий со сделками и выглядит как «At Risk» и
«VIP». См. [Клиентский портал](customer-portal.md#help-articles).

**Публикация доходит до клиентов.** Статья, которая одновременно `approved` и `is_published`, доступна
для чтения любому вошедшему контакту портала в организации и предлагается ему при подаче запроса, а
также питает подсказки для сотрудников. Снятие с публикации отзывает и то, и другое.

`POST /api/cases/solutions/{id}/publish/` и `POST /api/cases/solutions/{id}/unpublish/`
(`SolutionPublishView`/`SolutionUnpublishView`, `:281-336`) оба требуют
`assert_solution_release_access`. Публикация дополнительно требует `status == "approved"` (иначе
`400`); комментарий к представлению снятия с публикации прямо говорит, что убрать плохой ответ является
*тем же* переключателем, что и выдать его клиентам, и поэтому ограничено так же, хотя довод о срочности
работает в обратную сторону.

Чтение статей, связанных с обращением, не является отдельным эндпоинтом. Связанный набор возвращается в
составе `GET /api/cases/{id}/` (ключ `solutions`, [выше](#retrieve-update-delete)). Связывание
выполняется через `POST /api/cases/{id}/solutions/`, а отвязывание через
`DELETE /api/cases/{id}/solutions/{solution_id}/` (`CaseSolutionLinkView`, `cases/views.py:1058-1134`),
оба ограничены `assert_case_write_access` для *обращения*: комментарий к `.post` отмечает, что это
закрывает обходное чтение. До этой проверки участник, которому обращение отвечало `403`, всё равно мог
привязать к нему статью и затем прочитать название, описание, компанию и контакты обращения через
`linked_cases` этой статьи. Сторона чтения той же уязвимости закрыта в
`SolutionDetailSerializer.get_linked_cases` из `cases/solution_serializers.py`, который пропускает
возвращаемые обращения через тот же `visible_cases_qs`, что используют список и карточка обращений, а не
возвращает все обращения, с которыми статья оказалась связана.

## Импорт CSV {#csv-import}

Два эндпоинта, доступные администраторам организации или участникам с `has_sales_access`
(`can_mass_import` в `common/permissions.py`). Все остальные получают `403`.

`POST /api/cases/import/preview/` (`CaseImportPreviewView`, `import_views.py:56-88`) читает загрузку
`multipart/form-data` в поле `file` (требуется расширение `.csv`). Ограничение в 5 МБ проверяется по
`upload.size`, то есть по размеру загруженного файла, который сообщает Django и который доступен до
вызова `.read()`, **а не** по фактически прочитанным байтам, а когда `upload.size` ложно, проверка
вообще пропускается (`if upload.size and upload.size > MAX_UPLOAD_BYTES`, `import_views.py:48-51`).
Затем проверяется каждая строка, при этом ничего не записывается. Номера строк начинаются с 1 и
считаются по строкам *данных*, а не по строкам файла. Заголовок никогда не учитывается, поэтому первая
строка данных имеет `"row": 1` (`enumerate(data_rows, start=1)` по `rows[1:]`,
`services/csv_import.py:216-217`):

```json
{
  "header_error": null,
  "valid": [
    {
      "row": 1, "name": "Cannot log in", "status": "New", "priority": "High",
      "description": "", "case_type": "Incident", "closed_on": null,
      "account_id": "<uuid or null>", "contact_ids": [], "assigned_ids": [],
      "team_ids": [], "tag_names": []
    }
  ],
  "errors": [{"row": 2, "field": "status", "message": "Status must be one of: New, Assigned, Pending, Closed, Rejected, Duplicate"}],
  "summary": {"total": 2, "valid": 1, "invalid": 1}
}
```

`POST /api/cases/import/commit/` (`CaseImportCommitView`, `:91-125`) заново проверяет тот же файл и
записывает все корректные строки в одной транзакции; **если хотя бы одна строка не прошла проверку,
ничего не записывается** (`commit_rows` в `services/csv_import.py`: «Don't write anything if any row
failed; users must fix the file first»). При успехе (`200`):
`{"error": false, "created": 12, "ids": ["<uuid>", "..."]}`.

Обязательные заголовки: `name`, `status`, `priority`. Распознаваемые необязательные заголовки:
`description`, `case_type`, `account_name`, `contact_emails`, `assigned_emails`, `team_names`, `tags`,
`closed_on` (`REQUIRED_HEADERS`/`OPTIONAL_HEADERS`, `services/csv_import.py:36-46`). Неизвестный
заголовок или отсутствие обязательного проваливает весь файл с `header_error` ещё до проверки строк.
`contact_emails`, `assigned_emails` и `team_names` принимают несколько значений в ячейке через `;` и
должны соответствовать существующему контакту, активному участнику или команде в организации
вызывающего, иначе строка получает ошибку (`:396-438`). `status`/`priority`/`case_type` сопоставляются
без учёта регистра с теми же наборами вариантов, которые раздел [Поля](#fields) описывает для самого API.
Название обращения должно быть уникальным в пределах организации, и это проверяется как по
существующим обращениям, так и по более ранним строкам того же файла (`:338-355`). Файл ограничен 5000
строками данных (`MAX_ROWS`, `:49`).

## Поля {#fields}

`CaseCreateSerializer.Meta.fields` (`cases/serializer.py:442-458`) определяет, что принимают
`POST /api/cases/`, `PUT /api/cases/{id}/` и `PATCH /api/cases/{id}/`. «Обязательно» ниже означает
обязательность на `POST` и на `PUT` (который работает не в частичном режиме); `PATCH` передаёт
`partial=True`, поэтому там ничего не обязательно: см.
[Получение, изменение, удаление](#retrieve-update-delete).

| Поле | Тип | Обязательность | Примечания |
| --- | --- | --- | --- |
| `name` | string, max 64 | **обязательно** (POST/PUT) | Уникально в пределах организации без учёта регистра |
| `status` | одно из `STATUS_CHOICE` | **обязательно** (POST/PUT) | `New`, `Assigned`, `Pending`, `Closed`, `Rejected`, `Duplicate` |
| `priority` | одно из `PRIORITY_CHOICE` | **обязательно** (POST/PUT) | `Low`, `Normal`, `High`, `Urgent` |
| `case_type` | одно из `CASE_TYPE` | необязательно | `Question`, `Incident`, `Problem` |
| `closed_on` | date | необязательно | У закрытого обращения дата есть всегда: отправленная дата имеет приоритет, отсутствующая или `null` сохраняет записанную, иначе ставится сегодняшний день в часовом поясе организации. См. [Получение, изменение, удаление](#retrieve-update-delete) |
| `description` | text | необязательно | |
| `is_active` | boolean | необязательно | По умолчанию `true`; флаг мягкого удаления, по умолчанию скрыт из `GET /api/cases/` |
| `account` | uuid | необязательно при создании; **задаётся один раз** | Должно принадлежать организации вызывающего; на `PUT`/`PATCH` молча становится `read_only`. См. [Получение, изменение, удаление](#retrieve-update-delete) |
| `custom_fields` | object | необязательно | Проверяется по строкам `CustomFieldDefinition` организации |
| `parent` | uuid | необязательно | Из той же организации и доступно вызывающему для чтения; не само обращение, без циклов, не более 3 уровней, без слитых обращений с обеих сторон. См. [выше](#retrieve-update-delete) |
| `is_problem` | boolean | необязательно | По умолчанию `false`; помечает обращение как «problem» по ITIL (обобщающее) |
| `org` |. | **только чтение** | Определяется сервером из `request.profile.org`; указано в `Meta.fields`, но недоступно для записи |

Не входят в сериализатор, но принимаются в том же теле запроса и разрешаются представлением (каждое
представляет собой список id в рамках организации): `contacts`, `teams`, `assigned_to`, `tags`. Разбор
одинаков на каждом методе (см. [Создание обращения](#create-a-case)), а *запись* нет, и эта разница
становится настоящей ловушкой с потерей данных: `POST` только добавляет. `PUT` заменяет все четыре
M2M-связи **безусловно** (`.clear()` для команд, ответственных и тегов и `replace_visible_contacts` для
контактов) ещё до проверки, упоминались ли они в запросе вообще (`views.py:496,500,506,514`), поэтому
`PUT` без `assigned_to` в теле снимает с обращения всех ответственных, а не оставляет их без изменений.
`PATCH` очищает конкретную M2M-связь, только если её ключ вообще присутствует в теле
(`if "assigned_to" in data:` в `update_case`, `cases/updates.py`, и так же для остальных трёх).
Отсутствие ключа в `PATCH` действительно оставляет связь нетронутой. `case_attachment` (файл multipart)
принимается на `POST` и `PUT` (`views.py:391,521`), но **не на `PATCH`**; `CaseDetailView.patch` вообще
не читает `request.FILES`, поэтому multipart-запрос `PATCH` с `case_attachment` молча теряет файл без
ошибки.

`GET /api/cases/{id}/` и `GET /api/cases/` дополнительно возвращают, но никогда не принимают на вход:
`id`, `created_by`, `created_at`, `escalation_count`, `last_escalation_fired_at`, поля SLA
(`sla_first_response_hours`, `sla_resolution_hours`, `first_response_at`, `resolved_at`,
`sla_paused_at`, `first_response_sla_deadline`, `resolution_sla_deadline`,
`is_sla_first_response_breached`, `is_sla_resolution_breached`), `parent_summary`, `child_count` и
`time_summary` (`CaseSerializer.Meta.fields`, `cases/serializer.py:239-281`).
