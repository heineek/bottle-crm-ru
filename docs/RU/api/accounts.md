# Компании

Маршруты в `backend/accounts/urls.py`, все обслуживаются `backend/accounts/views.py`. Правила
пагинации, фильтрации и структуры ответа, которые здесь подразумеваются и не повторяются, описаны в
разделе [Соглашения](conventions.md), а принцип «404 или 403» в разделе [Ошибки](errors.md).

## Список компаний {#list-accounts}

`GET /api/accounts/` (`AccountsListView.get`, `backend/accounts/views.py:312-314`) делит результат на
активные и неактивные компании, а не на открытые и закрытые: у `Account` нет поля статуса, только
`is_active` (`accounts/views.py:237-238`):

```json
{
  "per_page": 10,
  "page_number": [1],
  "active_accounts": {"offset": 10, "open_accounts": [ { "...": "AccountSerializer" } ], "open_accounts_count": 37},
  "closed_accounts": {"offset": null, "close_accounts": [ { "...": "..." } ], "close_accounts_count": 4},
  "contacts": [{"id": "...", "first_name": "..."}],
  "teams": [{"...": "..."}],
  "countries": [["GB", "United Kingdom"]],
  "industries": [["SOFTWARE", "SOFTWARE"]],
  "tags": [{"...": "..."}],
  "users": [{"id": "...", "user__email": "..."}],
  "leads": [{"...": "LeadSerializer"}],
  "status": ["active", "inactive"]
}
```

Вызывающий без прав администратора видит только компании, которые он создал или за которые отвечает
(`accounts/views.py:195-199`). Фильтры: `name`, `city`, `industry` (все `icontains`); `tags`,
`assigned_to` (можно повторять, `__id__in`); `search` (ищет только по `name`, в отличие от `search`
у лидов, который объединяет через OR четыре поля); `created_at__gte`/`created_at__lte`; `cf_<key>`
(`accounts/views.py:201-233`).

Каждая компания в списке (и в детальном просмотре ниже) содержит объект **`rollups`**:
`won_amount`, `won_count`, `open_pipeline`, `open_deal_count`, `overdue_amount`, `open_tickets`,
`first_won_on`. Они вычисляются коррелированными подзапросами по строкам `Opportunity`, `Invoice` и
`Case` этой компании и никогда не хранятся (`annotate_rollups` для количеств, `attach_money_rollups`
для денежных сумм). У сделок и счетов есть своя валюта, а курсов обмена нет, поэтому три денежных
поля никогда не суммируются по разным валютам: каждое содержит простое число, если валюта не больше
одной, и `null`, если их несколько, а `rollups.by_currency` в любом случае перечисляет
`{currency, won_amount, open_pipeline, overdue_amount}` по каждой валюте (сделка без валюты
учитывается в `default_currency` организации). `rollups` равен `null`, а не заполнен нулями, в любой
сериализации, которая пропускает аннотацию (`AccountSerializer.get_rollups`,
`accounts/serializer.py:41-54`); оба эндпоинта здесь, список и детальный просмотр, её применяют,
поэтому на практике через эндпоинты этой страницы вы всегда увидите его заполненным.

## Создание компании {#create-an-account}

`POST /api/accounts/` (`AccountsListView.post`, `accounts/views.py:322-400`) проверяется
сериализатором `AccountCreateSerializer` (`accounts/serializer.py:189-257`); см. [Поля](#fields). При
успехе (`200`):

```json
{"error": false, "message": "Account Created Successfully", "id": "<uuid>"}
```

Два валидатора, о которых стоит знать: **`name` должно быть уникальным в пределах организации без
учёта регистра** (`validate_name`, `accounts/serializer.py:199-210`); при дубликате возвращается
`{"error": true, "errors": {"name": ["Account already exists with this name"]}}`; и
**`annual_revenue` не может быть отрицательным** (`validate_annual_revenue`, `:212-224`), такое
значение отклоняется с `400`, а не доходит до собственного ограничения базы данных
`account_revenue_non_negative` и не превращается в необработанный `500`.

`contacts`, `tags`, `teams` и `assigned_to` не входят в сериализатор. Каждое из них представляет
собой список id (в multipart-теле это список в кодировке JSON), той же формы, что принимают `PUT` и
`PATCH`, и представление разрешает их в пределах `org=request.profile.org`: id из другой организации
или несуществующий id игнорируется, а некорректный id приводит к `400` с указанием поля. `tags`
разбирается до сохранения компании; остальные три разрешает `handle_m2m_assignment` в
`common/utils.py`. Id существующего тега прикрепляет этот тег и не создаёт новых. Multipart-файл
`account_attachment` принимается так же.

## Получение, изменение, удаление {#retrieve-update-delete}

`GET /api/accounts/{id}/` (`AccountDetailView.get`, `accounts/views.py:604-704`) ищет запись только
в организации вызывающего и обрабатывает некорректный id так же, как отсутствующий. В обоих случаях
`404` (`get_object`, `:407-421`, перехватывает `ValidationError` от `UUIDField`, который один лишь
`get_object_or_404` не ловит). Затем `assert_account_access` (`:423-445`) требует, чтобы вызывающий
был администратором, создателем компании или одним из ответственных, иначе запрос отклоняется с
`403`. Ответ вкладывает запись под ключ `account_obj` и также содержит `contacts` (`Account.contacts`,
а не внешний ключ `Contact.account`. См. [Контакты: связанные компании](contacts.md#fields)),
`opportunity_list`, `cases`, `tasks`, `invoices`, `emails`, `comments`, `attachments`, `teams`,
`users`, `users_mention`, `comment_permission`, `leads`, `countries`, `currencies`, `case_types`,
`case_priority`, `case_status`, `custom_field_definitions`, фиксированный список из двух значений
`status: ["open", "close"]` (`accounts/views.py:692`: статический список, не связанный с
`Account.is_active`, который на самом деле и определяет деление на активные и неактивные в
[списке компаний](#list-accounts)), а также два ключа, на которые стоит обратить отдельное внимание:

```json
{
  "stages": [["PROSPECTING", "Prospecting"], ["QUALIFICATION", "Qualification"], ["CLOSED_WON", "Closed Won"]],
  "sources": [["NONE", "NONE"], ["CALL", "CALL"], ["WEBSITE", "WEBSITE"], ["OTHER", "OTHER"]]
}
```

(`accounts/views.py`.) `stages` содержит этапы воронки сделок организации по умолчанию в виде пар
`[code, label]`, а `sources` представляет собой фиксированный набор из восьми ключей источников.
Оба отдаются здесь потому, что на странице компании находится форма «добавить сделку для этой
компании», а не потому, что у компании есть свои этапы или источники. Собственный список
организации, по которому проверяется `lead_source` сделки, описан в разделе
[Источники лидов](leads.md#lead-sources).

`PUT /api/accounts/{id}/` (`:453-575`) и `PATCH /api/accounts/{id}/` (`:763-871`) оба вызывают
`assert_account_access` **до** проверки тела запроса, намеренно: вызывающий без доступа узнаёт, что
ему запрещено, раньше, чем узнаёт, корректен ли его payload (`accounts/views.py:456-459`). Оба
принимают ту же обработку M2M `contacts`/`tags`/`teams`/`assigned_to` и загрузку
`account_attachment`, что и создание. Успех:
`{"error": false, "message": "Account Updated Successfully"}`.

Ответ детального просмотра также содержит `can_delete`: будет ли принят `DELETE` от этого
вызывающего, чтобы клиент предлагал это действие только в таком случае.

`DELETE /api/accounts/{id}/` (`:582-597`) разрешён администратору или создателю компании
(условие отказа `request.profile.user_id != self.object.created_by_id`, `:584-591`).
Все остальные получают `403`.

## Комментарии и вложения {#comments-and-attachments}

`POST /api/accounts/{id}/` (`AccountDetailView.post`, `accounts/views.py:712-755`) добавляет
комментарий и/или файл `account_attachment` к существующей компании и проверяется тем же правилом
`assert_account_access`, что и `GET`/`PUT`/`PATCH` (`:719`). Ответ возвращает `account_obj`,
`attachments` и `comments`.

`PUT` / `PATCH` / `DELETE /api/accounts/comment/{id}/` (`AccountCommentView`,
`accounts/views.py:874-968`) доступны только администратору или автору комментария
(`request.profile == obj.commented_by`. Это корректно, поскольку `commented_by` является внешним
ключом на `Profile`).

У `DELETE /api/accounts/attachment/{id}/` (`AccountAttachmentView.delete`, `:971-1010`) поиск
корректно ограничен организацией вызывающего
(`get_object_or_404(self.model, pk=pk, org=self.request.profile.org)`, `:989-991`, некорректные id
тоже превращаются в `404`), а проверка владельца сравнивает значения правильных типов
(`request.profile.user_id == self.object.created_by_id`, `:997`). Поэтому компании входят в пять
приложений этого API, где поиск при удалении вложения ограничен организацией. То же верно для
контактов (`contacts/views.py:1046`), обращений (`cases/views.py:1119-1121`), задач
(`tasks/views/task_views.py:975-977`) и счетов (`invoices/api_views.py:1821`). Только у **лидов и
сделок** по-прежнему версия без ограничения по организации. См.
[Лиды: комментарии и вложения](leads.md#comments-and-attachments) и
[Архитектура: права и роли](../architecture/permissions-and-roles.md#object-level-checks).
(Один устаревший комментарий в `cases/views.py` утверждает, что у задач это всё ещё сломано. Это не
так: исправление вошло, а комментарий не обновили. Проверено непосредственно по
`tasks/views/task_views.py:975-987`, а не принято на веру из комментария.)

## Дубликаты и объединение {#duplicates-and-merging}

`POST /api/accounts/duplicates/` принимает в теле JSON поля, которые пользователь уже ввёл в форму
создания (`name`, `email`, `phone`, `website`), и отвечает `{"duplicates": [...]}`: не более 10
активных компаний, сначала самые новые. `GET /api/accounts/{id}/duplicates/` возвращает такой же
список для сохранённой компании, исключая саму компанию, плюс `can_delete` для этой компании. Каждое
совпадение содержит только `id`, `name`, `email`, `phone`, `matched_on` (правила, по которым оно
совпало) и `can_delete` (может ли вызывающий поглотить её объединением), но никогда не саму запись.
Оба ищут только среди компаний, которые вызывающий может открыть, поэтому скрытая компания не
выводится и не учитывается, а скрытый или отсутствующий `{id}` даёт одинаковый `404`. Значение
длиннее допустимого моделью даёт `400`. Проверка из формы создания сделана как `POST`, который ничего
не записывает, чтобы адрес электронной почты и номер телефона никогда не попадали в URL и в журналы
доступа, которые его записывают. Начиная с django-crm 1.13.0 токену для неё нужна только область
`read` модуля (`accounts:read`), поскольку она ничего не записывает; раньше требовалась
`accounts:write`. Ограничение частоты: 120 запросов в минуту на пользователя, а клиенты применяют
debounce с запасом ниже этого порога.

Сопоставление: email без учёта регистра; название после отбрасывания регистра, пунктуации, начального
«The» и конечного юридического суффикса («Inc», «Ltd», «LLC», …), поэтому «Acme» находит «ACME,
Inc.», но не «Acme Widgets»; хост веб-сайта без учёта схемы, «www.» и пути. Номера телефонов
сравниваются по последним десяти цифрам (или по всем цифрам более короткого номера, минимум семи)
независимо от разделителей.

`POST /api/accounts/{id}/merge/` с `{"merge_id": "<uuid>"}` объединяет компанию, указанную в теле, с
компанией из URL. Вызывающий должен иметь возможность открыть обе (если одна скрыта или отсутствует,
это одинаковый `404`), должен иметь право редактировать сохраняемую (для компаний это любой, кто
может её открыть) и должен подпадать под правило удаления для поглощаемой (администратор,
суперпользователь или её создатель), иначе `403`. Объединение компании с самой собой, а также
отсутствующий или некорректный `merge_id` дают `400`. На время объединения обе строки блокируются,
а само объединение выполняется в одной транзакции:

- Каждая связь с поглощаемой компанией переходит к сохраняемой: контакты (обе связи), сделки,
  обращения, заказы, счета, коммерческие предложения, регулярные счета, задачи, карточки на досках, а
  также письма компании, комментарии, вложения и активность. Связь, которая у сохраняемой компании
  уже есть, не дублируется.
- Побеждают значения сохраняемой компании. Её пустые поля, включая дополнительные поля по каждому
  ключу, получают значения другой; владельцы (`assigned_to`, `teams`) берутся, только если у
  сохраняемой компании их нет; теги и связанные контакты объединяются из обеих.
- Затем поглощённая компания удаляется, что отправляет обычный вебхук `account.deleted`, а в журнал
  аудита записывается строка `RECORD_MERGED` с обоими id и обоими названиями. Отмены нет. Начиная с
  django-crm 1.13.0 поле `assigned_to` этого вебхука перечисляет владельцев, которые были у
  поглощённой компании до объединения, даже если они перешли к сохраняемой; раньше оно формировалось
  после переноса и могло оказаться пустым.

Ответ: `{"error": false, "message": "...", "id": "<kept id>"}`.

## Поля {#fields}

`AccountCreateSerializer.Meta.fields` (`accounts/serializer.py:226-249`) определяет, что принимают
`POST /api/accounts/`, `PUT /api/accounts/{id}/` и `PATCH /api/accounts/{id}/`. На уровне модели
обязательно только `name` (`accounts/models.py:26`, без `blank=True`); у всех остальных полей этого
сериализатора есть `blank=True, null=True` или значение по умолчанию.

| Поле | Тип | Обязательно | Примечания |
| --- | --- | --- | --- |
| `name` | string | **обязательно** | Уникально в пределах организации без учёта регистра |
| `email` | string | необязательно | |
| `phone` | string | необязательно | |
| `website` | string | необязательно | `URLField`, проверяется как URL, в отличие от `Lead.website` (см. [Лиды](leads.md#fields)) |
| `industry` | одно из `INDCHOICES` | необязательно | например, `SOFTWARE` |
| `number_of_employees` | integer | необязательно | Неотрицательное (`PositiveIntegerField`) |
| `annual_revenue` | decimal | необязательно | Неотрицательное, проверяется в сериализаторе, а не только в БД |
| `currency` | одно из `CURRENCY_CODES` | необязательно | Если не передано, а `annual_revenue` задано, берётся из `default_currency` организации |
| `address_line`, `city`, `state`, `postcode` | string | необязательно | |
| `country` | одно из `COUNTRIES` | необязательно | |
| `description` | text | необязательно | |
| `is_active` | boolean | необязательно | По умолчанию `true` |

Не входят в сериализатор, но принимаются в том же запросе и разрешаются представлением (см.
[Создание компании](#create-an-account)): `contacts`, `tags`, `teams`, `assigned_to` (каждое список
id, ограниченный организацией) и `account_attachment` (multipart-файл).

`GET /api/accounts/` и `GET /api/accounts/{id}/` дополнительно возвращают, но никогда не принимают на
вход: `id`, `created_by`, `created_at`, `org` (вложенный), `country_display`, `account_attachment`,
`cases`, `tasks`, `opportunities`, `rollups` (см. [Список компаний](#list-accounts)) и `custom_fields`
(проверяется отдельно по строкам `CustomFieldDefinition` организации).
