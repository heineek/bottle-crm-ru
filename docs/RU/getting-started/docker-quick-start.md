# Быстрый старт с Docker

Самый быстрый способ запустить BottleCRM локально: Docker Compose. Он поднимает PostgreSQL, Redis,
Django API, два процесса Celery и фронтенд на SvelteKit из одного файла, а конфигурацию берёт из
добавленного в репозиторий `.env.docker`.

## Требования {#prerequisites}

- Docker Engine с плагином Compose v2 (подкоманда `docker compose`, а не отдельный бинарный файл
  `docker-compose`: `docker-compose.yml` написан для плагина).
- Клон репозитория с `docker-compose.yml` в корне.

## Клонирование и настройка {#clone-and-configure}

Все команды ниже выполняются из корня репозитория, то есть из каталога, где лежат
`docker-compose.yml` и `Dockerfile`.

`.env.docker` добавлен в репозиторий с рабочими значениями по умолчанию для разработки и
загружается каждым сервисом в `docker-compose.yml`. Чтобы получить работающий стек, ничего
копировать или править не нужно. Если вы хотите переопределить значение локально (например,
добавить учётные данные Google OAuth), создайте рядом `.env.docker.local`: `docker-compose.yml`
загружает его как необязательный второй `env_file`, игнорируемый git, и его значения имеют
приоритет над `.env.docker`.

Переменные, которые на самом деле задаёт `.env.docker`:

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | Секретный ключ Django. Поставляемое значение является небезопасной заглушкой для разработки. |
| `DEBUG` | `True` в compose-файле для разработки. Это же позволяет запускать `devlogin` (см. [Первый вход](first-sign-in.md)). |
| `ENV_TYPE` | `dev`. |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1,backend`. |
| `DOMAIN_NAME` | `http://localhost:8000`. |
| `DBNAME`, `DBUSER`, `DBPASSWORD`, `DBHOST`, `DBPORT` | Параметры подключения, по которым контейнеры Django `backend` (и Celery) обращаются к `db`. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Используются только самим сервисом `db`, чтобы создать базу данных и собственную роль суперпользователя. |
| `CELERY_BROKER_URL`, `CELERY_RESULT_BACKEND` | Оба указывают на сервис `redis`, база данных `0`. |
| `DEFAULT_FROM_EMAIL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Консольный бэкенд почты (для разработки) и учётные данные для создания суперпользователя админки Django. См. [Что вы получили](#what-you-got). |
| `CORS_ALLOW_ALL` | `True` для локальной разработки. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | По умолчанию пусты; вход через Google отключён, пока не заданы оба. Redirect URI не является настройкой: фронтенд передаёт его в теле запроса при каждом вызове. |
| `PUBLIC_DJANGO_API_URL` | Адрес API, к которому обращается серверный код фронтенда, `http://backend:8000`. Используется имя сервиса compose, потому что `localhost` внутри контейнера фронтенда означает сам этот контейнер. Ваш браузер по-прежнему обращается к API по `http://localhost:8000`. |

## Запуск стека {#start-the-stack}

```bash
docker compose up --build
```

Команда собирает и запускает шесть сервисов, определённых в `docker-compose.yml`:

| Сервис | Образ / сборка | Порт на хосте |
|---|---|---|
| `db` | `postgres:16-alpine` | `5432` |
| `redis` | `redis:7-alpine` | `6379` |
| `backend` | собирается из `Dockerfile` в корне репозитория | `8000` |
| `celery-worker` | тот же образ, что у `backend`, запускает `celery -A crm worker --loglevel=info` |. |
| `celery-beat` | тот же образ, что у `backend`, запускает `celery -A crm beat --loglevel=info` |, |
| `frontend` | собирается из `frontend/Dockerfile` | `5181` |

`backend`, `celery-worker` и `celery-beat` перед запуском ждут, пока `db` и `redis` не сообщат о
работоспособности. Точка входа контейнера `backend` (`docker/backend/entrypoint.sh`) ждёт, пока
PostgreSQL начнёт принимать подключения, выполняет `migrate`, выполняет `create_default_admin`,
собирает статические файлы и затем запускает dev-сервер Django на `0.0.0.0:8000`.

**Роль базы данных важна.** `db` запускается под суперпользователем `postgres` (из
`POSTGRES_USER`). Эта учётная запись существует только для того, чтобы контейнер мог создать базу
данных `crm_db`. При первом запуске автоматически выполняется `docker/postgres/init-rls-user.sql`
(через механизм Postgres `/docker-entrypoint-initdb.d/`), который создаёт вторую роль без прав
суперпользователя, `crm_user`, и выдаёт ей нужные привилегии на `crm_db`. Контейнеры Django
подключаются как `crm_user` (`DBUSER` в `.env.docker`) и никогда как `postgres`. Это обязательно, а
не случайно: при подключении суперпользователя PostgreSQL Row-Level Security полностью обходится,
поэтому если бы приложение когда-нибудь подключилось как `postgres`, все политики RLS в схеме
молча перестали бы действовать, и изоляция тенантов держалась бы только на фильтрации в коде
приложения.

## Миграции и заполнение данными {#migrate-and-seed}

`entrypoint.sh` уже выполняет `migrate` при каждом запуске контейнера, поэтому схема актуальна, как
только `backend` сообщает, что принимает запросы. Чтобы загрузить демоданные, запустите заполнение
внутри работающего контейнера `backend`:

```bash
docker compose exec backend python manage.py seed_data --email you@example.com
```

`seed_data` создаёт организацию **`MicroPyramid`** (первая создаваемая им организация всегда
называется так, чтобы при локальной разработке было известное, стабильное имя для входа) и
**профиль администратора** для пользователя, переданного в `--email`, а также полный набор
демонстрационных лидов, компаний, контактов, сделок, обращений, задач, счетов и прочего. Повторный
запуск команды использует существующие организацию `MicroPyramid` и пользователя-администратора, а
не создаёт дубликаты.

Миграции можно запустить и вручную, так же, как любую другую команду управления в контейнере:

```bash
docker compose exec backend python manage.py migrate
```

## Вход {#sign-in}

При `DEBUG=True` (значение по умолчанию в `.env.docker`) быстрее всего войти через `devlogin`,
команду управления, которая выпускает пару JWT напрямую, без Google OAuth и почты. Все
подробности, включая то, как она разбирает `--org` и что требует от целевого пользователя,
описаны в разделе [Первый вход](first-sign-in.md). Для только что созданных организации и
пользователя:

```bash
docker compose exec backend python manage.py devlogin you@example.com --org MicroPyramid
```

Команда выводит access-токен, refresh-токен и UUID организации `MicroPyramid`, уже
привязанный к токену. Как использовать их во фронтенде на `http://localhost:5181`, описано в
разделе [Первый вход](first-sign-in.md).

## Что вы получили {#what-you-got}

После `docker compose up --build` и одного запуска `seed_data` у вас есть:

- База данных PostgreSQL 16 (`crm_db`) с политиками RLS, применёнными миграциями.
- Django API на `http://localhost:8000`, работающий под dev-сервером (не под производственным
  WSGI-сервером: этот compose-файл предназначен для разработки).
- Воркер Celery и планировщик Celery beat, оба подключены к сервису `redis` и выполняют
  периодические и фоновые задачи, зарегистрированные в `backend/crm/celery.py`.
- Фронтенд на SvelteKit на `http://localhost:5181`, который обращается к API по сети compose по
  адресу `PUBLIC_DJANGO_API_URL=http://backend:8000`.
- Суперпользователь админки Django, автоматически созданный `create_default_admin` при первом
  запуске с `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env.docker` (`admin@localhost` / `admin`, если
  вы их не переопределили). Эта учётная запись может входить в собственный сайт Django `/admin/`;
  профиля в организации CRM у неё нет, поэтому войти в само приложение CRM она не может, пока вы не
  дадите ей профиль через `seed_data` или процесс создания организации.
- Если вы запускали `seed_data`, организация `MicroPyramid` с профилем администратора для
  переданного email и большой набор демонстрационных записей.
