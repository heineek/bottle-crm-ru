# Демоданные и отраслевые пакеты

В BottleCRM есть два независимых способа наполнить организацию данными: команда управления
`seed_data`, которая генерирует большой случайный набор данных для целой организации, и
**отраслевые пакеты**, которые применяют к уже существующей организации небольшой подобранный
набор воронок и примеров записей для конкретной отрасли.

## Заполнение демоорганизации {#seeding-a-demo-organization}

```bash
uv run python manage.py seed_data --email you@example.com
```

Запускайте из `backend/` (или `docker compose exec backend python manage.py seed_data --email
you@example.com` для стека Docker). Именно эта команда упоминается в разделах
[Быстрый старт с Docker](docker-quick-start.md) и [Первый вход](first-sign-in.md).

Команда (`backend/common/management/commands/seed_data.py`) создаёт организацию и заполняет её
правдоподобными вымышленными данными: контактами, компаниями, лидами, сделками, обращениями,
задачами, товарами, счетами, коммерческими предложениями, регулярными счетами, целями продаж,
командами и тегами. Для этого она использует подобранные наборы имён, компаний и адресов и
зарезервированные демонстрационные домены (`example.com`, `.example`), чтобы ничто
сгенерированное не напоминало реального человека или компанию. **Первая** создаваемая ею
организация всегда называется **`MicroPyramid`**, чтобы при локальной разработке было стабильное,
известное имя организации для входа через `devlogin --org MicroPyramid`. **Профиль
администратора** создаётся для того `--email`, который вы передали. Повторный запуск команды с тем
же email использует существующие организацию и пользователя, а не создаёт дубликаты. Запускать её
несколько раз безопасно.

Количество записей каждого типа (`--leads`, `--accounts`, `--opportunities`, `--invoices` и так
далее) и локаль (`--currency`, `--country`) задаются флагами; полный список выводит `--help`. Флаг
`--clear` удаляет существующие данные CRM для повторного заполнения (но никогда не пользователей,
организации или профили). Это отдельная, более широкая операция, чем очистка примеров данных,
описанная ниже, и она не ограничена записями, созданными пакетом.

## Отраслевые пакеты {#vertical-packs}

Отраслевой пакет представляет собой небольшой декларативный JSON-манифест, а не генератор данных,
который настраивает организацию под одну отрасль: начальная воронка (с этапами) для лидов,
обращений и задач; несколько определений дополнительных полей; теги; товары; некоторые замены
терминологии (например, «Lead» переименовывается в «Enquiry»); и короткий список именованных
примеров записей (компании, контакты, сделки, обращения, лиды, задачи), которые ссылаются друг на
друга по имени внутри манифеста.

В `backend/common/packs/manifests/` поставляются четыре пакета, по одному файлу манифеста на пакет:

| Id пакета | Файл | Описание |
|---|---|---|
| `real-estate` | `real-estate.json` | Брокеры, агентства и застройщики, продающие жилую и коммерческую недвижимость. |
| `professional-services` | `professional-services.json` | Агентства, консалтинговые и бухгалтерские фирмы, продающие оплачиваемую работу. |
| `education-admissions` | `education-admissions.json` | Учебные центры, тренинговые институты и колледжи, ведущие набор студентов. |
| `events-weddings` | `events-weddings.json` | Свадебные организаторы, ивент-агентства и площадки, ведущие запросы до проведённого мероприятия. |

Каждый манифест строго проверяется при загрузке (`backend/common/packs/schema.py`). Неизвестный
ключ, недопустимый `stage_type`, ссылка в `sample_data` на компанию или этап, не объявленные в
другом месте того же пакета, и подобные ошибки не проходят проверку, а не игнорируются молча и не
применяются наполовину.

## Применение пакета {#applying-a-pack}

Применение пакета выполняет `apply_pack()` из `backend/common/packs/applier.py`, доступный через:

- **Интерфейс**: страница «Настройки → Организация» (для существующей организации) и страница
  создания организации (для новой) предлагают выбор пакета и вызывают один и тот же эндпоинт
  бэкенда.
- **API**: `POST /api/packs/<pack_id>/apply/`, только для администратора организации
  (`request.profile.role == "ADMIN"`); любой аутентифицированный участник может получить список
  доступных пакетов через `GET /api/packs/`, но применить пакет может только администратор.

**Применение пакета строго аддитивно.** Собственное описание модуля применения: он создаёт
недостающее и пропускает уже существующее и «never calls `.update()`, never calls `.save()` on a
row it did not just construct, and never deletes». Воронка, имя которой уже есть в организации,
пропускается целиком (вместе с этапами); дополнительное поле, тег или товар, уже существующие по
совпадающему ключу, пропускаются по отдельности. Поэтому повторное применение того же пакета или
применение второго пакета к организации, где уже есть один, безопасно: можно только добавить ещё
недостающее, но нельзя перезаписать или удалить то, что вы с тех пор изменили. Единственное
исключение составляют терминология и метка `vertical` организации: они объединяются (добавляются
только ещё не заданные ключи), а не дублируются.

Примеры записей, созданные пакетом (компании, контакты, сделки, обращения, лиды и задачи),
помечаются логическим полем `is_sample`, которое устанавливает только модуль применения. Оно
`read_only` в каждом сериализаторе, который его отдаёт, поэтому запрос клиента никогда не может его
установить. Каждая строка примера также получает тег «Sample data» и назначается администратору,
применившему пакет, исключительно для наглядности в интерфейсе; тег не даёт особых полномочий, и
система не по нему определяет, что строка является примером.

Даты в примерах записаны относительно одного дня, который манифест хранит как
`sample_dates_written_on`. При применении пакета каждая дата примера (сроки задач, даты закрытия
сделок и значения дополнительных полей с `field_type` равным `date`) сдвигается на число дней между
этим днём и сегодняшним днём в часовом поясе организации. Задача, записанная со сроком на следующий
день, получает срок на день после применения пакета, а сделка, закрытая тремя неделями раньше, так
и остаётся закрытой тремя неделями раньше. Манифест, в строках примеров которого есть даты, но нет
`sample_dates_written_on`, не проходит проверку.

Если в организации уже есть строки примеров (из этого пакета или предыдущего), повторное
применение `sample_data` пропускается. Примеры данных пакета создаются в организации только один
раз, сколько бы раз вы его ни применяли.

## Очистка примеров данных {#clearing-sample-data}

**Удаляет примеры записей только `clear_sample_data()`**, через `DELETE /api/packs/sample-data/`
(тоже только для администратора, тоже доступно со страницы «Настройки → Организация»). Это
единственный противовес примерам данных из пакетов: больше ничто в системе не удаляет строки лишь
потому, что у них установлен `is_sample`.

Очистка строго ограничена строками с `is_sample=True` вызывающей организации и удаляет их в таком
порядке, чтобы дочерние записи (задачи, лиды) удалялись раньше родительских, на которые они могут
ссылаться (обращения, сделки, контакты, компании). Ничего другого она не удаляет. Настоящая запись,
созданная вами, не затрагивается, даже если она ссылается на пример, а строка примера
**сохраняется, а не удаляется**, если от неё всё ещё зависит настоящая запись (например, реальный
счёт, выставленный демокомпании). Сохранённые строки возвращаются в ответе, а не пропускаются
молча, чтобы вызывающий знал, что часть примеров оставлена намеренно, и не считал очистку
незавершённой. Строки примеров, принадлежащие модулю, который организация отключила (см.
[Модули](modules.md)), тоже сохраняются, и ответ считает их в `switched_off_by_type`.
