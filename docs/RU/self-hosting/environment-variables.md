# Переменные окружения

`backend/crm/settings.py` читается один раз, при импорте, каждой точкой входа Django:
`manage.py runserver`, `manage.py migrate`, воркером Gunicorn/Uvicorn, воркером Celery, management-командой.
Эта страница объясняет, откуда берутся эти значения и какие из них вам действительно нужно задать
самостоятельно; полная таблица по каждой переменной находится в разделе «Справочник».

## Как загружается конфигурация {#how-configuration-is-loaded}

`backend/crm/settings.py` вызывает `load_dotenv()` (из `python-dotenv`) в начале модуля, до чтения
любой настройки, поэтому файл `.env` рядом с `manage.py`, созданный копированием
`backend/.env.example` согласно разделу [Ручная установка](../getting-started/manual-setup.md),
автоматически загружается в окружение процесса. `docker-compose.yml` делает то же самое для
контейнеров, перечисляя `.env.docker` и затем необязательный, игнорируемый git файл
`.env.docker.local` в `env_file:` каждого сервиса, именно в таком порядке, так что значения из
`.env.docker.local` имеют приоритет.

Почти каждая настройка в `crm/settings.py` следует одному шаблону: `os.environ.get("NAME",
<default>)`, поэтому незаданная переменная откатывается к рабочему (обычно ориентированному на
разработку) значению по умолчанию, а не приводит к ошибке. Так читаются `SECRET_KEY`, `DEBUG`,
`ALLOWED_HOSTS`, `DBNAME`/`DBUSER`/`DBPASSWORD`/`DBHOST`/`DBPORT`, `EMAIL_BACKEND`,
`CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`,
`DOMAIN_NAME` и `FRONTEND_URL`. У меньшего набора переменных значения по умолчанию нет вовсе:
`backend/crm/server_settings.py` (импортируется только при `ENV_TYPE=prod`, см.
[Развёртывание в продакшене](production-deploy.md)) читает `AWS_BUCKET_NAME`,
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SES_REGION_NAME`, `AWS_SES_REGION_ENDPOINT` и
`SENTRY_DSN` через обычный `os.environ[...]`. Отсутствие любой из них даёт `KeyError` при импорте,
то есть процесс вообще отказывается запускаться, а не стартует наполовину настроенным.

Поскольку всё это выполняется при импорте, а не на каждый запрос, изменённая переменная окружения
вступает в силу только при следующем перезапуске процесса: правка `.env` при уже запущенном
`runserver` ничего не даёт, пока вы его не перезапустите (или, в конфигурации Docker Compose, пока не
перезапустится контейнер, что автоматически происходит при `docker compose up --build`).

## Минимум для рабочей установки {#the-minimum-for-a-working-install}

Значений из `.env.example` и `.env.docker` достаточно, чтобы поднять стек и пользоваться им локально;
чтобы пройти [Быстрый старт с Docker](../getting-started/docker-quick-start.md) или
[Ручную установку](../getting-started/manual-setup.md), больше ничего трогать не нужно. Прежде чем
экземпляр станет доступен кому-то, кроме вас, настоящие значения нужны следующим переменным:
`SECRET_KEY` (уникальный секрет, а не поставляемая заглушка `django-insecure-...`), `DEBUG=False`,
`ALLOWED_HOSTS` (ваши реальные имена хостов), `CSRF_TRUSTED_ORIGINS` (каждой записи нужна схема,
например `https://crm.example.com`), `DBUSER`, указывающая на роль PostgreSQL без прав суперпользователя,
и `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`, указывающие на экземпляр Redis под вашим контролем.
[Развёртывание в продакшене](production-deploy.md#required-settings) содержит полный список и
описывает, от чего защищает каждая из них; [PostgreSQL и RLS](postgresql-and-rls.md) объясняет,
почему роль базы данных важна не меньше любой из настроек Django.

## База данных {#database}

`DATABASES["default"]` в `crm/settings.py` читает `DBNAME` (по умолчанию `crm_db`), `DBUSER` (по
умолчанию `postgres`), `DBPASSWORD` (по умолчанию `postgres`), `DBHOST` (по умолчанию `localhost`) и
`DBPORT` (по умолчанию `5432`). `DBUSER` по умолчанию на большинстве установок является учётной
записью суперпользователя PostgreSQL, а суперпользователь незаметно обходит все политики Row-Level
Security, на которые проект опирается для изоляции тенантов. Как создать и проверить роль без прав
суперпользователя, прежде чем направлять эти переменные куда-либо, кроме локальной одноразовой базы,
описано в разделе [PostgreSQL и RLS](postgresql-and-rls.md).

## Почта {#email}

`EMAIL_BACKEND` по умолчанию равен `django.core.mail.backends.console.EmailBackend`, поэтому исходящая
почта (приветственные письма, письма со ссылкой для входа, уведомления об упоминаниях в комментариях)
выводится в stdout, а не отправляется. `.env.example` явно задаёт `EMAIL_BACKEND` тем же консольным
бэкендом; `.env.docker` вообще не задаёт `EMAIL_BACKEND`, в нём лишь комментарий о том, что активен
консольный бэкенд, то есть он полагается на то же значение по умолчанию. `DEFAULT_FROM_EMAIL`
и `ADMIN_EMAIL` по умолчанию равны `noreply@localhost`/`admin@localhost`. Переход на настоящий
почтовый бэкенд и связанные с Amazon SES переменные подробно описаны в разделе
[Почта и Celery](email-and-celery.md).

## Интеграции {#integrations}

`GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` в `crm/settings.py` по умолчанию пустые строки, и
`.env.docker` и `.env.example` поставляются с обоими пустыми. Вход через Google остаётся выключенным,
пока они не заданы, и на бэкенде, и на фронтенде SvelteKit. Настройки `GOOGLE_REDIRECT_URI` нет:
redirect URI для обмена токенов берётся из тела запроса, которое фронтенд отправляет при каждом
вызове, поэтому настройка с таким именем читалась в Django и больше нигде не использовалась.
Что делает каждая из них и где взять значения, описано в разделе [Google OAuth](google-oauth.md).
`SENTRY_DSN` читается (без значения по умолчанию) только внутри `server_settings.py`, то есть только
при `ENV_TYPE=prod`; в остальных случаях она вообще не используется.

`CACHE_URL` по умолчанию пуст, из-за чего кэшем Django по умолчанию становится `LocMemCache` на
каждый процесс. Для `runserver` это нормально, а для всего, где больше одного воркера, неправильно,
потому что DRF хранит там счётчики throttling: при N воркерах Gunicorn фактический лимит запросов
становится примерно в N раз больше настроенного и сбрасывается при каждом перезапуске. Публичный
эндпоинт отправки [веб-формы](../integrations/web-forms.md) сейчас единственное, чья защита от спама
от этого зависит, поэтому в любом реальном развёртывании направьте `CACHE_URL` на Redis, который
у вас уже работает для Celery (отдельная база, например `redis://localhost:6379/1`).
`WEBFORM_THROTTLE_IP` и `WEBFORM_THROTTLE_GLOBAL` задают эти лимиты, и у обеих есть рабочие значения
по умолчанию. [Вебхуки лидов](../features/lead-capture.md#limits-and-settings) зависят от него так же,
через `LEAD_INTAKE_THROTTLE_MINUTE` и `LEAD_INTAKE_THROTTLE_DAY`, как и почтовый ящик
[Mailgun](../integrations/inbound-email.md#mailgun), токены доставленных писем которого запоминаются
там.

`INBOUND_EMAIL_DOMAIN` и `INBOUND_EMAIL_TOPIC_ARN` по умолчанию пусты, и тогда администраторы вводят
свои входящие адреса сами. Задайте обе, чтобы администраторы могли генерировать адреса в вашем
собственном домене для входящей почты: подтвердите домен для приёма в Amazon SES, направьте его
MX-запись на SES, добавьте для домена одно правило получения, действие SNS которого публикует в этот
топик, и подпишите топик на общий вебхук `https://<your API host>/api/cases/inbound/email/`. Общий
приёмник принимает только этот топик. См.
[Сгенерированные адреса](../integrations/inbound-email.md#generated-addresses).
