# Docker

`docker-compose.yml` в корне репозитория запускает весь стек: базу данных, кэш/брокер, API, фоновые
воркеры и фронтенд, в виде шести сервисов из одного файла. Эта страница описывает этот файл сервис за
сервисом. Самый быстрый путь к работающему экземпляру с загруженными демоданными описан в разделе
[Быстрый старт с Docker](../getting-started/docker-quick-start.md); здесь же речь о том, что
настраивать, как сохраняются данные и как обновлять экземпляр, который вы собираетесь держать
запущенным.

**Этот compose-файл предназначен для разработки, а не является защищённой продакшен-конфигурацией.**
Его сервис `backend` монтирует репозиторий через bind-mount (`./backend:/app`), а его entrypoint
(`docker/backend/entrypoint.sh`) в конце запускает `python manage.py runserver 0.0.0.0:8000`, то есть
dev-сервер Django, а не Gunicorn. `.env.docker` к тому же поставляется с `DEBUG=True`. Запуск как есть
обеспечивает корректное взаимодействие всех сервисов друг с другом, но сам по себе не удовлетворяет
требованиям раздела [Развёртывание в продакшене](production-deploy.md).

## Сервисы {#the-services}

`docker-compose.yml` определяет:

| Сервис | Образ / сборка | Порт на хосте | Назначение |
|---|---|---|---|
| `db` | `postgres:16-alpine` | `5432` | База данных PostgreSQL, `crm_db`. Политики Row-Level Security, которые применяют миграции Django, требуют настоящего PostgreSQL. См. [PostgreSQL и RLS](postgresql-and-rls.md). |
| `redis` | `redis:7-alpine` | `6379` | Брокер и бэкенд результатов Celery (`CELERY_BROKER_URL` и `CELERY_RESULT_BACKEND` указывают сюда). |
| `backend` | собирается из `Dockerfile` в корне репозитория | `8000` | Django API, в этом compose-файле обслуживается через `manage.py runserver` (см. предупреждение выше). |
| `celery-worker` | тот же образ, что у `backend` | (порт не публикуется) | Запускает `celery -A crm worker --loglevel=info`; выполняет фоновые задачи, например отправку исходящей почты и задачи с учётом RLS-контекста в `backend/common/tasks.py`. |
| `celery-beat` | тот же образ, что у `backend` | (порт не публикуется) | Запускает `celery -A crm beat --loglevel=info`; по расписанию запускает периодические задачи, зарегистрированные в `backend/crm/celery.py` (регулярные счета, проверки просрочки и истечения сроков, сканирование SLA, задачи очистки). |
| `frontend` | собирается из `frontend/Dockerfile` | `5181` | Приложение SvelteKit, обслуживается через `pnpm dev --host 0.0.0.0`, тоже dev-сервер, а не продакшен-сборка. |

`backend`, `celery-worker` и `celery-beat` объявляют `depends_on: db (service_healthy), redis
(service_healthy)` с использованием healthcheck-ов `pg_isready` и `redis-cli ping`, определённых для
этих двух сервисов, поэтому они ждут, пока оба действительно начнут принимать подключения, а не
просто пока запустятся их контейнеры.

## Конфигурация {#configuration}

Каждый сервис загружает два env-файла по порядку: `.env.docker` (хранится в репозитории, рабочие
значения по умолчанию) и затем `.env.docker.local` (необязательный, игнорируется git,
`required: false`; создайте его рядом с `.env.docker`, чтобы переопределить отдельные значения, не
трогая отслеживаемый файл; его значения имеют приоритет).

Переменные, которые задаёт `.env.docker`: `SECRET_KEY` (небезопасная заглушка. Прочитайте
[Развёртывание в продакшене](production-deploy.md), прежде чем этот экземпляр станет чем-то, кроме
локального), `DEBUG=True`, `ENV_TYPE=dev`, `ALLOWED_HOSTS=localhost,127.0.0.1,backend`,
`DOMAIN_NAME` (`http://localhost:8000`), `DBNAME`/`DBUSER`/`DBPASSWORD`/`DBHOST`/`DBPORT`, через
которые контейнеры `backend` и Celery подключаются к `db`, `POSTGRES_DB`/`POSTGRES_USER`/
`POSTGRES_PASSWORD` (используются только самим сервисом `db` для создания базы данных и собственной
роли суперпользователя. Почему приложение никогда не подключается под этой ролью, объясняется в
разделе [PostgreSQL и RLS](postgresql-and-rls.md)), `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`
(обе указывают на `redis`), `DEFAULT_FROM_EMAIL`/`ADMIN_EMAIL`/`ADMIN_PASSWORD`, `CORS_ALLOW_ALL=True`,
`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (пустые. Вход через Google остаётся выключенным, пока обе не
заданы), и `PUBLIC_DJANGO_API_URL=http://backend:8000`: имя compose-сервиса, по которому серверный код
фронтенда обращается к API, а также `BODY_SIZE_LIMIT=6M`: наибольший размер тела запроса, который
принимает фронтенд. Значение по умолчанию у Node-адаптера 512K, и с ним импорт таблицы контактов или
лидов (API принимает до 5 МБ) был бы отклонён ещё до того, как дошёл бы до API. Опубликованный образ
фронтенда сам задаёт `6M`; задавайте её вручную, только если запускаете фронтенд каким-то другим
способом.

## Запуск {#running-it}

Из корня репозитория (каталога, где лежат `docker-compose.yml` и `Dockerfile`):

```bash
docker compose up --build
```

Для этого нужен плагин Compose v2 (подкоманда `docker compose`, а не отдельный бинарник
`docker-compose`). При первом запуске `docker/postgres/init-rls-user.sql` выполняется автоматически
через механизм PostgreSQL `/docker-entrypoint-initdb.d/` и создаёт роль `crm_user` без прав
суперпользователя, под которой на самом деле подключается `backend`. Затем
`docker/backend/entrypoint.sh` ждёт, пока PostgreSQL начнёт принимать подключения, выполняет
`manage.py migrate --noinput`, `manage.py create_default_admin`, `manage.py collectstatic --noinput`
и, наконец, запускает dev-сервер. Каждый из этих шагов выполняется заново при каждом перезапуске
контейнера, а не только при первом.

Разовую management-команду запускайте внутри работающего контейнера `backend` через
`docker compose exec`, например:

```bash
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py manage_rls --status
```

## Сохранение данных {#persisting-data}

`docker-compose.yml` объявляет два именованных тома:

| Том | Точка монтирования | Содержимое |
|---|---|---|
| `postgres_data` | `/var/lib/postgresql/data` в `db` | Сама база данных: каждая организация, запись и строка под защитой RLS. Именно этот том должен пережить пересборку. |
| `frontend_node_modules` | `/app/node_modules` во `frontend` | Установленные зависимости фронтенда, кэш сборки, а не пользовательские данные. Его можно удалить: `pnpm install` создаст его заново. |

Всё остальное: bind-mount исходного кода с хоста, а не тома под управлением Docker:
`./backend:/app` в `backend`/`celery-worker`/`celery-beat` и `./frontend:/app` во `frontend`.
Одно следствие, которое стоит знать: с `ENV_TYPE=dev` (значение по умолчанию) `MEDIA_ROOT` в Django
равен `BASE_DIR/media`, что внутри контейнера превращается в `/app/media`, а поскольку `/app` это
смонтированный каталог `./backend`, загруженные файлы (вложения счетов, вложения обращений и так
далее) автоматически оказываются в `backend/media/` на хосте. Они сохраняются при пересборке
контейнеров по той же причине, что и исходный код, без отдельного именованного тома, но **не**
защищены томом вроде `postgres_data`, поэтому, если вы полагаетесь на загруженные файлы, резервируйте
`backend/media/` вместе с базой данных.

`docker compose down` удаляет контейнеры и сеть по умолчанию, но оставляет именованные тома; удаляет
их только `docker compose down -v` или явное удаление `postgres_data`/`frontend_node_modules`.

## Обновление {#upgrading}

Чтобы перейти на новую версию приложения, получите новый исходный код, затем пересоберите и
перезапустите:

```bash
docker compose up --build
```

Поскольку `entrypoint.sh` выполняет `manage.py migrate --noinput` при каждом запуске контейнера (а не
только при первом), пересборки и перезапуска достаточно, чтобы привести схему в актуальное состояние.
Отдельного шага миграции, о котором нужно помнить, нет. `collectstatic` тоже выполняется при каждом
запуске, поэтому обновлённые статические ресурсы подхватываются автоматически.

Сделайте резервную копию тома `postgres_data` (и `backend/media/`, как сказано выше) перед
обновлением через любое изменение, в обратной совместимости которого с вашими данными вы не уверены:
ничто в этой конфигурации compose не создаёт резервную копию за вас.
