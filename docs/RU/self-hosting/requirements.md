# Требования

Что должно быть верно для вашего окружения, прежде чем следовать разделам [Docker](docker.md) или
[Развёртывание в продакшене](production-deploy.md). Эта страница описывает только версии, характер
оборудования и сервисы. Команды для их установки приведены в разделе
[Ручная установка](../getting-started/manual-setup.md).

## Поддерживаемые версии {#supported-versions}

| Компонент | Версия | Источник |
|---|---|---|
| Python | 3.12 или новее | `backend/pyproject.toml` задаёт `requires-python = ">=3.12"`; `backend/.python-version` фиксирует ровно `3.12`. |
| Django | 6.1.2 или новее | Зависимость `django>=6.1.2` в `backend/pyproject.toml`. |
| PostgreSQL | 16 | Сервис `db` в `docker-compose.yml` использует образ `postgres:16-alpine`. Это также единственная версия, на которой когда-либо запускается собственный CI проекта. См. примечание ниже. |
| Redis | 7 | Сервис `redis` в `docker-compose.yml` использует образ `redis:7-alpine`. |
| Node.js | 24 | Задание `frontend-checks` в `.github/workflows/tests.yml` устанавливает `node-version: '24'`. |
| pnpm | 10 | То же задание фиксирует action pnpm на `version: 10`. |

Зависимости бэкенда (`djangorestframework`, `djangorestframework-simplejwt`, `celery`,
`weasyprint`, `gunicorn` и остальные) зафиксированы в `backend/uv.lock`; `uv sync` из каталога
`backend/` устанавливает ровно те версии, с которыми проверены CI и эта документация.

**PostgreSQL обязателен.** Мультитенантность BottleCRM обеспечивается механизмом Row-Level
Security (RLS) в PostgreSQL, привязанным к сессионной переменной `app.current_org`. Как это работает
и почему это важно, описано в разделе [PostgreSQL и RLS](postgresql-and-rls.md). RLS: возможность
PostgreSQL, у которой нет аналога в SQLite. SQLite встречается в кодовой базе только в
`backend/crm/test_settings.py`, который подставляет in-memory базу SQLite для набора тестов
именно потому, что «RLS ... is PostgreSQL-only and is skipped on SQLite» (так сказано в его
собственном docstring). Запуск самого приложения на SQLite не поддерживается ни одним модулем
настроек в этом репозитории.

По той же причине задание `backend-tests` в `.github/workflows/tests.yml` запускает
`pytest -m "not postgres_only"` на SQLite и явно исключает все тесты с маркером
`postgres_only`: этим тестам нужно настоящее подключение к PostgreSQL, чтобы проверить RLS, и в этом
задании они не запускаются вовсе. Считайте PostgreSQL 16, зафиксированный в `docker-compose.yml`,
той версией, которую проект действительно проверяет; ничто в этом репозитории не документирует
поддержку или тестирование какой-либо другой мажорной версии.

## Оборудование {#hardware}

В репозитории нет руководства по сайзингу на основе бенчмарков, и эта страница не станет его
выдумывать. Планировать мощности нужно исходя из списка процессов, которые полный стек на своём сервере
запускает одновременно: `docker-compose.yml` определяет шесть долгоживущих сервисов: `db`
(PostgreSQL), `redis`, `backend` (Django API), `celery-worker`, `celery-beat` и `frontend`. Все,
кроме `frontend` (он нужен, только если вы отдаёте dev-сервер SvelteKit, а не собранный статический
бандл), необходимы для работы API и фоновых задач; запуск их всех на одном хосте означает, что
ресурсы нужно рассчитывать сразу на базу данных, хранилище «ключ-значение», сервер приложения и
воркер задач, а не только на процесс Django. `backend/Dockerfile` также устанавливает
Cairo/Pango/gdk-pixbuf (зависимости WeasyPrint для рендеринга PDF). Генерация PDF для счетов и
коммерческих предложений выполняется синхронно в запросе или задаче, которая её запускает, поэтому
учитывайте это для процесса, который её обрабатывает.

## Обязательные сервисы {#required-services}

- **PostgreSQL 16**: единственный поддерживаемый бэкенд базы данных (`django.db.backends.postgresql`:
  единственный `ENGINE`, который задаёт любой нетестовый модуль настроек в этом репозитории).
  Необходим для изоляции тенантов на основе RLS; см. [PostgreSQL и RLS](postgresql-and-rls.md).
- **Redis**: `backend/crm/settings.py` читает `CELERY_BROKER_URL` и `CELERY_RESULT_BACKEND`,
  оба по умолчанию `redis://localhost:6379/0`. Redis служит и брокером сообщений Celery, и
  бэкендом результатов; без него `celery -A crm worker` и `celery -A crm beat` не к чему
  подключаться.

Больше ничего для работы самого API не требуется. Отправка почты (по умолчанию консольный бэкенд,
опционально SES), Google OAuth и Sentry настраиваются переменными окружения с рабочими значениями
по умолчанию или явным выключенным состоянием. Что нужно каждому из них при включении, описано в
разделе [Развёртывание в продакшене](production-deploy.md).
