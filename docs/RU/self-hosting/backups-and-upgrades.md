# Резервное копирование и обновление

Эта страница описывает, что действительно нужно резервировать в экземпляре BottleCRM на своём сервере и
что означает «обновление» для конфигурации Docker Compose и для ручной установки.

## Что резервировать {#what-to-back-up}

Состояние, которое больше ничем нельзя восстановить, хранят две вещи: **база данных PostgreSQL** и
**каталог медиафайлов**. Всё остальное (код приложения, статические ресурсы (вывод `collectstatic`),
установленные зависимости, брокер и хранилище результатов в Redis) либо хранится в системе контроля
версий, либо пересобирается из неё, либо не нужно. Redis в особенности не требует резервного
копирования: это брокер и бэкенд результатов Celery (`CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`), а
не хранилище бизнес-данных. Потерянная при перезапуске очередь выполняемых задач означает повторную
попытку, а не потерянные записи, поскольку сами записи хранятся в PostgreSQL.

## Резервное копирование PostgreSQL {#backing-up-postgresql}

Каждая организация, каждая запись, каждая строка под защитой RLS хранится в базе данных, заданной
через `DBNAME`/`DBUSER`/`DBHOST`/`DBPORT` (см. [Переменные окружения](environment-variables.md#database)).
Для логической резервной копии достаточно обычного `pg_dump`:

```bash
pg_dump -h <DBHOST> -p <DBPORT> -U <DBUSER> -d <DBNAME> -F c -f backup.dump
```

В Docker Compose запустите его на сервисе `db`:

```bash
docker compose exec db pg_dump -U postgres -d crm_db -F c -f /tmp/backup.dump
docker compose cp db:/tmp/backup.dump ./backup.dump
```

`docker-compose.yml` также объявляет именованный том `postgres_data`, смонтированный в
`/var/lib/postgresql/data` сервиса `db`. Это и есть база данных на диске, и именно он должен
пережить `docker compose down` (который удаляет контейнеры, но оставляет именованные тома) или
пересборку. Удаляет его только `docker compose down -v` или явное удаление тома. См.
[Docker](docker.md#persisting-data).

## Медиафайлы {#media-files}

`MEDIA_ROOT` зависит от того, какой модуль настроек активен. С `ENV_TYPE=dev` (по умолчанию)
`crm/settings.py` задаёт `MEDIA_ROOT` как локальный каталог `media/` внутри `BASE_DIR`, и загруженные
файлы (вложения счетов, вложения обращений и подобные) попадают на локальный диск. В Docker Compose
это `/app/media` внутри контейнера `backend`, а поскольку `/app` смонтирован bind-mount из каталога
`./backend`, а не является именованным томом, загрузки автоматически оказываются в `backend/media/`
на хосте, но **не** подпадают под гарантии тома `postgres_data`. Резервируйте `backend/media/` (или
соответствующий локальный путь к медиафайлам при ручной установке) вместе с базой данных.

С `ENV_TYPE=prod` модуль `backend/crm/server_settings.py` переключает `DEFAULT_FILE_STORAGE` на
`storages.backends.s3boto3.S3Boto3Storage`, и медиафайлы записываются в S3-бакет, указанный в
`AWS_BUCKET_NAME`, а не на локальный диск. В такой конфигурации резервируйте бакет привычными для вас
средствами AWS (версионирование, репликация или отдельное задание резервного копирования), а не
копированием файловой системы.

## Обновление {#upgrading}

В Docker Compose `docker/backend/entrypoint.sh` выполняет `manage.py migrate --noinput`,
`manage.py create_default_admin` и `manage.py collectstatic --noinput` при **каждом** запуске
контейнера, а не только при первом, поэтому вся процедура обновления сводится к получению нового
исходного кода и пересборке:

```bash
git pull
docker compose up --build
```

Отдельного шага миграции, о котором нужно помнить, нет: схема и статические ресурсы обновляются
автоматически при перезапуске. Сделайте резервную копию `postgres_data` и `backend/media/`, как
описано в разделах выше, перед обновлением через любое изменение, в обратной совместимости которого с
вашими данными вы не уверены: ничто в этой конфигурации compose не создаёт резервную копию за вас.

Для ручной установки (без Docker) порядок такой: получите новый исходный код, выполните `uv sync`
для обновления зависимостей, затем сами запустите миграции и `collectstatic` перед перезапуском
процесса (см. [Миграции](#migrations) ниже и
[Развёртывание в продакшене](production-deploy.md#before-you-start)).

## Миграции {#migrations}

`manage.py migrate` применяет изменения схемы и, в случае миграций, связанных с RLS, заново
применяет политики Row-Level Security, описанные в разделе
[PostgreSQL и RLS](postgresql-and-rls.md#enabling-policies). RLS включается и выключается
миграциями, а не какой-либо отдельной командой. Эти миграции выполняются с `atomic = False`
(комментарий рядом, повторённый в каждой миграции, вызывающей `get_enable_policy_sql`, говорит
прямо: «RLS policy creation can't run inside an atomic block»), а сама `get_enable_policy_sql()`
выполняет `DROP POLICY IF EXISTS` перед каждым `CREATE POLICY`, поэтому повторный запуск `migrate`
после прерванного запуска безопасен и не падает на дублирующейся политике.

Собственный CI проекта гарантирует, что ни одно изменение модели не выходит без соответствующей
миграции: `.github/workflows/tests.yml` запускает

```bash
uv run python manage.py makemigrations --check --dry-run
```

отдельным шагом перед набором тестов. Если вы делаете форк проекта и добавляете или меняете модель,
сами выполните `manage.py makemigrations` и закоммитьте результат. Проверка прямо называет проблему;
без неё вы узнали бы о ней косвенно, по тесту или запросу, падающему из-за столбца, которого нет в
базе данных.
