# PostgreSQL и RLS

Мультитенантность BottleCRM не сводится к соглашению на уровне приложения. Каждая таблица в рамках
организации защищена механизмом Row-Level Security (RLS) в PostgreSQL, который централизованно
настраивается в `backend/common/rls/__init__.py` и включается миграциями Django. Эта страница
объясняет, почему это важно, как настроить роль базы данных, от которой зависит RLS, как применяются
политики и как убедиться, что изоляция действительно работает, а не просто предполагать это.

## Зачем RLS {#why-rls}

У каждой таблицы под защитой RLS есть столбец `org_id`, и PostgreSQL, а не только ORM Django,
отказывается возвращать или принимать строки, у которых `org_id` не совпадает с контекстом
организации текущей сессии. Этот контекст хранится в сессионной переменной PostgreSQL
`app.current_org`, которую задаёт middleware приложения (см. [Проверка изоляции](#verifying-isolation)
ниже) по аутентифицированной организации вызывающего. Политики в `get_enable_policy_sql()` применяют
этот фильтр через `USING (org_id::text = (select
NULLIF(current_setting('app.current_org', true), '')))`, поэтому он действует даже для «сырого»
SQL-запроса вне ORM, для запроса во view Django, который забыл свой `.filter(org=...)`, или при ошибке
в коде приложения. Это эшелонированная защита: `Model.objects.filter(org=request.profile.org)` в коде
приложения по-прежнему остаётся контрактом, а RLS служит страховочной сеткой под ним.

**Самый важный факт в этом разделе: роль суперпользователя PostgreSQL полностью обходит RLS, и делает
это незаметно: ни ошибки, ни строки в логе, ничего.** Об этом прямо говорит вывод `--status` самого
`manage_rls.py`: `Database user "X" is a SUPERUSER - RLS will be bypassed!`
Все политики по-прежнему существуют и выглядят правильно настроенными; подключение суперпользователя
просто их игнорирует. Если роль базы данных вашего приложения является суперпользователем (а значение
по умолчанию в `backend/crm/settings.py`, `DBUSER` равный `postgres`, именно таково, если вы его не
переопределите), каждая политика RLS в вашей схеме оказывается мёртвым грузом, и изоляция тенантов
целиком зависит от того, помнит ли каждый путь кода приложения о собственном фильтре по организации.
Ничто в этой кодовой базе не обнаруживает этого и не предупреждает об этом во время запроса; это видно,
только если вы сознательно запустите `manage_rls --verify-user` или `--status`.

## Создание роли приложения {#creating-the-application-role}

Приложение должно подключаться под ролью PostgreSQL **без прав суперпользователя**. Подключившись под
суперпользователем `postgres` (или эквивалентной административной учётной записью):

```sql
CREATE DATABASE crm_db;
CREATE USER crm_user WITH PASSWORD 'crm_password';
GRANT ALL PRIVILEGES ON DATABASE crm_db TO crm_user;
\connect crm_db;
GRANT ALL ON SCHEMA public TO crm_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO crm_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO crm_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON FUNCTIONS TO crm_user;
```

(Это повторяет то, что `docker/postgres/init-rls-user.sql` автоматически выполняет в конфигурации
Docker Compose, см. [Docker](docker.md), с той разницей, что этот скрипт выполняется безусловно,
обёрнутый в блок `DO $$ ... IF NOT EXISTS ...`, поэтому его повторный запуск на существующей базе
безопасен.)

Выдача прав на схему и таблицы (`GRANT ALL ON SCHEMA`, `GRANT ALL ... ON TABLES`) **не** ослабляет
RLS: эти права управляют DDL и прямым доступом на чтение и запись; политики на уровне строк обходят
только атрибут роли `BYPASSRLS` или статус суперпользователя. Не выдавайте роли приложения
`BYPASSRLS`: ничему в этой кодовой базе он не нужен, и в репозитории нет межорганизационной панели в
духе суперадмина, которая могла бы его оправдать.

Направьте Django на новую роль через `DBNAME`, `DBUSER`, `DBPASSWORD`, `DBHOST`, `DBPORT` в вашем
`.env` (см. [Ручная установка](../getting-started/manual-setup.md)) или в
`.env.docker`/`.env.docker.local` (см. [Docker](docker.md)), затем убедитесь, что всё применилось
правильно:

```bash
cd backend
uv run python manage.py manage_rls --verify-user
```

Команда выполняет `SELECT usename, usesuper, usecreatedb FROM pg_user WHERE usename = current_user` и
выводит `Is superuser: False` (и строку об успехе), если всё настроено правильно, или явное
`WARNING: Superusers bypass RLS!` с SQL для исправления, если нет.

## Включение политик {#enabling-policies}

RLS включается и выключается **миграциями Django, а не какой-либо management-командой**, о чём прямо
говорит docstring модуля `manage_rls.py`. Политики фактически применяет запуск миграций:

```bash
cd backend
uv run python manage.py migrate
```

Набор таблиц, получающих политики, централизованно задан в `ORG_SCOPED_TABLES` в
`backend/common/rls/__init__.py`. Количество смотрите в этом списке, а не здесь: оно меняется в обе
стороны (`security_audit_log` был удалён из него, когда `common/0036` удалила его политики, поэтому в
более раннем черновике этой страницы было 61). Список охватывает основные записи (`lead`,
`accounts`, `contacts`, `opportunity`, `case`, `task`, `invoice`, …), вспомогательные данные
(`comment`, `attachments`, `document`, `activity`, `tags`, …), Kanban-доски и таблицы этапов
воронки, таблицы счетов, коммерческих предложений и регулярных счетов и многое другое. Одно
намеренное исключение: `personal_access_token` **не** входит в `ORG_SCOPED_TABLES`. Поиск в ней
выполняется по хешу токена ещё до появления какого-либо контекста тенанта (комментарий в том файле
называет её таблицей «auth-bootstrap», по аналогии с самой таблицей `Org`), а её изоляция вместо этого
обеспечивается явными фильтрами `org`/`profile` в `backend/common/views/pat_views.py`.

Для каждой таблицы `get_enable_policy_sql(table)` выполняет:

```sql
ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "<table>" FORCE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS org_isolation ON "<table>";
DROP POLICY IF EXISTS org_insert_check ON "<table>";

CREATE POLICY org_isolation ON "<table>"
    FOR ALL
    USING (org_id::text = (select NULLIF(current_setting('app.current_org', true), '')));

CREATE POLICY org_insert_check ON "<table>"
    FOR INSERT
    WITH CHECK (org_id::text = (select NULLIF(current_setting('app.current_org', true), '')));
```

Благодаря двум выражениям `DROP POLICY IF EXISTS` повторный запуск `manage.py migrate` после
прерванного запуска безопасен и не падает на дублирующейся политике. См.
[Устранение неполадок](troubleshooting.md#migrations-fail) и
[Резервное копирование и обновление](backups-and-upgrades.md#migrations).

`FORCE ROW LEVEL SECURITY` важен именно потому, что иначе владелец таблицы (обычно роль, которая
выполняла миграции) по умолчанию освобождён от политик RLS собственной таблицы; принудительное
включение закрывает эту брешь без необходимости в отдельной роли приложения, не владеющей таблицами.

Чтобы добавить RLS для новой модели в рамках организации: унаследуйте её от `BaseOrgModel`, добавьте
имя таблицы в `ORG_SCOPED_TABLES` и напишите миграцию, которая вызывает
`get_enable_policy_sql('your_table')` внутри операции `RunPython` (с защитой
`if schema_editor.connection.vendor != 'postgresql': return`, поскольку в SQLite нет понятия
безопасности на уровне строк).

## Проверка изоляции {#verifying-isolation}

`manage_rls` (`backend/common/management/commands/manage_rls.py`) это диагностическая команда с тремя
флагами, каждый из которых доказывает своё; ни один из них не изменяет базу данных:

```bash
cd backend
uv run python manage.py manage_rls --status
uv run python manage.py manage_rls --verify-user
uv run python manage.py manage_rls --test
```

- **`--status`** доказывает, *на каких таблицах применены политики и является ли подключённая роль
  суперпользователем*. Он запрашивает `current_user`/`usesuper` из `pg_user`, затем для каждой
  таблицы из `ORG_SCOPED_TABLES` проверяет `pg_class.relrowsecurity`/`relforcerowsecurity` и выводит
  `ENABLED (forced)`, `disabled` или `TABLE NOT FOUND`, завершая итогом `Enabled: N, Disabled: N`.
- **`--verify-user`** доказывает, *что подключённая роль базы данных не может обойти RLS*. Это
  проверка суперпользователя из `--status` сама по себе, с явным SQL для исправления, если роль
  оказывается суперпользователем.
- **`--test`** доказывает, *что изоляция действительно соблюдается на реальных данных*, а не только
  что политики существуют. Он выбирает до двух организаций, у которых есть строки `lead` (если лидов
  ещё нет ни у одной, берёт первые две организации в базе, а если организаций меньше двух, вообще
  пропускает проверку), по очереди задаёт `app.current_org` каждой и считает видимые лиды, затем
  задаёт контекст **пустой строкой** и считает снова. Ненулевые значения для двух реальных
  организаций и ноль для пустого контекста и есть настоящее доказательство изоляции, которое не могут
  дать два других флага.

**Почему важен подсчёт с пустым контекстом:** сессионная переменная называется `app.current_org`, и её
задаёт `RequireOrgContext` (`backend/common/middleware/rls_context.py`, подключён в `MIDDLEWARE` в
`backend/crm/settings.py`) из `request.org`, который, в свою очередь, раньше в той же цепочке
middleware определяет `GetProfileAndOrg` (`backend/common/middleware/get_company.py`) по claim
`org_id` в подписанном JWT вызывающего, проверив перед этим, что у этого пользователя в этой
организации есть активный `Profile`. Запрос, пришедший без контекста организации, отклоняется с 403,
а не выполняется без него. Каждая политика использует
`NULLIF(current_setting('app.current_org', true), '')`: когда контекст не задан, `current_setting`
возвращает пустую строку, `NULLIF` превращает её в SQL `NULL`, а `org_id::text = NULL` никогда не
истинно. **Нет контекста: ноль строк, так задумано**. Это fail-safe поведение по умолчанию, а не
пограничный случай, который нужно обходить отдельно.

`RequireOrgContext` сбрасывает переменную в `''` после каждого запроса (`SELECT set_config
('app.current_org', '', false)`) именно для того, чтобы она не утекала между запросами на
переиспользуемых подключениях из пула.

**Воркеры Celery никогда не выполняют этот middleware.** Фоновые задачи в `backend/common/tasks.py`,
которые обращаются к таблицам в рамках организации, первой строкой, до любого запроса ORM, вызывают
`set_rls_context(org_id)`, также определённую в `common/tasks.py`:

```python
from common.tasks import set_rls_context

@shared_task
def my_task(data_id, org_id):
    set_rls_context(org_id)  # required before any org-scoped query
    ...
```

`set_rls_context` представляет собой тонкую обёртку над тем же вызовом
`set_config('app.current_org', ...)`, что использует middleware, с ранним возвратом на подключениях не
к PostgreSQL (поэтому под тестовыми настройками SQLite она ничего не делает). Задача, которая
пропускает этот вызов и обращается к таблице под защитой RLS, выполняется с тем контекстом, который
случайно оказался у подключения; на свежем подключении воркера он пуст, что (согласно описанному выше
дизайну) возвращает ноль строк, а не строки чужой организации. Но это всё равно ошибка, которую стоит
ловить, поскольку «незаметно ничего не возвращает» порождает свой класс запутанных сбоев. Не каждой
задаче в `common/tasks.py` это нужно: `flush_expired_refresh_tokens` работает с `OutstandingToken`
из simplejwt, у которой нет столбца `org` и которой нет в `ORG_SCOPED_TABLES`, поэтому никакой
контекст к ней не применяется.

`purge_read_notifications` служит контрпримером, и его стоит изучить, потому что он выглядит как тот
же случай, но им не является. Его docstring утверждает, что RLS здесь не нужен контекст организации,
но `notification` *входит* в `ORG_SCOPED_TABLES`, поэтому на роли без прав суперпользователя, которую
предписывает эта страница, задача выполняется с пустым контекстом, и её удаление ничего не затрагивает.
Прочитанные уведомления никогда не удаляются. Воспринимайте это как практическое предупреждение:
docstring, утверждающий, что задача освобождена от правила, не является доказательством, а сбой
незаметен: задача сообщает об успехе, не сделав вообще ничего.

## Типичные ошибки {#common-mistakes}

- **Оставлять роль базы данных по умолчанию `postgres`.** Ничто не заставит вас использовать роль без
  прав суперпользователя; настройка `DATABASES` в `backend/crm/settings.py` по умолчанию задаёт
  `DBUSER` равным `postgres`, если переменная окружения не задана. Почти везде, где установлен
  PostgreSQL, это суперпользователь. Запускайте `manage_rls --verify-user` после любого изменения
  окружения, а не только один раз при настройке.
- **Считать «зелёный» локальный или dev-прогон доказательством работы RLS.** Если пользователь вашей
  базы для разработки является суперпользователем (очень частый случай. Это путь наименьшего
  сопротивления, чтобы «просто запустить»), каждый эндпоинт будет выглядеть правильно изолирующим
  тенантов исключительно потому, что вызовы `.filter(org=
  ...)` на уровне приложения оказались верными, тогда как сам RLS ничего не делает. Это выявляет только
  `--verify-user` (или `--status`); функциональное тестирование не может.
- **Забыть `set_rls_context(org_id)` в новой задаче Celery**, которая обращается к модели в рамках
  организации. См. [Проверка изоляции](#verifying-isolation) выше.
- **Добавить новую модель в рамках организации, не зарегистрировав её.** `BaseOrgModel` даёт внешний
  ключ `org`, но политики RLS создаются только для таблиц, перечисленных в `ORG_SCOPED_TABLES`, с
  миграцией, вызывающей `get_enable_policy_sql`. Если пропустить этот шаг, таблица может содержать
  реальные данные с `org_id` и просто не иметь защиты RLS; `manage_rls --status` сообщает только о
  таблицах, которые изначально есть в этом списке, поэтому незарегистрированная таблица даже не
  появится как «disabled».
- **Считать анонимные эндпоинты клиентского портала (ссылки на счета и коммерческие предложения,
  опросы CSAT) либо сломанными, либо незащищёнными. Это намеренное узкое исключение, и локальное
  тестирование может ввести в заблуждение в обе стороны.** `RequireOrgContext.EXEMPT_PATHS` в
  `backend/common/middleware/rls_context.py` освобождает `/api/public/invoice/`,
  `/api/public/estimate/` и `/api/public/csat/` (среди других перечисленных там анонимных префиксов)
  от обязательного контекста организации, потому что это действительно анонимные запросы (клиент
  нажимает ссылку из письма), авторизованные токеном владения, а не JWT. Вебхук входящей почты
  (`/api/cases/inbound/<mailbox_id>/`) и общий приёмник сгенерированных адресов
  (`/api/cases/inbound/email/`) освобождены так же, но по имени URL в `EXEMPT_VIEW_NAMES`, а не по
  префиксу. См. `backend/docs/PORTAL_RLS.md`. Освобождение от *обязательного* контекста не равно
  его *установке*: `_set_org_context` возвращается раньше, когда `request.org` равен `None`, поэтому
  эти запросы выполняются с пустым `app.current_org`, а это, согласно описанному выше fail-safe
  дизайну, означает, что строки `invoice`/`estimate`/`csat_survey`, которые пытается прочитать view,
  тоже невидимы под RLS, пока сам view не определит организацию по токену и явно не вызовет
  `set_rls_context`. Именно такое маскирует dev-база с суперпользователем: с `DBUSER=
  postgres` RLS ничего не делает, поэтому локально сломанный и локально рабочий эндпоинт портала
  выглядят одинаково. Прежде чем доверять эндпоинтам портала, проверьте их на настоящей роли без прав
  суперпользователя.
