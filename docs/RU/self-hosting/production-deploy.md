# Развёртывание в продакшене

Ни `docker-compose.yml`, ни `Dockerfile` в корне репозитория не собирают защищённое
продакшен-развёртывание «из коробки». См. предупреждение в разделе [Docker](docker.md). Эта страница
описывает, что меняется: процесс, обслуживающий запросы, обработка статических файлов, что стоит перед
Django и какие переменные окружения сама кодовая база считает значимыми для безопасности.
Предполагается, что у вас уже есть рабочая установка по разделу
[Ручная установка](../getting-started/manual-setup.md) или [Docker](docker.md) и роль PostgreSQL,
настроенная по разделу [PostgreSQL и RLS](postgresql-and-rls.md).

## Прежде чем начать {#before-you-start}

В репозитории нет готового продакшен-файла `docker-compose`, unit-файла systemd или конфигурации
менеджера процессов. `Dockerfile` собирает образ (`backend/Dockerfile` добавляет в `PATH` зависимости
под управлением `uv` и каталог `bin/` виртуального окружения, поэтому `gunicorn`, `celery` и `python`
внутри него находятся), но какую команду этот образ *запускает*, решаете вы: сервис `backend` в
`docker-compose.yml` переопределяет её на `/entrypoint.sh`, который вызывает `manage.py runserver`,
то есть dev-сервер Django. Для продакшен-контейнера или процесса на хосте вместо этого скрипта
entrypoint вы указываете собственную команду запуска (см. [Сервер приложения](#application-server)
ниже).

Как бы вы его ни запускали, примените миграции и соберите статические файлы до того, как начнёте
обслуживать трафик:

```bash
cd backend
uv run python manage.py migrate
uv run python manage.py collectstatic --noinput
```

## Сервер приложения {#application-server}

`backend/pyproject.toml` указывает в зависимостях `gunicorn>=26.0.0` с комментарием «Production
WSGI server». Gunicorn это WSGI-сервер, который проект поставляет как зависимость для обслуживания
самого приложения Django. `backend/crm/wsgi.py` предоставляет стандартный вызываемый объект
`application`, поэтому из каталога `backend/`:

```bash
cd backend
uv run gunicorn crm.wsgi:application --bind 0.0.0.0:8000
```

**Рекомендуемый путь: WSGI, и причин предпочитать ASGI больше нет.** Ранние релизы требовали
ASGI-сервер (`uvicorn crm.asgi:application`), потому что эндпоинт уведомлений в приложении был
потоком Server-Sent Events, а долгоживущий асинхронный view под WSGI удерживает воркер. Этот поток
удалили 2026-08-03 в пользу опроса (polling), и это был единственный асинхронный код в проекте, так
что сейчас ASGI ничему не нужен. `backend/crm/asgi.py` по-прежнему существует и работает, если вы
предпочитаете его, но ничего вам не даёт.

Предпочитайте WSGI по конкретной причине помимо простоты: **он ограничивает число подключений к базе
данных по построению.** Под ASGI Django выполняет каждый запрос в собственном thread-sensitive
executor с собственным thread-local подключением и без верхней границы, так что параллельные запросы
один к одному превращаются в бэкенды PostgreSQL. Именно это вызвало два инцидента с исчерпанием
подключений в истории проекта. Под Gunicorn пиковое число подключений равно `workers × threads`, и это
число вы задаёте в командной строке:

```bash
cd backend
uv run gunicorn crm.wsgi:application --bind 0.0.0.0:8000 --workers 3 --threads 4
```

В этом примере на хост приходится не более 12 подключений к базе данных плюс то, что использует
Celery. О пулинге, который всё ещё может пригодиться при большом числе воркеров Gunicorn или потоков,
см. раздел [Подключения к базе данных](#database-connections) ниже.

`uvicorn[standard]>=0.51.0` остаётся зависимостью, чтобы путь ASGI продолжал работать у тех, кто уже
развернулся так. Если вы работаете под ASGI, прочитайте следующий раздел до запуска: ограничение
подключений там обязательно.

## Подключения к базе данных {#database-connections}

Под ASGI Django выполняет каждый запрос в собственном thread-sensitive executor, и каждый из них
получает собственное thread-local подключение к базе данных. Ничто это не ограничивает. Всплеск
параллельных запросов превращается во всплеск бэкендов PostgreSQL, и `max_connections` (по умолчанию
`100`) достигается задолго до того, как само приложение окажется под нагрузкой. Проект уже
сталкивался с этим в продакшене.

Задайте `DB_POOL_ENABLED=true`, чтобы поставить перед базой данных ограниченный пул `psycopg_pool`.
`DB_POOL_MAX_SIZE` (по умолчанию `10`) задаёт верхнюю границу на процесс. Выбирайте размер осознанно:
пул создаётся на каждый процесс, поэтому пиковое использование примерно равно
`DB_POOL_MAX_SIZE × (uvicorn workers + Celery prefork children)`. Расчёт и разобранный пример см. в
разделе [Переменные окружения](../reference/environment-variables.md#connection-pooling).

Две вещи, которые нужно знать перед включением:

- **Пулу нужен psycopg 3.** Именно от него зависит проект (`psycopg[binary,pool]`); под psycopg2
  Django выбрасывает `ImproperlyConfigured`, если заданы параметры пула. Делать ничего не нужно, если
  вы сами не зафиксировали драйвер.
- **Не настраивайте пул вручную.** Изоляция тенантов зависит от `app.current_org`, сессионной
  настройки PostgreSQL, которая переживает транзакцию и запрос. `psycopg_pool` не очищает состояние
  сессии при возврате подключения, поэтому пул без callback-функции `reset` проекта отдаст данные
  одного тенанта следующему, кто возьмёт это подключение. `DB_POOL_ENABLED=true` подключает этот
  callback за вас. Собственный блок `OPTIONS["pool"]` без него означает утечку данных между тенантами.

Внешний пулер подключений вполне допустим, с одним жёстким ограничением: он должен работать в режиме
**session**. Пулинг в режиме transaction (режим по умолчанию в PgBouncer) не сохраняет сессионные
настройки между выражениями, что незаметно ломает RLS-контекст, на который приложение опирается для
изоляции тенантов.

## Статические файлы {#static-files}

`whitenoise.middleware.WhiteNoiseMiddleware` находится в `MIDDLEWARE` (сразу после
`SecurityMiddleware`), а `STATICFILES_STORAGE` задан как
`whitenoise.storage.CompressedManifestStaticFilesStorage`. Это значит, что Django сам отдаёт
статические ресурсы, сжатые и с хешем содержимого в имени, прямо из процесса WSGI/ASGI; для
корректной работы отдельный сервер статических файлов или блок `location /static/` в обратном
прокси не нужен. Статические файлы собираются в `STATIC_ROOT` (`backend/staticfiles/`, то есть
`BASE_DIR/staticfiles`) под `STATIC_URL = "/static/"` командой `manage.py collectstatic`, которую вы
должны запускать сами. Gunicorn её за вас не запускает (entrypoint Docker Compose запускает, но лишь
потому, что `docker/backend/entrypoint.sh` явно вызывает её при каждом старте).

Медиафайлы (загруженные пользователями файлы: вложения счетов, вложения обращений и подобные)
отделены от статических файлов, и WhiteNoise их не обслуживает. С `ENV_TYPE=dev` (по умолчанию)
`MEDIA_ROOT`/`MEDIA_URL` указывают на локальный каталог `media/`, который отдаёт сам Django; с
`ENV_TYPE=prod` вместо этого импортируется `backend/crm/server_settings.py`, который переключает
`DEFAULT_FILE_STORAGE` на `storages.backends.s3boto3.S3Boto3Storage`, читая `AWS_BUCKET_NAME`,
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SES_REGION_NAME`, `AWS_SES_REGION_ENDPOINT` и
`SENTRY_DSN` из окружения через `os.environ[...]`: если хоть одна не задана, при импорте возникает
обычный `KeyError`, и процесс отказывается запускаться. Он также переключает
`MAILERS["default"]["BACKEND"]` на `django_ses.SESBackend` и жёстко задаёт
`SESSION_COOKIE_DOMAIN = ".bottlecrm.io"`. Этот домен относится к облачной версии BottleCRM,
а не к вашему развёртыванию. Если задать `ENV_TYPE=prod`, не будучи готовым предоставить учётные
данные AWS S3, SES и Sentry и не собираясь ограничивать сессионные cookie доменом `bottlecrm.io`,
результат будет не тем, что вам нужно. Практические последствия описаны в разделе
[Обязательные настройки](#required-settings) ниже.

## Обратный прокси {#reverse-proxy}

Ничто в `backend/crm/settings.py` не терминирует TLS, а `SECURE_PROXY_SSL_HEADER` задаётся, только
если вы явно включите это через `TRUST_PROXY_SSL_HEADER=true` (см.
[Переменные окружения](../reference/environment-variables.md)). Конкретно: если вы терминируете TLS
на обратном прокси (nginx, Caddy или подобном) и передаёте Gunicorn/Uvicorn обычный HTTP, то
`request.is_secure()` в Django будет возвращать `False` для каждого запроса, пока эта переменная не
задана и ваш прокси не перезаписывает `X-Forwarded-Proto`. `SECURE_HSTS_SECONDS = 31536000`
(один год), `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`, `SECURE_HSTS_PRELOAD = True` и
`SECURE_CONTENT_TYPE_NOSNIFF = True` безусловно заданы в `backend/crm/settings.py`, но
`SecurityMiddleware` в Django отдаёт заголовок `Strict-Transport-Security` только на запросы, которые
считает защищёнными, поэтому без правильно настроенного для вашего прокси `SECURE_PROXY_SSL_HEADER`
эта конфигурация HSTS незаметно никогда не вступает в силу.

Направьте прокси на порт, который слушает ваш сервер приложения (`8000` в примерах выше), и
маршрутизируйте туда `/`. Готовой конфигурации прокси (файла сайта nginx, Caddyfile или подобного) в
репозитории нет. Детали пишете вы, с одним требованием: журнал доступа прокси записывает ссылки на
календарную ленту, счёт, коммерческое предложение и опрос, путь которых содержит действующие учётные
данные. Приложение скрывает их в собственных логах, но до логов прокси дотянуться не может.
`log_format` для nginx, который это делает, приведён в разделе
[Токены публичных ссылок в логах](security-hardening.md#public-link-tokens-in-logs).

URL, которые API выдаёт для использования где-то ещё, строятся из `DOMAIN_NAME`, а не из пришедшего
запроса: фрагменты кода для встраивания веб-формы и URL отправки формы, а начиная с django-crm 1.13.0
и URL календарной ленты задач (`/api/public/calendar/<token>.ics`, см.
[API: Задачи](../api/tasks.md#calendar-feed)). URL ленты вставляют в Google Calendar или Outlook,
которые загружают его из интернета, а фрагмент кода на сайт клиента, поэтому `DOMAIN_NAME` должен быть
публичным origin API, например `https://api.example.com`. Веб-приложение запрашивает их со своего
сервера по `PUBLIC_DJANGO_API_URL`, который может быть внутренним адресом, например
`http://backend:8000` из compose-файла; в показываемые URL он больше не просачивается. При `ENV_TYPE`
с любым значением, кроме `dev`, бэкенд отказывается запускаться, если `DOMAIN_NAME` указывает на
loopback или не является абсолютным URL.

## Обязательные настройки {#required-settings}

`backend/crm/settings.py` читает их из окружения при импорте (то есть при запуске процесса, а не на
каждый запрос):

| Переменная | Поведение |
|---|---|
| `SECRET_KEY` | Если не задана, по умолчанию равна буквальной строке `"django-insecure-dev-key-please-change-in-production"`. Модуль сам это проверяет: если `SECRET_KEY` пуст или начинается с `"django-insecure"` **и** `ENV_TYPE != "dev"`, при импорте выбрасывается `ValueError("SECRET_KEY must be set to a secure value in non-dev environments")`, то есть жёсткий отказ запуска, а не предупреждение. Эта защита срабатывает, только когда `ENV_TYPE` имеет значение, отличное от `dev`; учитывая описанные выше последствия `ENV_TYPE=prod` (обязательные переменные S3/SES/Sentry, жёстко заданный домен cookie `.bottlecrm.io`), не полагайтесь только на эту проверку. Задайте настоящий уникальный `SECRET_KEY` независимо от `ENV_TYPE`. |
| `DEBUG` | В продакшене должна быть `False`. Читается как `os.environ.get("DEBUG", "False").lower() == "true"` и по умолчанию уже `False`, поэтому избегать нужно *явного* задания `DEBUG=True` (как делает `.env.docker` для локальной разработки) и переноса этого значения в продакшен. |
| `ALLOWED_HOSTS` | Переменная окружения со значениями через запятую: `os.environ.get("ALLOWED_HOSTS", "localhost,127.0.0.1").split(",")`. Задайте имена хостов, на которых сервис действительно будет доступен, например `ALLOWED_HOSTS=crm.example.com`. |
| `CSRF_TRUSTED_ORIGINS` | Тоже через запятую: `os.environ.get("CSRF_TRUSTED_ORIGINS", "").split(",")`, по умолчанию пусто. Django требует, чтобы каждая запись включала схему (например `https://crm.example.com`), а не голое имя хоста. |

Ещё несколько переменных, которые читает тот же модуль и которые стоит задать осознанно, а не
оставлять по умолчанию: `CORS_ALLOWED_ORIGINS` (через запятую, по умолчанию два локальных origin
dev-фронтенда), `CORS_ALLOW_ALL` (`CORS_ORIGIN_ALLOW_ALL`; `.env.docker` задаёт `True` для локальной
разработки. В продакшене оставьте `False` и полагайтесь на `CORS_ALLOWED_ORIGINS`) и `FRONTEND_URL`,
которая подставляется в каждую ссылку в письмах (вход по ссылке, портал счетов и коммерческих
предложений клиента, опрос CSAT, внутренние уведомления) и поэтому должна указывать на ваше реальное
публичное имя хоста. `FRONTEND_URL` теперь проверяется при запуске: при `ENV_TYPE` с любым значением,
кроме `dev`, значение-loopback или неабсолютное значение вызывает ошибку, а не отправку клиенту
нерабочей ссылки. `DOMAIN_NAME`, публичный origin самого API, проверяется так же (см. выше).
