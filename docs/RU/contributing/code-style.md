# Стиль кода

## Python {#python}

`backend/ruff.toml` существует, и это настоящая конфигурация, сохранённая в репозитории:

```toml
indent-width = 4

[format]
indent-style = "space"
line-ending = "lf"
quote-style = "double"

[lint]
select = ["E", "F", "I"]
ignore = ["E501"]
```

Она включает ошибки pycodestyle (`E`), pyflakes (`F`) и сортировку импортов (`I`) и явно
игнорирует длину строки (`E501`): проект сознательно решил не ограничивать длину строки, а не
забыл об этом.

`ruff` является единственным инструментом стиля Python здесь, и это настоящая dev-зависимость,
поэтому `uv sync` её устанавливает, и эти команды работают на свежем клоне:

```bash
cd backend
uv run ruff check .          # lint: E, F, I as ruff.toml selects them
uv run ruff check --fix .    # and fix what is safely fixable
uv run ruff format .         # format the tree
uv run ruff format --check . # or just report, which is what CI runs
```

**Здесь нет `black` и нет `isort`.** `ruff format` является переписанным black и даёт тот же
результат, а правила `I` в ruff делают работу isort, так что все три инструмента делали бы одну
работу, причём два из них избыточны, а black и `ruff format` могут расходиться в пограничных
случаях. Старая документация и привычки предлагают `uv run black . && uv run isort .`; ни один из
них не установлен, и добавлять их не нужно.

**CI запускает обе команды, и обе должны пройти.** `.github/workflows/tests.yml` выполняет
`uv run ruff check .` и `uv run ruff format --check .` как обязательные шаги, а не предупреждения.
`uv run`, а не `uvx`, выбран намеренно: ruff зафиксирован в `uv.lock`, поэтому ваша машина и CI
проверяют одной версией, и новый релиз ruff не может за ночь сделать сборку красной.

**Дерево соответствует правилам.** Оно было полностью отформатировано 2026-08-07 (205 файлов),
а ещё в 112 файлах были отсортированы импорты, так что `ruff format .` на чистой рабочей копии
ничего не меняет, и ваш diff остаётся вашим diff. В этом и смысл форматирования всего сразу: до
него запуск форматтера по всему дереву превращал любой сфокусированный PR в непроверяемый, поэтому
раньше здесь советовали запускать `uvx` только для затронутых файлов. Этот совет больше не
действует. Запускайте команды выше на всём дереве и коммитьте только то, что собирались изменить.

Одну вещь стоит знать, прежде чем запускать `--fix` по чужому коду: `# noqa` привязывается к
строке, на которой ruff сообщает о диагностике, поэтому подавление, которое съехало на следующую
строку или указывает неверный код правила, молча ничего не подавляет, и автоисправление удалит то,
что оно защищало. Живой пример: импорт `SecurityAuditLog` в `common/models.py`. Он существует
только для того, чтобы Django обнаружил модель для миграций, и его `# noqa: F401,E402` должен
стоять на той же строке, что и импортируемое имя.

## Фронтенд {#frontend}

`frontend/package.json` определяет настоящие команды:

```bash
pnpm run lint     # prettier --check . && eslint .
pnpm run format   # prettier --write .
pnpm run check    # svelte-kit sync && svelte-check --tsconfig ./tsconfig.json
```

Эти инструменты установлены (`prettier`, `eslint`, `svelte-check` и их плагины перечислены в
`devDependencies` файла `frontend/package.json`), и CI запускает все три, но не одинаково: задача
`frontend-checks` в `.github/workflows/tests.yml` запускает проверку Prettier с запасным вариантом
`|| echo "::warning::..."`, поэтому расхождение форматирования отображается в CI как
**предупреждение**, а не упавшая сборка. У шага ESLint (`pnpm eslint .`) такого запасного варианта
нет. Ошибка линтера роняет задачу. `pnpm check` (svelte-check) и `pnpm build` выполняются после
этого безусловно и тоже роняют задачу при ошибке. На практике: исправляйте ошибки ESLint и ошибки
типов до открытия PR, но не удивляйтесь, если расхождения Prettier отмечены как предупреждение, а
не жёсткая ошибка. Запускайте `pnpm run format` сами, а не полагайтесь на то, что это поймает CI.

### Типы {#types}

Фронтенд целиком написан на TypeScript: каждый модуль, каждый компонент (`<script lang="ts">`) и
каждый тест (`*.test.ts`), и `pnpm check` проверяет типы в полном строгом режиме. Импорты сохраняют
путь `#lib/....js`, как и вызовы `vi.mock`: Vite, vitest и svelte-check разрешают его в файл `.ts`.
В коде приложения нет `any`, ни явного, ни подразумеваемого: ESLint
(`@typescript-eslint/no-explicit-any`) падает на явном, `noImplicitAny` на нетипизированном
параметре, а `src/lib/no-any.test.ts` на `$props()` без типа, который иначе сделал бы каждый prop
`any` без всякой ошибки. Тесты могут использовать `any` для дублёров; ESLint разрешает его только в
`*.test.ts`. Данные, которые действительно произвольны (значения дополнительных полей, полезная
нагрузка вебхука), имеют тип `unknown` и проверяются перед использованием.

Типы ответов API генерируются из OpenAPI-схемы бэкенда в `frontend/src/lib/api-schema.d.ts`.
`apiRequest` обобщённый: его ответ получает тип переменной или возвращаемого значения, которому он
присваивается, и равен `unknown`, когда такого нет.

```ts
import type { components } from '#lib/api-schema.js';
type Schemas = components['schemas'];

const response: Schemas['TaskListResponse'] = await apiRequest(`/tasks/?${query}`, {}, { cookies });
```

Страница типизирует свои props из load: `let { data, form }: PageProps = $props();`, а load
записывается как `export const load: PageServerLoad = async (event) => {...}`, оба типа из
`./$types`. Переменная `catch` имеет тип `unknown`; разбирайте неудачный запрос через
`apiStatus(err)` и `apiErrorBody(err)` из `#lib/api-errors.js`. У эндпоинтов, которые обслуживает
только корпоративный пакет (пользовательские объекты, биллинг, поддержка), есть свой
сгенерированный файл, `frontend/src/lib/enterprise-api-schema.d.ts`, собранный из схемы этого
пакета; его никогда не правят вручную.

Тела запросов тоже типизированы. Тело, собранное из типизированных значений, имеет тип запроса
эндпоинта: аннотируйте переменную или напишите у литерала
`{ ... } satisfies Schemas['LeadPipelineCreateRequest']`. Тело, переданное из формы, значения которой
являются строками, которые API разбирает и проверяет, имеет тип
`FormBody<Schemas['LeadCreateSwaggerRequest']>` из `#lib/api-helpers.js`: он проверяет имена полей и
оставляет значения API. Тело типа `Record<string, unknown>` отклоняется: оно не называет полей,
поэтому в нём нечего проверить.

`pnpm check` завершается скриптом `scripts/api-contract.ts`, который сверяет каждый вызов
`apiRequest` с эндпоинтом, названным его путём: метод должен существовать у эндпоинта, тип ответа,
объявленный вызывающим кодом, должен вмещать ответ эндпоинта, а тело должно соответствовать типу
запроса (`FormBody` может называть только поля, которые принимает эндпоинт, а `FormData` идёт только
на эндпоинт, принимающий multipart). В файлах `.ts` ESLint с учётом типов (`no-unsafe-*`) не даёт
`any`, который возвращает библиотека (`res.json()`, `JSON.parse`, нетипизированный ответ axios),
попасть в код приложения: приведите ответ `.json()` к типу его схемы или разберите его как `unknown`
и проверьте.

Если сгенерированный тип неверен, исправляйте схему, а не фронтенд: набор тестов бэкенда сверяет со
схемой каждый ответ, который видит (см. [Тестирование](testing.md#the-schema-contract)). После
изменения сериализатора, `@extend_schema` у view или эндпоинта перегенерируйте типы из `frontend/`
командой `pnpm api:types` (она запускает drf-spectacular в `backend/`, затем `openapi-typescript`) и
из `mobile/` командой `dart run tool/api_models.dart`, и закоммитьте новые `api-schema.d.ts` и
`schema.g.dart` вместе с изменением.

View, который читает тело, объявляет его через `@extend_schema(request=...)`, а тот, что не читает
ничего, указывает `request=None`; `PUT`, который view применяет с `partial=True`, принимает
`request=Serializer(partial=True)`. drf-spectacular выводит `unable to guess serializer` для каждого
view, тело или ответ которого он не видит, и этот список поддерживается пустым.

## Flutter {#flutter}

```bash
cd mobile
dart format .
flutter analyze --no-fatal-infos
```

`mobile/analysis_options.yaml` подключает `package:flutter_lints/flutter.yaml` без добавленных или
удалённых правил проекта. Ни один из двух workflow GitHub Actions этого репозитория (`tests.yml`,
`codeql-analysis.yml`) вообще не упоминает Flutter, Dart или `mobile/`, поэтому в CI ничто не
проверяет форматирование Dart и чистоту линтера. В отличие от бэкенда, где теперь есть барьер ruff,
запуск этих команд вручную перед открытием PR остаётся единственной проверкой. Полный набор команд,
включая `flutter test`, см. в разделе [Сборка и настройка](../mobile/build-and-configure.md#tests-and-analysis).

Приложение читает ответы API через сгенерированные типы передачи (wire types), а не по ключам.
`tool/api_models.dart` записывает по одному классу на компонент ответа в `lib/data/api/schema.g.dart`
(а корпоративные эндпоинты в `enterprise_schema.g.dart`); каждое поле допускает null и читается
снисходительно, поэтому более старый или более новый сервер приводит к деградации, а не к
исключению. `fromJson` модели начинается с её wire-класса, `final w = api.Lead.fromJson(json);`,
берёт каждое поле из `w` и передаёт вложенный объект его собственной модели через типизированное
поле (`Comment.fromJson(c.json)`). Поле, нужное приложению, но отсутствующее в wire-классе, это
пробел в схеме бэкенда: исправьте схему и перегенерируйте.

Запросы проверяются так же во время выполнения. В отладочных сборках и тестах
`lib/services/api_contract.dart` сверяет каждый вызов `ApiService` с операциями, которые публикует
схема: путь, метод и имя каждого поля тела. `test/flutter_test_config.dart` роняет любой тест,
отправляющий запрос за их пределы, поскольку DRF отвечает 200 на поле тела, которое игнорирует, и
правка пользователя теряется без ошибки.
