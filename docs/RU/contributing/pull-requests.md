# Pull request

## Перед тем как открыть PR {#before-you-open-one}

`CONTRIBUTING.md` (в корне репозитория) описывает процесс, который подразумевает эта страница:
создавайте ветку от `master` с понятным названием, держите изменение сфокусированным и не
смешивайте его с посторонними правками, добавляйте тесты, где это практично, и обновляйте
документацию, когда меняется поведение, установка или публичный API. Документацию правьте в
`docs/EN/` (источник истины) и одновременно обновляйте русский перевод в `docs/RU/`. Чек-лист
из `CONTRIBUTING.md` стоит перечитать прямо перед тем, как открыть PR:

- Изменение сфокусировано и не содержит посторонних правок.
- Нужные проверки бэкенда и фронтенда проходят. Что запускать локально перед push, см. в разделах
  [Настройка окружения разработки](development-setup.md) и [Тестирование](testing.md).
- Тесты покрывают новое или изменённое поведение, где это практично. Если изменение затрагивает
  проверку разрешений, отдельно см. [Правила безопасности](security-rules.md#prove-permission-checks-can-fail).
- Нужные миграции включены. Что происходит, если миграции нет, см. ниже в разделе
  [Что запускает CI](#what-ci-runs).
- Документация обновлена.
- В коммиты не попали учётные данные, токены или приватные данные.

В описании самого PR объясните, что изменилось и почему, как вы это проверяли, и приложите
скриншоты для любого видимого изменения интерфейса.

## Что запускает CI {#what-ci-runs}

`.github/workflows/tests.yml` определяет три задачи, `backend-tests`, `frontend-checks` и
`docs-build`, которые запускаются двумя событиями, оба ограничены одним и тем же списком путей
(`backend/`, `frontend/`, `docs/`, `mkdocs.yml`, `.readthedocs.yaml`, `.coveragerc` или сам файл
workflow): pull request в `master` или **push именно в `master`** (`branches: [master]` у триггера
`push`). Push отдельной feature-ветки ничего из этого не запускает. Вы увидите эти задачи только
после того, как откроете PR в `master`, так что не ждите обратной связи от CI после одного
`git push`.

**`backend-tests`** устанавливает системные библиотеки WeasyPrint, выполняет `uv sync --frozen`
(ставит ровно то, что зафиксировано в `uv.lock`, без повторного разрешения зависимостей), а затем
два шага по порядку:

```bash
uv run python manage.py makemigrations --check --dry-run
uv run pytest -m "not postgres_only" --tb=short -v
```

**Изменение модели без соответствующей миграции роняет первый шаг**, ещё до запуска тестов:
`makemigrations --check --dry-run` завершается с ненулевым кодом, если автодетектор Django находит
изменение модели, которого ещё нет в файле миграции. Создайте и закоммитьте миграцию
(`uv run python manage.py makemigrations`) до push. Что шаг тестов покрывает и что нет, см. в
разделе [Тестирование](testing.md#what-ci-runs). Важно, что эта задача работает на SQLite, поэтому
не проверяет ни одной политики RLS, что бы вы ни изменили. При push в `master` (но не в
pull request'ах) эта задача также заново генерирует и коммитит бейдж покрытия.

**`frontend-checks`** устанавливает зависимости через `pnpm install --frozen-lockfile`, затем
запускает проверку Prettier (расхождение форматирования выдаётся как предупреждение, а не ошибка:
см. [Стиль кода](code-style.md#frontend)), `pnpm eslint .` (вот он роняет задачу), `pnpm check`
(svelte-check) и наконец `pnpm build`.

**`docs-build`** устанавливает группу зависимостей `docs` (`uv sync --frozen --group docs`) и
выполняет

```bash
uv run mkdocs build --strict -f ../mkdocs.yml -d site
uv run mkdocs build --strict -f ../mkdocs.ru.yml -d site-ru
```

`--strict` роняет сборку на сломанном пункте навигации или внутренней ссылке на несуществующую
цель. Следующий шаг запускает `common/tests/test_docs_build_excludes_internal.py`, который ещё раз
собирает оба сайта и проверяет, что ничего из `docs/superpowers/` или `docs/EN/design/` (внутренние
спецификации и планы, исключённые через `exclude_docs` в `mkdocs.yml`) не попало в результат. Если
вы добавляете страницу документации, те же две команды можно сначала запустить локально; вызов через `uv run --group docs` описан в разделе
[Настройка окружения разработки](development-setup.md#backend).

## Чего ждать от ревью {#review-expectations}

Стиль Python в бэкенде CI не навязывает (почему, см. в разделе [Стиль кода](code-style.md#python)).
Ревьюер всё равно может попросить привести форматирование к окружающему коду, даже если ни один бот
этого автоматически не отметит. Стиль фронтенда в основном проверяется (ошибки ESLint и ошибки типов
блокируют сборку; расхождения Prettier дают только предупреждение). Для Flutter CI нет вообще,
поэтому `dart format .` и `flutter analyze` перед открытием PR остаются единственной проверкой
изменений в мобильном приложении.

Помимо стиля, ревью будет сосредоточено на двух вещах, которые в этом коде не обсуждаются: каждый
новый или изменённый queryset фильтруется по `org=request.profile.org` (или покрыт RLS с тестом,
который это доказывает, см. [Добавление модели с привязкой к организации](adding-an-org-scoped-model.md)),
и каждую новую или изменённую проверку разрешений можно доказать в обе стороны. См.
[Правила безопасности](security-rules.md#prove-permission-checks-can-fail). Чаще всего здесь
просят добавить к PR, который добавляет эндпоинт, тест не только на успешный сценарий, но и на
отклонённый или запрещённый.
