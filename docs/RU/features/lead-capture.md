# Сбор лидов

Лиды приходят в BottleCRM извне тремя путями: через [веб-формы](../integrations/web-forms.md),
встроенные в ваш сайт, через **вебхуки лидов**, на которые отправляют данные другие инструменты, и
через адреса для лидов, которые превращают письма в лиды. Все три пути проходят через один сервис
(`backend/leads/intake.py`, `receive_lead`), поэтому повторное обращение распознаётся одинаково,
каким бы путём оно ни пришло.

На этой странице описаны вебхуки, экраны настроек для управления ими и то, что каждый путь делает с
пришедшим лидом.

## В приложении {#in-the-app}

**Веб: Настройки, Сбор лидов** (`/settings/lead-capture`) собирает в одном месте:

- **Вебхуки** (только для администраторов). В каждой строке видны название, пресет, источник,
  который он записывает, его состояние («Выключен», «Ждёт первой отправки» или «Принимает») и то,
  была ли отклонена последняя отправка. **Новый вебхук** запрашивает название, пресет и
  записываемый источник. Затем URL и ключ показываются один раз, с кнопками копирования.
- **Веб-формы**, которые создают лиды, со ссылкой на страницу каждой формы.
- **Адреса для лидов** (входящие почтовые ящики, настроенные на создание лидов), со ссылкой на
  раздел «Входящая почта».

Страница вебхука состоит из трёх частей:

- **Куда отправлять лиды**: URL с кнопкой копирования, последние четыре символа ключа, заметки по
  настройке для пресета и действия **Отправить тест**, **Выключить** (или включить),
  **Заменить ключ** и **Удалить**.
- **Во что превращается отправка**: название, источник, подысточник, ответственный (никто или один
  участник), теги и редактор сопоставления полей.
- **Доставки**: 50 последних отправок, новые сверху, у каждой результат, время, ошибка и ссылка на
  лид, который она создала или с которым объединилась.

**Телефонное приложение: Настройки, Сбор лидов** показывает те же вебхуки. Администратор может
скопировать URL, заменить ключ (новый ключ показывается один раз), выключить или включить вебхук и
просмотреть его доставки. Создание вебхука и редактирование его сопоставления доступны только в
вебе.

Участники видят веб-формы и адреса для лидов, но не вебхуки: настройки вебхука говорят, откуда
приходят лиды организации и кто их получает, поэтому все маршруты вебхуков, включая чтение,
доступны только администраторам.

## Отправка на вебхук {#sending-to-a-webhook}

```
POST /api/public/leads/<webhook id>/
```

URL никогда не меняется. Передайте его инструменту, который должен отправлять лиды, а ключ укажите
одним из способов ниже. Они проверяются в этом порядке (решает первый найденный):

1. `Authorization: Bearer <key>`. Используйте этот способ всегда, когда инструмент позволяет задать
   заголовок.
2. Собственные учётные данные пресета: поле `google_key` у Google Ads или заголовок
   `Tally-Signature` у Tally (см. [Пресеты](#presets)).
3. `?key=<key>` в URL, для инструментов, которые принимают только URL. Прокси записывают в журналы
   полные URL, поэтому лучше использовать заголовок; BottleCRM вырезает ключ из собственных
   журналов, а в разделе
   [Усиление безопасности](../self-hosting/security-hardening.md#public-link-tokens-in-logs)
   показано, как сделать то же в вашем обратном прокси.

Ключ показывается целиком только при создании вебхука и при замене ключа. После этого приложение
показывает его последние четыре символа. **Заменить ключ** выпускает новый ключ, а старый
продолжает работать 7 дней, чтобы отправляющий инструмент можно было обновить без потери лидов.
Повторная замена в течение этих 7 дней сразу прекращает действие более старого ключа. Ключ может
создавать лиды только в этой организации и больше ничего.

Тело запроса: объект JSON или тело в формате form-encoded, не больше 64 КБ и с вложенностью не
глубже 32 уровней.

### Ответы {#replies}

| Статус | Тело | Когда |
|---|---|---|
| 201 | `{"result": "created", "lead": "<id>"}` | Новый лид |
| 200 | `{"result": "merged", "lead": "<id>"}` | Повторное обращение, объединённое с существующим лидом (или записанное на контакт, которым стал конвертированный лид) |
| 200 | `{"result": "duplicate", "lead": "<id>"}` | Та же отправка ещё раз (тот же внешний id): ничего не изменилось |
| 200 | `{"result": "test"}` | Тестовая отправка от отправителя: записана в журнал, лид не создан |
| 400 | `{"result": "rejected", "detail": ..., "errors": {"<field>": [...]}}` | Сопоставленное значение недопустимо для своего поля (email, который не является email, номер телефона с буквами). Значение, которое лишь слишком длинное, не отклоняется: оно обрезается по размеру поля и целиком сохраняется в заметках лида (слишком длинный email или номер телефона не попадает в своё поле и сохраняется в заметках) |
| 400 | `{"detail": ...}` | Тело не является объектом JSON или формой, повреждено или вовсе не содержит полей лида |
| 401 | `{"detail": "Wrong key."}` | Ключа нет или он неверный |
| 403 | `{"detail": "Leads are switched off for this organization."}` | В организации выключен модуль «Лиды» (это узнаёт только вызывающий с ключом) |
| 404 | `{"detail": "Not found."}` | Такого вебхука нет или он выключен. Эти два случая намеренно неразличимы |
| 413 | `{"detail": "The body is larger than 64 KB."}` | |
| 429 | `{"detail": "Too many posts. Try again later."}`, с `Retry-After` | Отправка с ключом сверх 120 в минуту или 5000 в день для этого вебхука; или слишком много отклонённых отправок с одного адреса (неизвестный вебхук, неверный ключ, неверная подпись) |
| 500 | `{"detail": "The lead could not be saved. Try again."}` | Ничего не сохранено; отправители, которые повторяют запрос при 5xx (Google Ads, Tally), попробуют снова |

Ответ никогда не содержит ничего о лиде, кроме его id.

Каждая отправка с ключом записывается как доставка, включая отклонённые (недопустимое значение,
отправка сверх лимита, выключенный модуль «Лиды»), поэтому лид, который не пришёл, оставляет след
на странице вебхука вместе с отправленным телом (`google_key` от Google Ads заменяется на
`[Filtered]`). Отправка без ключа ничего не записывает: ни доставки, ни отметки «последняя отправка
отклонена», и она не расходует лимит вебхука, так что тот, кто знает только URL, не может скрыть
или вытеснить отправки настоящего отправителя. Такие отказы вместо этого ограничиваются по адресу
отправителя, и отправку с ключом этот лимит никогда не задерживает, поскольку инструменты вроде
Google Ads отправляют данные многих аккаунтов с общих адресов. Доставки содержат персональные
данные, поэтому доставка старше 30 дней удаляется, когда вебхук в следующий раз получает отправку
или когда администратор читает его (`GET /api/leads/intakes/<id>/` или его `deliveries/`, которые
запрашивает страница вебхука и в вебе, и на телефоне).

## Пресеты {#presets}

Пресет задаёт новому вебхуку начальное сопоставление и сообщает BottleCRM, куда этот инструмент
кладёт собственный id лида, признак теста, временную метку и ключ.

| Пресет | Id лида (проверка дубликатов) | Тестовые отправки | Временная метка | Ссылка (`source_ref`) | Ключ |
|---|---|---|---|---|---|
| Любой инструмент (`generic`) | `external_id` | нет | `occurred_at` | нет | заголовок или `?key=` |
| Форма лида Google Ads (`google_ads`) | `lead_id` | `is_test: true` | `lead_submit_time` | `campaign_id` | `google_key` в теле |
| Tally (`tally`) | `data.responseId` | нет | `data.createdAt` | `data.formId` | `Tally-Signature` |
| Gravity Forms (`gravity_forms`) | `id` | нет | `date_created` | `form_id` | заголовок или `?key=` |

- **Google Ads**: в настройках вебхука формы лида вставьте URL, а ключ укажите в поле **Key**.
  Google возвращает его как `google_key` в каждой отправке. Сопоставление читает ответы в
  `user_column_data` по `column_id`: имя (или полное имя), фамилия, email (или рабочий email),
  телефон (или рабочий телефон), компания, должность, город, регион и почтовый индекс. Остальные
  ответы сохраняются в тексте обращения.
- **Tally**: в интеграции вебхука формы вставьте URL и задайте ключ как секрет подписи. Tally
  подписывает каждое тело с помощью HMAC-SHA256 и отправляет подпись в кодировке base64 в
  `Tally-Signature`. Ключи вопросов в Tally разные в каждой форме, поэтому сопоставление находит
  вопросы про email и телефон по типу, а вопросы про имя, компанию и сообщение по их обычным
  подписям (`First name`, `Last name`, `Full name`, `Name`, `Company`, `Message`). Ответы с выбором
  записываются как текст варианта.
- **Gravity Forms**: когда дополнение Webhooks Add-On отправляет все поля, входные данные
  индексируются по id поля, и пресет сопоставляет поле Name с id 1 (`1.2` обращение, `1.3` имя,
  `1.6` фамилия). Id остальных полей вашей формы сопоставьте сами или выберите в Gravity Forms
  **Select Fields** и назовите каждое поле по полю лида (`email`, `phone`, `company_name`): тогда
  сопоставление не нужно.
- **Любой инструмент**: сопоставление изначально пустое. Телу, у которого имена верхнего уровня
  совпадают с именами полей лида (`email`, `first_name`, `phone`), сопоставление не нужно; в
  остальных случаях добавьте строки.

## Сопоставление {#the-mapping}

Каждая строка говорит, какое поле отправки заполняет какое поле лида:
`{"from": "<path in the post>", "to": "<lead field>"}`.

- **To**: одно из полей лида, которые есть у веб-форм (`salutation`, `first_name`, `last_name`,
  `email`, `phone`, `company_name`, `job_title`, `website`, `title`, `description`, `city`,
  `state`, `country`, `postcode`, `industry`), или `custom_fields.<key>` для одного из ваших
  дополнительных полей лида. Больше ничего заполнить нельзя: ответственного, статус, этап и сумму
  отправитель никогда не задаёт. Сопоставление, в котором названо что-то другое, отклоняется при
  сохранении.
- **From**: путь через точку, например `contact.email`. На списке шаг выбирает первый элемент, у
  которого `column_id`, `key`, `label`, `name` или `type` совпадает с ним (без учёта регистра), и
  читает `string_value` или `value` этого элемента; число выбирает элемент по позиции. Ключ, который
  сам содержит точки (`1.3`), сначала сравнивается целиком.
- Строки читаются по порядку, и поле заполняет первая строка, которая нашла значение, поэтому
  запасная строка (рабочий email после email) заполняет только то, что первая оставила пустым.
- Имена верхнего уровня, совпадающие с полем лида, заполняют его, если этого ещё не сделала ни одна
  строка.
- `country` и `industry` принимают свой код или название (`GB` или `United Kingdom`).

**Ничего не теряется.** Всё, что сопоставление не использует (кроме собственных id, временной метки
и ключа пресета), записывается в лид строками `Label: value`: в заметки нового лида, после
сопоставленного сообщения, если оно есть, и в обращение при каждом поступлении.

## Что происходит с пришедшим лидом {#what-happens-to-an-arriving-lead}

Одни и те же правила действуют для веб-форм, вебхуков и адресов для лидов.

**Поиск совпадения** среди лидов организации в любом статусе, по порядку:

1. Тот же отправитель и тот же id лида (`lead_id` вебхука, `responseId` и так далее). Это точный
   повтор: ответ `duplicate`, ничего не меняется.
2. Тот же адрес email без учёта регистра и окружающих пробелов.
3. Тот же номер телефона в международном формате. Номера сравниваются в формате E.164 и читаются со
   страной организации по умолчанию, поэтому `+1 (555) 123-4567` и `555-123-4567` совпадают в
   организации из США. Номер, который так прочитать нельзя (местный номер в организации без
   заданной страны), никогда ничего не объединяет: ошибочное объединение потеряло бы данные, а
   пропущенное лишь оставит дубликат, который покажет панель дубликатов.

**Совпадения нет**: создаётся новый лид со статусом «Назначен», источником, подысточником и тегами
вебхука, id лида и ссылкой; он назначается ответственному вебхука, если этот участник активен.
Ответственному приходит письмо о том, что лид теперь его.

**Совпадение есть**, в зависимости от лида:

- **Открытый** (назначен, в работе, возвращён в работу): объединяется. Пустые поля заполняются, и
  ничего не перезаписывается, так что тот, кто знает чей-то адрес email, не может переписать его
  запись. Совпадение только по номеру телефона никогда не забирает пришедший адрес email, и адрес,
  который уже есть у другого лида, никогда не копируется. Email или номер телефона, отличающийся от
  указанного в лиде, не теряется: он записывается в обращение как `Email: ...` или `Phone: ...`.
  Теги вебхука добавляются, обращение записывается в хронологию лида, а активным ответственным
  лида приходит письмо о том, что человек обратился снова. Статус, ответственный, источник и
  воронка остаются прежними. Если у лида ещё не было id лида, он получает этот.
- **Закрытый**: то же самое, и его статус становится «Возвращён в работу», то есть он снова открыт.
  Лид на выигрышном или проигрышном этапе воронки переходит на первый открытый этап этой воронки.
- **Конвертированный**: новый лид не создаётся, и ни одно поле старого не заполняется (он получает
  id лида, если его не было). Обращение записывается в хронологию контакта, которым стал лид
  (контакт находится по адресу email лида и связывается с компанией этого контакта; если такого
  контакта нет, обращение записывается на сам лид), и об этом сообщается ответственным контакта.

**Повторы.** Отправка на вебхук с id лида, который вебхук уже получил и разместил на лиде, получает
ответ `duplicate` с этим лидом, даже если первая отправка объединилась с лидом, у которого уже был
id другого отправителя. Отправки на один вебхук принимаются по одной, поэтому две копии отправки,
пришедшие одновременно, дают один лид и одно обращение.

**Каждое поступление является обращением.** Каждое из них, новый лид или объединение, записывается
как [взаимодействие](../api/interactions.md) `enquiry` в хронологии лида (или контакта, для
конвертированного лида): входящее, с формой, вебхуком или адресом в качестве темы и с сообщением и
строками `Label: value`, если они есть, в качестве текста, до 10 000 символов. `duplicate` ничего не
записывает. Обращения доступны только для чтения и никогда не считаются ответом на лид. Обращения,
пришедшие до появления этой функции, являются комментариями и ими остаются.

Каждое поступление обновляет время **последнего обращения** лида (`last_enquiry_at`).

**Запоздавшие отправки.** Если собственная временная метка отправки старше 24 часов (отправитель
догоняет после сбоя или импортирует старые ответы формы), лид создаётся или объединяется, как
описано выше, но правила автоматизации не запускаются и никому не отправляются письма. Временем
последнего обращения становится собственное время отправки.

**Веб-формы** отличаются в двух отношениях: у веб-формы нет собственного id лида, поэтому она
никогда не отвечает `duplicate`, и она сохраняет собственное уведомление, одно письмо списку
получателей формы и ответственным лида (с 1.42.0 для конвертированного лида ответственным
контакта), вместо писем, описанных выше.

## Лимиты и настройки {#limits-and-settings}

| Настройка | По умолчанию | Что ограничивает |
|---|---|---|
| `LEAD_INTAKE_THROTTLE_MINUTE` | `120/min` | Отправки на вебхук в минуту от всех отправителей вместе |
| `LEAD_INTAKE_THROTTLE_DAY` | `5000/day` | Отправки на вебхук в день |

Оба лимита учитывают только отправки с ключом. Отклонённые отправки ограничиваются по адресу
отправителя (60 в минуту; чтобы изменить, задайте `lead_intake_refused_ip` в
`REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]`). Чтобы все они действовали для всех воркеров, нужен
общий кеш (`CACHE_URL`).

## API {#api}

Все маршруты только для администраторов; участник получает 403, а id вебхука другой организации
даёт 404. При выключенном модуле «Лиды» маршруты отвечают 404 модуля.

| Маршрут | Что делает |
|---|---|
| `GET /api/leads/intakes/` | `{"intakes": [...]}`, по названию |
| `POST /api/leads/intakes/` | Создание; ответ содержит `key`, один раз |
| `GET`, `PATCH`, `DELETE /api/leads/intakes/<id>/` | Чтение, изменение, удаление (204) |
| `POST /api/leads/intakes/<id>/key/` | Замена ключа; ответ содержит новый `key`, один раз |
| `GET /api/leads/intakes/<id>/deliveries/` | `{"deliveries": [...]}`, 50 последних за 30 дней |
| `POST /api/leads/intakes/<id>/test/` | Записывает доставку `test` (отклоняется, пока вебхук выключен); отвечает `{"delivery": {...}}` |

Вебхук: `id`, `name`, `preset` (`generic`, `google_ads`, `tally`, `gravity_forms`), `url`,
`key_hint` (последние четыре символа), `key` (только при создании и замене), `mapping`,
`default_source` (ключ из активных источников лидов организации или пусто; сохранённый источник,
который с тех пор выведен из употребления, сохраняется), `source_detail`, `tags` (id тегов),
`assignee` (id профиля участника или null; деактивированного участника выбрать нельзя),
`assignee_details`, `is_active`, `last_received_at`, `last_error`, `created_at`. Новый вебхук, для
которого не заданы сопоставление или источник, начинает с тех, что заданы в его пресете. `key`,
`org` и две отметки о доставках записать нельзя.

Доставка: `id`, `received_at`, `result` (`created`, `merged`, `duplicate`, `test`, `rejected`),
`lead` (id или null), `external_id`, `error`.

## Адреса для лидов {#lead-addresses}

Адрес для лидов: это [входящий почтовый ящик](../integrations/inbound-email.md), настроенный на
создание лидов (`creates: "leads"`) вместо обращений. Перешлите на него запрос клиента или укажите
его порталу или форме на сайте как адрес для уведомлений, и каждое письмо станет лидом через тот же
сервис, что и у вебхуков, так что описанные выше
[поиск совпадений и объединение](#what-happens-to-an-arriving-lead) действуют без изменений.

**Настройка.** На странице **Настройки, Входящая почта** администратор создаёт адрес, который
создаёт лиды, указывая источник, который записывают его лиды (`email`, если не выбран другой),
подысточник и ответственного (ответственного по умолчанию для ящика), которому принадлежит каждый
лид, созданный этим адресом. Чтобы владение следовало за адресом, заведите по адресу на каждого
сотрудника. Если у сервера есть входящий домен (`INBOUND_EMAIL_DOMAIN`), **Сгенерировать адрес**
создаёт адрес вроде `acme-k3x9q2@in.example.com`, который сразу работает: каждый сгенерированный
адрес принимается через общий вебхук сервера, `POST /api/cases/inbound/email/`
([Сгенерированные адреса](../integrations/inbound-email.md#generated-addresses)). В противном случае
введите собственный адрес и доставляйте его почту через Amazon SES, Postmark или Mailgun на
собственный вебхук ящика, `POST /api/cases/inbound/<mailbox id>/`, как описано в разделе
[Входящая почта](../integrations/inbound-email.md#providers).

### Кто становится лидом {#who-the-lead-is}

Отправитель не всегда тот, кто обращается, поэтому каждое письмо разбирается в таком порядке:

1. **В пересланном письме** ищется исходное сообщение внутри него: «Forwarded message» в Gmail,
   «Begin forwarded message» в Apple Mail и «Original Message» или строка правила в Outlook, когда
   тема начинается с `Fwd:` или `FW:`. Пересылка пересылки прослеживается до оригинала. Собственная
   приписка пересылающего над ним не сохраняется.
2. **Автоматический отправитель** никогда не становится лидом. Отправитель считается
   автоматическим, если его адрес начинается с `noreply`, `no-reply`, `donotreply`,
   `do-not-reply`, `notifications`, `notification`, `alerts` или `mailer` (до любого `+tag`) или
   если письмо содержит `Auto-Submitted` (любое значение, кроме `no`) или `Precedence: bulk`, `list`
   или `junk`. Так приходят уведомления порталов. Тогда email лида берётся из `Reply-To`, а иначе
   это первый адрес в теле письма (предпочтительно на строке, подписанной как email), который не
   является ни одним из этих: адрес отправителя, адрес в домене отправителя (так пропускается
   `support@` в подвале портала), любой из входящих адресов организации, адрес участника
   организации, адрес получателя письма или другой адрес в стиле no-reply. Имя берётся из строки
   `Name:` (или строк `First name:` и `Last name:`), а **домен отправителя** (`portal.example.com`)
   становится подысточником лида.
3. **Письмо человека**: лидом становится `Reply-To`, если он отличается от `From` (и не является
   адресом в стиле no-reply или одним из адресов организации), иначе `From`, а его отображаемое имя
   становится именем. Подысточник ящика сохраняется.

**Участник никогда не становится лидом.** Письмо от участника организации (любого профиля,
активного или нет), которое не является пересылкой, отбрасывается, как и письмо, у которого
исходный отправитель или адрес, названный в качестве лида, принадлежит участнику.

### Что получает лид {#what-the-lead-gets}

- **Email и имя**, как описано выше. Адрес, который не является корректным email, не используется.
- **Телефон**: первый номер на строке, подписанной как телефон (`Phone`, `Tel`, `Mobile`, `Cell`,
  `WhatsApp`, `Contact number`), а иначе первый в теле письма, который читается как номер для
  страны организации по умолчанию (любой международный номер с `+` читается и без неё).
  Бесплатные и платные номера пропускаются, поскольку в уведомлении это номера самого портала.
  Поиск идёт только по первым 200 строкам тела (и первым 20 000 символам), и проверяется не больше
  20 номеров-кандидатов.
- **Название**: тема (для пересылки тема оригинала), до 255 символов.
- **Заметки**: тело в виде простого текста (письмо только в HTML конвертируется) без цитируемой
  переписки: удаляются `On ... wrote:` и всё ниже, заголовок ответа Outlook и строки с `>`. Не
  больше 20 000 символов.
- **Вложения** становятся вложениями лида, каждое с тем же ограничением размера, что и при загрузке
  (25 МБ); файл большего размера пропускается, а лид всё равно создаётся.
- **Ответственный, источник и подысточник** берутся из ящика, как описано выше; **id лида**
  (`external_id`) это `Message-ID` письма, а `external_source` равен `email:<mailbox id>`.
- **Нет ни адреса email, ни номера телефона**: лид всё равно создаётся из темы и тела, и его заметки
  начинаются с «No email address or phone number was found in this email.» Такой лид ни с чем не
  совпадает, поэтому два таких лида остаются двумя лидами: автоматическое уведомление никогда не
  собирает всех в один общий лид «noreply».

Ответственному приходит письмо о новом лиде, а ответственным объединённого лида о том, что человек
обратился снова, как и для вебхуков. Заголовок `Date` письма не используется как его время (это
часы отправителя): адрес для лидов всегда считает, что письмо пришло сейчас.

### Что игнорируется {#what-is-ignored}

| Игнорируется | Почему |
| --- | --- |
| Возвраты (отчёты о статусе доставки) | Это не обращение |
| Письмо с самого адреса или с любого из входящих адресов организации | Петля |
| Письмо, которое провайдер пометил как спам, вирус или подделку отправителя | Вердикт SES по спаму или вирусам `FAIL` или DMARC `FAIL`, когда домен отправителя требует `quarantine` или `reject`; `X-Spam-Status: Yes` у Postmark, `X-Mailgun-Sflag: Yes` у Mailgun |
| Собственное письмо участника | См. выше |
| То же письмо ещё раз | Каждое письмо записывается один раз на организацию по его `Message-ID` (по хешу содержимого, если его нет), поэтому повторная доставка от провайдера никогда не создаёт и не объединяет лид дважды, а одно и то же письмо на два адреса для лидов одной организации приходит один раз |
| Больше 300 писем в день | На адрес, за последние 24 часа, считая письма, которые создали лид или объединились с ним; число меняет `INBOUND_EMAIL_DAILY_LIMIT`. Письмо сверх лимита не записывается, поэтому то же письмо ещё может прийти на другие адреса для лидов организации |

В отличие от адресов для обращений, адреса для лидов принимают письма с `Auto-Submitted`, массовые
рассылки, письма списков рассылки и `X-Autoreply`, потому что уведомления порталов содержат эти
заголовки, а адрес для лидов никогда не отвечает, так что защищаться от почтовой петли не нужно.
Адрес для лидов также никогда не предлагается как `Reply-To` в письмах по обращению.

Каждое письмо на адрес для лидов оставляет в ящике строку `EmailMessage` (по ней определяется его
время «последнего получения»), в которой нет ни отправителя, ни темы, ни тела: они хранятся в лиде,
и удаление лида не должно оставлять копию. Игнорируемые письма тоже оставляют такую строку, кроме
писем сверх дневного лимита или сверх такого же числа игнорируемых писем за день; собственное
письмо участника записывается только для этого одного адреса, а не для всей организации. Одно и то
же письмо, отправленное на адрес для лидов и на адрес для обращений одной организации, доходит до
обоих.

**Модуль «Лиды» выключен.** Адрес для лидов принимает почту, только пока включён модуль «Лиды», а
адрес для обращений, только пока включён модуль «Обращения»; на почту для выключенного модуля
приходит такой же ответ, как для неизвестного адреса. Выключить «Лиды» нельзя, пока активен хотя бы
один адрес для лидов (`Leads still receives email at ...`), так же как «Обращения» при активных
адресах для обращений.

### API адресов для лидов {#lead-address-api}

[Эндпоинты входящих ящиков](../integrations/inbound-email.md#configuring-a-mailbox) содержат поля
адреса для лидов и работают, пока включён модуль «Обращения» или «Лиды»:

| Поле | Примечания |
| --- | --- |
| `creates` | `tickets` (по умолчанию) или `leads`. Выбор значения, модуль которого выключен, даёт `400`. |
| `lead_source` | Ключ из активных [источников лидов](../api/leads.md) организации; по умолчанию `email`. Источник, выведенный из употребления позже, остаётся у ящика. |
| `lead_source_detail` | Подысточник, до 100 символов. Для автоматической почты вместо него записывается домен отправителя. |
| `is_generated` | Только чтение: адрес создан во входящем домене сервера. |
| `generate_address` | Только при создании, только запись: `true` создаёт адрес вместо введённого вручную. |

`GET /api/cases/mailboxes/` также возвращает `generated_domain`: входящий домен или `null`, если
этот сервер не создаёт адреса.
