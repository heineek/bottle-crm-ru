# Management-команды

Все команды ниже принадлежат самому BottleCRM. Пакет `common/management/commands/` содержит ровно
эти пять файлов. Если запустить `uv run python manage.py help` из `backend/`, всё, что находится вне
раздела `[common]`, относится к самому Django или к установленным сторонним пакетам
(`django`, `auth`, `contenttypes`, `sessions`, `staticfiles`, `django_ses`, `drf_spectacular`,
`rest_framework`, `token_blacklist`); ничего из этого не специфично для проекта, поэтому здесь не
повторяется. Любую команду запускайте из `backend/` через `uv run python manage.py <command>` (или,
для стека Docker, `docker compose exec backend python manage.py <command>`).

## manage_rls {#manage_rls}

Диагностика Row-Level Security только на чтение. Ни один из трёх флагов не изменяет базу данных.
Политики RLS включаются и выключаются миграциями Django через `get_enable_policy_sql()`, но никогда
этой командой (собственный docstring модуля прямо об этом говорит). Команда проверяет таблицы из
`ORG_SCOPED_TABLES` (`common/rls/__init__.py`), где на момент написания **61 запись**. В `CLAUDE.md`
репозитория до сих пор написано 24; эта цифра устарела, и число намеренно не повторяется нигде, кроме
самого `ORG_SCOPED_TABLES`, чтобы оно снова не разошлось.

```bash
uv run python manage.py manage_rls --status
uv run python manage.py manage_rls --test
uv run python manage.py manage_rls --verify-user
```

| Флаг | Что делает |
| --- | --- |
| `--status` | Для каждой таблицы из `ORG_SCOPED_TABLES` запрашивает `pg_class.relrowsecurity`/`relforcerowsecurity` и выводит `ENABLED (forced)`, `disabled` или `TABLE NOT FOUND`, а также является ли подключённая роль суперпользователем. Это также поведение **по умолчанию**: `manage_rls` без флагов выполняет `--status`. |
| `--test` | Выбирает две организации (предпочитая те, где действительно есть записи `Lead`), по очереди задаёт контекст RLS для каждой и считает видимые лиды, затем задаёт пустой контекст и считает снова. Ноль записей без контекста и ненулевое число с реальным контекстом означает, что изоляция работает; ненулевое число записей без контекста это предупреждение, а не ошибка, поскольку некоторые политики намеренно допускают пустой контекст. |
| `--verify-user` | Запрашивает в `pg_user` значения `usesuper`/`usecreatedb` для подключённой роли и, если роль является суперпользователем, выводит явное `WARNING: Superusers bypass RLS!` с SQL для исправления. |

Здесь описано только то, что делает сама команда. Почему роль суперпользователя молча обходит все
политики, как создать правильно ограниченную роль и что на самом деле доказывает вывод каждого флага,
описано в разделе [PostgreSQL и RLS](../self-hosting/postgresql-and-rls.md#verifying-isolation).

## seed_data {#seed_data}

Генерирует большой случайный набор данных (компании, контакты, лиды, сделки, обращения, задачи, счета
и многое другое) для одной или нескольких организаций, целиком из подобранных вымышленных имён и
названий компаний и зарезервированных демонстрационных доменов (`example.com`/`.example`), так что
ничего из созданного не похоже на реального человека или бизнес. Первая создаваемая организация
(индекс 0 в `--orgs`) всегда называется `MicroPyramid`, именно для того, чтобы в локальной разработке
было стабильное имя организации для входа через `devlogin --org MicroPyramid` (см. ниже). При запуске
по умолчанию с одной организацией повторный запуск команды с тем же `--email` переиспользует
существующих пользователя, организацию и профиль, а не создаёт дубликаты; `create_org` выполняет
`Org.objects.get_or_create(name="MicroPyramid", ...)`. Эта гарантия переиспользования касается только
индекса 0: любая организация после первой (`--orgs 2` и больше) при каждом запуске получает имя,
случайно выбранное из набора названий компаний, поэтому повторный запуск с `--orgs 2` обычно
накапливает дополнительные организации, а не переиспользует вторую из предыдущего запуска.

```bash
uv run python manage.py seed_data --email you@example.com
uv run python manage.py seed_data --email you@example.com --orgs 2 --leads 100 --seed 42
uv run python manage.py seed_data --email you@example.com --clear --no-input
```

| Флаг | По умолчанию | Что делает |
| --- | --- | --- |
| `--email` | `aswin.1231@gmail.com` | Email пользователя-администратора, которого нужно создать (или переиспользовать) как профиль администратора заполняемой организации. |
| `--orgs` | `1` | Число создаваемых организаций. |
| `--users-per-org` | `3` | Число дополнительных пользователей без прав администратора в каждой организации. |
| `--leads` | `20` | Лидов на организацию. |
| `--accounts` | `10` | Компаний на организацию. |
| `--contacts` | `15` | Контактов на организацию. |
| `--opportunities` | `10` | Сделок на организацию. |
| `--cases` | `5` | Обращений на организацию. |
| `--tasks` | `10` | Задач на организацию. |
| `--goals` | `8` | Целей продаж на организацию. |
| `--teams` | `2` | Команд на организацию. |
| `--tags` | `5` | Тегов на организацию. |
| `--products` | `20` | Товаров на организацию. |
| `--invoices` | `50` | Счетов на организацию. |
| `--estimates` | `15` | Коммерческих предложений на организацию. |
| `--recurring-invoices` | `5` | Регулярных счетов на организацию. |
| `--invoice-templates` | `3` | Шаблонов счетов на организацию. |
| `--currency` | `USD` | Валюта организации по умолчанию; допустимы только значения из `CURRENCY_CODES`. |
| `--country` | `US` | Код страны организации по умолчанию; также выбирает локаль Faker для генерируемых имён и адресов (для кода без сопоставления используется `en_US`). |
| `--seed` | нет | Начальное значение генератора случайных чисел для воспроизводимого запуска. |
| `--password` | `testpass123` | Пароль, который получают вновь созданные пользователи. |
| `--clear` | выключен (флаг) | Удаляет существующие данные CRM перед заполнением, но **не** пользователей, организации и профили. Запрашивает подтверждение, если не указан также `--no-input`. Это отдельная, более широкая операция, чем очистка демонстрационных данных отраслевого пакета (см. [Демоданные и отраслевые пакеты](../getting-started/demo-data.md#clearing-sample-data)), и она не ограничена записями, созданными пакетами. |
| `--no-input` | выключен (флаг) | Пропускает запрос подтверждения для `--clear`. |

Пошаговое описание, включая то, как выглядит полностью заполненная организация и как поверх неё
накладываются отраслевые пакеты, приведено в разделе
[Демоданные и отраслевые пакеты](../getting-started/demo-data.md).

## devlogin {#devlogin}

Выпускает пару JWT access/refresh для существующего пользователя прямо из командной строки, без
OAuth-провайдера, без исходящей почты и без обращения из браузера. **Отказывается запускаться, если
`settings.DEBUG` не равен `True`**: самое первое, что делает `handle()`, это выбрасывает `CommandError`.
То есть в любом окружении с `DEBUG=False` команда выводит ошибку и завершается с ненулевым кодом, а не
молча ничего не делает.

```bash
uv run python manage.py devlogin <email> --org <name-or-uuid>
uv run python manage.py devlogin <email> --create
```

| Аргумент | Что делает |
| --- | --- |
| `email` (позиционный, обязательный) | Пользователь, для которого выпускается токен. |
| `--org` | Необязательное имя или UUID организации. **Сначала ищет по id, затем по имени**: пробует `Org.objects.get(id=org_arg)` и только при неудаче (не найдено или `org_arg` вообще не является корректным UUID) ищет совпадение по `Org.name`. Если это имя носят несколько организаций, команда сразу отказывается, а не угадывает; в этом случае передайте id. У пользователя уже должен быть **активный** `Profile` в найденной организации. Команда его не создаёт и, если его нет, выбрасывает `CommandError` с указанием пары пользователь/организация. |
| `--create` | Создаёт пользователя (со случайным паролем, который сразу отбрасывается), если пользователя с таким email ещё нет. Создаётся только запись `User`. На требование к `Profile` выше это не влияет; только что созданному пользователю по-прежнему нужен `Profile` в целевой организации, чтобы `--org` для него сработал. |

При успехе команда выводит access-токен и refresh-токен, UUID организации, если был указан `--org`
(токен, выпущенный таким образом, уже содержит claim `org_id`, поэтому дополнительный вызов
переключения организации не нужен), и фрагмент `localStorage.setItem(...)` для консоли браузера. Один
этот фрагмент **не** выполняет вход в само приложение на SvelteKit; какие cookie на самом деле
проверяет `hooks.server.ts`, описано в разделе
[Использование токенов в браузере](../getting-started/first-sign-in.md#using-the-tokens-in-the-browser).
Полное пошаговое описание, включая то, что происходит вообще без `--org`, приведено в разделе
[Первый вход: локальная разработка](../getting-started/first-sign-in.md#local-development-devlogin).

## create_default_admin {#create_default_admin}

Создаёт суперпользователя Django, но только если ни одного ещё нет; `User.objects.filter(is_superuser=
True).exists()` превращает всю команду в пустую операцию, если суперпользователь найден, поэтому её
безопасно запускать при каждом старте. Аргументов у неё нет совсем (`add_arguments` не
переопределён). Она читает `ADMIN_EMAIL` и `ADMIN_PASSWORD` напрямую через `os.environ.get`, независимо
от `crm/settings.py` (`ADMIN_EMAIL` совпадает по имени и значению по умолчанию с копией, которую тоже
читает `settings.py`; `ADMIN_PASSWORD` больше нигде не читается). **Если `ADMIN_PASSWORD` не задан или
пуст, команда использует буквальный пароль `admin`** и выводит предупреждение. От создания учётной
записи она не отказывается. Команда автоматически запускается при каждом старте контейнера Docker
(`docker/backend/entrypoint.sh`, сразу после `migrate`), поэтому в быстром старте с Docker её никогда
не нужно вызывать напрямую, а незаданный `ADMIN_PASSWORD` в реальном развёртывании означает, что
пароль начального суперпользователя действительно `admin`, пока его не сменят вручную.

```bash
uv run python manage.py create_default_admin
```

## audit_org_fields {#audit_org_fields}

Одноразовый инструмент усиления мультитенантности фазы 1, а не универсальный или самообновляющийся
аудитор: он проверяет **жёстко заданную** в самой команде пару списков Python,
`models_with_nullable_org` (сейчас только `common.Address` и `common.Tags`) и `models_with_required_org`
(тринадцать перечисленных моделей), а не все существующие сегодня модели с привязкой к организации.
Модель, добавленная в код после последней правки этой команды, для неё в любом случае невидима.

```bash
uv run python manage.py audit_org_fields
uv run python manage.py audit_org_fields --fix
uv run python manage.py audit_org_fields --verbose
```

Аудит выполняется всегда; отключить его можно, только не вызывая команду. Раньше парсер принимал флаг
`--check`, но `handle()` его никогда не читал, поэтому вывод с ним и без него был одинаковым; флаг
удалён, чтобы не оставлять флаг, который ничего не значит.

| Флаг | Что делает |
| --- | --- |
| `--fix` | Для записей `common.Address` с пустым `org` пытается заполнить его из связанного `Profile`. Для `common.Tags` `--fix` **ничего** не исправляет, а выводит сообщение с просьбой проверить вручную. Для любой другой модели, у которой обнаружился пустой `org`, тоже просто выводится "Automatic fix not implemented." |
| `--verbose` | Два эффекта, по одному на проход: в проходе nullable-org выводит конфигурацию поля каждой модели (`null`, `blank`, `related_query_name`); в проходе required-org только с ним вообще выводится предупреждение "Model not found". Без `--verbose` `LookupError` там молча проглатывается. |

Вывод помечает каждую модель значками ✅/❌/⚠️ и завершается сводкой и блоком с рекомендуемыми
следующими шагами (создать миграцию, выполнить `makemigrations`/`migrate`): сама команда никогда не
изменяет схему, только данные, и только при переданном `--fix`.
