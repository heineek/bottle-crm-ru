# Переменные окружения

Эта страница содержит исчерпывающую таблицу: все переменные окружения, которые читает
`backend/crm/settings.py`, их фактические значения по умолчанию и назначение.
[Развёртывание на своём сервере: переменные окружения](../self-hosting/environment-variables.md) служит
повествовательным дополнением к ней: там описано, как на самом деле загружается конфигурация
(`load_dotenv()`, наслоение `.env.docker` / `.env.docker.local`), и приведён меньший, отобранный список
переменных, которые оператору действительно нужно задать для рабочей установки с нестандартными
настройками. Если вы настраиваете развёртывание, сначала прочитайте ту страницу; возвращайтесь сюда,
когда понадобится полный список или точное значение по умолчанию.

## Как их задать {#how-to-set-them}

Каждая переменная из таблицы ниже читается через `os.environ.get("NAME", <default>)` (или эквивалентный
`os.getenv`) прямо в `crm/settings.py` во время импорта процесса: `manage.py runserver`, `migrate`,
воркер Gunicorn/Uvicorn, воркер Celery и все management-команды читают одни и те же значения одним и тем
же способом. Файл `.env` рядом с `manage.py` (при ручной установке) или `.env.docker`/`.env.docker.local`
(для стека Docker Compose) загружается в окружение процесса до выполнения этих вызовов, поэтому
незаданная переменная получает значение из столбца **По умолчанию**, а не приводит к немедленному падению.
Это верно даже для `SECRET_KEY`: его собственный вызов `os.environ.get` всегда успешен, но полученное
значение затем проходит отдельную проверку несколькими строками ниже, которая выбрасывает `ValueError`,
как только `ENV_TYPE` отличается от `dev` (см. строку `SECRET_KEY` ниже): значение по умолчанию, которое
устраивает `os.environ.get`, не обязательно устраивает всё, что идёт после него. Переменные, у которых в
коде действительно нет значения по умолчанию, читаются через обычный `os.environ[...]`, поэтому
отсутствие любой из них сразу даёт `KeyError`, а не откат к значению по умолчанию. Они находятся вообще
вне `crm/settings.py` и описаны в списке ниже, а не в таблице.

Три группы реальных переменных окружения, которые читает проект, **не** читаются самим
`crm/settings.py`, поэтому их нет в таблице ниже:

- **`ADMIN_PASSWORD`** читается напрямую management-командой `create_default_admin` (см.
  [Management-команды](management-commands.md#create_default_admin)). Тем не менее у неё есть своя
  строка ниже, потому что она относится к тому же процессу начальной настройки Docker, что и
  `ADMIN_EMAIL`, который *читается* в `settings.py`.
- **`AWS_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `SENTRY_DSN`** читаются через
  обычный `os.environ[...]` (без значения по умолчанию) в `backend/crm/server_settings.py`, который
  `crm/settings.py` импортирует только при `ENV_TYPE=prod`. Отсутствие любой из них даёт `KeyError` во
  время импорта: процесс отказывается запускаться, а не запускается наполовину настроенным. `ENV_TYPE`
  подчиняется тому же правилу: он читается в `settings.py`, но это внутренний переключатель dev/prod,
  который собственные тесты проекта намеренно исключают из таблицы, а не отдельная настройка
  для тех, кто разворачивает систему на своём сервере. Что на самом деле требует `ENV_TYPE=prod` и почему его не
  стоит задавать просто так, описано в разделах
  [Развёртывание в продакшене](../self-hosting/production-deploy.md#required-settings) и
  [Усиление безопасности](../self-hosting/security-hardening.md#secrets).
- **`BCRM_MCP_ENABLED`** и **`BCRM_BASE_URL`** больше нигде не читаются. Они управляли MCP-сервером,
  который раньше был подключён по адресу `/mcp` и удалён в пользу REST API. Обе переменные можно
  спокойно удалить из окружения существующего развёртывания. Как агент подключается теперь, описано в
  разделе [ИИ-агенты](../integrations/ai-agents.md).

## Справочник {#reference}

### Ядро Django {#django-core}

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `SECRET_KEY` | `django-insecure-dev-key-please-change-in-production` | Да, как только `ENV_TYPE` отличается от `dev` (см. выше) | Криптографический ключ подписи Django. Он же *является* JWT `SIGNING_KEY`: `SIMPLE_JWT["SIGNING_KEY"]` задаётся прямо равным `SECRET_KEY`, поэтому отдельной настройки ключа подписи JWT в этом коде нет, а смена `SECRET_KEY` делает недействительными все выданные access- и refresh-токены. **Длина не меньше 32 байт.** JWT подписываются HS256, а RFC 7518, раздел 3.2, требует, чтобы ключ HMAC был не короче выхода хеш-функции; более короткий ключ вызывает ошибку при импорте вне `dev` и предупреждение в `dev`. Сгенерировать ключ: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. См. [Архитектура: аутентификация](../architecture/authentication.md#token-model) и [Усиление безопасности](../self-hosting/security-hardening.md#secrets). |
| `DEBUG` | `False` | Нет | Режим отладки Django. Кроме того, единственное условие для management-команды `devlogin`. См. [Management-команды](management-commands.md#devlogin). |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | Да, как только система обслуживает трафик под реальным именем хоста | Список через запятую, разбивается по `,` в `ALLOWED_HOSTS` Django. |
| `TRUST_PROXY_SSL_HEADER` | `False` | Да, если TLS завершается на прокси перед Django | Значение `true` (без учёта регистра) задаёт `SECURE_PROXY_SSL_HEADER` Django равным `("HTTP_X_FORWARDED_PROTO", "https")`. Без него запрос, пришедший от nginx или ALB по обычному HTTP, делает `request.is_secure()` ложным, и тогда `SecurityMiddleware` вообще **не** отправляет заголовок `Strict-Transport-Security`, так что настройки `SECURE_HSTS_SECONDS` / `INCLUDE_SUBDOMAINS` / `PRELOAD` молча не действуют. Включайте только если этот прокси единственный путь к приложению **и** он перезаписывает `X-Forwarded-Proto`, а не пропускает присланный клиентом, иначе любой, кто обращается к Django напрямую, может заставить `request.is_secure()` вернуть true. Перенаправление с http на https должно быть на прокси; `SECURE_SSL_REDIRECT` намеренно не задан. |
| `NUM_PROXIES` | не задана | Только если `REMOTE_ADDR` это прокси (gunicorn за nginx: `1`). Не задавайте при uvicorn с `--proxy-headers` | Сколько прокси перед Django дописывают значение в `X-Forwarded-For` (nginx с `$proxy_add_x_forwarded_for` считается за один). Задаёт `NUM_PROXIES` в DRF, который читает `common.request_meta.client_ip`; он поставляет каждый записываемый IP-адрес клиента (журнал аудита безопасности, заявки веб-форм, принятие коммерческих предложений, токены входа по magic link и в портал) и каждый лимит по IP (отправка веб-формы, справочный центр, календарная лента, вход по magic link и в портал). Используется запись, отстоящая на столько позиций справа, то есть адрес, который увидел самый внешний прокси; записи левее неё присланы вызывающим и игнорируются, поэтому подмена заголовка не позволяет ни выбрать корзину лимита, ни подделать записываемый адрес. Если переменная не задана или равна `0`, используется `REMOTE_ADDR`. Это правильно, когда сервер приложения уже определяет клиента по доверенным прокси, как uvicorn с `--proxy-headers --forwarded-allow-ips=127.0.0.1`; если поверх этого задать `NUM_PROXIES`, прокси будет учтён дважды. В любом случае запрос, который сервер SvelteKit пересылает от имени посетителя, приходит от ретранслятора; различать таких посетителей позволяет `RELAY_SECRET`. Когда `REMOTE_ADDR` это сам прокси (gunicorn за nginx), без этой переменной все посетители делят одну корзину лимита, поэтому задайте число прокси. Если задать больше реального числа прокси, вызывающие снова смогут выбирать IP. |
| `RELAY_SECRET` | не задана | Рекомендуется везде, где сервер SvelteKit пересылает запросы анонимных посетителей (страницы входа веб-приложения, справочный центр и портал коммерческих предложений, контактная форма маркетингового сайта) | Общий секрет с этими серверами SvelteKit. Запросу, у которого заголовок `X-BottleCRM-Relay-Secret` совпадает с ним (сравнение за постоянное время), доверяют в части адреса посетителя из `X-BottleCRM-Client-IP`, поэтому каждый посетитель получает свою корзину лимита по IP и свой записываемый адрес вместо адреса ретранслятора. Без совпадения оба заголовка игнорируются и решает `NUM_PROXIES`, как описано выше; адрес посетителя, который не является IP, обрабатывается так же. Задайте то же значение в `RELAY_SECRET` в окружении веб-приложения (приватная переменная, никогда не `PUBLIC_`) и запускайте это приложение с `ADDRESS_HEADER=X-Forwarded-For` и `XFF_DEPTH=1` за nginx, чтобы `getClientAddress()` возвращал посетителя, а не nginx, и с `HOST=127.0.0.1`, чтобы к нему нельзя было обратиться в обход nginx с поддельным `X-Forwarded-For`. Ретрансляторы также передают посетителя в `X-Forwarded-For` для API версий до 1.12.0, которые читают его первую запись; этот выпуск игнорирует этот заголовок, если не задан `NUM_PROXIES`. Не короче 32 символов: `crm/settings.py` отказывается запускаться с более коротким значением, и `client_ip` никогда с ним не совпадёт. Сгенерировать: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Любой, у кого есть этот секрет, может выбрать адрес, под которым его ограничивают и записывают, поэтому обращайтесь с ним как с паролем; его заголовок вычищается из событий Sentry. |
| `DJANGO_ORG_API_KEY_AUTH` | `true` | Нет | Значение `false`, `0`, `no` или `off` полностью запрещает API-ключ организации (`Token: <org.api_key>`) как способ аутентификации на всех эндпоинтах. Ключ представляет собой одни бессрочные учётные данные на тенанта, которые сопоставляются с произвольным активным ADMIN, поэтому его нельзя отозвать для отдельной интеграции и он читает все записи организации. Даже во включённом состоянии он работает только на чтение и не имеет доступа к эндпоинтам учётных данных (см. [Токены и API-ключи](../api/tokens-and-api-keys.md)), но в развёртывании, где все интеграции перешли на персональные токены доступа, его стоит отключить. По умолчанию включён, чтобы обновление ничего не сломало. |

### Пул соединений {#connection-pooling}

Пул использует `psycopg_pool` из psycopg 3 через бэкенд PostgreSQL в Django. По умолчанию он **выключен**, поэтому обновление не меняет молча поведение соединений в существующем развёртывании. Включение пула также включает `CONN_HEALTH_CHECKS`; `CONN_MAX_AGE` зафиксирован равным `0`, потому что Django выбрасывает `ImproperlyConfigured` ("Pooling doesn't support persistent connections"), если пул настроен вместе с постоянными соединениями.

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `DB_POOL_ENABLED` | `False` | Нет | `"true"` (без учёта регистра) ставит `psycopg_pool.ConnectionPool` перед базой данных по умолчанию и устанавливает описанный ниже callback сброса RLS. Любое другое значение оставляет поведение соединений без изменений. |
| `DB_POOL_MIN_SIZE` | `2` | Нет | Сколько соединений пул держит открытыми в каждом процессе даже в простое. |
| `DB_POOL_MAX_SIZE` | `10` | Нет | Предел одновременных соединений на процесс. Именно этого ограничения не хватало, когда API исчерпал соединения PostgreSQL: под ASGI каждый выполняющийся запрос иначе берёт своё соединение без верхней границы. |

**Подбирайте размер с учётом `max_connections` и помните, что пул создаётся на процесс, а не на хост.** Пиковое использование примерно равно `DB_POOL_MAX_SIZE × (воркеры uvicorn + дочерние процессы prefork Celery)` плюс `DB_POOL_MIN_SIZE` простаивающих соединений у каждого из этих процессов. `docker-compose.yml` запускает `celery -A crm worker` без `--concurrency`, поэтому каждый воркер порождает по одному дочернему процессу на CPU. На хосте с 8 ядрами, 3 воркерами uvicorn и настройками по умолчанию это `10 × (3 + 8) = 110` соединений в пике при стандартном для PostgreSQL `max_connections`, равном 100.

**Почему важен callback сброса.** Контекст RLS хранится в `app.current_org`, настройке уровня сессии, которая переживает и транзакцию, и запрос. `psycopg_pool` не очищает состояние сессии при возврате соединения; он только откатывает открытую транзакцию. Поэтому пул без `common.rls.pool.reset_rls_context` отдаёт следующему потребителю соединение, всё ещё привязанное к предыдущему тенанту. `DB_POOL_ENABLED` подключает этот callback автоматически, а `common/tests/test_pool_rls_isolation.py` доказывает, что он очищает контекст и оставляет соединение в состоянии `IDLE`, которого требует `psycopg_pool`. Не настраивайте пул вручную без него.

### Кэш и ограничение частоты запросов {#cache-and-rate-limiting}

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `CACHE_URL` | *(пусто, используется `LocMemCache` в каждом процессе)* | Да, если вы запускаете больше одного воркера и хотите, чтобы ограничение частоты действительно работало | URL Redis для кэша Django по умолчанию, например `redis://localhost:6379/1`. Здесь хранит счётчики механизм ограничения частоты DRF. | `WEBFORM_THROTTLE_IP` | `10/hour` | Нет | Лимит на отправку публичных веб-форм для одного IP-адреса клиента и одной формы. | `HELP_CENTER_THROTTLE_IP` | `600/hour` | Нет | Лимит для публичного API справочного центра (`/api/public/help/`) на один IP-адрес клиента. | `HELP_CENTER_THROTTLE_GLOBAL` | `10000/hour` | Нет | Лимит для публичного API справочного центра на один справочный центр по всем клиентам. Корзины ведутся отдельно для каждого справочного центра, так что трафик на страницы одной организации никогда не ограничивает другую. Увеличьте его для загруженного справочного центра. |
| `CALENDAR_FEED_THROTTLE_IP` | `1000/hour` | Нет | Лимит для календарной ленты задач (`/api/public/calendar/<token>.ics`) на один IP-адрес клиента. IP определяет `common.request_meta.client_ip`. |
| `MAGIC_LINK_THROTTLE_IP` | `30/hour` | Нет | Лимит на запросы входа по magic link (`/api/auth/magic-link/request/`) на один IP-адрес клиента. Каждый адрес отдельно ограничен пятью ссылками в час. |
| `MAGIC_LINK_THROTTLE_GLOBAL` | `300/hour` | Нет | Лимит на запросы входа по magic link по всем клиентам: последний рубеж против отправителя, распределённого по множеству адресов, который использует экземпляр для рассылки писем на произвольные адреса. При его достижении письма для входа приостанавливаются для всех до конца часа, поэтому держите его значительно выше реального трафика входов. |
| `PORTAL_LOGIN_THROTTLE_IP` | `30/hour` | Нет | Лимит на запросы кода входа в клиентский портал (`/api/portal/login/<org_id>/request/`) на один IP-адрес клиента по всем организациям. Та же оговорка про `RELAY_SECRET`, что и у `MAGIC_LINK_THROTTLE_IP`. |
| `PORTAL_LOGIN_THROTTLE_ORG` | `100/hour` | Нет | Лимит на запросы кода входа в клиентский портал на одну организацию по всем клиентам. При его достижении вход в портал приостанавливается только для этой организации. |

### CORS и CSRF {#cors-and-csrf}

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `CORS_ALLOW_ALL` | `False` | Нет | Задаёт `CORS_ORIGIN_ALLOW_ALL` в Django. Обратите внимание, что имя не совпадает с настройкой Django, которой оно управляет. `"true"` (без учёта регистра) разрешает все источники; любое другое значение оставляет настройку выключенной. |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5181,http://127.0.0.1:5181` | Да, как только фронтенд обслуживается с реального домена | Список разрешённых источников CORS через запятую; у каждого элемента обрезаются пробелы по краям, пустые элементы отбрасываются. |
| `CSRF_TRUSTED_ORIGINS` | *(пусто, доверенных источников нет)* | Да, прежде чем к экземпляру сможет обратиться кто-то кроме вас | Список через запятую с тем же правилом обрезки, что и у `CORS_ALLOWED_ORIGINS`. Каждый элемент должен содержать схему, например `https://crm.example.com`. Голое имя хоста для проверки CSRF в Django молча бесполезно. |

### URL-адреса {#urls}

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `DOMAIN_NAME` | `http://localhost:8000` | **Да**, при развёртывании на своём сервере под реальным доменом (начиная с django-crm 1.13.0) | Публичный origin **бэкенда**, например `https://api.example.com`. Начиная с django-crm 1.13.0 это основа каждого URL, который API выдаёт для использования где-то ещё (`common.links.api_url`): URL календарной ленты задач, на которую подписывается календарное приложение, а также фрагменты встраивания веб-формы и URL отправки внутри встроенной формы. Раньше они строились по входящему запросу, поэтому веб-приложение, которое обращается со своего сервера по `PUBLIC_DJANGO_API_URL` (`http://backend:8000` в Docker), показывало хост, недоступный извне, и `http://`, если не был задан `TRUST_PROXY_SSL_HEADER`. Когда `ENV_TYPE` отличается от `dev`, `crm/settings.py` выбрасывает ошибку при импорте, если значение указывает на loopback-хост (`localhost`, `127.0.0.1`, `0.0.0.0`, `::1`) или не является абсолютным URL `http`/`https`; ту же проверку проходит `FRONTEND_URL`. Завершающий слэш отбрасывается. В ссылки из писем значение больше не попадает: они берутся из `FRONTEND_URL`, а четыре аргумента `domain=`, которые по-прежнему передаются задачам Celery для счетов (`invoices/tasks.py`, `invoices/api_views.py`), этими задачами игнорируются. |
| `FRONTEND_URL` | `http://localhost:5181` | **Да**, при развёртывании на своём сервере под реальным доменом | Базовый URL фронтенда на SvelteKit и единственный источник всех ссылок, которые покидают систему в письмах: приветственное письмо и URL входа по magic link (`common/tasks.py`), ссылки на портал в письмах со счетами и коммерческими предложениями, ссылка на опрос CSAT и ссылка на счёт «назначен вам» (все через `common.links.frontend_url`). Ссылки для клиентов уходят людям вне организации, поэтому значение `localhost` по умолчанию в реальном развёртывании рассылает клиентам нерабочие ссылки. **Теперь такая конфигурация отклоняется, а не приводит к отправке писем:** когда `ENV_TYPE` отличается от `dev`, `crm/settings.py` выбрасывает ошибку при импорте, если значение указывает на loopback-хост (`localhost`, `127.0.0.1`, `0.0.0.0`, `::1`) или не является абсолютным URL `http`/`https`, так что развёртывание не запускается, вместо того чтобы молча ломаться в чужом почтовом ящике. Обычный HTTP с реальным хостом разрешён для развёртывания за собственным TLS-терминатором. Завершающий слэш отбрасывается, поэтому `https://app.example.com` и `https://app.example.com/` работают одинаково. |

### Входящая почта {#inbound-email}

| Переменная | По умолчанию | Обязательна | Назначение |
| --- | --- | --- | --- |
| `INBOUND_SNS_ACCOUNT_IDS` | *(пусто, ни один аккаунт не разрешён)* | Нет. Без неё администратор вводит SNS Topic ARN каждого почтового ящика вручную | 12-значные id аккаунтов AWS через запятую, например `123456789012,210987654321` (пробелы вокруг каждого игнорируются). Появилась в django-crm 1.13.0. [Входящий почтовый ящик](../integrations/inbound-email.md#securing-the-endpoint), у которого ещё нет Topic ARN, закрепляет за собой топик первого `SubscriptionConfirmation` SNS с проверенной подписью, **только если этот топик принадлежит одному из этих аккаунтов**; подтверждение из любого другого аккаунта отклоняется с `403` и ничего не закрепляет, как и любое уведомление, пока закрепления нет. SNS позволяет любому аккаунту AWS подписать любой HTTPS-эндпоинт на свой топик, поэтому до 1.13.0 URL почтового ящика принадлежал тому, кто первым на него подписался. Укажите аккаунт, которому принадлежат топики правил получения SES (облачная версия BottleCRM указывает свой аккаунт). Почтовый ящик, для которого администратор ввёл Topic ARN, игнорирует эту настройку: принимается только этот точный ARN. `crm/settings.py` в любом окружении выбрасывает ошибку при импорте, если какой-либо элемент не состоит ровно из 12 цифр ASCII, так что опечатка срывает развёртывание, а не оставляет все почтовые ящики молча незакреплёнными. |
