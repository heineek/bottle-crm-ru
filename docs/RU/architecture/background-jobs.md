# Фоновые задачи

Эта страница для тех, кто пишет новую задачу Celery. Если вы эксплуатируете развёртывание, а не
пишете код, обратитесь к разделу
[Почта и Celery](../self-hosting/email-and-celery.md#rls-in-background-tasks): там описан запуск
процессов worker и beat и то же правило, что ниже, но со стороны администратора. Эта страница
существует потому, что правило легко соблюсти, скопировав существующую задачу, и легко нарушить,
написав задачу с нуля.

## Топология {#topology}

`backend/crm/celery.py` определяет приложение: `Celery("crm")`, настраиваемое из настроек Django в
пространстве имён `CELERY_`, поэтому фактически оно подключается по `CELERY_BROKER_URL` и
`CELERY_RESULT_BACKEND` (`backend/crm/settings.py`, оба по умолчанию `redis://localhost:6379/0`).
Отдельного конфигурационного файла только для Celery нет. `app.autodiscover_tasks()` находит
`tasks.py` в каждом приложении; второй вызов, `app.autodiscover_tasks(related_name="celery_tasks")`,
существует именно потому, что модуль задач Django-приложения `tasks` называется `celery_tasks.py`,
чтобы не конфликтовать с именем самого приложения.

С этим единым определением приложения работают два процесса, и ни один из них не нужен, чтобы сам
API отвечал на запросы:

- **`celery -A crm worker`** выполняет задачи, поставленные в очередь API: приветственные письма,
  отправку magic-link, уведомления о назначении и другие.
- **`celery -A crm beat`** запускает расписание из `app.conf.beat_schedule` (десять записей:
  генерация регулярных счетов, проверка просроченных счетов, напоминания об оплате, проверка
  истёкших коммерческих предложений, поиск застрявших сделок и достигнутых этапов целей, проверка
  нарушений SLA по обращениям каждые пять минут, очистка зависших таймеров и ночная очистка
  прочитанных уведомлений и записей об истёкших refresh-токенах). Ничего из этого не
  выполняется, если не запущен и `beat`.

Команды запуска и эксплуатационное назначение каждой записи расписания описаны в разделе
[Почта и Celery](../self-hosting/email-and-celery.md#running-a-worker).

## Задачи и отключённые модули {#jobs-and-switched-off-modules}

Администратор организации может отключить части CRM (см.
[Модули](../api/modules.md#scheduled-jobs)). Задача, которая обходит все организации, проверяет
`common.modules.module_is_available(org, key)` для обслуживаемого ею модуля и пропускает
организацию, если модуль выключен; задача, поставленная в очередь для одной записи, проверяет это
перед отправкой. Снова включённый модуль начинает с чистого листа: обходы по датам игнорируют даты
раньше `module_on_since(org, key)`, а `change_modules` при повторном включении модуля выполняет два
хука «начать с чистого листа», перечисленных в `START_FRESH`
(`backend/common/module_settings.py`). Новая задача, которая действует по датам или отправляет
письма клиенту, должна следовать тому же шаблону и иметь тест на то, что дата из периода
отключения ни к чему не приводит.

## Как написать задачу {#writing-a-task}

Воркеры Celery никогда не проходят через стек HTTP middleware Django. `GetProfileAndOrg` и
`RequireOrgContext`, два класса middleware, которые определяют тенант для обычного запроса (см.
[Обзор архитектуры](overview.md#request-lifecycle)), для задачи просто не выполняются, поэтому никто не
установит за вас переменную сессии PostgreSQL `app.current_org` на соединении воркера. Новое
соединение воркера имеет пустой контекст, и по отказоустойчивому замыслу RLS (см.
[Мультитенантность и RLS](multi-tenancy-and-rls.md#policies-and-org_scoped_tables)) пустой
контекст заставляет каждый запрос к таблице, привязанной к организации, на правильно настроенной
роли базы данных без прав суперпользователя возвращать ноль строк. Не строки чужой организации, но
и не те строки, которые вам были нужны.

Исправление занимает одну строку, и это должно быть первое, что делает задача, работающая с
таблицей, привязанной к организации. `set_rls_context(org_id)`, определённая в
`backend/common/tasks.py`, устанавливает ту же переменную сессии, что установил бы middleware:

```python
# backend/contacts/tasks.py
from celery import shared_task

from common.tasks import set_rls_context
from contacts.models import Contact


@shared_task
def send_email_to_assigned_user(recipients, contact_id, org_id):
    """Send Mail To Users When they are assigned to a contact"""
    set_rls_context(org_id)
    contact = Contact.objects.get(id=contact_id)
    ...
```

У любой задачи, поставленной в очередь из view, уже есть `org_id` (`request.profile.org.id`),
который можно передать аргументом. Передавайте его и вызывайте с ним `set_rls_context` перед
первым запросом, каждый раз.

Задача, которая должна обойти все организации, а не обработать одну запись, вызывает
`set_rls_context` один раз для каждой организации, внутри цикла, непосредственно перед запросами
этой организации, например `cases.tasks.scan_for_breached_cases`:

```python
for org in Org.objects.filter(id__in=list(org_ids)):
    set_rls_context(org.id)
    try:
        total += _scan_org(org)
    except Exception:
        logger.exception("Escalation scan failed for org=%s", org.id)
```

Два вида задач обоснованно обходятся без этого вызова. Первый: задача, чья таблица вообще не
привязана к организации. `flush_expired_refresh_tokens` работает с таблицей `OutstandingToken` из
simplejwt, у которой нет столбца `org_id` и которой нет в `ORG_SCOPED_TABLES`, так что контекста
организации, который нужно было бы установить, просто нет. Второй: задача, которая уже
устанавливает контекст для каждой организации внутри цикла, как выше, и не нуждается в нём снова
вне цикла. Исключением не считается довод «запрос, кажется, фильтрует по чему-то другому».

## Правило RLS {#the-rls-rule}

Скажем прямо, ведь эта страница существует ради того, чтобы это правило нельзя было пропустить:
**любая задача Celery, которая читает или пишет таблицу, привязанную к организации, должна вызвать
`set_rls_context(org_id)` до своего первого запроса к этой таблице.** Ничто другое не определяет
тенант для процесса воркера.

В кодовой базе есть живой пример того, что происходит, если задача этот вызов пропускает.
`purge_read_notifications` (`backend/common/tasks.py:381-397`) удаляет прочитанные уведомления
старше заданного порога:

```python
@shared_task
def purge_read_notifications(days=NOTIFICATION_PURGE_DAYS):
    """... Runs once across all orgs. RLS does not need a per-org context
    here because the query targets `read_at`, which is intrinsic to the row,
    not org-scoped logic."""
    cutoff = timezone.now() - timedelta(days=days)
    deleted, _ = Notification.objects.filter(
        read_at__isnull=False, read_at__lt=cutoff
    ).delete()
    ...
```

Рассуждение в docstring не выдерживает проверки: то, зависит ли *условие запроса* от организации,
никак не связано с тем, привязана ли к организации *таблица*, а `notification` привязана. Она есть
в `ORG_SCOPED_TABLES` (`backend/common/rls/__init__.py`) и имеет ту же политику
`FORCE ROW LEVEL SECURITY`, что и любая другая таблица из этого списка. Эта задача никогда не
вызывает `set_rls_context`, поэтому на роли базы данных без прав суперпользователя, которую требует
проект, она работает с пустым `app.current_org`, и её `DELETE` молча затрагивает ноль строк во всех
организациях при каждом запуске по расписанию. Она не падает с шумом и не удаляет данные чужой
организации. Она просто никогда ничего не удаляет, и это отдельный тихий вред: таблица растёт без
ограничений, а запись расписания, которая должна это предотвращать, продолжает сообщать об
успехе. Прежде чем доверять задаче или комментарию над ней, читайте код, который она на самом деле
выполняет.
