# Мультитенантность и RLS

Эта страница для тех, кто собирается добавить модель, привязанную к организации, или пытается
понять, почему запрос не вернул ни одной строки, хотя должен был. Здесь модель мультитенантности
описана со стороны кода приложения; раздел [PostgreSQL и RLS](../self-hosting/postgresql-and-rls.md)
описывает тот же механизм со стороны администратора: создание роли базы данных, запуск
`manage_rls` и проверку того, что изоляция действительно работает на реальных данных. Прочтите и ту
страницу, прежде чем что-либо разворачивать; эта же посвящена тому, что делать при написании новой
модели.

## Модель {#the-model}

Данные всех тенантов хранятся в одной базе данных, в одних и тех же таблицах, и различаются
столбцом `org_id`. Изоляция обеспечивается дважды, независимо:

1. **В коде приложения** каждый queryset, затрагивающий таблицу, привязанную к организации, явно
   фильтрует `Model.objects.filter(org=request.profile.org)`, а каждый
   `create()`/`serializer.save()` передаёт `org=request.profile.org`, а не доверяет значению от
   клиента.
2. **В PostgreSQL** с помощью Row-Level Security. У каждой таблицы, привязанной к организации, есть
   политика, сравнивающая её столбец `org_id` с переменной сессии `app.current_org`
   (`backend/common/rls/__init__.py`), которую `RequireOrgContext` устанавливает при каждом запросе
   по проверенному JWT вызывающего; когда именно, см. в разделе [Обзор архитектуры](overview.md#request-lifecycle).

Ни один уровень не является необязательным, и на практике ни один не покрывает другой полностью:
почему должны соблюдаться оба, объясняет раздел [Двухуровневый контракт](#the-two-layer-contract)
ниже.

## BaseOrgModel {#baseorgmodel}

`BaseOrgModel` (`backend/common/base.py`) является подклассом `BaseModel`, который добавляет
внешний ключ `org` на `common.Org` и индекс `["org", "-created_at"]`. Его собственный docstring
прямо формулирует замысел: «All tenant-owned models should inherit from this instead of
`BaseModel`.»

Тем не менее, прежде чем считать, что ему следует каждая модель, привязанная к организации,
проверьте это по реальным файлам моделей, потому что большинство ему не следует. Поиск по кодовой
базе классов, действительно наследующих `BaseOrgModel`, находит четыре: `Order` и `OrderLineItem`
(`backend/orders/models.py`), а также `PersonalAccessToken` и `PackApplication`
(`backend/common/models.py`). Все основные модели CRM (`Lead`, `Account`, `Contact`,
`Opportunity`, `Case`, `Task`) и большинство окружающих их вспомогательных таблиц (`CaseWatcher`,
`CsatSurvey`, `Macro`, `BusinessCalendar` и другие) вместо этого наследуют обычный `BaseModel` и
вручную объявляют своё поле `org = models.ForeignKey(Org, on_delete=models.CASCADE,
related_name="...")`, по форме идентичное тому, что дал бы им `BaseOrgModel`. Это не дрейф и не
недосмотр: несколько таких моделей прямо говорят об этом в своих docstring, ссылаясь на
согласованное решение предпочесть вручную объявленный FK вместо `BaseOrgModel`. Например,
`backend/cases/models.py` о `CaseWatcher`:

```python
class CaseWatcher(BaseModel):
    """A profile subscribed to updates on a case.

    Per `docs/cases/COORDINATION_DECISIONS.md` D2 we inherit BaseModel and
    declare our own org FK rather than using BaseOrgModel. RLS still
    applies via the migration that adds the `case_watcher` table.
    """
```

(Файла `docs/cases/COORDINATION_DECISIONS.md`, на который ссылаются этот комментарий и ещё два
похожих в `backend/business_hours/models.py` и `backend/macros/models.py`, в этом checkout нет;
считайте источником истины рассуждения, записанные в самих комментариях кода.)

Практический вывод: наследование `BaseOrgModel` является правильным и рекомендуемым способом
добавить поле `org` в новую модель, и по умолчанию стоит выбирать его, если только у вас нет
конкретной причины следовать более распространённому в кодовой базе соглашению с вручную
объявленным FK (например, ради единообразия с соседней моделью в том же приложении). Но защиту RLS
обеспечивает не наследование, и само по себе оно недостаточно: `PersonalAccessToken` наследует
`BaseOrgModel` и *намеренно исключён* из RLS (см.
[Политики и ORG_SCOPED_TABLES](#policies-and-org_scoped_tables) ниже). Что на самом деле
определяет, защищена ли таблица, описано в следующем разделе.

## Политики и ORG_SCOPED_TABLES {#policies-and-org_scoped_tables}

`ORG_SCOPED_TABLES` в `backend/common/rls/__init__.py` представляет собой единый список,
определяющий, какие таблицы получают политики RLS. На момент написания в нём 61 запись.
`get_enable_policy_sql(table)` генерирует SQL, который защищает каждую из них:

```sql
ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "<table>" FORCE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS org_isolation ON "<table>";
DROP POLICY IF EXISTS org_insert_check ON "<table>";

CREATE POLICY org_isolation ON "<table>"
    FOR ALL
    USING (org_id::text = (select NULLIF(current_setting('app.current_org', true), '')));

CREATE POLICY org_insert_check ON "<table>"
    FOR INSERT
    WITH CHECK (org_id::text = (select NULLIF(current_setting('app.current_org', true), '')));
```

`FORCE ROW LEVEL SECURITY` важен, потому что без него владелец таблицы (обычно роль, которая
выполняла миграции) был бы освобождён от политик собственной таблицы. `NULLIF` превращает
неустановленную (пустую строку) переменную сессии в SQL `NULL`, а `org_id::text = NULL` никогда не
истинно, поэтому пустой контекст даёт ноль строк, а не строки всех организаций: отказоустойчивость
обеспечена самим построением, а не договорённостью.

Добавление RLS для новой модели, привязанной к организации, состоит ровно из трёх шагов, и пропуск
любого из них оставляет таблицу с видимостью защиты при её фактическом отсутствии:

1. **Добавьте модели поле `org`.** Унаследуйте `BaseOrgModel` или, следуя преобладающему в кодовой
   базе шаблону (см. [BaseOrgModel](#baseorgmodel) выше), объявите
   `org = models.ForeignKey(Org, on_delete=models.CASCADE, related_name="...")` напрямую.
2. **Добавьте имя таблицы из `db_table` в `ORG_SCOPED_TABLES`** в `backend/common/rls/__init__.py`.
3. **Напишите миграцию**, которая вызывает `get_enable_policy_sql('your_table')` внутри операции
   `RunPython` с защитой, превращающей её в пустую операцию на SQLite (у тестовой базы данных нет
   понятия защиты строк):

Вот реальная миграция, `backend/opportunity/migrations/0012_enable_rls_sales_goal.py`, целиком:

```python
from django.db import connection, migrations

from common.rls import get_disable_policy_sql, get_enable_policy_sql

TABLE = "sales_goal"


def enable_rls(apps, schema_editor):
    if connection.vendor != "postgresql":
        return
    with connection.cursor() as cursor:
        cursor.execute(get_enable_policy_sql(TABLE))


def disable_rls(apps, schema_editor):
    if connection.vendor != "postgresql":
        return
    with connection.cursor() as cursor:
        cursor.execute(get_disable_policy_sql(TABLE))


class Migration(migrations.Migration):
    atomic = False

    dependencies = [
        ("opportunity", "0011_opportunity_kanban_order"),
    ]

    operations = [
        migrations.RunPython(enable_rls, disable_rls),
    ]
```

`get_enable_policy_sql` начинается с двух операторов `ALTER TABLE`, а затем, перед обоими
`CREATE POLICY`, удаляет обе политики через `DROP POLICY IF EXISTS`, поэтому повторный запуск
такой миграции идемпотентен. Это полезно, если политику таблицы нужно пересоздать после изменения
схемы.

Если пропустить шаг 2, последствия хуже, чем «нет защиты»: `manage_rls --status` сообщает только о
таблицах, которые действительно есть в `ORG_SCOPED_TABLES`, поэтому незарегистрированная таблица
не отображается как «отключённая». Она не отображается вообще, и пробел невидим для единственного
инструмента, который должен его ловить. Единственное намеренное исключение в кодовой базе:
`personal_access_token`. Она наследует `BaseOrgModel` (так что поле `org` у неё есть), но
намеренно не включена в `ORG_SCOPED_TABLES`, потому что поиск в ней выполняется по `token_hash` ещё
до того, как может существовать контекст тенанта. Это таблица «начальной аутентификации», той же
категории, что и сама `Org`. Её изоляция обеспечивается явными фильтрами `org`/`profile` в
`backend/common/views/pat_views.py`. Это исключение и доказывает, что наследование `BaseOrgModel` и
защита RLS представляют собой два отдельных факта, а не один.

## Двухуровневый контракт {#the-two-layer-contract}

RLS служит страховочной сеткой, а не заменой фильтра ORM. Каждый view и сериализатор по-прежнему
пишет `Model.objects.filter(org=request.profile.org)` и явно передаёт `org=request.profile.org`
при создании. Контрактом является именно фильтр ORM; RLS ловит случаи, когда фильтр отсутствует,
забыт или ошибочен. Два уровня отказывают по-разному, и именно поэтому нужны оба:

- Если фильтра ORM нет, но RLS настроен правильно (роль базы данных без прав суперпользователя, см.
  [PostgreSQL и RLS](../self-hosting/postgresql-and-rls.md#why-rls)), запрос всё равно вернёт
  только строки организации вызывающего: RLS молча вас спас.
- Если роль базы данных является суперпользователем, а так и есть по умолчанию (если `DBUSER` не
  задан, используется `postgres`), пока вы сознательно это не измените, RLS полностью обходится,
  молча, без ошибки и без строки в журнале. В такой конфигурации фильтр ORM оказывается
  *единственным*, что стоит между запросом и данными другой организации. Среда разработки, где роль
  базы данных случайно оказалась суперпользователем, выглядит одинаково с фильтром ORM и без него;
  только `manage_rls --verify-user` на реальной, правильно настроенной роли скажет, что у вас на
  самом деле работает.

Относитесь к каждому новому queryset одинаково, независимо от того, о каком уровне вы думаете:
пишите фильтр `org=` так, будто RLS не существует, потому что в неправильно настроенном
развёртывании его действительно нет.

## Токены портала {#portal-tokens}

!!! note "Какой портал"
    Этот раздел посвящён **ссылкам на счета, коммерческие предложения и опросы CSAT**, где URL и
    есть все учётные данные. [Клиентский портал](../api/customer-portal.md), куда клиент входит,
    чтобы читать свои обращения в поддержку, этот механизм не использует, и он ему не нужен: его
    токен содержит claim `org_id`, поэтому `GetProfileAndOrg` определяет организацию до выполнения
    `RequireOrgContext`, и запрос получает настоящий контекст RLS, как любой другой. Единственное
    исключение составляют два его анонимных эндпоинта входа, которые исключены по префиксу
    `/api/portal/login/` и сами устанавливают контекст по id организации из URL. Там ничто не
    читает строку, привязанную к организации, до установки контекста.

Клиентский портал (ссылки на счета и коммерческие предложения, отправленные клиентам по почте, и
ссылки на опросы CSAT) является единственным местом в кодовой базе, где нужно читать строки,
привязанные к организации, вообще без аутентифицированного пользователя и без JWT. Для RLS это
настоящая проблема курицы и яйца: нельзя установить `app.current_org`, пока не известна
организация, а когда RLS обеспечивает изоляцию, нельзя прочитать строку, из которой можно узнать
организацию, пока контекст ещё не установлен.

`common.models.PortalAccessToken` (`backend/common/models.py`, определение начинается со строки
910) разрывает этот цикл. Это небольшая, намеренно **не привязанная к организации** таблица (её нет
в `ORG_SCOPED_TABLES`, политики RLS у неё нет), которая сопоставляет `sha256(url_token)` с
`org_id` и заполняется в тот же момент, когда выпускается каждый токен портала
(`common/portal_tokens.py:register_portal_token`). Публичный view хеширует токен, полученный в
URL, ищет организацию в этой непривязанной таблице и только затем устанавливает контекст RLS и
запрашивает сам ресурс:

```python
# backend/invoices/public_views.py
def _resolve_org_context(token, resource_type):
    org_id = resolve_portal_org(token, resource_type)
    if org_id:
        set_rls_context(org_id)
    return org_id
```

Неизвестный или искажённый токен оставляет контекст RLS пустым; следующий запрос к привязанной
таблице тогда ничего не возвращает благодаря отказоустойчивому поведению RLS по умолчанию, и
вызывающий получает тот же 404, что и для отключённой ссылки. Посторонний, перебирающий значения
токенов, ничего не узнаёт о том, настоящий ли токен. Это тот же шаблон «сначала определить
организацию узким запросом к непривязанной таблице, затем вызвать `set_rls_context`», который
используют задачи Celery (см. [Фоновые задачи](background-jobs.md)); он добавляет отдельную узкую
поверхность, а не ослабляет политику изоляции самих `invoice`, `estimate` или `csat_survey`.
`backend/docs/PORTAL_RLS.md` описывает рассуждения и намеренно отвергнутые альтернативы (в
частности, выдачу анонимному пути `BYPASSRLS`), но его раздел «what is still open» описывает
состояние *до* появления `PortalAccessToken`; сегодня на деле работает решение, описанное выше.
