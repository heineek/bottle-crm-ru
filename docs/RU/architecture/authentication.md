# Аутентификация

В BottleCRM три отдельных типа учётных данных: короткоживущий JWT для интерактивных клиентов,
персональный токен доступа для агентов и скриптов и API-ключ организации для интеграций между
серверами. На этой странице описано, как каждый из них подтверждает личность и как сервер решает,
что ему разрешено. В основе всех трёх лежит одно правило, сформулированное в разделе
[Мультитенантность и RLS](multi-tenancy-and-rls.md): пользователь, организация и роль являются
фактами, которые сервер выводит и проверяет сам, а не значениями, которые передаёт клиент. Ничто в
теле запроса, строке запроса или пользовательском заголовке не меняет того, под кем вы
аутентифицированы.

## Модель токенов {#token-model}

Интерактивный вход (Google OAuth и беспарольный вход по magic-link/OTP) выдаёт пару JSON Web Token
на основе `djangorestframework-simplejwt`. `SIMPLE_JWT` в `backend/crm/settings.py` задаёт:

```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(hours=1),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=14),
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
    "ALGORITHM": "HS256",
    "SIGNING_KEY": SECRET_KEY,
    ...
}
```

Access-токены живут один час, refresh-токены 14 дней. Оба подписываются самим `SECRET_KEY`.
Отдельной настройки ключа подписи JWT в кодовой базе нет, поэтому смена `SECRET_KEY` сразу делает
недействительными все выданные токены. Эксплуатационные последствия этого описаны в разделе
[Усиление безопасности](../self-hosting/security-hardening.md#secrets).
`rest_framework_simplejwt.token_blacklist` добавлен в `INSTALLED_APPS` именно для того, чтобы
существовал вызываемый `RefreshToken.blacklist()`: без этого приложения
`BLACKLIST_AFTER_ROTATION` молча ничего бы не делал, и именно о таком сценарии отказа
предупреждает собственный комментарий кодовой базы у этой записи в `INSTALLED_APPS`.

Токены выпускает `OrgAwareRefreshToken` (`backend/common/serializer.py`), подкласс
`RefreshToken`, чей classmethod `for_user_and_org(user, org, profile=None)` встраивает claims
организации и роли прямо в payload токена (см. [Claims](#claims)), чтобы фронтенду не нужно было
делать дополнительный вызов `/api/auth/profile/`, лишь бы узнать, от имени какой организации или
роли он работает.

Наряду с JWT существуют ещё два типа учётных данных, описанные ниже на этой странице:
[персональные токены доступа](#personal-access-tokens) (`bcrm_pat_…`, выпускаются
самостоятельно, привязаны к одному профилю) и [API-ключи организации](#organization-api-keys)
(по одному на организацию, управляются администратором, равносильны сессии администратора).
Сравнение возможного ущерба от их компрометации приведено в разделе
[Усиление безопасности](../self-hosting/security-hardening.md#token-surfaces).

## Claims {#claims}

Помимо стандартных claims simplejwt (`token_type`, `exp`, `iat`, `jti` и id пользователя под
`USER_ID_CLAIM = "user_id"`), `OrgAwareRefreshToken.for_user_and_org` встраивает:

- `user_email`, `user_name` (выводится из email, поскольку у `User` нет полей имени и фамилии),
  `user_profile_pic`
- `org_id`, `org_name`, только если организация есть; токен, выпущенный до того, как
  пользователь выбрал организацию (см. [Переключение организации](#organization-switching)), не
  содержит ни того, ни другого
- `org_settings`: `default_currency`, `currency_symbol`, `default_country`
- `role`, только если передан `Profile`, то есть только когда организация уже известна

Важнее всего claim `org_id`: именно его читает `GetProfileAndOrg`
(`backend/common/middleware/get_company.py`), чтобы определить `request.org`, а значит, именно его
использует `RequireOrgContext`, чтобы установить переменную сессии PostgreSQL, которую проверяет
каждая политика RLS. См. [Обзор архитектуры](overview.md#request-lifecycle). Принципиально то, что middleware
не просто доверяет claim: он заново проверяет его по активной строке `Profile` при каждом запросе:

```python
profile = Profile.objects.select_related("org").get(
    user_id=user_id, org_id=org_id, is_active=True
)
```

Поэтому токен, выпущенный, пока пользователь был участником организации, работает лишь до тех
пор, пока это членство остаётся активным. Если членство отозвано после выдачи токена, этот запрос
выбрасывает `Profile.DoesNotExist`, и middleware превращает его в 403 с просьбой войти заново,
вместо того чтобы доверять устаревшему claim. `role` в токене служит удобством для отображения, а
не источником истины для авторизации: каждая проверка прав из раздела
[Права и роли](permissions-and-roles.md) читает `request.profile.role` заново из хранящегося в
базе `Profile`, который middleware только что перепроверил, а не из payload JWT.

## Обновление и ротация {#refresh-and-rotation}

Старая документация проекта утверждала, что есть ротация refresh-токенов и их учёт на сервере,
но не указывала на код. Вот что код делает на самом деле. `POST /api/auth/refresh-token/`
(`OrgAwareTokenRefreshView`, `backend/common/views/auth_views.py`, подключён в
`backend/common/urls.py:58-62`) является единственным эндпоинтом обновления. Отдельного маршрута
со стандартным `TokenRefreshView` из simplejwt нет, поэтому показанные выше настройки
`ROTATE_REFRESH_TOKENS`/`BLACKLIST_AFTER_ROTATION` описывают замысел, а сама логика ротации
написана вручную в этом view, а не делегирована стандартному сериализатору simplejwt:

```python
with transaction.atomic():
    token.blacklist()
    new_token = OrgAwareRefreshToken.for_user_and_org(user, org, profile)
```

Предъявленный refresh-токен декодируется и проверяется, его claim `org_id` (если есть) заново
сверяется с активным `Profile` точно так же, как описано выше в разделе [Claims](#claims). Отозванное
членство и здесь получает 403, а не новый токен. Затем в одной атомарной транзакции предъявленный
токен заносится в чёрный список и выпускается замена с тем же контекстом организации. Обе записи
выполняются в одной транзакции именно для того, чтобы сбой никогда не оставил клиента без токена,
пока старый токен ещё годен. Это настоящая ротация с настоящим состоянием на сервере:
`RefreshToken.blacklist()` пишет в собственные таблицы simplejwt
`OutstandingToken`/`BlacklistedToken` (из приложения `token_blacklist`), и именно на них
наткнётся украденный refresh-токен, повторно предъявленный после того, как легитимный клиент
уже обновился. Токен из чёрного списка при повторном использовании не проходит проверку. Эти
служебные строки не хранятся вечно: `flush_expired_refresh_tokens` (`backend/common/tasks.py`)
удаляет строки `OutstandingToken`, когда истёк их собственный `expires_at`, и запускается каждую
ночь. См. [Фоновые задачи](background-jobs.md).

Истёкший или уже занесённый в чёрный список refresh-токен приводит к `TokenError`, который этот
view превращает в 401. Refresh-токен для `User`, чья учётная запись с тех пор деактивирована
(`user.is_active`), тоже отклоняется, явно, с кодом 403.

## Переключение организации {#organization-switching}

Вошедший пользователь может состоять в нескольких организациях, а один JWT всегда содержит только
один `org_id`. `POST /api/auth/switch-org/` (`OrgSwitchView`) позволяет клиенту перейти в другую:
он требует только `IsAuthenticated` (а не `HasOrgContext`), потому что должен работать и для
токена, у которого ещё вообще нет claim организации. В таком состоянии находится токен сразу после
входа через Google OAuth, поскольку `GoogleOAuthCallbackView`/`GoogleIdTokenView` выпускают
первоначальный токен с `org=None` и оставляют выбор организации отдельному шагу.

View заново проверяет членство так же, как эндпоинт обновления
(`Profile.objects.get(user=request.user, org_id=org_id, is_active=True)`), и возвращает 403
(с записью `permission_denied` в журнале аудита), если у вызывающего нет активного профиля в
запрошенной организации. Затем он при необходимости выводит из оборота refresh-токен, от
которого клиент уходит:

```python
if str(token.get("user_id")) != str(request.user.id):
    return
token.blacklist()
```

Эта проверка владельца не случайна. Без неё `refresh` позволил бы любому аутентифицированному
пользователю занести в чёрный список *любой* refresh-токен, который он смог увидеть, и удобный
параметр превратился бы в удалённый выход из чужой сессии. Вывод старого токена из оборота
необязателен намеренно (не все существующие клиенты его передают, а отказывать в переключении из-за
отсутствия необязательного поля хуже, чем позволить одному токену истечь по своему 14-дневному
графику). Но если токен передан и принадлежит вызывающему, он перестаёт работать сразу, а не
остаётся действительным для предыдущей организации до конца срока жизни. Само переключение
организации, то есть вывод старого токена и выпуск замены, происходит в одной транзакции по той же
причине, что и в эндпоинте обновления.

## Персональные токены доступа {#personal-access-tokens}

Персональные токены доступа (`bcrm_pat_…`, `PersonalAccessToken` в `backend/common/models.py`)
предназначены для агентов и скриптов, которым нужно аутентифицироваться как конкретный
пользователь, не проходя поток JWT/OAuth при каждом вызове. Токен генерируется один раз
(`PersonalAccessToken.generate(profile, name, ...)`), показывается вызывающему ровно один раз и
хранится только в виде хеша SHA-256 (`token_hash`); восстановить открытый текст из базы данных
потом невозможно.

Токен разбирается дважды за запрос, и это сделано намеренно: `GetProfileAndOrg` разбирает PAT
первым (чтобы `request.org`, а дальше и контекст RLS, был установлен до выполнения
`RequireOrgContext`), а класс DRF `PATAuthentication` (`backend/common/pat_auth.py`) повторно
использует тот же разобранный токен (сохранённый как `request._pat`), а не ищет его второй раз.
Оба используют одну функцию проверки, `resolve_valid_pat`, которая убеждается, что токен не
отозван и не истёк (`PersonalAccessToken.is_valid()`) и что профиль-владелец и его организация
всё ещё активны. Поэтому деактивация профиля сразу отключает его персональные токены доступа, без
отдельного шага отзыва.

Токен аутентифицируется **как** профиль-владелец и полностью наследует его роль и организацию.
У `PersonalAccessToken` есть поле `scopes`, но прежде чем считать, что оно что-то ограничивает,
прочтите собственный комментарий модели:

```python
# NOTE: scopes are stored for forward-compatibility but are NOT enforced in
# Phase 1: a token always inherits the owning profile's full role/permissions.
# Do not treat `scopes` as a trust boundary until enforcement lands.
```

Считайте персональный токен доступа ровно настолько мощным, насколько мощен создавший его
пользователь. PAT администратора может всё, что этот администратор может через интерфейс.
Управление своими токенами (самообслуживание) находится в `profile/tokens/` (пользователь управляет только
своими); надзор администратора за всеми токенами организации, включая токены деактивированного
коллеги, намеренно вынесен в отдельный эндпоинт `org/tokens/`, доступный только администраторам,
чтобы ради надзора никогда не пришлось ослаблять защиту самостоятельного управления. Подробнее об
этом различии в разделе [Усиление безопасности](../self-hosting/security-hardening.md#token-surfaces).

## API-ключи организации {#organization-api-keys}

У каждой `Org` ровно один API-ключ (`Org.api_key`, генерируется при создании), которым управляют
через `GET`/`POST /api/org/api-key/` (`OrgApiKeyView`), в обоих направлениях только для
администраторов. В отличие от персонального токена доступа, этот ключ не аутентифицирует какого-то
конкретного человека: `_process_api_key_auth` в `GetProfileAndOrg` сопоставляет запрос с этим
ключом (в заголовке `Token`) с **первым активным профилем `ADMIN`** организации:

```python
profile = Profile.objects.filter(
    org=organization, role="ADMIN", is_active=True
).first()
```

Именно заимствование профиля реального человека делало этот ключ таким опасным: он никогда не
истекает, на тенанта он один, поэтому его нельзя отозвать для отдельной интеграции, и до появления
проверки областей действия он мог всё, что мог этот администратор, включая удаление записей и
выпуск персонального токена доступа от его имени.

Теперь действуют два ограничения, оба в middleware, до выполнения любого view:

- **Ключ только для чтения.** Любой небезопасный метод (`POST`, `PUT`, `PATCH`, `DELETE`)
  отклоняется с кодом 403. Ключ оценивается как список областей `("*:read",)`, поэтому ключ
  организации и персональный токен доступа только для чтения проходят через одну реализацию
  (`common/scopes.py`).
- **Ключ не может добраться до учётных данных.** `/api/profile/tokens/`, `/api/org/tokens/` и
  `/api/org/api-key/` находятся в списке запретов, который не удовлетворяет ни одна область, поэтому
  ключ не может прочитать себя, сменить себя или создать токен от имени администратора, чью
  личность он заимствует.

`common.external_auth.APIKeyAuthentication` содержит те же два ограничения. Это независимая
вторая копия разбора ключа, которая срабатывает, когда DRF аутентифицирует запрос, пропущенный
middleware, поэтому защита только одной из них оставила бы уровень DRF пропускать то, что
middleware отклоняет.

`DJANGO_ORG_API_KEY_AUTH=false` полностью отключает этот путь на всех эндпоинтах. По умолчанию он
включён, чтобы обновление ничего не сломало; в развёртывании, где все интеграции уже перешли на
персональные токены доступа, его стоит выключить. Даже в режиме только для чтения этот ключ читает
все записи организации, поэтому остаётся самым грубым из трёх типов учётных данных на этой
странице. Предпочитайте персональный токен доступа с ограниченными областями.

Смена ключа (`POST /api/org/api-key/`) сразу делает недействительным предыдущий ключ, о чём
сообщает ответ. Ключ исключён из всех вложенных представлений API (`OrganizationSerializer`
никогда его не встраивает) и отдаётся только этим одним эндпоинтом, который теперь требует
интерактивной сессии.

## Учётные данные клиентского портала {#customer-portal-credentials}

Всё, что описано выше, аутентифицирует кого-то на **вашей** стороне: участника организации или
скрипт, действующий с полномочиями участника. Клиентский портал (`/api/portal/`) аутентифицирует
того, кто находится по другую сторону обращения, и это намеренно отдельная область. Его субъект:
`Contact`, то есть запись в вашей CRM, а не учётная запись в вашей системе: ни строки `User`, ни
`Profile`, ни роли, ни членства в организации.

`mint_portal_token` (`backend/common/portal_auth.py`) выдаёт access-токен на 24 часа с
`typ: "portal"`, `org_id` и `contact_id`. Refresh-токена нет, поэтому ротация, отзыв токенов
обновления и аннулирование при смене привилегий на этой поверхности полностью отсутствуют. Это те
части системы аутентификации, которые труднее всего сделать правильно и опаснее всего сделать
неправильно, а порталу, который посещают несколько раз за обращение, они не нужны.

Граница между двумя областями обеспечивается в трёх независимых местах, потому что граница,
которая держится на том, что каждый будущий автор о ней помнит, границей не является:

1. **`PortalContactAuthentication` никогда не входит в `DEFAULT_AUTHENTICATION_CLASSES`.** Эта
   настройка глобальная, поэтому всё, что в ней перечислено, аутентифицирует каждый view проекта.
   Views портала вместо этого явно указывают класс, а значит, добавление эндпоинта, принимающего
   клиента, всегда осознанное действие.
2. **Субъект сообщает `is_authenticated = False`.** Если токен портала всё же попадёт во
   внутренний view, собственный `IsAuthenticated` DRF откажет ему по построению. По той же
   причине он сообщает `is_anonymous = True`, из-за чего `BaseModel.save` не трогает
   `created_by`, а не пытается записать `Contact` во внешний ключ на `User`.
3. **`GetProfileAndOrg` отклоняет токен портала на любом пути вне `/api/portal/`** с кодом 403
   ещё до выполнения любого view. View, написанный позже, не может обойти это, забыв класс прав.

Трафик в обратном направлении особой обработки не требует. Токен портала выпускается без claim
`user_id`, поэтому `get_user` из SimpleJWT отклоняет его сам, а персональный токен доступа,
API-ключ организации и внутренний JWT каждый отклоняются порталом. Все три направления покрыты
тестами.

Сам вход выполняется по коду, отправленному на email в рамках организации, и намеренно хранится в
собственной таблице `PortalLoginToken`, а не в столбце `MagicLinkToken`, допускающем null. Общая
таблица означала бы один эндпоинт проверки, принимающий учётные данные другой области, а это
клиент, входящий в ваше внутреннее приложение. Примерно сорок продублированных строк покупают
границу, которую не пересечь одной ошибкой. Эндпоинты описаны в разделе
[API: Клиентский портал](../api/customer-portal.md).

## Связанная конфигурация {#related-configuration}

Одна связанная деталь конфигурации, о которой стоит знать: настройки redirect URI нет. Redirect
URI, используемый при обмене кода Google OAuth (`GoogleOAuthCallbackView.post`), берётся из тела
запроса клиента при каждом вызове (`request.data.get("redirect_uri")`). Настройка
`GOOGLE_REDIRECT_URI` раньше существовала в `backend/crm/settings.py`, была определена и никогда
не читалась; её удалили. Настройки, которые действительно важны, описаны в разделе
[Google OAuth](../self-hosting/google-oauth.md).
