# Правила автоматизации

Правило автоматизации говорит BottleCRM: «когда с записью происходит вот это и выполняются вот эти
условия, сделай вот то». Когда сделка выиграна, создать задачу на стартовый созвон для её
ответственных и сообщить команде компании. Когда лид приходит из веб-формы, назначить его следующему
человеку по очереди. Всё находится в `backend/automation/`, а правилами управляют через API по адресу
`/api/automation/`.

## Кто может их использовать {#who-can-use-them}

Создавать, читать, изменять, пробовать и удалять правила могут только администраторы организации, и
это касается даже чтения списка и истории запусков: в запусках упоминаются записи и люди, которых
участник может не иметь права видеть. Участник получает `403` на любом маршруте.

Правилами можно управлять только из сессии вошедшего пользователя. `/api/automation/` входит в список
запрещённых для учётных данных в `backend/common/scopes.py`, поэтому персональный токен доступа или
API-ключ организации там отклоняется, какие бы области доступа у него ни были. Правило продолжает
действовать и после отзыва токена, которым было записано, поэтому создание правила является действием
того же рода, что и создание вебхука.

## Что такое правило {#what-a-rule-is}

Правило читается как предложение: **Когда** (триггер), **Только если** (условия), **Тогда** (действия).

| Часть | Значение |
| --- | --- |
| `name` | Как правило называется в списках, уведомлениях и ленте активности. |
| `object_key` | Тип записей, за которыми оно следит: `lead`, `contact`, `account`, `deal`, `ticket` или `task`. |
| `trigger` | Что его запускает: `{"event", "field", "to"}`. См. [Триггеры](#triggers). |
| `match` | `all` (выполняются все условия) или `any` (выполняется хотя бы одно). Один уровень, без групп. |
| `conditions` | До 20 проверок `{"field", "op", "value"}`. Пустой список выполняется всегда. |
| `actions` | До 10 действий, выполняются по порядку. См. [Действия](#actions). |
| `is_active` | Включено ли правило. |
| `position` | Его место в списке. Правила для одного и того же изменения выполняются в порядке списка. |
| `owner` | Администратор, который последним включил правило. Правило действует от имени этого человека. Только для чтения. |

Правила сверяются с тем, что предлагает организация, при сохранении и ещё раз перед каждым запуском,
поэтому правило не может задать поле или вариант, который отклонила бы форма редактирования его
записи, и не может указать человека, эндпоинт вебхука или связь за пределами своей организации.
Некорректное правило отклоняется с `400`, ошибки в котором сгруппированы по пути, чтобы редактор мог
отметить нужную строку:

```json
{
  "errors": {
    "conditions[2].value": ["Enter a number."],
    "actions[0].people": ["Each person must be an active member of this org."]
  }
}
```

Правило, которое было корректным, а потом сломалось (его поле выключили, вариант удалили, человека
деактивировали), остаётся сохранённым и включённым. Его запуски завершаются ошибкой с указанием
причины, список показывает его как **Требует внимания**, а сохранение или повторное включение проверяет
его заново. Переименовать или выключить его можно всегда, поэтому сломанное правило можно отложить.

Каждый id в правиле является строкой UUID в каноническом виде: в нижнем регистре и с дефисами, как
API возвращает id.

## Поля {#fields}

`GET /api/automation/catalogue/` перечисляет для каждого объекта поля, которые могут читать правила,
их тип, варианты значений и то, может ли правило их задавать. Редакторы строятся только по нему. В
каталоге никогда нет полей, которыми владеет сервер: `org`, id, `created_by`, `updated_by`, метки
времени, `is_active`, токены и всё, что сериализатор объекта считает доступным только для чтения. Поле
можно задать ровно тогда, когда его записывает собственная форма редактирования объекта.

| Объект | Поля |
| --- | --- |
| Лид | заголовок, имя и фамилия, email, телефон, компания, должность, сайт, город, страна, статус, источник, отрасль, рейтинг, этап (только для чтения), оценочная стоимость, вероятность, ожидаемая дата закрытия, следующий контакт, ответственный |
| Контакт | имя и фамилия, email, телефон, компания, должность, отдел, город, страна, не звонить, ответственный |
| Компания | название, email, телефон, сайт, город, страна, отрасль, сотрудники, годовая выручка, ответственный |
| Сделка | название, этап, исход (только для чтения), тип, источник, сумма, вероятность, дата закрытия, ответственный |
| Обращение | тема, статус, приоритет, тип, дата закрытия, ответственный |
| Задача | заголовок, статус, приоритет, срок, ответственный |

Активные дополнительные поля организации типов text, textarea, number, date, dropdown и checkbox
добавляются к своему объекту как `custom_fields.<key>`. Объект, который установленное приложение
добавляет в реестр объектов (`common.object_registry.register_hook`), появляется в каталоге, если его
запись предлагает адаптер автоматизации.

Некоторые поля ведут себя особым образом:

- **Этап сделки** принимает id этапа и перечисляет этапы всех воронок, сгруппированные по воронкам.
  Правило может перевести сделку только на этап её собственной воронки.
- **Исход сделки** (`stage_kind`) равен `open`, `won` или `lost` и берётся из типа этапа сделки,
  поэтому «исход меняется на won» срабатывает при выигрыше в любой воронке, как бы ни назывался этап.
  Поле только для чтения.
- **Статус лида** предлагает `converted` для чтения, но не для записи: конвертация лида создаёт
  компанию, контакт и сделку и никогда не является редактированием. **Статус обращения** так же
  обращается с `Duplicate`, потому что его задаёт только объединение.
- **Ответственный** является полем типа `people`: списком id профилей. Его можно читать и задавать,
  но изменение списка людей не может быть триггером.

Значения сравниваются по типу: текст и варианты как строки, числа как десятичные, даты как
`YYYY-MM-DD`, да/нет как логические значения, люди как списки id. Текстовое сравнение через
`contains` не учитывает регистр.

### Родители и связи {#parents-and-links}

Действия могут затрагивать как саму запись, так и её единственного родителя:

| Объект | Родитель |
| --- | --- |
| Сделка | её компания |
| Обращение | его компания |
| Задача | лид, компания, сделка или обращение, к которому она относится |
| Лид, контакт, компания | нет |

Приложение, добавляющее собственные объекты, может также предлагать связи с другими записями через
`automation.links.register_link_hook`; каталог перечисляет их в `links` каждого объекта. В community
edition хуков связей нет.

## Триггеры {#triggers}

| Триггер | JSON | Срабатывает, когда |
| --- | --- | --- |
| Создание | `{"event": "created", "field": null, "to": null}` | Создана запись объекта. |
| Изменение | `{"event": "updated", "field": null, "to": null}` | Изменилось любое поле записи из каталога. |
| Изменение поля | `{"event": "updated", "field": "status", "to": null}` | Это поле изменилось, на любое значение. |
| Изменение поля на значение | `{"event": "updated", "field": "stage_kind", "to": "won"}` | Это поле перешло в указанное значение. |

«Меняется на» срабатывает только при переходе в значение: старое значение отличалось, а новое
совпадает. Последующие правки выигранной сделки не запускают «исход меняется на won» повторно. Вместе
с правилами цепочек из раздела [Как выполняется запуск](#how-a-run-happens) именно это не даёт
правилу запускать само себя.

### Что запускает правило {#what-sets-a-rule-off}

Считается любое сохранение, сделанное через приложение: веб- и мобильное приложения, REST API и
персональные токены доступа, карточка, перемещённая в другую колонку на доске, отправка публичной веб-формы,
обращение, пришедшее по почте, и сохранения, сделанные задачами Celery. Веб-формы и входящая почта
являются основными источниками новых лидов и обращений, поэтому правило «создание» срабатывает на них,
даже если никто не вошёл в систему.

Правила выполняются при завершении запроса, после того как представление всё сохранило и
присоединило ответственных и теги, и до того, как уходит ответ. Поэтому страница, которая
перезагружается после сохранения, уже показывает, что сделали правила, а условие вроде «ответственный
не пуст» видит ответственных, заданных в том же сохранении. Маршрутизация обращений выполняется
раньше, при создании обращения, поэтому правило «обращение создано» видит назначенных маршрутизацией
ответственных. Вне запроса (задача Celery, команда управления) правила выполняются при фиксации
изменения, в процессе, который его сохранил.

Запись, сохранённая дважды за один запрос, считается одним изменением: создание с последующими
обновлениями остаётся созданием, а два обновления сохраняют первое старое значение и последнее новое.
Откатанное изменение ничего не запускает.

### Что не запускает правила {#what-does-not-set-rules-off}

- **Импорт из таблиц** лидов, контактов и обращений, а также **демонстрационные данные отраслевых
  пакетов** при их создании пакетом (последующая правка демонстрационной записи считается как любое
  другое сохранение). Импорт на 2000 строк при активном правиле «лид создан: создать задачу» не
  создаёт ни одной задачи.
- **Команда управления `seed_data`**, которая наполняет организацию демонстрационными записями.
- **Массовое редактирование обращений** (`POST /api/cases/bulk/update/`). Закрытие 200 обращений
  разом не запускает ни одного правила.
- **Массовые операции с базой данных в обход сигналов сохранения**: `update()`, `bulk_create()` и
  `bulk_update()` у queryset, например перемещения внутри объединения или разделения обращений и
  перенумерация остальных карточек колонки доски, когда одну из них бросают между ними. Вебхуки их тоже
  не видят.
- **Изменения полей «многие-ко-многим»** (ответственные, теги, команды) в качестве триггеров. Условия
  по-прежнему могут их читать.
- **Удаление записи.** Удаление не является триггером; его покрывают вебхуки.

## Условия {#conditions}

Каждое условие имеет вид `{"field", "op", "value"}`. Допустимые операторы зависят от типа поля:

| Тип | Операторы |
| --- | --- |
| Текст | `eq`, `neq`, `contains`, `not_contains`, `empty`, `not_empty` |
| Число | `eq`, `neq`, `gt`, `lt`, `empty`, `not_empty` |
| Дата | `eq`, `neq`, `gt` (после), `lt` (до), `empty`, `not_empty` |
| Выбор | `eq`, `neq`, `in`, `not_in`, `empty`, `not_empty` |
| Да/нет | `true`, `false` |
| Человек, люди | `eq`, `includes`, `excludes`, `empty`, `not_empty` |

- `empty`, `not_empty`, `true` и `false` принимают `"value": null`. Пустое поле да/нет считается
  ложным.
- `in` и `not_in` принимают список вариантов. Даты принимаются в формате `YYYY-MM-DD`; относительные
  даты («в ближайшие 7 дней») не предлагаются.
- `includes` и `excludes` принимают один id профиля; `eq` для людей принимает список и сравнивает весь
  набор.
- `was` и `was_not` сравнивают значение **до** этого сохранения, для любого типа поля, кроме людей, и
  только для триггера `updated`. Для поля, которое сохранение не изменило, они читают его текущее
  значение.
- Операторов шаблонов и регулярных выражений нет. Текст организации только сравнивается и никогда не
  вычисляется.

Условия читают запись в том виде, в каком она есть на момент выполнения правила, после завершения
запроса.

## Действия {#actions}

Каждое действие сначала планируется (каких записей и людей оно достигнет, подходят ли ещё его
значения), а затем применяется. Действия правила выполняются по порядку внутри одной транзакции,
поэтому последующее действие видит то, что сделало предыдущее: назначьте кого-то, затем уведомите
ответственных за запись, и уведомление получит новый ответственный.

`{name}` является единственной подстановкой, в заголовках задач и сообщениях уведомлений. Она
заменяется отображаемым именем записи в виде обычного текста; ничто, написанное организацией, не
отрисовывается как шаблон, markdown или HTML, поэтому запись с именем `<img onerror=...>` показывается
именно этими символами.

### Задать поле {#set-a-field}

```json
{"type": "set_field", "target": "record", "field": "probability", "value": 90}
```

`target` равен `record`, `parent` или id связи из каталога. `value: null` очищает поле. Поле людей
принимает список id профилей.

Запись идёт через собственный путь редактирования объекта как частичное обновление от имени владельца
правила, поэтому проходит ровно те проверки, что применяет форма редактирования. Сделке, переведённой
на выигрышный этап, по-прежнему нужны сумма и дата закрытия; лид нельзя конвертировать; правила
закрытия и согласования обращения соблюдаются. Отказ завершает шаг ошибкой с собственным сообщением
формы. Поведение, которое есть только у доски (заполнение даты закрытия и вероятности сделки или
статуса лида по его этапу при перетаскивании карточки), не копируется. Цель без родителя (сделка без
компании) даёт пропущенный шаг, а не ошибку.

### Назначить {#assign}

```json
{"type": "assign", "people": ["<profile id>", "<profile id>"], "mode": "rotate"}
```

`replace` принимает ровно одного человека; `rotate` принимает от 2 до 20 и отдаёт каждую запись
следующему человеку по очереди, пропуская тех, кто больше не активен. В обоих случаях текущие
ответственные записи **заменяются**. Позиция очереди хранится для каждого действия отдельно, поэтому
два действия с очередью не делят одну очередь. Новые ответственные получают обычное для модуля письмо о
назначении.

### Создать задачу {#create-a-task}

```json
{
  "type": "create_task",
  "title": "Kick-off call: {name}",
  "due_in_days": 2,
  "priority": "High",
  "assign_to": "record",
  "person": null
}
```

- `title`: от 1 до 200 символов, обрезается по длине после подстановки `{name}`.
- `due_in_days`: `null`, если срока нет, или от 0 до 365 дней от сегодняшнего дня в часовом поясе
  организации.
- `priority`: `Low`, `Medium` или `High`.
- `assign_to`: `record` (ответственные за запись), `parent` (ответственные за родителя), `owner`
  (владелец правила) или `person` с id этого профиля в `person`.

Задача создаётся через собственный путь создания API задач от имени владельца правила. Она
связывается с записью там, где задача это допускает (лид, компания, сделка или обращение, а контакт
через его контакты); в остальных случаях её описание содержит ссылку на запись.

### Уведомить {#notify}

```json
{
  "type": "notify",
  "to": ["record_assignees", "parent_assignees"],
  "people": [],
  "message": "{name} is won. Time to say hello."
}
```

`to` принимает любые из `record_assignees`, `record_creator`, `parent_assignees`, `admins` и
`linked:<link id>` для ответственных за связанные записи. `people` добавляет выбранные профили. Хотя
бы одно из двух полей должно указывать кого-то. `message` содержит от 1 до 500 символов.

Каждый получатель получает уведомление в приложении (глагол `automation.message`, текст в его `data`)
и письмо с сообщением и ссылкой на запись. Уведомления получают только активные участники
организации; отправить на внешний адрес нельзя, и такой адрес отклоняется при сохранении правила.

### Отправить вебхук {#send-a-webhook}

```json
{"type": "webhook", "endpoint": "<webhook endpoint id>"}
```

Эндпоинт должен быть одним из собственных активных вебхуков организации в формате **Подписанный JSON**.
Доставка идёт через путь [вебхуков](webhooks.md), поэтому подпись, правила для URL, повторы и журнал
доставок те же. Событие называется `rule.triggered` и отправляется на выбранный эндпоинт независимо
от того, на какие события он подписан:

```json
{
  "id": "4b0f7e0c-8f0e-4b8e-9d0f-2f4d6c1a9e11",
  "event": "rule.triggered",
  "created_at": "2026-10-22T10:15:02.114Z",
  "org_id": "a3f1c2d4-0000-4000-8000-000000000001",
  "data": {
    "rule": {"id": "9c2e...", "name": "Deal won: onboarding"},
    "object": "deal",
    "record": {"id": "0d6f...", "name": "Acme renewal", "stage": "CLOSED_WON", "...": "..."}
  }
}
```

`record` содержит ту же полезную нагрузку, что и собственные события вебхуков объекта.

### Никто не узнаёт о записи, которую не может открыть {#nobody-learns-about-a-record-they-cannot-open}

«Уведомить» и «Создать задачу» достигают только тех, кто может открыть запись; это проверяется
правилом чтения данного объекта. Сделки и лиды часто видны только их ответственным, поэтому не все
«ответственные за компанию» могут иметь право видеть сделку. Каждый отсеянный упоминается в шаге
("Skipped Meera: cannot open this deal"); если не остаётся никого, шаг пропускается, а не завершается
ошибкой. Администраторы могут открыть всё.

## Как выполняется запуск {#how-a-run-happens}

- **Порядок.** Для каждого изменения выполняется каждое подходящее включённое правило организации для
  этого объекта, в порядке списка. «Остановиться здесь» нет.
- **Одно правило, одна транзакция.** Если любой шаг правила завершается ошибкой, записи этого правила
  откатываются, запуск записывается как неудачный с причиной из шага, а следующее правило всё равно
  выполняется. Письма и вебхуки отправляются только после фиксации транзакции правила. Сломанное
  правило никогда не блокирует и не отменяет сохранение, которое его запустило.
- **От чьего имени оно действует.** От имени владельца правила. Создаваемые им записи и задаваемые
  поля приписываются владельцу, а не тому, кто сохранил запись (и не остаются пустыми для анонимной
  веб-формы), а лента активности указывает имя правила рядом с изменением.
- **Цепочки.** Собственные записи правила тоже являются изменениями и могут запускать другие правила,
  до глубины 3. Правило действует на конкретную запись не более одного раза за цепочку, поэтому два
  правила, отменяющие друг друга, останавливаются. Правило никогда не выполняется на изменении,
  сделанном его собственным запуском, поэтому правило «задача создана: создать задачу» добавляет одну
  задачу. Запуск, вызванный записью другого правила, показывает, какой запуск его вызвал.
- **Владельцы, теряющие права.** Когда владелец правила перестаёт быть администратором,
  деактивирован, покидает организацию или удалён, его активные правила выключаются с указанием причины,
  а остальным администраторам сообщается об этом. Другой администратор забирает правило себе, снова
  включив его, и становится его владельцем.
- **Сбои доходят до человека.** Когда запуск завершается ошибкой, владелец правила получает
  уведомление в приложении, не чаще одного раза в день на правило.

Для выполнения правил воркер Celery не нужен. Он нужен для их писем и доставки вебхуков, как и везде
в приложении; см. [Почта и Celery](../self-hosting/email-and-celery.md).

## Ограничения {#limits}

Одинаковы для всех установок:

| Ограничение | Значение |
| --- | --- |
| Условий в правиле | 20 |
| Действий в правиле | 10 |
| Записей, которых может коснуться одно действие | 100 (при большем числе шаг завершается ошибкой, а не выполняется частично) |
| Глубина цепочки | 3 |
| Запусков на организацию в час | 1000 |
| История запусков | 30 дней |

Запуски сверх часового ограничения не выполняются и не сохраняются по строке на каждый: каждое
правило получает за час один пропущенный запуск, который их подсчитывает ("312 runs skipped: the org
reached its hourly limit"), а администраторы организации получают одно уведомление за этот час.
Поэтому поток отправок форм не может раздуть таблицу запусков сверх ограничения.

## Запуски {#runs}

Каждый запуск сохраняет запись, на которой он выполнялся (с её именем на тот момент, чтобы история
читалась и после переименования), свой статус, причину и по одному шагу на каждое действие.

| Статус запуска | Значение |
| --- | --- |
| `done` | Каждый шаг выполнен или пропущен. |
| `failed` | Шаг завершился ошибкой или правило перестало проходить проверку, и ничего из записанного им не сохранилось; либо отправленное им письмо не удалось доставить. |
| `skipped` | Учтён сверх часового ограничения; `skipped_count` показывает, сколько таких. |

| Статус шага | Значение |
| --- | --- |
| `done` | Изменение шага сохранено. |
| `undone` | Шаг был применён, а затем откатан вместе со своим неудачным правилом. |
| `failed` | Шаг не удалось выполнить; его текст объясняет почему. |
| `skipped` | Делать было нечего, например не осталось никого для уведомления. |

Запуски старше 30 дней удаляются задачей Celery, которая ставится в очередь по мере записи новых
запусков, не чаще одного раза в день на организацию, а также ежедневным заданием beat
`automation.tasks.prune_runs` там, где запущен beat.

Правила отправляют следующие уведомления в приложении, каждое с текстом в `data`:

| Глагол | Кому | `data` |
| --- | --- | --- |
| `automation.message` | получателям действия «Уведомить» | `message`, `rule` |
| `automation.failed` | владельцу правила, не чаще одного раза в день на правило | `rule`, `rule_id`, `reason` |
| `automation.paused` | остальным администраторам организации | `rules`, `reason` |
| `automation.limit` | администраторам организации, раз в час | `window_start` |

## Пробный запуск правила {#trying-a-rule}

`POST /api/automation/rules/<id>/try/` с `{"record_id": "<id>"}` выполняет только этап планирования
каждого действия для одной записи объекта правила и отвечает, что сделал бы запуск. Он никогда ничего
не записывает: запись, её связи, уведомления, задачи и позиция очереди остаются как были.

```json
{
  "steps": [
    {"action": 0, "type": "create_task", "status": "planned",
     "text": "Would create the task 'Kick-off call: Acme renewal' for Asha and Ravi"},
    {"action": 1, "type": "notify", "status": "planned",
     "text": "Would notify Ravi. Skipped Meera: cannot open this deal"}
  ]
}
```

Запись другого объекта или другой организации даёт `404`. Правило, которое ещё никто не включал,
планируется от имени администратора, который его пробует. Правило, которое больше не проходит
проверку, возвращает каждый шаг как `failed` с указанием причины.

## Создание правил в приложениях {#building-rules-in-the-apps}

Администраторы создают правила в веб-приложении и в мобильном приложении, в обоих в разделе
**Настройки → Автоматизация**. Участникам этот пункт не показывается, а участнику, который всё же попал на
страницу, сообщается, что правила автоматизации может видеть только администратор организации.

- **Список** показывает все правила по порядку с их статусом (включено, выключено, приостановлено, не
  выполняется или требует внимания), причиной под ним, если она есть, и числом запусков и сбоев за
  последние семь дней. У каждого правила есть стрелки вверх и вниз для изменения места. **Новое правило**
  начинает новое правило: выберите название и тип записей для отслеживания, затем сохраните. Правило
  включается и выключается в редакторе (**Сохранить и включить**, **Выключить**). У приостановленного
  правила кнопка называется **Сохранить и взять на себя**: включив его, вы становитесь его владельцем.
- **Редактор** читается так же, как правило: **Когда**, **Только если**, **Тогда**. Поля, варианты, люди и
  эндпоинты берутся из каталога, поэтому выбрать можно только то, что предлагает организация.
  Значение, которое было корректным при сохранении, а теперь нет, остаётся видимым с пометкой
  «(больше недоступно)», и если сохранить его без изменений, сервер укажет строку. Отклонённое
  сохранение оставляет редактор в том виде, в каком вы его оставили, и показывает текст сервера. Тип
  записей фиксируется после создания правила; другой тип означает новое правило.
- **Проверить на записи** выбирает запись объекта правила и показывает, что сделал бы запуск, ничего не
  записывая. Используется сохранённое правило, поэтому кнопка недоступна, пока в редакторе есть
  несохранённые изменения. Триггер и условия не проверяются: показывается только, что сделали бы
  действия.
- **История запусков** перечисляет запуски правила от новых к старым, по 20 за раз. Каждый запуск
  раскрывается до своих шагов.

Правила отправляют четыре вида уведомлений в приложении, которые появляются на странице уведомлений
со ссылкой на соответствующее правило или запись.

## API {#api}

Всё находится под `/api/automation/`, только для администраторов, только из сессии вошедшего
пользователя:

| Метод и путь | Что делает |
| --- | --- |
| `GET catalogue/` | объекты с их полями, родителями и связями; операторы; типы действий; активные участники организации; её вебхуки Signed JSON; ограничения на условия и действия |
| `GET rules/` | правила организации, каждое со `status`, `status_text`, `runs_7d` и `failures_7d` |
| `POST rules/` | создание, в конце списка |
| `GET rules/<id>/` | одно правило |
| `PATCH rules/<id>/` | изменение (`PUT` нет) |
| `DELETE rules/<id>/` | удаление правила и его запусков |
| `POST rules/<id>/try/` | шаги, которые запуск выполнил бы для одной записи, без записи данных |
| `GET rules/<id>/runs/` | его запуски от новых к старым, с пагинацией `limit`/`offset` |
| `POST rules/reorder/` | новый порядок списка: `{"ids": [...]}`; неуказанные правила сохраняют свой порядок после указанных |

Для id из другой организации ответ `404`.

Включение правила выполняется созданием или `PATCH` с `"is_active": true` для выключенного или
приостановленного правила. Вызывающий становится владельцем правила, а причина приостановки, если
была, очищается. Редактирование уже включённого правила сохраняет его владельца. Установка может
зарегистрировать хук тарифного плана (`automation.plan.register_plan_hook`), который отклоняет
включение правила с `403` и `"code": "plan_limit"` или помечает некоторые включённые правила как
невыполняемые (статус `over_limit`) со строкой `summary` в списке. Community edition таких хуков не
регистрирует: любое правило можно включить, и любое включённое правило выполняется.

Правило, объект которого относится к модулю, выключенному в организации (см.
[Модули](../api/modules.md)), показывается в списке как `paused` с текстом
`Paused: <Module> is switched off` и не выполняется. Его по-прежнему можно включить, и оно
возобновится вместе с модулем. Создание правила для такого объекта или изменение объекта, триггера,
условий, действий или match правила даёт `400` с сообщением о модуле. Пока выключены задачи, `actions`
в каталоге не содержит `create_task`, а новый шаг «Создать задачу» даёт `400` с сообщением о модуле;
шаг, который у правила уже есть, сохраняется и пропускается при выполнении правила.

`status` в списке равен `on`, `off`, `paused` (с причиной в `status_text`), `needs_attention` (с
первой проблемой) или `over_limit`, если так сообщает хук тарифного плана.

Основной пример, создание и включение одним запросом:

```json
{
  "name": "Deal won: onboarding",
  "object_key": "deal",
  "trigger": {"event": "updated", "field": "stage_kind", "to": "won"},
  "match": "all",
  "conditions": [{"field": "amount", "op": "gt", "value": 0}],
  "actions": [
    {
      "type": "create_task",
      "title": "Kick-off call: {name}",
      "due_in_days": 2,
      "priority": "High",
      "assign_to": "record",
      "person": null
    },
    {
      "type": "notify",
      "to": ["parent_assignees"],
      "people": [],
      "message": "{name} is won. Time to say hello."
    }
  ],
  "is_active": true
}
```

Запуск в том виде, в каком его возвращает `GET rules/<id>/runs/`:

```json
{
  "count": 1,
  "results": [
    {
      "id": "7a51...",
      "created_at": "2026-10-22T10:15:02.114Z",
      "record_id": "0d6f...",
      "record_name": "Acme renewal",
      "object_key": "deal",
      "status": "done",
      "reason": "",
      "steps": [
        {"action": 0, "type": "create_task", "status": "done",
         "text": "Created the task 'Kick-off call: Acme renewal' for Asha and Ravi"},
        {"action": 1, "type": "notify", "status": "done",
         "text": "Notified Ravi. Skipped Meera: cannot open this deal"}
      ],
      "skipped_count": 0,
      "depth": 1,
      "triggered_by": null
    }
  ]
}
```
