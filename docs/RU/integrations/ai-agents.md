# ИИ-агенты

ИИ-агент работает с BottleCRM так же, как любая другая программа: через REST API под `/api/`,
с аутентификацией по персональному токену доступа. Отдельного протокола для агентов, отдельного
эндпоинта и сервисной учётной записи нет. Агент является обычным клиентом API, поэтому RLS, RBAC и
валидация полей действуют для него точно так же, как для веб-приложения и мобильного приложения.

Это осознанное решение. Раньше BottleCRM поставлялся с сервером Model Context Protocol (MCP) по адресу
`/mcp`: тонким прокси, который переотправлял каждый вызов инструмента HTTP-запросом к этому же API. Он
покрывал восемь сущностей из всего продукта и не давал ни одной возможности, которой не было бы у API,
поэтому его удалили. Направьте агента прямо на API, и ему будет доступно всё.

## Выдайте агенту токен {#give-the-agent-a-token}

Создайте персональный токен доступа в CRM в разделе **Настройки → API-токены** (`/settings/api-tokens`)
или через `POST /api/profile/tokens/`. Исходное значение показывается ровно один раз, при создании.
Хранится только SHA-256-хеш, поэтому потерянный токен нельзя восстановить, его можно только заменить.

Каждый запрос передаёт его как bearer-токен:

```bash
curl -H "Authorization: Bearer bcrm_pat_..." \
     https://api.bottlecrm.io/api/leads/
```

Полный жизненный цикл (создание, срок действия, проверка и отзыв) описан в разделе
[Токены и API-ключи](../api/tokens-and-api-keys.md#personal-access-tokens).

## Дайте агенту изучить API {#let-the-agent-discover-the-api}

Бэкенд публикует схему OpenAPI 3, которую генерирует drf-spectacular. Передайте её агенту, и он сам
разберётся в эндпоинтах, телах запросов, перечислениях и обязательных полях. Вам не придётся вручную
поддерживать реестр инструментов, который расходится с настоящим URLconf:

| Что | Где |
| --- | --- |
| Машиночитаемая схема | `GET /schema/` |
| Интерактивная документация в браузере | `/swagger-ui/` |
| Отображение в ReDoc | `/api/schema/redoc/` |
| Список эндпоинтов, составленный вручную | [Указатель эндпоинтов](../api/endpoint-index.md) |

Форма запросов и ответов, пагинация, фильтрация и формат ошибок описаны в разделах
[Соглашения API](../api/conventions.md) и [Ошибки](../api/errors.md).

## Права доступа {#permissions}

**У агента ровно те права, что и у его токена, не больше и не меньше.**
`PATAuthentication` (`backend/common/pat_auth.py`) находит по токену его `Profile`-владельца и
заполняет из него `request.profile` и `request.org`; это тот же путь в коде, через который проходит
любой другой запрос с аутентификацией по PAT. Агент наследует роль, организацию и область RLS этого
пользователя.

У токена есть поле `scopes`, но **пока его ничто не проверяет**. Сейчас нельзя выдать агенту токен с
доступом уже, чем у его владельца. Считайте каждый токен, настроенный в агенте, равнозначным передаче
агенту вашего логина на весь срок действия токена, и выдавайте его профилю, чья роль соответствует
нужной работе.

Токен перестаёт работать, как только его профиль-владелец или организация деактивированы:
`resolve_valid_pat` отклоняет его с сообщением "Token owner or org is inactive". Поэтому токен
деактивированного пользователя спит, а не действует. Тем не менее при увольнении сотрудника его
стоит отозвать, потому что повторная активация учётной записи оживляет токен.

## Отзыв {#revoking}

Чтобы немедленно отключить агента, отзовите его токен. Нужный эндпоинт зависит от вашей роли:

- **Любая роль, собственный токен**: `DELETE /api/profile/tokens/{id}/`. Самообслуживание, только
  для своих токенов. Для id токена другого пользователя возвращается 404, и токен не отзывается.
- **Администраторы, любой токен в организации**: `DELETE /api/org/tokens/{id}/` вместе со списком
  для контроля по всей организации `GET /api/org/tokens/`. Именно их вызывает страница
  **Настройки → API-токены**. Пользователь без прав администратора, открывший эту страницу, видит
  «Только для администраторов», а не список токенов.

Отзыв идемпотентен: повторный вызов для уже отозванного токена ничего не делает и возвращает 200.

## Практические замечания {#practical-notes}

Несколько деталей API, на которых часто спотыкается первая интеграция с агентом:

- **Комментарии не являются вложенным действием.** Каждый модуль принимает их по адресу
  `comment/<id>/`, например `POST /api/leads/comment/<id>/`, а не `/api/leads/<id>/add_comment/`.
- **Конвертация лида является сменой статуса**, а не отдельным эндпоинтом действия:
  `PATCH /api/leads/<id>/` с `{"status": "converted"}`.
- **Статьи базы знаний находятся в приложении обращений** по адресу `/api/cases/solutions/`, а не на
  верхнем уровне `/api/solutions/`.
- **`InvoiceDetailView` реализует только `get` и `put`.** `PATCH` или `DELETE` к
  `/api/invoices/<id>/` возвращает 405. Используйте полный `PUT` или `POST /api/invoices/<id>/send/`,
  чтобы отправить счёт. См. [Счета и коммерческие предложения](../api/invoices.md).
- **Отправка счёта отправляет письмо клиенту.** Если вы разрешаете агенту этот вызов, поставьте перед
  ним шаг подтверждения. API не переспросит.

Готовые примеры на двух языках: [Python](python-sample.md) и [JavaScript](javascript-sample.md).
