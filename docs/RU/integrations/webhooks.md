# Вебхуки

Вебхук отправляет подписанный HTTPS `POST` на выбранный вами URL всякий раз, когда в вашей организации
что-то происходит: создан лид, выиграна сделка, клиент получил публичный ответ в обращении. Направьте
его в Zapier, n8n, канал Slack или Teams или собственный код. Всё находится в `backend/webhooks/`.

## Настройка {#setting-one-up}

`/settings/webhooks` в веб-приложении, **Настройки → Вебхуки** в мобильном приложении или API по
адресу `/api/webhooks/`. Видеть и изменять вебхуки может только администратор организации, и это
касается даже чтения списка: URL хука часто сам по себе является секретом (Zapier и Slack помещают
свой секрет в путь), а каждый эндпоинт получает копии ваших записей. Участник получает `403` на любом
маршруте.

Вебхуками можно управлять только из сессии вошедшего пользователя. `/api/webhooks/` входит в список
запрещённых для учётных данных в `backend/common/scopes.py`, поэтому персональный токен доступа или
API-ключ организации там отклоняется, какие бы области доступа у него ни были. Вебхук продолжает
отправлять события и после отзыва токена, которым был создан, поэтому создание вебхука является
действием того же рода, что и выпуск токена.

У каждого вебхука есть:

- **URL**: `https://` на порту 443, доступный из публичного интернета. Что отклоняется, см. в разделе
  [Правила для URL](#url-rules).
- **События**: одно или несколько из [каталога](#events).
- **Формат**: *Подписанный JSON* (по умолчанию), *Сообщение Slack* или *Сообщение Teams* (1.39.0).
- **Секрет подписи**: генерируется сервером (`whsec_...`). Полностью он показывается ровно дважды за
  всё время: в ответе на создание вебхука и в ответе на **Сменить секрет**. Во всех остальных местах
  видны только последние четыре символа. Выбрать секрет самостоятельно нельзя; запрос, в котором он
  указан, отклоняется.

У организации может быть до 10 вебхуков.

Начиная с 1.43.0 установленное приложение может владеть собственными эндпоинтами, которые
принадлежат его участнику-приложению (участнику организации, который является приложением, а не
человеком; см. [Токены и API-ключи](../api/tokens-and-api-keys.md#app-members)). Они принадлежат
приложению, а не администратору: `/api/webhooks/` никогда их не перечисляет, каждый маршрут отвечает
на них `404` (детали, изменение, удаление, тест, смена секрета, доставки, повторная доставка), они не
учитываются в лимите 10, и правило автоматизации не может отправлять на них. Такой эндпоинт
приостанавливается, только когда деактивирован его участник-приложение, и никогда из-за его
создателя, с причиной «Paused because its connected app was disconnected.»

## События {#events}

| Модуль   | События                                                                         |
| -------- | ------------------------------------------------------------------------------- |
| Лиды     | `lead.created`, `lead.updated`, `lead.deleted`                                  |
| Контакты | `contact.created`, `contact.updated`, `contact.deleted`                         |
| Компании | `account.created`, `account.updated`, `account.deleted`                         |
| Сделки   | `deal.created`, `deal.updated`, `deal.deleted`, `deal.won`, `deal.lost`         |
| Обращения | `ticket.created`, `ticket.updated`, `ticket.comment_added`                     |
| Задачи   | `task.created`, `task.updated`, `task.deleted`                                  |
| Счета    | `invoice.created`, `invoice.updated`, `invoice.paid`                            |
| Взаимодействия | `interaction.created`                                                     |

Это встроенные группы. Сам каталог приходит с сервера, для каждой организации свой:
`GET /api/webhooks/` возвращает его как `event_catalogue`, и оба приложения строят из него флажки
событий. Он читается из реестра объектов (`backend/common/object_registry.py`), где каждый объект
записей называет события, которые отправляет (`webhook`), плюс взаимодействия и ответы в
обращениях, которые объектами записей не являются. Установленное приложение, добавляющее записи
реестра через `register_hook`, может добавить собственные группы после встроенных, поэтому в каталоге
организации может быть больше групп, чем в этой таблице. Событие, которое организации больше не
предлагается (его модуль выключен или запись, которая его предлагала, исчезла), остаётся у
эндпоинта, уже подписанного на него, и отклоняется как новая подписка.

- `deal.won` / `deal.lost` срабатывают, когда сделка переходит на этап с типом «выиграна» или
  «проиграна», как бы этот этап ни назывался в вашей воронке. Сохранение уже выигранной сделки
  повторно событие не вызывает.
- `invoice.paid` срабатывает, когда статус счёта становится «Оплачен».
- `ticket.comment_added` срабатывает только для **публичных** ответов. Внутренние заметки никуда не
  отправляются.
- `interaction.created` срабатывает для каждого [взаимодействия](../api/interactions.md): звонка,
  встречи или сообщения, которые кто-то зафиксировал, и каждого обращения, сделанного лидом. Поля
  ответа лида (`first_response_at`, `last_outbound_at`) меняются вместе с ним и не отправляют
  `lead.updated`.
- Организация может выключить модули лидов, воронки, обращений, счетов и задач (см.
  [Модули](../api/modules.md#records-that-mention-an-off-module)). Для выключенного модуля ничего не
  отправляется, каталог не показывает его события, а эндпоинт сохраняет события, на которые уже был
  подписан; подписка на новое событие выключенного модуля даёт `400` в `events`. Уже поставленные в
  очередь доставки всё равно отправляются. Событие задачи по-прежнему содержит голые id сделки,
  обращения или лида этой задачи.
- `ping` отправляется только кнопкой **Отправить тест**, подписаться на него нельзя.

События собираются в рамках запроса и отправляются после его завершения, поэтому создание записи и
её назначение в одном сохранении приходит одним `*.created`, у которого `assigned_to` уже заполнен, а
не созданием и последующим обновлением. Откатанное изменение ничего не отправляет.

Изменения, сделанные массовыми операциями с базой данных в обход сигналов сохранения Django
(`update()` и `bulk_create()` у queryset), событий не порождают.

## Полезная нагрузка {#payload}

Каждая доставка в формате JSON имеет одинаковую обёртку:

```json
{
  "id": "4b0f7e0c-8f0e-4b8e-9d0f-2f4d6c1a9e11",
  "event": "deal.won",
  "created_at": "2026-09-26T10:15:02.114Z",
  "org_id": "a3f1c2d4-0000-4000-8000-000000000001",
  "data": {
    "id": "0d6f...",
    "name": "Acme renewal",
    "pipeline_id": "91be...",
    "stage": "CLOSED_WON",
    "amount": "12000.00",
    "currency": "USD",
    "probability": 100,
    "closed_on": "2026-09-26",
    "account_id": "5c1a...",
    "assigned_to": ["e2d9..."],
    "created_at": "2026-09-01T08:00:00Z",
    "updated_at": "2026-09-26T10:15:02Z"
  }
}
```

`id` является id события. Он одинаков для всех эндпоинтов, куда ушло событие, и для каждой его
повторной доставки, поэтому используйте его для устранения дубликатов. Суммы передаются строками,
чтобы сохранить точность десятичной части.

`data` содержит фиксированный явный набор полей для каждого модуля, перечисленный в
`backend/webhooks/events.py`: id, название или заголовок, статус или этап, суммы с валютой, ключевые
даты и id назначенных профилей. Больше ничего не отправляется. В частности, никогда не отправляются
токен публичной ссылки счёта, какие-либо секреты и поля паролей, и никогда не появляется id из другой
организации. Событие `*.deleted` содержит запись такой, какой она была непосредственно перед
удалением. Для лида, контакта или компании, объединённых с другой записью, это состояние до начала
объединения: начиная с django-crm 1.13.0 их `assigned_to` перечисляет профили, за которыми они были
закреплены, даже если объединение перенесло их в сохранённую запись.

## Заголовки и подпись {#headers-and-signature}

| Заголовок               | Значение                                            |
| ----------------------- | --------------------------------------------------- |
| `Content-Type`          | `application/json`                                  |
| `User-Agent`            | `BottleCRM-Webhooks`                                |
| `X-BottleCRM-Event`     | имя события, например `lead.created`                |
| `X-BottleCRM-Delivery`  | id доставки (новый при каждой повторной доставке)   |
| `X-BottleCRM-Signature` | `t=<unix seconds>,v1=<hex>`                         |

`v1` является шестнадцатеричным HMAC-SHA256 с ключом в виде секрета вебхука от метки времени, точки и
**исходного тела запроса** ровно в том виде, в каком оно получено: `"<t>." + body`. Проверяйте подпись,
прежде чем доверять доставке, сравнивайте за постоянное время и отклоняйте метку времени старше пяти
минут, чтобы перехваченный запрос нельзя было воспроизвести позже.

Python:

```python
import hashlib
import hmac
import time


def verify(secret: str, header: str, body: bytes, tolerance: int = 300) -> bool:
    parts = dict(item.split("=", 1) for item in header.split(","))
    timestamp = int(parts["t"])
    if abs(time.time() - timestamp) > tolerance:
        return False
    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, parts["v1"])


# Django: verify(SECRET, request.headers["X-BottleCRM-Signature"], request.body)
```

Node:

```js
import crypto from 'node:crypto';

export function verify(secret, header, rawBody, tolerance = 300) {
  const parts = Object.fromEntries(header.split(',').map((p) => p.split('=', 2)));
  const timestamp = Number(parts.t);
  if (Math.abs(Date.now() / 1000 - timestamp) > tolerance) return false;
  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${timestamp}.`)
    .update(rawBody)
    .digest('hex');
  const a = Buffer.from(expected);
  const b = Buffer.from(parts.v1 ?? '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

// Express: app.post('/hook', express.raw({ type: 'application/json' }), (req, res) => {
//   if (!verify(SECRET, req.get('X-BottleCRM-Signature'), req.body)) return res.sendStatus(401);
//   const event = JSON.parse(req.body);
//   res.sendStatus(204);
// });
```

Проверяйте по исходным байтам. Повторная сериализация разобранного JSON меняет пробелы и порядок
ключей, и подпись не совпадёт.

## Доставка, повторы и журнал {#delivery-retries-and-the-log}

- Доставка выполняется сразу после фиксации изменения, с таймаутом 10 секунд.
- Любой `2xx` считается успехом. Перенаправления **не** выполняются и считаются ошибкой.
- Всё остальное (статус не 2xx, таймаут, отказ в соединении) повторяется через 1 минуту, 5 минут,
  30 минут, 2 часа и 6 часов: шесть попыток примерно за восемь с половиной часов, после чего доставка
  помечается как Failed.
- `410 Gone` означает «остановиться»: доставка сразу завершается ошибкой, а вебхук выключается, и
  рядом с ним показывается причина. Повторное включение очищает причину.
- Доставка выполняется как минимум один раз. Получатель, который медленно отвечает, может увидеть одно
  и то же событие дважды, поэтому устраняйте дубликаты по `id` из обёртки. Порядок событий не
  гарантируется.

На странице каждого вебхука показан его журнал доставок: событие, статус, попытки, HTTP-статус,
которым ответил эндпоинт, и краткое описание ошибки (никогда не тело ответа самого эндпоинта).
**Отправить снова** отправляет завершённую доставку ещё раз новой строкой с тем же id события.
**Отправить тест** ставит в очередь `ping`. Журнал хранится 30 дней; более старые строки удаляются каждую
ночь.

Повторами управляет задача Celery beat `webhooks.tasks.dispatch_due_deliveries`, которая запускается
каждую минуту, поэтому для отправки повторов (и всего, что попало в очередь, пока воркер не работал)
Celery beat должен быть запущен. См. [Почта и Celery](../self-hosting/email-and-celery.md).

## Правила для URL {#url-rules}

Сервер выполняет запросы по URL, который ввёл администратор, поэтому URL проверяется при сохранении и
ещё раз перед каждой попыткой (`backend/webhooks/ssrf.py`):

- Только `https` на порту 443. При `DEBUG=True` также принимаются `http` и порт 80.
- Никаких имени пользователя и пароля в URL.
- Имя хоста разрешается, и **каждый** полученный адрес должен быть публичным. Отклоняются loopback,
  частные (10/8, 172.16/12, 192.168/16), link-local (включая адрес облачных метаданных
  169.254.169.254), carrier-grade NAT (100.64/10), multicast, зарезервированные и неуказанные адреса,
  а также unique-local и site-local IPv6 и формы IPv6, оборачивающие один из этих IPv4-адресов
  (IPv4-mapped, 6to4, NAT64).
- Соединение устанавливается ровно с тем адресом, который прошёл проверку, а исходное имя хоста
  используется для заголовка `Host`, TLS SNI и проверки сертификата. Ответ DNS, изменившийся между
  проверкой и соединением, не может перенаправить запрос.

Поэтому получатель, размещённый в вашей собственной частной сети, не может быть целью вебхука.
Вместо этого опубликуйте его через публичный HTTPS-эндпоинт.

## Slack {#slack}

Создайте в Slack [входящий вебхук](https://api.slack.com/messaging/webhooks), вставьте его URL
`https://hooks.slack.com/services/...` и выберите формат **Сообщение Slack**. Каждое событие публикуется
одной строкой текста, например `BottleCRM: Deal won: Acme renewal`. Имена экранируются, поэтому лид с
именем `<!channel>` не сможет упомянуть весь ваш канал. Сообщения Slack не подписываются так, чтобы
Slack это проверял; секретом является URL вебхука, поэтому обращайтесь с ним как с паролем и
перевыпустите его в Slack, если он утёк.

## Microsoft Teams {#microsoft-teams}

Новое в django-crm 1.39.0. В Teams откройте **Workflows** канала и выберите шаблон
**Post to a channel when a webhook request is received**, затем скопируйте выданный URL. В BottleCRM
добавьте вебхук с этим URL и выберите формат **Сообщение Teams**. Каждое событие публикуется как
Adaptive Card с той же строкой, что и в формате Slack, например
`BottleCRM: Deal won: Acme renewal`. Тело запроса:

```json
{
  "type": "message",
  "attachments": [
    {
      "contentType": "application/vnd.microsoft.card.adaptive",
      "content": {
        "$schema": "http://adaptivecards.io/schemas/adaptive-card.json",
        "type": "AdaptiveCard",
        "version": "1.4",
        "body": [
          {"type": "TextBlock", "text": "BottleCRM: Deal won: Acme renewal", "wrap": true}
        ]
      }
    }
  ]
}
```

Имена укладываются в одну строку, а символы, которые Teams читает как форматирование (`\`, `*`, `_`,
`[`, `]`, `` ` ``, `<`, `>`), экранируются обратной косой чертой, поэтому лид с именем
`[Pay now](https://...)` показывается как текст, а не как ссылка. События,
[правила для URL](#url-rules), повторы и журнал доставки такие же, как для любого другого формата. Как
и Slack, Teams не проверяет заголовок подписи: секретом является URL workflow.

## Рецепт для Zapier {#zapier-recipe}

1. В Zapier создайте Zap с триггером **Webhooks by Zapier -> Catch Hook**. Скопируйте выданный им
   URL пользовательского вебхука.
2. В BottleCRM добавьте вебхук с этим URL, форматом **Подписанный JSON** и нужными событиями, например
   `lead.created`.
3. Создайте лид в BottleCRM (у `ping` из **Отправить тест** другая форма, поэтому настоящее событие даёт
   Zapier более подходящий образец). В Zapier выполните **Test trigger** и выберите запрос.
4. Сопоставьте поля из `data` (`data__first_name`, `data__email` и так далее) с шагами действий.
   Фильтруйте по `event`, если один хук слушает несколько событий.

Catch Hook не умеет проверять подпись HMAC, поэтому его защищает неугадываемый URL хука. Если URL
утёк, замените хук в Zapier и обновите вебхук в BottleCRM.

## Рецепт для n8n {#n8n-recipe}

1. Добавьте узел **Webhook**. HTTP-метод `POST`, путь на ваш выбор, **Respond**: *Immediately*.
   Используйте **Production URL** узла (тестовый URL слушает, только пока открыт редактор) и убедитесь,
   что ваш n8n доступен по публичному HTTPS.
2. В BottleCRM добавьте вебхук с этим URL, форматом **Подписанный JSON** и вашими событиями. Активируйте
   процесс, затем нажмите **Отправить тест** или измените запись.
3. Чтобы проверять подпись, включите у узла Webhook параметр **Raw Body** и добавьте после него узел
   **Code**, который выполняет функцию Node `verify` из примера выше над исходным телом и заголовком
   `x-bottlecrm-signature` и останавливает процесс, если она возвращает false. В n8n на своём
   сервере узлу Code нужен `NODE_FUNCTION_ALLOW_BUILTIN=crypto`, чтобы загрузить `crypto`.
4. Маршрутизируйте по `{{$json.body.event}}` узлом **Switch**, если один вебхук слушает несколько
   событий.

## API {#api}

Всё находится под `/api/webhooks/`, только для администраторов, только сессия JWT:

| Метод и путь                              | Что делает                                              |
| ----------------------------------------- | ------------------------------------------------------- |
| `GET /`                                   | список, а также `event_catalogue` и `limit`             |
| `POST /`                                  | создание; ответ один раз содержит `secret`              |
| `GET /<id>/`                              | один вебхук (только `secret_hint`)                      |
| `PATCH /<id>/`                            | изменение `url`, `description`, `events`, `format`, `is_active` |
| `DELETE /<id>/`                           | удаление вебхука и его журнала доставок                 |
| `POST /<id>/test/`                        | постановка `ping` в очередь                             |
| `POST /<id>/rotate-secret/`               | новый секрет; ответ один раз содержит его               |
| `GET /<id>/deliveries/`                   | журнал доставок с пагинацией `limit`/`offset`           |
| `POST /deliveries/<delivery id>/redeliver/` | повторная отправка завершённой доставки               |

`format` принимает значения `json`, `slack` или `teams`. Для id из другой организации ответ `404`.
